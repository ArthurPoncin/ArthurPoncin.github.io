Fiche de revision : MSPR-ETL

Support de revision pour la soutenance MSPR1. Objectif : comprendre le role du service, le flux global et les points techniques importants, sans rentrer dans le detail ligne a ligne.

0. Vocabulaire a connaitre avant de lire

Les 7 termes qui reviennent partout dans cette fiche. Pas besoin de les retenir par coeur, mais savoir ce que chaque mot veut dire.

Terme Definition en une phrase
ETL Extract, Transform, Load. Lire des donnees brutes, les nettoyer, les charger en base.
Pipeline Chaine de traitement qui transforme des donnees d'une source vers une destination.
Scheduler Programme qui declenche des taches a intervalle regulier (ex : tous les jours a 2h).
Expression cron Syntaxe standard pour decrire un planning. Ex : 0 2 * * * = "a 2h00, tous les jours".
DataFrame Tableau en memoire (type Excel) avec colonnes typees. Concept central de la librairie pandas.
Idempotence Propriete qui fait qu'on peut relancer la meme operation N fois sans creer de doublons.
Conteneur Docker "Boite" isolee qui contient le programme et ses dependances, identique d'une machine a l'autre.

1. TL;DR

MSPR-ETL est le service d'ingestion : il prend des fichiers bruts (1 JSON + 4 CSV telecharges depuis Kaggle), les nettoie (validation, conversion d'unites, rejets), et les charge dans la base PostgreSQL healthai.

C'est un ETL classique :

  • Extract : lire le fichier source
  • Transform : nettoyer, valider, convertir
  • Load : inserer en base

Il tourne en continu dans un conteneur Docker. Au demarrage, il lance ses 4 pipelines une premiere fois, puis les relance chaque nuit a 2h grace a un scheduler interne (APScheduler avec expression cron 0 2 * * *).

  • Stack : Python 3.12, pandas, psycopg2, APScheduler
  • Entree : 1 JSON + 4 CSV dans data/raw/
  • Sortie : 5 tables PostgreSQL (exercises, nutrition_entries, exercise_entries, biometric_entries, diet_recommendations) + trace dans etl_logs
  • Reseau : se branche sur mspr_data_network (un reseau virtuel Docker cree par MSPR-DB pour que les conteneurs communiquent entre eux)

3. Stack technique

Composant Role Pourquoi ce choix
Python 3.12 Langage Ecosysteme data tres mature (pandas, psycopg2)
pandas 2.2.2 Extraction + transformation Librairie standard pour manipuler des DataFrames CSV/JSON
psycopg2-binary 2.9.9 Connexion PostgreSQL "Driver" = librairie qui permet a Python de parler a PostgreSQL. Supporte le bulk insert : inserer plusieurs lignes en une seule requete SQL, au lieu d'une par une (x100 plus rapide)
APScheduler 3.10+ Scheduler interne Permet de garder le process Python vivant et de relancer les pipelines sur une expression cron. Plus simple que le cron du systeme Linux
Ruff 0.15.6 Linter + formateur Un linter est un outil qui lit le code et signale les erreurs / incoherences de style. Ruff est tres rapide et remplace black + flake8
Pytest Tests automatises Tests unitaires + d'integration (avec un vrai Postgres lance par GitHub Actions)
Docker + tini Packaging tini est un mini programme qui tourne en "PID 1" (le processus principal du conteneur). Son role : faire suivre proprement les signaux d'arret (Ctrl+C, docker stop) a l'application Python

Dependances minimales volontairement (requirements.txt : 3 libs seulement). Les outils de dev (pytest, ruff) sont separes dans requirements-dev.txt.

4. Les 4 pipelines

L'ordre d'execution est defini dans pipelines/__init__.py : exercisedb -> nutrition -> gym_tracking -> diet_recommendations.

Pipeline Source Lignes brutes Tables cibles Regles de nettoyage
exercisedb exercises.json ~1500 exercises Rejette si external_id ou name vide. Les listes (muscles, equipements) sont stockees dans le type TEXT[] de PostgreSQL (une liste de chaines dans une seule colonne)
nutrition_dataset daily_food_nutrition_dataset.csv ~650 nutrition_entries Calories doivent etre dans [0, 10000] sinon la ligne est rejetee. Les valeurs negatives de protein/carbs/fat sont clampees a 0 (on force a 0, on ne rejette pas)
gym_tracking 2 CSVs gym (reel + synthetique) 973 + 1800 exercise_entries, biometric_entries Conversions d'unites (heures -> minutes, metres -> cm). Controle des bornes sur poids, taille, BMI, BPM, fat_pct, duree
diet_recommendations diet_recommendations_dataset.csv ~1000 diet_recommendations Rejette si Patient_ID vide. Bornes sur poids, taille, BMI

Anatomie d'un pipeline

Chaque pipeline est un simple dictionnaire Python (dict). Pas de classe, pas d'heritage : c'est voulu, ca reste lisible et facile a modifier.

PIPELINE = {
    "name": "nutrition_dataset",
    "extract": lambda: csv_extractor.extract(NUTRITION_CSV, required_columns, ...),
    "clean": cleaner.clean,          # fonction (df) -> (df_propre, df_rejetes)
    "tables": [TableConfig(...)],    # table(s) cible(s) + regle anti-doublon
    "source": "NUTRITION_DATASET",   # label ajoute automatiquement dans la colonne `source`
}

Ajouter un nouveau pipeline = creer 3 fichiers (pipelines/X.py, cleaners/X.py, extractor si format nouveau) + ajouter une ligne d'import dans pipelines/__init__.py.

5. Points techniques importants

5.1 Idempotence

Rappel : idempotent = on peut executer l'operation plusieurs fois, le resultat est le meme qu'une seule execution. Pour un ETL, ca veut dire "relancer sans creer de doublons".

Technique utilisee : chaque requete SQL INSERT est suivie de ON CONFLICT ... DO NOTHING. Traduction : "si cette ligne existe deja (selon telle contrainte d'unicite), alors ne fais rien, passe a la suivante". Les contraintes d'unicite sont definies au niveau du schema DB (migrations V3 et V7 dans MSPR-DB).

Table Cle d'unicite (ce qui definit "la meme ligne")
exercises external_id (identifiant de l'exercice dans la source)
nutrition_entries (food_name, category, meal_type, source)
exercise_entries le tuple complet (workout_type, duration, calories, BPMs, source)
biometric_entries le tuple complet (weight, height, BMI, fat%, BPMs, source)
diet_recommendations external_patient_id

Consequence concrete : on peut relancer l'ETL autant de fois qu'on veut, aucune donnee n'est dupliquee. C'est aussi ce qui rend le "run au demarrage du conteneur" sans risque.

5.2 Gestion des rejets

Le cleaner de chaque pipeline renvoie deux DataFrames : les lignes propres (clean_df) et les lignes rejetees (rejected_df). Les rejetees embarquent une colonne reason qui explique pourquoi elles ont ete exclues (ex : "calories hors bornes; weight_kg hors bornes").

Les rejets ne partent jamais en base. Ils sont exportes dans data/processed/{pipeline}_rejected.json pour pouvoir etre inspectes, corriges, et potentiellement reinjectes plus tard.

Les fonctions de validation sont mutualisees dans utils/cleaning.py (helpers init_validation, require_non_empty, check_bounds, split_valid_rejected). Chaque cleaner les combine a sa sauce, mais le pattern est identique partout : accumuler les raisons de rejet au fur et a mesure, puis couper le DataFrame en deux a la fin.

5.3 Validation par bornes

Les bornes sont centralisees dans utils/validators.py :

BOUNDS = {
    "calories": (0, 10_000),
    "weight_kg": (20, 300),
    "height_cm": (50, 250),
    "bmi": (10, 80),
    "heart_rate": (30, 250),
    "fat_percentage": (2, 70),
    "duration_min": (0, 480),
}

Pas de hardcoding dans les cleaners, modifier une borne = 1 ligne.

5.4 Observabilite

Observabilite = la capacite a savoir, apres coup, ce qui s'est passe dans le service : est-ce que ca a tourne ? combien de lignes ? quelles erreurs ? C'est indispensable en production pour deboguer sans avoir a ouvrir le code.

Quatre mecanismes :

  • Logs structures JSON (via utils/logger.py) : chaque ligne de log est un JSON ({"timestamp": ..., "level": "INFO", "message": ...}) au lieu de texte libre. Avantage : facile a ingerer dans un outil de monitoring type Loki, Elasticsearch ou Datadog.
  • Table etl_logs en base : une ligne par run de pipeline, avec le nombre de lignes lues, inserees, rejetees, le statut (OK / ERREUR), et une colonne details au format JSONB (type PostgreSQL qui stocke du JSON et permet de faire des requetes dessus). Le JSONB contient les stats par table, le top des raisons de rejet, la duree du run.
  • Rapport de qualite JSON genere dans data/processed/quality_report.json apres chaque run complet (tous pipelines confondus). Agrege le nombre total de lignes lues / inserees / rejetees et le taux de rejet global.
  • Samples (5 premieres lignes brutes + 5 nettoyees) exportes dans data/samples/ pour pouvoir inspecter visuellement l'effet du nettoyage sans avoir a ouvrir la base.

5.5 Resilience

Resilience = capacite du service a continuer de fonctionner correctement face aux imprevus (erreur ponctuelle, arret brutal, souci reseau).

Pool de connexions DB

Un pool de connexions est un "reservoir" de connexions deja ouvertes vers la base, qu'on reutilise au lieu d'en ouvrir une nouvelle a chaque requete. Ouvrir une connexion coute cher (echange TCP + authentification), le pool evite ce cout repete.

Ici on utilise psycopg2.pool.ThreadedConnectionPool (min=1, max=5). L'initialisation est paresseuse (le pool est cree au premier appel a get_cursor(), pas au demarrage), ce qui evite un echec immediat si la base n'est pas encore prete.

Context manager get_cursor()

En Python, un context manager est une structure with ... : qui garantit qu'une ressource est bien liberee a la fin, meme si une erreur survient. Exemple typique : with open(f) as file: ... ferme toujours le fichier.

Ici, with get_cursor() as cur: garantit que :

  • un COMMIT est fait automatiquement si tout s'est bien passe
  • un ROLLBACK est fait automatiquement si une exception est levee (on annule la transaction, la base reste propre)
  • la connexion est remise dans le pool dans tous les cas (meme en cas d'erreur)

Scheduler robuste

  • misfire_grace_time=3600 : si le run de 2h a ete rate (conteneur eteint, machine redemarree...), APScheduler rattrape l'execution tant que le retard est inferieur a 1h. Au-dela, il passe au prochain creneau.
  • Gestion des signaux d'arret (SIGTERM envoye par docker stop, SIGINT envoye par Ctrl+C) : le scheduler attend la fin du pipeline en cours avant de quitter, avec un timeout de 10 minutes max. Evite de couper brutalement un run en plein milieu.
  • tini comme PID 1 : dans un conteneur Docker, le processus principal (PID 1) a une responsabilite speciale : faire suivre les signaux aux processus enfants. Python ne le fait pas bien tout seul. tini est un mini programme qui le fait correctement : sans lui, docker stop enverrait le signal mais Python ne le recevrait jamais proprement.

Bizarreries gerees

Le CSV de nutrition contient des noms d'aliments avec des virgules ("Chicken, grilled"), ce qui casse le parsing CSV classique (la virgule est le separateur). On a du ecrire un parser manuel dans _extract_with_food_quirk qui reconstruit le nom en rassemblant les colonnes en trop.

5.6 CI/CD (.github/workflows/ci.yml)

CI/CD = Continuous Integration / Continuous Delivery. Automatisation qui tourne a chaque push de code sur GitHub : elle verifie que le code compile, que les tests passent, que le style est bon, et peut publier une nouvelle version automatiquement.

4 jobs declenches sur push ou PR vers master :

  1. lint : ruff check + ruff format --check (verifie le style du code sans le modifier)
  2. test : pytest en ne lancant que les tests unitaires (flag -m "not integration"). Pas besoin de base de donnees, donc rapide.
  3. test-integration : pytest sur les tests d'integration uniquement. Un vrai PostgreSQL 16 est lance dans un conteneur par GitHub Actions (la partie services: du workflow) pour ces tests.
  4. publish : construction de l'image Docker et publication sur GHCR (GitHub Container Registry, le "registre" officiel de GitHub ou on stocke des images Docker, comme DockerHub mais sur GitHub). Publication conditionnelle : seulement si les 3 jobs precedents passent ET qu'on est sur un push vers master ou un tag de version (v1.2.3 par exemple).

6. Code essentiel a savoir expliquer au jury

Cette section regroupe les morceaux de code les plus importants a savoir relire et commenter. Si le jury dit "montrez-moi comment vous faites X", c'est ici qu'on pointe.

6.1 Lire un CSV en DataFrame (pandas)

import pandas as pd

df = pd.read_csv(path, encoding="utf-8")   # charge le CSV en memoire
df = df.dropna(how="all")                   # supprime les lignes 100% vides

required = {"Food_Item", "Calories (kcal)", "Protein (g)"}
missing = required - set(df.columns)
if missing:
    raise ValueError(f"Colonnes manquantes dans {path} : {missing}")

Ce qu'il faut savoir dire :

  • pd.read_csv charge tout le fichier en memoire sous forme de DataFrame (tableau 2D avec colonnes typees, comme une feuille Excel).
  • dropna(how="all") retire les lignes totalement vides (artefacts CSV frequents).
  • On verifie les colonnes obligatoires avant de commencer le nettoyage. Si la source a change de format, on prefere echouer tout de suite plutot que produire de la data bancale silencieusement.

6.2 Transformer une colonne (pandas)

# Conversion en numerique : les valeurs non-numeriques deviennent NaN (Not a Number)
df["calories"] = pd.to_numeric(df["calories"], errors="coerce")

# Clamp : force les valeurs negatives a 0 (au lieu de rejeter la ligne)
df["protein_g"] = df["protein_g"].clip(lower=0)

# Conversion d'unites : heures -> minutes, metres -> cm
df["duration_min"] = (df["Session_Duration (hours)"] * 60).round(2)
df["height_cm"]    = (df["Height (m)"] * 100).round(1)

# Normalisation d'une colonne texte
df["food_name"] = df["food_name"].astype(str).str.strip()

Ce qu'il faut savoir dire :

  • pandas est vectorise : les operations s'appliquent a toute la colonne d'un coup, sans boucle Python explicite. C'est ce qui le rend rapide.
  • errors="coerce" : si une valeur n'est pas convertible en nombre, elle devient NaN au lieu de planter. On decidera plus loin si on la rejette ou la garde.
  • On convertit toujours vers les unites attendues par la BDD (minutes, cm, kilos) pour que toutes les sources soient homogenes.

6.3 Separer les lignes valides des lignes rejetees

# Au depart : tout est valide, aucune raison de rejet
valid   = pd.Series(True, index=df.index)
reasons = pd.Series("",   index=df.index)

# Regle 1 : calories dans [0, 10000] (NaN tolere)
in_bounds = df["calories"].isna() | df["calories"].between(0, 10_000)
reasons   = reasons.where(in_bounds, reasons + "calories hors bornes; ")
valid    &= in_bounds

# Regle 2 : food_name non vide
not_empty = df["food_name"].notna() & df["food_name"].astype(str).str.strip().ne("")
reasons   = reasons.where(not_empty, reasons + "food_name manquant; ")
valid    &= not_empty

# Coupe le DataFrame en deux
df_clean    = df[valid].reset_index(drop=True)
df_rejected = df[~valid].copy()
df_rejected["reason"] = reasons[~valid]

Ce qu'il faut savoir dire :

  • On utilise des masques booleens : valid est une Series qui contient True ou False pour chaque ligne. df[valid] renvoie les lignes ou valid vaut True.
  • On accumule les raisons de rejet : si une ligne echoue a 2 regles, elle aura "calories hors bornes; food_name manquant;" dans reason. Tres utile pour comprendre pourquoi quelque chose a ete rejete.
  • A la fin, 2 DataFrames : le propre part en base, le rejete est exporte en JSON pour inspection.

6.4 Context manager pour gerer la connexion DB

from contextlib import contextmanager
from psycopg2 import pool

_pool = pool.ThreadedConnectionPool(minconn=1, maxconn=5, ...)

@contextmanager
def get_cursor():
    conn = _pool.getconn()              # emprunte une connexion au pool
    try:
        with conn.cursor() as cur:
            yield cur                    # "donne" le curseur au bloc `with`
        conn.commit()                    # tout s'est bien passe -> commit
    except Exception:
        conn.rollback()                  # erreur -> annule la transaction
        raise                            # et on relance l'exception
    finally:
        _pool.putconn(conn)              # on rend la connexion au pool (TOUJOURS)

# Utilisation
with get_cursor() as cur:
    cur.execute("INSERT INTO ...")
    # si ca plante ici -> rollback automatique + connexion remise au pool

Ce qu'il faut savoir dire :

  • Le yield coupe la fonction en deux : avant = setup (emprunt de la connexion), apres = teardown (commit/rollback + retour au pool).
  • Le finally garantit que la connexion est toujours rendue au pool, meme en cas d'exception. Sans ca, on "fuirait" des connexions jusqu'a epuiser le pool.
  • C'est le meme principe que with open(f) as file: qui ferme le fichier proprement : on delegue la gestion des ressources au context manager.

6.5 Insertion en masse avec anti-doublon (psycopg2)

from psycopg2.extras import execute_values

# Transforme le DataFrame en liste de tuples (une ligne = un tuple)
columns = ["food_name", "category", "calories", "source"]
rows = list(df[columns].itertuples(index=False, name=None))

sql = """
    INSERT INTO nutrition_entries (food_name, category, calories, source)
    VALUES %s
    ON CONFLICT (food_name, category, meal_type, source) DO NOTHING
    RETURNING id
"""
with get_cursor() as cur:
    results = execute_values(cur, sql, rows, page_size=1000, fetch=True)
    inserted = len(results)   # compte uniquement les vraies insertions

Ce qu'il faut savoir dire :

  • execute_values fait du bulk insert : 1 requete SQL pour 1000 lignes au lieu de 1000 requetes. Sans ca, on aurait 1000 aller-retours reseau, tres lents.
  • ON CONFLICT ... DO NOTHING : si la ligne existe deja (selon la contrainte d'unicite), PostgreSQL l'ignore silencieusement. C'est ce qui rend l'ETL idempotent.
  • RETURNING id : PostgreSQL renvoie les id des lignes reellement inserees (pas celles ignorees par ON CONFLICT). On compte le resultat pour savoir combien de nouvelles lignes ont ete ajoutees.

6.6 Scheduler cron (APScheduler)

from apscheduler.schedulers.blocking import BlockingScheduler
from apscheduler.triggers.cron import CronTrigger

def run_all_pipelines():
    for pipeline in PIPELINES:
        run_pipeline(pipeline)

# 1. Run immediat au demarrage
run_all_pipelines()

# 2. Puis planification recurrente
scheduler = BlockingScheduler()
scheduler.add_job(
    run_all_pipelines,
    CronTrigger.from_crontab("0 2 * * *"),   # tous les jours a 2h
    id="etl_pipelines",
    misfire_grace_time=3600,                  # tolere 1h de retard
)
scheduler.start()   # bloque le thread, le conteneur reste vivant

Ce qu'il faut savoir dire :

  • BlockingScheduler est synchrone : il bloque le thread principal. C'est ce qu'on veut dans un conteneur Docker : tant qu'il tourne, le conteneur est vivant. S'il se termine, le conteneur s'arrete.
  • CronTrigger.from_crontab("0 2 * * *") parse une expression cron standard : minute / heure / jour du mois / mois / jour de la semaine. 0 2 * * * = "a la minute 0 de la 2e heure, tous les jours".
  • misfire_grace_time=3600 : si la machine etait eteinte a 2h (ex : maintenance), APScheduler rattrape le run tant que le retard est inferieur a 1h. Au-dela, il skippe et attend le lendemain.

6.7 Requetes SQL utiles pour auditer les runs

-- 10 derniers runs, chronologique
SELECT source_name, started_at, status, rows_inserted, rows_rejected
FROM etl_logs
ORDER BY started_at DESC
LIMIT 10;

-- Runs en erreur des dernieres 24h (extraction du message d'erreur depuis le JSON)
-- Note : la colonne `details` est typee TEXT dans le schema actuel mais contient du JSON serialise.
-- Le cast `::jsonb` permet de l'interroger comme du JSON natif.
SELECT source_name,
       started_at,
       details::jsonb->>'error' AS error_message
FROM etl_logs
WHERE status = 'ERREUR'
  AND started_at > NOW() - INTERVAL '24 hours';

-- Taux de rejet moyen par source (indicateur qualite)
SELECT source_name,
       ROUND(AVG(rows_rejected::float / NULLIF(rows_read, 0))::numeric, 4) AS rejection_rate
FROM etl_logs
GROUP BY source_name
ORDER BY rejection_rate DESC;

Ce qu'il faut savoir dire :

  • details::jsonb->>'error' : le cast ::jsonb convertit le TEXT en JSONB a la volee, puis ->>'cle' extrait la valeur sous forme de texte. Une future migration (V8) pourrait convertir definitivement la colonne en JSONB pour eviter le cast a chaque requete.
  • NULLIF(rows_read, 0) : retourne NULL si rows_read vaut 0, ce qui evite la division par zero (Postgres renverrait une erreur sinon).
  • Ces requetes alimentent le dashboard MSPR-FRONT (vue /dashboard), qui affiche les metriques globales de l'ETL en temps reel.

7. Questions probables du jury

Q1. Pourquoi un ETL maison en Python plutot qu'Airflow, dbt ou Spark ?

Volumes faibles : moins de 5000 lignes au total, pas besoin d'un outil "distribue" (qui repartit le travail sur plusieurs machines). Airflow, dbt ou Spark sont des outils puissants mais concus pour des volumes massifs et de la multi-source complexe. Les deployer pour 5000 lignes aurait apporte une grosse complexite (UI, scheduler distribue, fichiers de config YAML/XML) pour zero benefice reel. Un script Python avec APScheduler tient dans un seul conteneur, est simple a debugger, et suffit largement pour la MSPR. Si la volumetrie explosait (millions de lignes, sources en streaming temps reel), on passerait a Airflow ou Dagster.

Q2. Comment garantissez-vous l'idempotence ?

ON CONFLICT DO NOTHING sur une contrainte d'unicite declaree dans le schema DB (migrations V3 et V7). Chaque relance insere uniquement les nouvelles lignes. C'est verifie dans tests/test_integration.py::test_load_is_idempotent.

Q3. Que se passe-t-il si la base tombe en plein run ?

Deux niveaux de protection :

  1. Le context manager get_cursor() detecte l'erreur, annule la transaction en cours (ROLLBACK automatique) pour que la base reste propre, et remet la connexion dans le pool.
  2. run_pipeline capture l'exception, enregistre le run comme ERREUR dans etl_logs (avec le message d'erreur), puis passe au pipeline suivant.

On ne perd aucune donnee : la prochaine execution reprendra de zero, et comme l'ETL est idempotent (voir 5.1), aucun doublon ne sera cree.

Q4. Que faites-vous des lignes rejetees ?

Exportees dans data/processed/{pipeline}_rejected.json avec la raison. Pour l'instant pas de traitement automatique, mais c'est concu pour permettre une revue manuelle ou une reinjection apres correction. Le front expose une vue /validation qui pourrait s'y brancher.

Q5. Pourquoi 4 pipelines separes et pas un pipeline generique parametrable ?

Chaque source a sa propre logique de nettoyage (bornes, conversions, colonnes obligatoires). Un pipeline generique noie cette logique dans de la config YAML complexe. 4 modules courts et lisibles sont plus faciles a maintenir a cette echelle. Le pattern "dict PIPELINE" capture la partie commune (orchestration) sans forcer l'abstraction de la partie specifique (transformations).

Q6. Votre validation des bornes est statique. Et si les regles changent ?

Les bornes sont centralisees dans utils/validators.py::BOUNDS. Modifier une borne = 1 ligne. Pour rendre cela dynamique (config externe, par source, par version), il suffirait de charger BOUNDS depuis un YAML ou une table DB au demarrage. Pas fait par choix de simplicite.

Q7. Strategie de tests ?

Deux niveaux :

  • Tests unitaires : testent chaque composant en isolation (cleaners, validators, extractors). Ils verifient les cas valides, les cas aux limites des bornes (est-ce que 10 000 kcal exactement est accepte ?), les cas rejetes, le clamping des valeurs negatives. Ils tournent sans base de donnees, donc tres rapides.
  • Tests d'integration (test_integration.py) : ils utilisent un vrai PostgreSQL (demarre par GitHub Actions ou via Docker en local). Ils verifient le chemin complet extract -> clean -> load et s'assurent que l'idempotence fonctionne bien (relancer un load avec les memes donnees n'insere rien).

Les deux categories sont separees par un marker pytest (un simple tag sur les tests d'integration : pytestmark = pytest.mark.integration). On peut donc lancer :

  • pytest -m "not integration" : uniquement les tests unitaires, rapides, sans Postgres
  • pytest -m integration : uniquement les tests d'integration, necessite Postgres
  • pytest : tous

Q8. Pourquoi le scheduler tourne au demarrage ET sur cron ?

Pour avoir des donnees en base des le premier up du conteneur (sinon il faudrait attendre 2h du matin). L'execution initiale au demarrage est idempotente donc sans risque. Ensuite, le cron gere les rafraichissements reguliers.

Q9. Le scheduler est mono-thread. Pourquoi un pool de connexions DB alors ?

Un pool n'est pas la que pour faire du parallele, il sert aussi a :

  • Reutiliser une connexion entre plusieurs requetes (eviter le cout TCP + authentification a chaque fois qu'on parle a la base).
  • Isoler les operations : pg_load() et log_etl_run() sont deux operations distinctes. Si elles partageaient la meme connexion, une erreur dans la premiere pourrait laisser la connexion dans un etat incoherent (transaction non commitee) au moment ou la seconde voudrait l'utiliser. Avec un pool, chacune prend sa propre connexion proprement geree.

Q10. Pourquoi conserver le pipeline faker_users dans les anciens README alors qu'il a ete supprime ?

Il a ete retire (commit dedie) suite a la migration V7 qui drop la table users. Les datasets sources sont anonymes, sans identifiant commun, donc les FK vers users n'avaient plus de sens. Les README du repo ETL mentionnent encore faker_users : a corriger pour la livraison finale.

Q11. Securite : le conteneur tourne-t-il en root ?

Non. Le Dockerfile cree un user non-privilegie etl, lui donne ownership de /app, et bascule dessus via USER etl. Le docker-compose.yml ajoute no-new-privileges: true. Les logs Docker sont rotates (max 10Mo x 3 fichiers).

Q12. Comment monitorer qu'un run a echoue en production ?

Trois vecteurs de monitoring existent :

  • Interroger la table etl_logs directement : SELECT source_name, status, error_count FROM etl_logs WHERE status = 'ERREUR' ORDER BY started_at DESC. C'est la source de verite.
  • Les logs JSON stdout peuvent etre envoyes vers une stack de monitoring type Loki + Grafana ou Elasticsearch + Kibana, qui permet de visualiser les logs et configurer des alertes.
  • Le healthcheck Docker (healthcheck.py) verifie la connectivite a la base toutes les 60 secondes. Apres 3 echecs consecutifs, Docker marque le conteneur comme unhealthy, ce qui declenche typiquement une alerte au niveau de l'orchestrateur (Swarm, Kubernetes).

En revanche, il n'y a pas d'alerting automatique (mail, Slack...) pour l'instant : c'etait hors du scope de la MSPR1.

Fiche de revision : MSPR-AUTH

Support de revision pour la soutenance MSPR1. Objectif : comprendre le role du service, le flux d'authentification et les points techniques importants, sans rentrer dans le detail de chaque route better-auth.

0. Vocabulaire a connaitre avant de lire

Terme Definition en une phrase
Authentification Verifier qui est l'utilisateur (email + mot de passe, OAuth, ...). Different de l'autorisation qui verifie ce que l'utilisateur a le droit de faire.
Session Etat conserve entre deux requetes pour reconnaitre un utilisateur connecte. Stockee cote serveur, identifiee par un cookie cote client.
JWT (JSON Web Token) Jeton d'authentification autoporteur : il contient les infos utilisateur et sa signature, verifiables sans appel a la base. Format : header.payload.signature en base64.
HMAC Signature symetrique : meme cle secrete pour signer et verifier. Simple, mais toutes les parties doivent avoir la cle.
RSA / EdDSA Signature asymetrique : cle privee pour signer, cle publique pour verifier. Les consommateurs du JWT n'ont besoin que de la cle publique.
CORS (Cross-Origin Resource Sharing) Protocole qui controle quels sites web ont le droit d'appeler une API depuis le navigateur.
ORM Object-Relational Mapping : librairie qui permet de manipuler la base via des objets/fonctions plutot qu'en ecrivant du SQL brut. Ici : Drizzle.
Runtime JavaScript Environnement qui execute du JavaScript/TypeScript cote serveur. Node.js est le plus connu, Bun est un concurrent plus recent et plus rapide.

1. TL;DR

MSPR-AUTH est le service d'authentification du projet. Il gere l'inscription, la connexion, la verification d'email, la reinitialisation de mot de passe, et expose un JWT pour les autres microservices.

  • Stack : Bun (runtime) + Hono (framework web) + better-auth (auth) + Drizzle ORM + PostgreSQL 17
  • Base de donnees dediee : auth_db (PostgreSQL 17 separee de healthai), port 5433 cote hote
  • Endpoint public : port 3000
  • Client : MSPR-FRONT (login / register / reset) + MSPR-API (validation JWT)
  • Independance : service autonome, ne depend d'aucun autre microservice pour fonctionner

Pourquoi une base separee ? Separation des responsabilites : les donnees d'authentification (emails, mots de passe hashes, sessions) ne se melangent pas avec les donnees metier (exercices, nutrition). Si la BDD metier tombe, l'auth continue de fonctionner, et inversement.

2. Flux d'authentification

sequenceDiagram
    participant F as MSPR-FRONT
    participant A as MSPR-AUTH
    participant DB as auth_db
    participant R as Resend (email)
    participant API as MSPR-API

    F->>A: POST /api/auth/sign-up (email, password)
    A->>DB: Insert user + account
    A->>R: sendVerificationEmail(user.email)
    R-->>F: Email avec lien
    F->>A: GET /api/auth/verify-email?token=...
    A->>DB: emailVerified = true
    A->>A: Auto sign-in

    F->>A: POST /api/auth/sign-in (email, password)
    A->>DB: Verifie hash bcrypt
    A->>DB: Cree une session
    A-->>F: Cookie de session (HttpOnly)

    F->>A: GET /api/jwt (cookie)
    A->>A: Lit la session, signe un JWT avec BETTER_AUTH_SECRET
    A-->>F: { token: "<jwt>" }

    F->>API: Request avec Authorization: Bearer <jwt>
    API->>API: Verifie le JWT avec BETTER_AUTH_SECRET
    API-->>F: Donnees metier

Point cle : MSPR-API ne parle jamais a MSPR-AUTH en runtime. L'API valide le JWT toute seule grace a BETTER_AUTH_SECRET (cle HMAC partagee). C'est ce qui rend les deux services independants.

3. Stack technique

Composant Role Pourquoi ce choix
Bun 1.x Runtime JavaScript / TypeScript Alternative moderne a Node.js : demarrage plus rapide, support natif TypeScript et .env, package manager integre, tests integres. Image oven/bun:1 disponible en prod.
Hono 4.x Framework web Alternative legere a Express. Natif TypeScript, ecosysteme middleware riche (CORS, JWT, auth). Fonctionne sur Bun, Node, Deno, Cloudflare Workers.
better-auth 1.4 Librairie d'authentification Gere sign-up / sign-in / email verification / reset password / sessions / JWT hors-la-boite. Alternative a NextAuth ou Passport.js.
Drizzle ORM 0.44 ORM TypeScript Syntax SQL-like (proche du SQL natif), tres typee, leger (pas de runtime lourd). Alternative a Prisma qui est plus gros.
Drizzle Kit Outil de migration Genere les migrations SQL a partir du schema TypeScript. Les migrations sont versionnees dans src/db/migrations/.
Resend Envoi d'emails transactionnels API moderne (vs Mailgun / SendGrid), free tier pour le dev. Utilise pour l'email de verification et le reset password.
pg (node-postgres) Driver PostgreSQL Connexion au backend Postgres avec pool (max 10 connexions).

4. Les 5 tables de auth_db

Toutes les tables sont gerees par better-auth et generees par Drizzle (schema declaratif dans src/db/schema.ts).

Table Role Details
user Utilisateurs id, name, email (unique), email_verified, image, created_at, updated_at
session Sessions actives id, token (unique), user_id (FK), expires_at, ip_address, user_agent. Supprimee en cascade si le user est supprime.
account Comptes / providers Lie un user a un mode d'auth : provider_id = "credential" (email/password) ou "google", "github", etc. Stocke le password hashé pour les comptes email.
verification Tokens temporaires Utilise pour la verification email, reset password, etc. identifier, value, expires_at.
jwks Cles asymetriques Paires cle publique / cle privee generees par le plugin jwt() de better-auth pour signer des JWT en RSA. Non utilisee par le endpoint /api/jwt custom (voir 5.3).

Les FK user_id sur session et account ont ON DELETE CASCADE : supprimer un utilisateur supprime aussi ses sessions et ses comptes.

5. Points techniques importants

5.1 better-auth : ce que ca fait pour nous

better-auth est une librairie qui implemente les routes d'authentification classiques a partir d'une config. En 50 lignes (src/lib/auth.ts), on obtient :

  • POST /api/auth/sign-up : inscription + envoi email de verification
  • POST /api/auth/sign-in : connexion avec verification du hash
  • POST /api/auth/sign-out : destruction de la session
  • GET /api/auth/verify-email?token=... : validation de l'email via le lien
  • POST /api/auth/forgot-password : envoi du mail de reset
  • POST /api/auth/reset-password : changement du mot de passe
  • GET /api/auth/get-session : recupere la session courante
  • GET /api/auth/reference : documentation OpenAPI auto-generee (grace au plugin openAPI())

On n'a pas ecrit ces routes nous-memes. app.on(["POST", "GET"], "/api/auth/*", (c) => auth.handler(c.req.raw)) : cette ligne dans index.ts delegue tout le /api/auth/* au handler better-auth.

5.2 Sessions + cookies

Le cookie est le standard web pour maintenir un utilisateur connecte entre plusieurs requetes. Le navigateur envoie automatiquement le cookie a chaque requete vers le meme domaine.

Apres un sign-in reussi, better-auth cree une ligne dans session et pose un cookie HttpOnly sur la reponse HTTP. Caracteristiques :

  • HttpOnly : le cookie n'est pas lisible depuis JavaScript. Protection contre le vol via XSS.
  • SameSite : empeche l'envoi du cookie depuis des sites tiers. Protection contre les attaques CSRF.
  • Expiration : correspond a session.expires_at en base.

A chaque requete, le middleware Hono (src/index.ts lignes 26-39) lit le cookie, interroge better-auth pour recuperer la session + l'utilisateur, et les attache a la requete via c.set("user", ...).

5.3 Deux mecanismes JWT coexistent (attention a ne pas confondre)

A. Le plugin jwt() de better-auth

  • Active dans la config (plugins: [openAPI(), jwt()]).
  • Utilise une crypto asymetrique (RSA / EdDSA) : paire de cles dans la table jwks.
  • Expose GET /api/auth/token (recupere un JWT asymetrique) et GET /api/auth/jwks (cle publique, pour validation).
  • Non utilise par l'API Spring Boot dans l'architecture actuelle.

B. Le endpoint custom /api/jwt (celui utilise par le reste du projet)

  • Code maison dans src/index.ts, lignes 57-76.
  • Utilise HMAC avec la cle secrete partagee BETTER_AUTH_SECRET.
  • Payload simple : { sub: user.id, email, name, exp }. Expiration 1h.
  • L'API Spring Boot valide ce JWT avec la meme cle BETTER_AUTH_SECRET.

Pourquoi garder les deux ? Le plugin jwt() de better-auth est arrive en cours de route (plus robuste pour du multi-services), mais l'integration Spring Boot cote API n'a pas ete migree. Dans une version future, on pourrait supprimer le endpoint custom et passer integralement sur le plugin.

5.4 Verification d'email obligatoire

Config :

emailAndPassword: {
  enabled: true,
  requireEmailVerification: true,
}
emailVerification: {
  sendOnSignUp: true,
  autoSignInAfterVerification: true,
  async sendVerificationEmail({ user, url, token }) { ... }
}

Consequences :

  • L'utilisateur ne peut pas se connecter tant qu'il n'a pas clique sur le lien de verification.
  • L'email contient une URL vers /api/auth/verify-email?token=...&callbackURL=<front>.
  • Apres verification, l'utilisateur est automatiquement connecte (plus pratique qu'un re-login).
  • Le template HTML de l'email est dans src/lib/email/template.ts (design soigne avec fallback mobile).

L'envoi se fait via Resend (from: noreply@arthurponcin.me). La cle API Resend est dans RESEND_API_KEY.

5.5 CORS configure avec credentials: true

app.use("/api/*", cors({
  origin: process.env.CORS_ORIGIN || "http://localhost:5173",
  allowMethods: ["POST", "GET", "OPTIONS"],
  credentials: true,
}));
  • origin pointe vers l'URL du front (port 5173 en local).
  • credentials: true : autorise le navigateur a envoyer les cookies sur les requetes cross-origin. Sans cela, le front ne pourrait pas faire un fetch(...,{ credentials: "include" }) vers l'auth.

C'est une config critique : sans elle, le sign-in fonctionnerait mais le cookie ne suivrait pas.

5.6 Migrations Drizzle

Contrairement a MSPR-DB (migrations SQL brutes), MSPR-AUTH utilise Drizzle Kit :

bun run db:generate:migration   # genere une migration SQL depuis le schema.ts
bun run db:migrate              # applique les migrations sur la base

Drizzle Kit compare le schema.ts avec l'etat actuel de la base et genere le SQL necessaire. Les fichiers sont versionnes dans src/db/migrations/ (ici 2 migrations : 0000_concerned_sunspot.sql, 0001_cheerful_the_hood.sql).

Dans le docker-compose.yml racine, un service auth-migrate one-shot execute bun run db:migrate avant le demarrage du service auth. Il attend que auth-db soit healthy :

auth-migrate:
  command: sh -c "bun run db:migrate"
  depends_on:
    auth-db:
      condition: service_healthy
auth:
  depends_on:
    auth-migrate:
      condition: service_completed_successfully

5.7 Pool de connexions PostgreSQL

Dans src/db/db.ts :

export const pool = new Pool({
    connectionString: process.env.DATABASE_URL,
    max: 10,
    idleTimeoutMillis: 30000,
})
  • max: 10 : jusqu'a 10 connexions simultanees vers PostgreSQL.
  • idleTimeoutMillis: 30000 : une connexion inactive depuis 30s est fermee pour liberer des ressources.
  • Drizzle s'appuie sur ce pool pour executer les requetes.

6. Code essentiel a savoir expliquer au jury

6.1 Configuration de better-auth

// src/lib/auth.ts
export const auth = betterAuth({
    database: drizzleAdapter(db, { provider: "pg" }),
    baseURL: process.env.BETTER_AUTH_URL,
    trustedOrigins: [process.env.CORS_ORIGIN || "http://localhost:5173"],
    plugins: [openAPI(), jwt()],

    emailVerification: {
        sendOnSignUp: true,
        autoSignInAfterVerification: true,
        async sendVerificationEmail({ user, url }) {
            await resend.emails.send({
                from: "noreply@arthurponcin.me",
                to: user.email,
                subject: "Verifiez votre adresse email",
                html: getVerificationEmailTemplate(url, user.name),
            });
        },
    },

    emailAndPassword: {
        enabled: true,
        requireEmailVerification: true,
        async sendResetPassword({ user, url }) {
            await resend.emails.send({
                from: "noreply@arthurponcin.me",
                to: user.email,
                subject: "Reinitialisation de mot de passe",
                html: `<p>Cliquez ici : <a href="${url}">${url}</a></p>`,
            });
        }
    }
});

Ce qu'il faut savoir dire :

  • C'est une config declarative : on dit ce qu'on veut, better-auth s'occupe du reste (routes, logique, stockage).
  • drizzleAdapter(db, { provider: "pg" }) : on branche better-auth sur notre base PostgreSQL via Drizzle. better-auth sait ou ecrire les users, sessions, etc.
  • sendVerificationEmail et sendResetPassword sont des callbacks : better-auth nous donne l'URL du lien et l'utilisateur, on choisit comment envoyer le mail (ici via Resend).
  • plugins: [openAPI(), jwt()] : deux modules optionnels de better-auth. openAPI() genere la doc, jwt() ajoute des routes de JWT asymetrique (non utilisees par l'API ici).

6.2 Middleware Hono qui injecte la session dans la requete

// src/index.ts
app.use("*", async (c, next) => {
  const session = await auth.api.getSession({ headers: c.req.raw.headers });

  if (!session) {
    c.set("user", null);
    c.set("session", null);
    await next();
    return;
  }

  c.set("user", session.user);
  c.set("session", session.session);
  await next();
});

Ce qu'il faut savoir dire :

  • Ce middleware tourne avant chaque route (app.use("*")).
  • auth.api.getSession({ headers }) : better-auth lit le cookie dans les headers, valide la session en base, retourne { user, session } ou null.
  • On attache l'utilisateur et la session au contexte de la requete (c.set). Les routes suivantes peuvent faire c.get("user") pour recuperer l'utilisateur connecte sans refaire un aller-retour en base.
  • Si pas de session valide : user = null, session = null. La route decidera si elle autorise ou non l'acces.

6.3 Endpoint custom /api/jwt (le JWT utilise par l'API)

import { sign } from 'hono/jwt'

app.get("/api/jwt", async (c) => {
  const user = c.get("user");
  if (!user) return c.json({ error: "Unauthorized" }, 401);

  const payload = {
    sub: user.id,
    email: user.email,
    name: user.name,
    exp: Math.floor(Date.now() / 1000) + 60 * 60,   // expire dans 1h
  };

  const secret = process.env.BETTER_AUTH_SECRET || "password";
  const token = await sign(payload, secret);   // signature HMAC

  return c.json({ token });
});

Ce qu'il faut savoir dire :

  • Le endpoint exige un utilisateur connecte (grace au middleware 6.2). Si user est null, on renvoie 401.
  • Le payload contient l'id utilisateur (sub = subject, standard JWT), son email et son nom. L'API pourra lire ca pour savoir qui fait la requete.
  • exp : timestamp Unix en secondes. Au-dela, le JWT est considere expire.
  • sign(payload, secret) signe le tout en HMAC-SHA256 (par defaut dans hono/jwt). Resultat : une chaine header.payload.signature que l'API pourra valider avec la meme cle.

6.4 Schema Drizzle (extrait : table user + session)

// src/db/schema.ts
import { pgTable, text, timestamp, boolean } from "drizzle-orm/pg-core";

export const user = pgTable("user", {
  id: text("id").primaryKey(),
  name: text("name").notNull(),
  email: text("email").notNull().unique(),
  emailVerified: boolean("email_verified").default(false).notNull(),
  image: text("image"),
  createdAt: timestamp("created_at").defaultNow().notNull(),
  updatedAt: timestamp("updated_at").defaultNow()
    .$onUpdate(() => new Date()).notNull(),
});

export const session = pgTable("session", {
  id: text("id").primaryKey(),
  expiresAt: timestamp("expires_at").notNull(),
  token: text("token").notNull().unique(),
  userId: text("user_id").notNull()
    .references(() => user.id, { onDelete: "cascade" }),
  // ...
});

Ce qu'il faut savoir dire :

  • Le schema est declare en TypeScript : la structure de la base est exprimee comme du code, pas du SQL brut.
  • pgTable("user", { ... }) : declare une table Postgres avec ses colonnes typees.
  • .references(() => user.id, { onDelete: "cascade" }) : cle etrangere. Si on supprime un user, toutes ses sessions le sont aussi.
  • $onUpdate(() => new Date()) : regle automatique pour mettre a jour updated_at a chaque modification. Drizzle gere ca en TypeScript, pas en SQL.
  • A partir de ce schema, Drizzle Kit genere les migrations SQL. Le schema est la source de verite.

6.6 Orchestration auth-migrate dans le compose racine

auth-migrate:
  build:
    context: ./MSPR-AUTH
  container_name: mspr-auth-migrate
  command: sh -c "bun run db:migrate"
  environment:
    DATABASE_URL: postgres://root:password@auth-db:5432/auth_db
  depends_on:
    auth-db:
      condition: service_healthy
  restart: "no"

auth:
  depends_on:
    auth-db:
      condition: service_healthy
    auth-migrate:
      condition: service_completed_successfully

Ce qu'il faut savoir dire :

  • Le conteneur auth-migrate est one-shot : il execute bun run db:migrate puis s'arrete (restart: "no").
  • Il attend que auth-db soit healthy avant de se lancer (sinon la migration echouerait).
  • Le service auth attend a son tour que auth-migrate ait termine avec succes (service_completed_successfully). Cela garantit que la base est migree avant que l'app demarre.
  • C'est un pattern classique pour les migrations au demarrage en Docker : un conteneur dedie qui tourne avant l'app principale.

7. Questions probables du jury

Q1. Pourquoi une base de donnees separee pour l'auth et pas la meme que le metier ?

Trois raisons :

  • Separation des responsabilites : les donnees sensibles (emails, mots de passe hashes) sont isolees des donnees metier. Un bug ou une compromission sur l'API metier ne donne pas acces aux credentials.
  • Independance de dispo : si healthai est en maintenance, les utilisateurs peuvent quand meme se connecter a l'app (meme si une partie des fonctionnalites est HS).
  • Schemas differents : better-auth gere son propre schema (user, session, account, verification, jwks) via Drizzle. Le mettre dans healthai ferait cohabiter deux outils de migration (SQL brut + Drizzle Kit) sur la meme base.

Q2. Pourquoi better-auth plutot qu'une auth maison ou NextAuth ?

  • Auth maison : reinventer la roue, risque de bugs de securite (hashage faible, CSRF, timing attacks). Ecrire une auth robuste prend des semaines.
  • NextAuth : orientee Next.js, plus lourd a integrer hors de cet ecosysteme.
  • better-auth : framework-agnostic (fonctionne avec Hono, Express, Next, etc.), supporte nativement les bonnes pratiques de securite (cookies HttpOnly SameSite, CSRF, email verification), facile a etendre via plugins.
  • Cout : on accepte une dependance externe, mais maintenue activement et testee en production chez plusieurs clients.

Q3. Pourquoi Bun et pas Node.js ?

  • Performances : Bun demarre ~3x plus vite que Node et execute le JS/TS plus rapidement dans beaucoup de benchmarks.
  • TypeScript natif : Bun execute du TypeScript sans transpilation prealable (pas de tsc a lancer), ce qui simplifie le dev.
  • Outillage integre : Bun inclut un package manager, un test runner, un bundler. Moins d'outils a installer.
  • Cout : ecosysteme plus recent, moins de libs testees. Ici, toutes nos dependances (Hono, better-auth, Drizzle, pg) sont compatibles.

Q4. Comment l'API valide-t-elle le JWT sans appeler AUTH ?

Grace a une cle secrete partagee. BETTER_AUTH_SECRET est passee en variable d'environnement a la fois au service AUTH (pour signer) et au service API (pour verifier). Les deux services peuvent donc signer/valider le meme JWT sans jamais communiquer.

L'API ne fait qu'une verification cryptographique locale (HMAC-SHA256 avec la cle, test de l'expiration exp). C'est ce qui rend le systeme scalable : on peut multiplier les instances d'API sans charger AUTH.

Q5. Que se passe-t-il si BETTER_AUTH_SECRET est compromis ?

C'est un incident de securite majeur :

  • N'importe qui pourrait forger des JWT valides et se faire passer pour n'importe quel utilisateur.
  • Il faudrait regenerer le secret et le deployer simultanement sur AUTH et API. Tous les JWT emis avant la rotation deviennent invalides, forcant les utilisateurs a se reconnecter.
  • En production reelle, on utiliserait plutot une crypto asymetrique (RSA/EdDSA) via le plugin jwt() de better-auth : la cle privee reste sur AUTH, l'API n'a que la cle publique. Une compromission d'AUTH necessite quand meme une rotation, mais l'API seule ne suffit pas a forger des JWT.

Q6. Pourquoi le cookie et pas uniquement un JWT cote front ?

  • Les cookies HttpOnly sont inaccessibles au JavaScript du navigateur. Un attaquant XSS ne peut pas les voler.
  • Un JWT stocke en localStorage est lisible par n'importe quel script executant sur la page. XSS = vol du token = compte compromis.
  • Ici, le front garde une session via cookie (posee par better-auth), et demande un JWT a AUTH uniquement quand il a besoin d'appeler l'API. Le JWT existe de facon ephemere, pas stocke durablement.

Q7. Deux mecanismes JWT coexistent dans le code. C'est normal ?

Non, c'est un vestige d'iterations. Le plugin jwt() de better-auth a ete ajoute dans la config (plugins: [openAPI(), jwt()]) mais l'API Spring Boot utilise encore le endpoint custom /api/jwt (HMAC). Pour une prod propre, on deciderait d'un seul mecanisme. Mon choix : passer sur le plugin asymetrique pour beneficier de la separation cle privee / cle publique.

Q8. Comment est gere le rate limiting sur le sign-in ?

Pas de rate limiting custom dans le code actuel. better-auth a une protection anti-brute-force interne sur les tentatives de login (configurable). Pour une prod, on ajouterait en plus :

  • Un middleware Hono de rate limiting (ex : limite X requetes / IP / min).
  • Un captcha sur les endpoints sensibles (sign-up, reset password) pour eviter le scraping.
  • Un WAF (Cloudflare, ModSecurity) en amont.

Q9. Pourquoi requireEmailVerification: true ?

  • Empeche la creation de comptes bidons (emails aleatoires) qui polluent la base.
  • Verifie que l'utilisateur possede bien l'adresse email (important pour le reset password).
  • Cas d'usage : si quelqu'un s'inscrit avec l'email d'un tiers, la verification protege le vrai proprietaire.

Cout : UX legerement degradee (un clic supplementaire). Mitige par autoSignInAfterVerification: true qui evite a l'utilisateur de se reloguer.

Q10. Comment tester l'auth en dev sans envoyer de vrais emails ?

  • Option 1 (actuelle) : clef Resend avec un domaine de test. Resend a un mode "sandbox" qui simule l'envoi.
  • Option 2 : mocker la fonction sendVerificationEmail pour logguer l'URL dans la console au lieu d'envoyer un mail. On copie-colle l'URL dans le navigateur.
  • Option 3 : desactiver requireEmailVerification en dev via une variable d'environnement (pas fait ici pour rester realiste).

Q11. La table jwks est populated. Quand ?

Lors du premier demarrage du service AUTH avec le plugin jwt() active. better-auth genere une paire de cles RSA et les stocke en base. Elles sont ensuite utilisees pour signer les JWT du plugin jwt() (pas ceux du endpoint custom).

En production reelle, on ajouterait une rotation des cles (nouvelle paire generee periodiquement, anciennes conservees le temps que les JWT emis avec expirent).

Q12. Pourquoi Drizzle et pas Prisma ?

  • Drizzle : leger, syntaxe proche du SQL, pas de runtime lourd, excellent support TypeScript. S'adapte bien a Bun.
  • Prisma : plus complet (introspection, generation de types avancee), mais runtime plus gros, demarrage plus lent, historiquement quelques soucis de compatibilite avec Bun.
  • Pour un service simple comme AUTH (5 tables, aucune requete complexe), Drizzle est amplement suffisant et plus rapide.

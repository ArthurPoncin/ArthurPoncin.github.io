Fiche de revision : MSPR-API

Support de revision pour la soutenance MSPR1. Objectif : comprendre le role du service, l'architecture en couches et les points techniques importants, sans rentrer dans le detail de chaque endpoint.

0. Vocabulaire a connaitre avant de lire

Terme Definition en une phrase

1. TL;DR

MSPR-API est l'API REST metier du projet. Elle expose les donnees ingerees par l'ETL au front Vue 3, et fournit aussi un CRUD pour que les admins/data scientists puissent corriger les donnees a la main.

  • Stack : Spring Boot 4.0.3 + Java 21 + Spring Data JPA (Hibernate) + Spring Security
  • Port : 8080
  • Context path : /api (toutes les URLs commencent par /api/...)
  • BDD : PostgreSQL healthai (MSPR-DB) via JDBC
  • Auth : valide les JWT emis par MSPR-AUTH avec BETTER_AUTH_SECRET (HS512). Aucun appel runtime a MSPR-AUTH.
  • Doc : Swagger UI sur http://localhost:8080/api/swagger-ui.html
  • 9 controllers repartis en 3 groupes : metier (Exercise, Nutrition, Workout, Biometric, DietRecommendation), qualite des donnees (DataQuality, Validation), utilitaires (Export, Health)

2. Flux d'une requete typique

flowchart LR
    F[MSPR-FRONT] -->|GET /api/nutrition<br/>Authorization: Bearer jwt| FILTER[JwtAuthenticationFilter]
    FILTER -->|valide via BETTER_AUTH_SECRET| CTRL[NutritionController]
    CTRL --> SVC[NutritionService]
    SVC --> REPO[NutritionEntryRepository]
    REPO -->|SQL via Hibernate| DB[(healthai)]

    DB -->|ResultSet| REPO
    REPO -->|Entity| SVC
    SVC -->|mapToDTO| CTRL

Principe : separation stricte des responsabilites entre les couches. Chaque couche ne connait que la couche juste en dessous.

5. Points techniques importants

5.1 Architecture en couches Controller -> Service -> Repository

C'est le pattern standard Spring. Chaque couche a une responsabilite unique :

  • Controller : traduit HTTP <-> Java. Ne contient aucune logique metier, juste le routage et la mise en forme des reponses.
  • Service : contient la logique metier (validation croisee, transactions, orchestration). Utilise un ou plusieurs repositories.
  • Repository : parle a la base via Spring Data JPA. Pas de logique, juste des requetes.

Cette separation permet de tester chaque couche independamment (le service avec un repo mocké, le controller avec un service mocké).

5.2 Spring Data JPA : des repositories quasi-vides

Exemple de ExerciseRepository :

@Repository
public interface ExerciseRepository extends JpaRepository<Exercise, Long> {
}

C'est tout. En heritant de JpaRepository, on obtient gratuitement : save(), findById(), findAll(), findAll(Pageable), deleteById(), count(), existsById(), etc.

Pour des requetes personnalisees, on ajoute des methodes :

  • Methodes nommees : countByStatus(String). Spring deduit la requete du nom.
  • Annotation @Query avec du JPQL (langage proche SQL mais sur les entities) ou du SQL natif.

Exemple reel dans NutritionEntryRepository :

@Query("SELECT n FROM NutritionEntry n WHERE n.calories > :maxCalories OR n.calories < 0")
List<NutritionEntry> findCalorieOutliers(BigDecimal maxCalories);

5.3 Mapping auto camelCase <-> snake_case

La convention Java est camelCase (foodName, proteinG), la convention PostgreSQL est snake_case (food_name, protein_g). On configure une fois pour toutes :

spring.jpa.hibernate.naming.physical-strategy=org.hibernate.boot.model.naming.CamelCaseToUnderscoresNamingStrategy

Hibernate fait la conversion automatiquement. On peut neanmoins forcer un nom avec @Column(name = "food_name") quand il y a ambiguite.

5.4 JPA en mode validate (pas update, pas create)

spring.jpa.hibernate.ddl-auto=validate

Au demarrage, Hibernate verifie que le schema de la base correspond aux entities Java. Il ne modifie rien. Si une colonne manque ou que le type est different, l'application refuse de demarrer.

Pourquoi : les migrations sont centralisees dans MSPR-DB. Autoriser l'API a modifier le schema serait une source de conflits (deux services qui ajoutent des colonnes differemment). Le mode validate est la ceinture de securite.

5.5 Security : validation JWT sans appel a MSPR-AUTH

// SecurityConfig.java (extrait)
http
  .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
  .csrf(csrf -> csrf.disable())
  .authorizeHttpRequests(authz -> authz
      .requestMatchers("/api/public/**", "/api/swagger-ui/**", "/api/actuator/health").permitAll()
      .anyRequest().authenticated())
  .addFilterBefore(new JwtAuthenticationFilter(jwtTokenProvider), UsernamePasswordAuthenticationFilter.class);

Trois points cle :

  • STATELESS : Spring Security ne cree pas de session HTTP cote serveur. Chaque requete est traitee independamment, l'authentification provient uniquement du JWT dans le header. Ideal pour une API REST scalable.
  • CSRF desactive : les attaques CSRF exploitent les cookies de session. Sans session, pas de vecteur d'attaque. Desactiver est correct.
  • JwtAuthenticationFilter : un filtre custom intercepte chaque requete, extrait le JWT du header Authorization: Bearer ..., le valide avec BETTER_AUTH_SECRET via JwtTokenProvider, et pose un Authentication dans le SecurityContext si valide.

Point critique : la validation est purement cryptographique, aucun appel reseau vers MSPR-AUTH. L'API peut scaler horizontalement sans charger l'auth.

5.6 Validation de la cle JWT au demarrage

// JwtTokenProvider.java
private static final int MIN_SECRET_BYTES = 64;

@PostConstruct
void validateSecret() {
    int length = jwtSecret.getBytes(StandardCharsets.UTF_8).length;
    if (length < MIN_SECRET_BYTES) {
        throw new IllegalStateException("app.jwt.secret must be at least 64 bytes for HS512");
    }
}

HS512 (HMAC-SHA512) exige une cle d'au moins 64 octets (512 bits) pour etre cryptographiquement solide. @PostConstruct = cette methode est appelee par Spring juste apres l'injection du champ jwtSecret. Si la cle est trop courte, l'application refuse de demarrer (fail-fast).

5.7 Gestion d'erreur centralisee

GlobalExceptionHandler (@RestControllerAdvice) intercepte les exceptions remontees par n'importe quel controller et les convertit en reponses HTTP JSON homogenes :

Exception Statut HTTP Usage
ResourceNotFoundException (custom) 404 Not Found Entity absente (findById(id).orElseThrow(...))
UnauthorizedAccessException (custom) 403 Forbidden User connecte mais pas autorise
MethodArgumentNotValidException (Spring) 422 Unprocessable Entity Validation @Valid echouee (DTO invalide)
AuthenticationException (Spring) 401 Unauthorized JWT invalide ou absent
RuntimeException (fallback) 400 Bad Request Erreur non prevue mais fautive client
Exception (catch-all) 500 Internal Server Error Erreur serveur

Toutes les reponses d'erreur ont la meme forme (ErrorResponse), ce qui simplifie le code cote front.

5.8 Injection de dependances par constructeur

@RestController
@RequestMapping("/nutrition")
public class NutritionController {
    private final NutritionService nutritionService;

    public NutritionController(NutritionService nutritionService) {
        this.nutritionService = nutritionService;
    }
    // ...
}

On ne fait jamais new NutritionService(). Spring instancie les beans (composants) et les injecte en parametre du constructeur. Les champs sont final, ce qui garantit l'immutabilite et facilite les tests (on peut passer un mock au constructeur).

5.9 Transactions JPA

@Transactional(readOnly = true)   // pour les lectures
public Page<NutritionEntryDTO> listNutritionEntries(Pageable pageable) { ... }

@Transactional                     // pour les ecritures
public NutritionEntryDTO createNutritionEntry(NutritionEntryDTO dto) { ... }
  • @Transactional ouvre une transaction au debut de la methode et la commit a la fin. Si exception -> rollback automatique.
  • readOnly = true : optimisation Hibernate (pas de dirty checking, lecture plus rapide). A utiliser pour tous les reads.

5.10 Documentation OpenAPI (Swagger UI)

L'interface est disponible sur http://localhost:8080/api/swagger-ui.html. Elle est generee automatiquement a partir des annotations :

  • @Tag(name = "Nutrition") sur le controller -> groupe dans l'UI
  • @Operation(summary = "...") sur chaque methode -> description de l'endpoint
  • @SecurityRequirement(name = "bearer-jwt") -> indique que l'endpoint requiert un JWT

Avantage enorme : la doc est toujours a jour avec le code (pas de doc separee qui se desynchronise). On peut aussi tester les endpoints directement depuis l'UI (bouton "Try it out").

6. Code essentiel a savoir expliquer au jury

6.1 Anatomie d'un CRUD (Controller + Service + Repository)

Controller : traduit HTTP <-> Java, zero logique.

@RestController
@RequestMapping("/nutrition")
public class NutritionController {
    private final NutritionService nutritionService;

    public NutritionController(NutritionService nutritionService) {
        this.nutritionService = nutritionService;
    }

    @PostMapping
    public ResponseEntity<NutritionEntryDTO> createNutritionEntry(@Valid @RequestBody NutritionEntryDTO dto) {
        NutritionEntryDTO saved = nutritionService.createNutritionEntry(dto);
        return ResponseEntity.status(HttpStatus.CREATED).body(saved);
    }
}

Service : logique metier, transactions, mapping entity <-> DTO.

@Service
public class NutritionService {
    private final NutritionEntryRepository repo;

    public NutritionService(NutritionEntryRepository repo) { this.repo = repo; }

    @Transactional
    public NutritionEntryDTO createNutritionEntry(NutritionEntryDTO dto) {
        NutritionEntry entry = new NutritionEntry();
        entry.setFoodName(dto.getFoodName());
        entry.setCalories(dto.getCalories());
        // ... (autres setters)
        NutritionEntry saved = repo.save(entry);
        return mapToDTO(saved);
    }
}

Repository : Spring Data JPA genere tout gratuitement.

@Repository
public interface NutritionEntryRepository extends JpaRepository<NutritionEntry, Long> {
    long countByStatus(String status);
}

Ce qu'il faut savoir dire :

  • Le @RestController combine @Controller + @ResponseBody : toutes les methodes renvoient directement du JSON.
  • @Valid declenche la validation du DTO (annotations @NotBlank, @Positive). Si invalide, exception interceptee par le GlobalExceptionHandler -> 422.
  • @Transactional (niveau service) : si une exception survient, tout est rollback. Permet aussi a Hibernate de differer les inserts jusqu'au commit.
  • Le repository est une interface : pas d'implementation ecrite par nous, Spring Data genere le proxy a l'execution.

6.2 Validation d'un JWT (JwtAuthenticationFilter)

public class JwtAuthenticationFilter extends OncePerRequestFilter {
    private final JwtTokenProvider tokenProvider;

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        try {
            String jwt = getJwtFromRequest(req);

            if (StringUtils.hasText(jwt) && tokenProvider.isTokenValid(jwt)) {
                String email = tokenProvider.getEmailFromToken(jwt);
                String name = tokenProvider.getNameFromToken(jwt);

                UsernamePasswordAuthenticationToken auth =
                    new UsernamePasswordAuthenticationToken(email, name, null);
                SecurityContextHolder.getContext().setAuthentication(auth);
            }
        } catch (Exception ex) {
            log.debug("Rejected invalid JWT: {}", ex.getMessage());
        }
        chain.doFilter(req, res);
    }

    private String getJwtFromRequest(HttpServletRequest req) {
        String header = req.getHeader("Authorization");
        if (StringUtils.hasText(header) && header.startsWith("Bearer ")) {
            return header.substring(7);  // retire "Bearer "
        }
        return null;
    }
}

Ce qu'il faut savoir dire :

  • OncePerRequestFilter garantit que le filtre s'execute une seule fois par requete (meme en cas de forward / include).
  • On extrait le JWT du header, on verifie sa signature avec BETTER_AUTH_SECRET, on attache l'utilisateur au SecurityContext de Spring. Les controllers pourront recuperer l'utilisateur via SecurityContextHolder.
  • Si le JWT est invalide, on ne renvoie pas d'erreur ici : on laisse passer la requete sans authentification. C'est la regle d'autorisation anyRequest().authenticated() qui fera un 401 plus tard. Separation des responsabilites.

6.3 Validation cryptographique (JwtTokenProvider)

@Service
public class JwtTokenProvider {
    @Value("${app.jwt.secret}")
    private String jwtSecret;

    @PostConstruct
    void validateSecret() {
        if (jwtSecret.getBytes(UTF_8).length < 64) {
            throw new IllegalStateException("Secret too short for HS512");
        }
    }

    private SecretKey getSigningKey() {
        return new SecretKeySpec(jwtSecret.getBytes(UTF_8), "HmacSHA512");
    }

    public boolean isTokenValid(String token) {
        try {
            Jwts.parser()
                .verifyWith(getSigningKey())
                .build()
                .parseSignedClaims(token);
            return true;
        } catch (Exception e) {
            log.error("JWT validation error: {}", e.getMessage());
            return false;
        }
    }

    public String getEmailFromToken(String token) {
        return (String) Jwts.parser()
            .verifyWith(getSigningKey())
            .build()
            .parseSignedClaims(token)
            .getPayload()
            .get("email");
    }
}

Ce qu'il faut savoir dire :

  • @Value("${app.jwt.secret}") : Spring injecte la valeur de la variable app.jwt.secret (definie dans application.properties comme ${BETTER_AUTH_SECRET}). On recupere donc la meme cle que MSPR-AUTH.
  • Jwts.parser().verifyWith(key).parseSignedClaims(token) : la librairie jjwt fait tout en une ligne : verifie la signature ET que le token n'est pas expire (exp). Si invalide, elle leve une exception.
  • HS512 = HMAC avec SHA-512. C'est de la crypto symetrique : meme cle pour signer (cote AUTH) et verifier (cote API). Simple mais il faut proteger la cle.

6.4 DTO avec validation et pattern Builder

public class NutritionEntryDTO {
    private Long id;

    @NotBlank(message = "Food name is required")
    private String foodName;

    @Positive(message = "Calories must be positive")
    private BigDecimal calories;

    @NotBlank(message = "Source is required")
    private String source;

    // ... getters/setters

    public static Builder builder() { return new Builder(); }

    public static class Builder {
        private NutritionEntryDTO dto = new NutritionEntryDTO();

        public Builder foodName(String v) { dto.foodName = v; return this; }
        public Builder calories(BigDecimal v) { dto.calories = v; return this; }
        public NutritionEntryDTO build() { return dto; }
    }
}

Ce qu'il faut savoir dire :

  • Les annotations @NotBlank, @Positive, @Email, etc. sont des contraintes Bean Validation (JSR-380). Elles sont declaratives : pas de code de validation a ecrire.
  • @Valid dans le controller declenche leur verification. Si echec, Spring leve une MethodArgumentNotValidException interceptee par GlobalExceptionHandler.
  • Le pattern Builder (NutritionEntryDTO.builder().foodName("Apple").build()) est plus lisible qu'un constructeur a 15 arguments et permet de mettre les champs dans n'importe quel ordre.
  • Le DTO est separe de l'entity JPA. Avantage : on peut changer la structure de la table (ex : renommer une colonne) sans casser le format de l'API.

6.5 Gestion d'erreur globale

@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex, WebRequest req) {
        ErrorResponse error = ErrorResponse.of(
            HttpStatus.NOT_FOUND,
            ex.getMessage(),
            "Resource not found",
            req.getDescription(false).replace("uri=", "")
        );
        return new ResponseEntity<>(error, HttpStatus.NOT_FOUND);
    }

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders h, HttpStatusCode s, WebRequest req) {
        ErrorResponse error = ErrorResponse.of(
            HttpStatus.UNPROCESSABLE_ENTITY,
            "Validation failed",
            ex.getBindingResult().getAllErrors().get(0).getDefaultMessage(),
            req.getDescription(false).replace("uri=", "")
        );
        return new ResponseEntity<>(error, HttpStatus.UNPROCESSABLE_ENTITY);
    }

    // + handlers pour Authentication, Runtime, Exception (catch-all)
}

Ce qu'il faut savoir dire :

  • @RestControllerAdvice : cette classe intercepte les exceptions de tous les controllers. Pas besoin de try/catch dans chaque endpoint.
  • Chaque @ExceptionHandler(XxxException.class) gere un type d'exception specifique et renvoie une reponse HTTP appropriee (404, 422, etc.).
  • ErrorResponse est une classe simple { status, message, error, path, timestamp } : format homogene cote front.
  • Bonne pratique : un catch-all @ExceptionHandler(Exception.class) pour eviter d'exposer les stack traces en cas d'erreur inattendue.

6.6 Configuration Spring Security (SecurityFilterChain)

@Configuration
@EnableWebSecurity
public class SecurityConfig {
    private final JwtTokenProvider jwtTokenProvider;

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(List.of(allowedOrigin));
        config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
        config.setAllowCredentials(true);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return source;
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .cors(cors -> cors.configurationSource(corsConfigurationSource()))
            .csrf(csrf -> csrf.disable())
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(authz -> authz
                .requestMatchers("/api/swagger-ui/**", "/api/v3/api-docs/**").permitAll()
                .requestMatchers("/api/actuator/health", "/api/actuator/info").permitAll()
                .anyRequest().authenticated())
            .addFilterBefore(new JwtAuthenticationFilter(jwtTokenProvider),
                             UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}

Ce qu'il faut savoir dire :

  • @EnableWebSecurity active l'infrastructure Spring Security. Sans cette annotation, les filtres de securite ne sont pas branches.
  • La chaine de filtres est declarative : on liste les regles, Spring construit la chaine derriere. C'est facile a lire.
  • L'ordre des requestMatchers compte : les plus specifiques d'abord, le catch-all (anyRequest()) a la fin.
  • addFilterBefore : notre JwtAuthenticationFilter s'execute avant le filtre de login classique de Spring (qui ne sera jamais utilise puisqu'on est en STATELESS).

6.7 Configuration multi-profils (application.properties)

# Datasource : variables d'env avec valeurs par defaut pour le dev local
spring.datasource.url=jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/${DB_NAME:healthai}
spring.datasource.username=${DB_USER:healthai_user}
spring.datasource.password=${DB_PASSWORD:password}

# JPA : validate uniquement (ne touche pas au schema)
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.hibernate.naming.physical-strategy=org.hibernate.boot.model.naming.CamelCaseToUnderscoresNamingStrategy

# Flyway : desactive (migrations chez MSPR-DB)
spring.flyway.enabled=false

# JWT : meme secret que MSPR-AUTH
app.jwt.secret=${BETTER_AUTH_SECRET}

# CORS : origine autorisee (= URL du front)
app.cors.allowed-origin=${CORS_ORIGIN:http://localhost:5173}

# Server : prefixe /api pour toutes les URLs
server.servlet.context-path=/api

Ce qu'il faut savoir dire :

  • ${VAR:default} : Spring lit la variable d'environnement VAR, ou utilise default si elle n'est pas definie. Pratique : valeurs de dev dans le fichier, override en prod via env.
  • ddl-auto=validate : Hibernate verifie le schema au demarrage, ne le modifie jamais. Ceinture de securite contre une modif accidentelle.
  • context-path=/api : toutes les URLs Spring sont prefixees par /api. Donc @RequestMapping("/nutrition") donne l'URL http://host:8080/api/nutrition.
  • 3 profils : application.properties (defaut / prod-like), application-dev.properties (ajoute show-sql=true et logs TRACE Hibernate), application-prod.properties (minimise les logs).

Ce qu'il faut savoir dire :

  • FROM ... as builder : nomme le premier stage. Le deuxieme stage peut y piocher des fichiers via COPY --from=builder.
  • COPY pom.xml puis mvn dependency:go-offline avant COPY src/: astuce pour cacher les dependances Maven dans une couche Docker separee. Si on change juste le code, Docker ne retelecharge pas les deps.
  • Image finale base sur Alpine : distribution Linux ultra-legere (~5 Mo), pas de glibc. Reduction massive de la taille.
  • USER spring : on ne tourne pas en root dans le conteneur. Meilleure pratique de securite.
  • Healthcheck avec nc -z localhost 8080 : check TCP minimal, ne valide pas que l'app repond, juste que le port ecoute. Suffisant pour detecter un crash.

7. Questions probables du jury

Q1. Pourquoi Spring Boot plutot que Node, Python (Flask/FastAPI) ou Go ?

  • Spring Boot est le standard de l'industrie en Java : ecosysteme massif, maturite, documentation, forte demande sur le marche de l'emploi.
  • Productivite : Spring Data JPA, auto-config, devtools font gagner un temps fou sur des CRUD classiques.
  • Typing fort : Java 21 + Hibernate catch enormement d'erreurs a la compilation (erreurs de schema, mauvais types).
  • Cout : plus verbeux que Python/Node, temps de demarrage plus long (~10s contre ~1s en Node). Acceptable pour notre cas.

Pour un projet data avec ETL deja en Python, on aurait pu rester en Python (FastAPI). Le choix Spring Boot est pedagogique (apprendre un stack different) et coherent avec l'ecosysteme Java dans l'entreprise.

Q2. Pourquoi des DTO separes des entities JPA ?

Plusieurs raisons :

  • Decouplage : on peut changer la structure de la base (renommer une colonne, ajouter une relation) sans casser le format de l'API. Les tests d'integration ne plantent pas a chaque migration.
  • Securite : on ne renvoie pas certains champs (ex : password_hash s'il en existait) en masquant simplement les getters dans le DTO.
  • Validation differenciee : les contraintes d'entrees (@NotBlank, @Positive) sont sur le DTO, pas sur l'entity. L'entity, elle, peut recevoir un NULL (ex : une valeur optionnelle).
  • Reprendre plusieurs entities : un DTO peut agreger des donnees de plusieurs tables (ex : AnalyticsOverviewDTO combine des comptages sur 4 tables).

Le cout : du boilerplate (mapping entity -> DTO). Les gros projets utilisent MapStruct pour l'automatiser. Ici le mapping est ecrit a la main, c'est acceptable avec 5 entities.

Q3. Comment l'API valide-t-elle le JWT sans parler a MSPR-AUTH ?

Grace au secret partage BETTER_AUTH_SECRET injecte en variable d'environnement dans les deux services. MSPR-AUTH signe le JWT en HS512 avec cette cle. MSPR-API extrait la cle, reconstruit la signature, et compare.

Pas d'appel reseau, pas de latence, pas de point de defaillance. Le seul inconvenient : si on voulait invalider un JWT specifique (ex : user desactive), l'API n'en saurait rien tant que le exp n'est pas atteint. On mitige en gardant exp court (1h).

Q4. Pourquoi ddl-auto=validate et pas update ou create ?

  • create / create-drop : efface tout au demarrage, genere le schema depuis les entities. Dangereux en prod (perte de donnees) et non synchronise avec les migrations SQL de MSPR-DB.
  • update : compare les entities et la base, applique les deltas. Semble pratique mais tres risque : Hibernate peut supprimer des colonnes, changer des types, rater des renommages.
  • validate : Hibernate ne touche a rien, il verifie juste que le schema correspond aux entities. Si oui, tout va bien. Si non, l'app refuse de demarrer.

Pour un projet ou les migrations sont pilotees par un autre service (MSPR-DB), validate est le seul mode acceptable.

Q5. Pourquoi STATELESS ? Qu'est-ce que cela change vs. une session HTTP classique ?

  • Session classique : Tomcat cree une session cote serveur a chaque login, attache un cookie JSESSIONID au client. Les donnees de session (user id, roles, etc.) sont stockees en memoire du serveur. Probleme : si on a 3 instances d'API derriere un load balancer, chaque instance a sa propre memoire, donc il faut une "sticky session" (toujours router vers la meme instance).
  • STATELESS : aucune session cote serveur. Chaque requete est auto-suffisante (le JWT contient l'user id). On peut scaler horizontalement sans effort.

C'est le choix standard pour une API REST, surtout en architecture microservices.

Q6. Comment tester un controller en isolation ?

Avec Mockito (vu dans NutritionControllerTest.java) :

@ExtendWith(MockitoExtension.class)
class NutritionControllerTest {
    @Mock
    private NutritionService nutritionService;

    @InjectMocks
    private NutritionController controller;

    @Test
    void createNutritionEntry() {
        when(nutritionService.createNutritionEntry(any())).thenReturn(dto);
        ResponseEntity<NutritionEntryDTO> response = controller.createNutritionEntry(dto);
        assertEquals(HttpStatus.CREATED, response.getStatusCode());
    }
}
  • @Mock cree un faux NutritionService qu'on programme (when(...).thenReturn(...)).
  • @InjectMocks injecte les mocks dans le controller.
  • On test uniquement la logique du controller : routage HTTP, statut, body. Pas de base, pas de vrai service.
  • Pour un test plus large (avec contexte Spring complet et vraie BDD), on utiliserait @SpringBootTest + @Testcontainers.

Q7. La couverture de tests est a 80%, pourquoi ce chiffre ?

  • En dessous de 50% : generalement insuffisant pour avoir confiance. Beaucoup de code non teste.
  • 80% : sweet spot. Force a tester la majorite du code, laisse de la marge pour du code trivial (getters, config).
  • Au-dessus de 95% : souvent du gaspillage. Les 5% restants (gestion d'erreurs tres specifiques, code defensif) coutent enormement a tester pour peu de valeur.

JaCoCo est configure pour faire echouer le build si on descend sous 80% (en lignes ou en branches). C'est une contrainte CI qui evite la derive.

Q8. L'API expose un Swagger publiquement. C'est un risque de securite ?

Nuance : la doc Swagger liste les endpoints, mais ne donne aucun acces. Un attaquant pourrait faire une recon plus rapide, mais les endpoints sont toujours proteges par JWT.

Pour une prod stricte (sante, finance), on desactiverait Swagger en production (springdoc.api-docs.enabled=false dans application-prod.properties). Pour la MSPR, Swagger est utile au jury et aux data scientists, le risque est faible.

Q9. L'ExportController lit le rapport ETL sur disque, c'est inhabituel pour une API ?

Oui, c'est un design un peu particulier. etlReportService.getReport() lit le fichier /app/etl-data/processed/quality_report.json genere par MSPR-ETL. Le fichier est expose via un volume partage en lecture seule dans le docker-compose :

api:
  volumes:
    - ./MSPR-ETL/data:/app/etl-data:ro

Alternatives plus propres :

  • Stocker le rapport en base (table etl_reports).
  • Exposer un endpoint cote ETL que l'API interroge.

Le choix du volume partage a ete fait pour simplifier : l'ETL genere deja le fichier, autant le lire directement. A ameliorer pour une prod reelle.

Q10. Pourquoi 9 controllers et pas un seul ?

Chaque controller gere un domaine fonctionnel. Decouper permet :

  • Fichiers plus petits (le plus gros fait 83 lignes).
  • Tests isoles par domaine.
  • Documentation Swagger organisee (via @Tag).
  • Plusieurs personnes peuvent bosser sur des controllers differents sans conflit Git.

Un controller unique de 1000 lignes serait une mauvaise pratique (code indigeste, responsabilites melangees, tests compliques).

Q11. Comment gerer une migration de schema qui ajouterait une colonne obligatoire ?

  1. Ajouter la colonne en SQL dans MSPR-DB (nouvelle migration V8__add_nutrition_calories_kj.sql).
  2. Mettre a jour l'entity Java (nouveau @Column private BigDecimal caloriesKj; + getter/setter).
  3. Mettre a jour le DTO si on veut l'exposer.
  4. Relancer les deux services (DB applique la migration, API revalide son schema).

L'ordre est crucial : la DB doit etre migree avant que l'API redemarre, sinon le mode validate echoue. Dans docker-compose.yml, l'API a un depends_on: db: service_healthy, ce qui garantit cet ordre.

Q12. L'API renvoie du JSON par defaut. Comment servir du XML si demande ?

Spring Boot supporte la content negotiation : le client envoie Accept: application/xml et Spring peut serialiser en XML si la dependance jackson-dataformat-xml est presente. Dans notre projet elle ne l'est pas, donc toute requete Accept: application/xml renverra un 406 Not Acceptable. C'est un choix volontaire : on ne supporte que JSON (le front Vue en a besoin, pas d'autres formats demandes).

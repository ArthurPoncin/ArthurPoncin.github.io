Fiche de revision : MSPR-DB

Support de revision pour la soutenance MSPR1. Objectif : comprendre le role du service, le schema global et les points techniques importants, sans rentrer dans le detail colonne par colonne.

0. Vocabulaire a connaitre avant de lire

Terme Definition en une phrase
SGBD Systeme de Gestion de Base de Donnees. Le moteur qui stocke et interroge les donnees (ici : PostgreSQL).
Schema Structure de la base : la liste des tables, de leurs colonnes et de leurs relations.
Table Stockage tabulaire typé (des lignes et des colonnes). Equivalent d'une feuille Excel, mais avec des types forts.
Migration Script SQL versionne qui modifie le schema (ajoute une table, une colonne, un index). Chaque migration se lance une seule fois.
Index Structure secondaire qui accelere les lectures sur une colonne, au prix d'un cout en ecriture et stockage. Equivalent de l'index d'un livre.
Contrainte d'unicite Regle SQL qui interdit les doublons sur une colonne ou un groupe de colonnes.
Cle etrangere (FK) Colonne qui pointe vers la cle primaire d'une autre table (ex : user_id -> users.id). Garantit l'integrite referentielle.
Volume Docker Dossier persistant stocke en dehors du conteneur. Si on supprime le conteneur, les donnees du volume restent.
docker-entrypoint-initdb.d Dossier special de l'image PostgreSQL : tous les .sql qui s'y trouvent sont executes automatiquement au premier demarrage du conteneur.

1. TL;DR

MSPR-DB est le service de base de donnees centrale du projet. C'est un conteneur PostgreSQL 17 qui embarque les migrations SQL dans son image Docker. Au premier demarrage, toutes les migrations s'appliquent automatiquement et creent le schema.

  • Stack : PostgreSQL 17 (image postgres:17-alpine)
  • Ecrit par : MSPR-ETL (insertions via pg_load)
  • Lu par : MSPR-API (CRUD via Spring Data JPA) et MSPR-FRONT (indirectement via l'API)
  • Contenu : 6 tables metier + 1 table de journal (etl_logs)
  • Port hote : 5434 (mappe sur 5432 interne au conteneur)
  • Reseau : mspr_data_network
  • Persistence : volume Docker nomme postgres_data

Un deuxieme conteneur PostgreSQL (auth-db, port 5433) est gere separement par MSPR-AUTH. MSPR-DB ne stocke pas les donnees d'authentification.

2. Qui ecrit, qui lit

flowchart LR
    ETL[MSPR-ETL] -->|INSERT pandas -> psycopg2| DB[(MSPR-DB<br/>PostgreSQL 17)]
    API[MSPR-API<br/>Spring Boot] -->|SELECT/INSERT/UPDATE<br/>via JPA| DB
    FRONT[MSPR-FRONT] -->|HTTP REST| API

    DB -.persiste.-> VOL[(volume postgres_data)]

L'ETL est le seul producteur de donnees metier. L'API expose ces donnees au front, plus quelques ajouts/modifications manuels (endpoints CRUD).

3. Stack technique

Composant Role Pourquoi ce choix
PostgreSQL 17 Moteur de BDD Standard open-source le plus complet. Supporte nativement JSONB, tableaux (TEXT[]), UNIQUE NULLS NOT DISTINCT, index GIN
Image alpine Packaging leger Base Linux Alpine : ~80 Mo contre ~400 Mo pour l'image debian. Plus rapide a telecharger, surface d'attaque reduite
docker-entrypoint-initdb.d Mecanisme de migration Fonction native de l'image PostgreSQL : aucun outil tiers (Flyway, Liquibase) a installer. Tres simple pour un projet MSPR
Volume nomme postgres_data Persistence Les donnees survivent a un docker compose down. Il faut un down -v pour tout effacer
Healthcheck pg_isready Fiabilite Permet aux autres services (API, ETL) d'attendre que la BDD soit prete via depends_on: condition: service_healthy

Le Dockerfile tient en 3 lignes :

FROM postgres:17-alpine
COPY migrations/*.sql /docker-entrypoint-initdb.d/

Tout le reste (user, password, mount du volume, reseau) est configure dans le docker-compose.yml racine.

4. Les tables

7 tables au total (6 metier + 1 journal). Les tables metier sont independantes (aucune FK entre elles depuis V7).

Table Role Source des donnees Volumetrie attendue
exercises Catalogue d'exercices (squat, pompe, traction...) avec muscles cibles, equipements, instructions Pipeline exercisedb ~1500 lignes
nutrition_entries Donnees nutritionnelles d'aliments (calories, macronutriments, micronutriments) Pipeline nutrition_dataset ~650 lignes
exercise_entries Seances de sport (type, duree, calories brulees, BPM) Pipeline gym_tracking ~2700 lignes
biometric_entries Mesures corporelles (poids, taille, BMI, frequence cardiaque, demographiques) Pipeline gym_tracking ~2700 lignes
diet_recommendations Recommandations dietetiques par profil patient (pathologie, regime, activite) Pipeline diet_recommendations ~1000 lignes
etl_logs Journal des runs ETL (lignes lues, inserees, rejetees, statut, details) ETL lui-meme (log_etl_run) croit au fil du temps

Pour le schema detaille de chaque table, voir MSPR-DB/migrations/V1__init_schema.sql et V2__diet_recommendations.sql.

Note sur la table users (supprimee)

Le schema initial contenait une table users avec FK user_id dans les tables d'entries. Elle a ete supprimee par la migration V7 : les datasets sources (Kaggle) sont anonymes et heterogenes, sans identifiant utilisateur commun, donc les FK etaient toujours NULL. Les profils utilisateurs reels sont stockes dans MSPR-AUTH (base auth_db, separee).

5. Points techniques importants

5.1 Mecanisme de migration

Pas de Flyway, pas de Liquibase. On utilise le mecanisme natif de l'image PostgreSQL : les fichiers .sql deposes dans /docker-entrypoint-initdb.d/ sont executes en ordre alphanumerique au premier demarrage du conteneur (quand le dossier de donnees /var/lib/postgresql/data est vide).

Consequences importantes :

  • Si on relance le conteneur sans supprimer le volume, les migrations ne sont pas rejouees. Elles ne tournent qu'une fois.
  • Pour appliquer une nouvelle migration sur une base existante, il faut la passer manuellement (docker exec ... psql -f V8__...sql), ou faire un docker compose down -v (efface tout, pas recommande en prod).
  • En MSPR, ce mode simplifie est acceptable. En production reelle, on utiliserait Flyway ou Liquibase pour tracer quelles migrations ont deja ete appliquees dans une table schema_version.

5.2 Convention de nommage des migrations

Inspire de Flyway : V{numero}__{description}.sql. L'ordre alphanumerique donne l'ordre d'execution.

Fichier Role
V1__init_schema.sql Creation des 6 tables initiales + users + tous les index
V2__diet_recommendations.sql Ajout de la table diet_recommendations
V3__add_unique_constraints.sql Contraintes UNIQUE NULLS NOT DISTINCT pour que l'ETL puisse utiliser ON CONFLICT DO NOTHING
V4__fix_nutrition_schema.sql Ajout colonne carbsg dans nutrition_entries (correction d'incoherence)
V5__add_missing_columns.sql Ajout age dans biometric_entries
V6__biometric_add_demographics.sql Ajout gender, experience_level dans biometric_entries
V7__drop_users_table.sql Suppression de la table users et de toutes les FK user_id

Les migrations V4 a V7 utilisent IF NOT EXISTS / IF EXISTS pour etre idempotentes : si on les rejoue par erreur, elles ne plantent pas.

5.3 Types PostgreSQL utilises

  • BIGSERIAL : entier 64 bits auto-incremente. Utilise comme cle primaire (id) sur toutes les tables.
  • DECIMAL(p, s) : nombre decimal precis (ex : DECIMAL(8, 2) = jusqu'a 8 chiffres dont 2 apres la virgule). Utilise pour les mesures (calories, poids). On evite FLOAT pour ne pas perdre en precision sur les calculs medicaux.
  • VARCHAR(n) : chaine de longueur variable avec limite. Utilise pour les libellés courts.
  • TEXT : chaine sans limite. Utilise pour les instructions d'exercice (longues).
  • TEXT[] : tableau de chaines stocke dans une seule colonne. Utilise pour body_parts, target_muscles, equipments. Evite de faire une table de jointure quand on n'a pas besoin de requeter sur les elements.
  • TIMESTAMP : date + heure. Avec DEFAULT NOW() pour les created_at.

5.4 Index : pourquoi et lesquels

Un index est un duplicata trie de la colonne, stocke a part, qui permet a PostgreSQL de trouver une ligne en O(log n) au lieu de O(n). Le cout : plus de stockage, ecritures un peu plus lentes (il faut maintenir l'index a jour).

On a 3 types d'index dans le projet :

Index GIN sur les TEXT[]

CREATE INDEX idx_exercises_body_parts ON exercises USING GIN (body_parts);

GIN (Generalized Inverted Index) est specifique aux types composites (tableaux, JSONB, full-text). Il permet de repondre tres vite a "quels exercices ciblent les pectoraux ?" (requete WHERE 'pectorals' = ANY(body_parts)). Sans GIN, il faudrait scanner toute la table.

Index B-tree sur les colonnes de filtrage

CREATE INDEX idx_nutrition_status ON nutrition_entries (status);
CREATE INDEX idx_etl_logs_started ON etl_logs (started_at DESC);

B-tree est l'index par defaut, bon pour les egalites (WHERE status = 'NETTOYE') et les tris (ORDER BY started_at DESC).

Contraintes UNIQUE (qui creent des index automatiquement)

UNIQUE NULLS NOT DISTINCT (food_name, category, meal_type, source) sur nutrition_entries. Cree un index qui sert a la fois a :

  • interdire les doublons (contrainte metier)
  • accelerer les recherches sur ce tuple (effet secondaire)

5.5 UNIQUE NULLS NOT DISTINCT : pourquoi ?

Probleme : le comportement standard SQL considere que NULL != NULL. Donc deux lignes avec category = NULL, meal_type = NULL seraient toutes les deux acceptees par une contrainte UNIQUE classique, creant un doublon logique.

Solution : depuis PostgreSQL 15, on peut ecrire UNIQUE NULLS NOT DISTINCT (col1, col2, ...). Les NULLs sont alors traites comme des valeurs egales entre elles. Concretement : deux lignes (Apple, NULL, NULL, NUTRITION_DATASET) sont bien detectees comme doublons et la deuxieme est rejetee par ON CONFLICT.

C'est indispensable ici parce que les datasets Kaggle ont souvent des champs manquants, et sans cette option le pipeline ETL creerait des doublons a chaque run.

5.6 Persistence et reinitialisation

  • Persistence : le volume postgres_data est monte sur /var/lib/postgresql/data du conteneur. Les donnees survivent a tout, sauf un docker compose down -v.
  • Reinitialiser la base from scratch : docker compose down -v && docker compose up -d db. Relance toutes les migrations depuis V1.
  • Export CSV : le script scripts/export_clean_data.sh dump toutes les tables en CSV via \COPY ... TO STDOUT WITH CSV HEADER. Utile pour livrer les donnees aux data scientists sans acces direct a la base.

5.7 Healthcheck et dependances Docker

healthcheck:
  test: ["CMD-SHELL", "pg_isready -U healthai_user -d healthai"]
  interval: 10s
  timeout: 5s
  retries: 5

pg_isready est un outil livre avec PostgreSQL qui verifie si le serveur accepte des connexions. Pendant que la BDD se prepare (quelques secondes au demarrage), elle est marquee unhealthy.

Les autres services utilisent cela pour attendre :

api:
  depends_on:
    db:
      condition: service_healthy

L'API ne demarre pas tant que la BDD ne repond pas. Evite les crashes au demarrage ("connection refused").

5.8 CI (.github/workflows/ci.yml)

2 jobs :

  1. validate : lance un PostgreSQL 17 dans GitHub Actions et rejoue toutes les migrations en ordre (for f in $(ls migrations/V*__*.sql | sort -V)). Si une migration est cassee, le CI echoue.
  2. publish : si validate passe et qu'on est sur main, build et push l'image Docker sur GHCR (GitHub Container Registry, nom d'image : ghcr.io/whitefoxxyt/mspr-db).

6. Code essentiel a savoir expliquer au jury

Les morceaux SQL cle a pouvoir commenter a l'oral.

6.1 Creation d'une table avec types forts

CREATE TABLE exercises (
    id BIGSERIAL PRIMARY KEY,
    external_id VARCHAR(100) UNIQUE NOT NULL,
    name VARCHAR(255) NOT NULL,
    body_parts TEXT ARRAY,
    target_muscles TEXT ARRAY,
    secondary_muscles TEXT ARRAY,
    equipments TEXT ARRAY,
    instructions TEXT,
    gif_url VARCHAR(500),
    source VARCHAR(50) NOT NULL DEFAULT 'EXERCISEDB',
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

Ce qu'il faut savoir dire :

  • BIGSERIAL PRIMARY KEY : entier 64 bits auto-incremente, cle primaire. Chaque insert se voit attribuer un id unique automatiquement.
  • UNIQUE NOT NULL sur external_id : on ne peut pas avoir deux exercices avec le meme identifiant source, et il doit etre renseigne.
  • TEXT ARRAY (synonyme de TEXT[]) : une colonne qui contient une liste de chaines. Permet d'eviter une table de jointure quand on n'a pas besoin de requeter sur les elements individuels.
  • DEFAULT NOW() : si on ne precise pas created_at lors de l'insert, PostgreSQL met l'horodatage du moment. Tres pratique pour l'audit.

6.2 Index GIN sur un tableau

CREATE INDEX idx_exercises_body_parts ON exercises USING GIN (body_parts);

Requete associee :

SELECT name FROM exercises WHERE 'pectorals' = ANY(target_muscles);

Ce qu'il faut savoir dire :

  • GIN = Generalized Inverted Index. C'est comme un index inverse dans un moteur de recherche : pour chaque valeur possible dans les tableaux, il stocke la liste des lignes qui la contiennent.
  • Sans cet index, la requete ci-dessus ferait un "sequential scan" (parcours lineaire) de toute la table. Avec l'index, PostgreSQL saute directement aux lignes pertinentes.
  • Cout : l'index pese en stockage (proportionnel au nombre d'elements dans les tableaux), et ralentit legerement les inserts. Pour un catalogue statique de 1500 exercices, c'est negligeable.

6.3 Migration idempotente (ALTER TABLE ... IF NOT EXISTS)

-- V6__biometric_add_demographics.sql
ALTER TABLE biometric_entries
    ADD COLUMN IF NOT EXISTS gender VARCHAR(10),
    ADD COLUMN IF NOT EXISTS experience_level INTEGER;

Ce qu'il faut savoir dire :

  • IF NOT EXISTS rend la migration idempotente : si on la relance, elle ne plante pas ("column already exists"). Elle detecte que la colonne est deja la et ne fait rien.
  • Sans cela, relancer la migration sur une base deja migree leverait une erreur et bloquerait les suivantes.
  • On utilise aussi IF EXISTS pour les suppressions : DROP COLUMN IF EXISTS user_id, DROP CONSTRAINT IF EXISTS ....

6.4 Contrainte UNIQUE NULLS NOT DISTINCT

-- V3__add_unique_constraints.sql
ALTER TABLE nutrition_entries
ADD CONSTRAINT uq_nutrition_entry
UNIQUE NULLS NOT DISTINCT (food_name, category, meal_type, source);

Ce qu'il faut savoir dire :

  • Contrainte composite : le tuple (food_name, category, meal_type, source) doit etre unique pour toute la table.
  • NULLS NOT DISTINCT (PostgreSQL 15+) : les NULL sont traites comme egaux entre eux. Sans cela, deux lignes (Apple, NULL, NULL, ...) seraient considerees differentes et la contrainte ne bloquerait pas le doublon.
  • Cette contrainte rend possible le ON CONFLICT DO NOTHING de l'ETL : c'est ce qui garantit l'idempotence cote base.

6.5 Dockerfile minimaliste

FROM postgres:17-alpine
COPY migrations/*.sql /docker-entrypoint-initdb.d/

Ce qu'il faut savoir dire :

  • On part de l'image officielle postgres:17-alpine qui a tout PostgreSQL pre-installe.
  • On copie juste les migrations dans le dossier special /docker-entrypoint-initdb.d/ : l'entrypoint de l'image execute automatiquement tous les .sql de ce dossier au premier demarrage, en ordre alphanumerique.
  • Aucune ligne de code Python/Java/Go n'est necessaire : tout le cycle de vie est geré par l'image de base. C'est l'idee : "on se sert du mecanisme existant plutot que de reinventer".

6.6 Configuration docker-compose (healthcheck + volume + reseau)

services:
  db:
    image: postgres:17-alpine
    container_name: mspr-healthai-db
    environment:
      POSTGRES_DB: healthai
      POSTGRES_USER: healthai_user
      POSTGRES_PASSWORD: password
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./MSPR-DB/migrations:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U healthai_user -d healthai"]
      interval: 10s
      timeout: 5s
      retries: 5
    ports:
      - "5434:5432"
    networks:
      - mspr_data_network
    security_opt:
      - no-new-privileges:true

volumes:
  postgres_data:

Ce qu'il faut savoir dire :

  • Variables POSTGRES_* : lues par l'entrypoint de l'image pour creer la base et l'utilisateur au premier demarrage.
  • 2 volumes : un nomme (postgres_data) pour la persistence des donnees, un bind mount en lecture seule (:ro) pour exposer les migrations au conteneur sans les inclure dans l'image.
  • Mapping 5434:5432 : le port 5432 du conteneur est expose sur le port 5434 de la machine hote (evite de conflicter avec un PostgreSQL local sur 5432, et avec l'auth-db qui est sur 5433).
  • no-new-privileges: true : securite Docker. Empeche un processus du conteneur d'obtenir plus de droits que le conteneur lui-meme (meme via setuid).

6.7 CI : rejeu des migrations dans un Postgres de test

services:
  postgres:
    image: postgres:17-alpine
    env:
      POSTGRES_DB: healthai_test
      POSTGRES_USER: healthai_user
      POSTGRES_PASSWORD: test

steps:
  - name: Application sequentielle des migrations
    env:
      PGHOST: localhost
      PGPORT: 5432
      PGUSER: healthai_user
      PGPASSWORD: test
      PGDATABASE: healthai_test
    run: |
      for f in $(ls migrations/V*__*.sql | sort -V); do
        echo "Applying $f..."
        psql -v ON_ERROR_STOP=1 -f "$f"
      done

Ce qu'il faut savoir dire :

  • GitHub Actions lance un vrai PostgreSQL ephemere pour ce job (bloc services:).
  • On applique toutes les migrations (V1, V2, ..., V7) dans l'ordre via sort -V (tri "version" qui gere V10 apres V9).
  • psql -v ON_ERROR_STOP=1 : si une migration echoue, psql s'arrete immediatement avec un code d'erreur non nul, ce qui fait echouer le job CI. Protection contre "la migration passe en local mais casse quand rejouee from scratch".

7. Questions probables du jury

Q1. Pourquoi PostgreSQL et pas MySQL, SQLite ou MongoDB ?

  • SQLite : base fichier mono-process, pas adaptee a une architecture multi-services ou plusieurs conteneurs (ETL, API) lisent/ecrivent en concurrence.
  • MySQL : tres bonne base mais moins riche en fonctionnalites (pas de TEXT[] natif, moins bon support JSON, pas de UNIQUE NULLS NOT DISTINCT).
  • MongoDB : base NoSQL orientee document. Pas adaptee aux donnees relationnelles avec contraintes strictes (types forts, unicite composite) comme ici. On l'utilise d'ailleurs dans MSPR2 pour le microservice recommandations, ou c'est plus adapte.
  • PostgreSQL coche toutes les cases : relationnel strict, types riches (arrays, JSONB), full-text search, extensions (PostGIS, pg_trgm), et c'est le standard de l'industrie.

Q2. Pourquoi ne pas utiliser Flyway ou Liquibase ?

Ces outils tracent les migrations deja appliquees dans une table schema_version, ce qui permet de gerer des environnements long-vivants (prod, staging, dev). Pour la MSPR, on n'en a pas besoin :

  • Un seul environnement reel (local / CI).
  • docker compose down -v + relance = reset propre en quelques secondes.
  • Les migrations V4 a V7 sont ecrites de maniere idempotente (IF NOT EXISTS), donc on peut les rejouer sans casse si besoin.

En production reelle avec plusieurs environnements et pas de droit au reset, on passerait a Flyway sans hesiter.

Q3. Pourquoi avoir supprime la table users ?

Les datasets ingeres (Kaggle) sont anonymises : il n'y a pas de colonne "user_id" dans les CSV. Du coup, les FK user_id dans les tables nutrition_entries, exercise_entries, biometric_entries etaient toutes a NULL. Cette table n'apportait rien et polluait le schema. La migration V7 la supprime.

Les vrais utilisateurs de l'application sont dans MSPR-AUTH (base auth_db separee, geree par better-auth). La separation base metier / base auth est volontaire : separation des responsabilites et possibilite de scaler independamment.

Q4. Pourquoi un index GIN sur les tableaux ?

Parce qu'on veut pouvoir requeter "trouve-moi les exercices qui ciblent les pectoraux" en O(log n). Sans index, PostgreSQL devrait scanner les 1500 lignes de la table exercises et tester le tableau de chaque ligne. Avec un index GIN, il sait directement quelles lignes contiennent pectorals dans target_muscles.

Q5. A quoi sert UNIQUE NULLS NOT DISTINCT ?

Le SQL standard dit que NULL != NULL. Donc une contrainte UNIQUE classique sur (food_name, category, meal_type, source) laisse passer deux lignes (Apple, NULL, NULL, NUTRITION_DATASET) comme si elles etaient differentes. On aurait un doublon logique a chaque run ETL.

UNIQUE NULLS NOT DISTINCT (dispo en PostgreSQL 15+) traite les NULL comme egaux. Deux lignes identiques meme avec des NULL sont bien detectees comme doublon, et l'ON CONFLICT DO NOTHING de l'ETL fonctionne.

Q6. Que se passe-t-il si on perd le volume postgres_data ?

On perd toutes les donnees de la BDD. Mais :

  • Le schema est rejouable via les migrations au prochain demarrage.
  • Les donnees metier sont re-ingerables via l'ETL (les CSV/JSON sont dans MSPR-ETL/data/raw/, versionnes dans le repo).
  • Les vrais utilisateurs sont dans auth_db (autre volume).

Donc perte de donnees reelle = uniquement les etl_logs et les modifications CRUD manuelles via l'API. Pour une prod reelle, on ferait un backup regulier (pg_dump quotidien).

Q7. Pourquoi le port 5434 sur l'hote ?

Trois PostgreSQL se baladent dans le projet :

  • Un eventuellement installe en local sur 5432 (celui du dev).
  • MSPR-AUTH sur 5433.
  • MSPR-DB sur 5434.

Choisir des ports non standard evite les collisions. En interne au reseau Docker, tous sont sur 5432 par defaut (chacun dans son conteneur isole), c'est juste le mapping vers l'hote qui change.

Q8. Comment monitore-t-on la sante de la BDD ?

  • Healthcheck Docker (pg_isready toutes les 10s) : le plus basique. Indique si PostgreSQL accepte des connexions.
  • Requete sur etl_logs : permet de voir si les derniers runs ETL ont ecrit correctement.
  • Logs Docker : docker logs mspr-healthai-db pour voir les erreurs SQL, les lenteurs, les problemes de connexion.
  • En prod, on brancherait un exporter Prometheus (ex : postgres_exporter) pour sortir des metriques (taille des tables, requetes lentes, nombre de connexions).

Q9. Les index ont un cout, pourquoi en avoir autant ?

Chaque index accelere les lectures mais ralentit les ecritures (il faut maintenir l'index a jour a chaque INSERT/UPDATE/DELETE). Ici :

  • Les donnees sont surtout lues (l'API fait beaucoup de SELECT pour le dashboard).
  • Les ecritures sont concentrees dans des batchs ETL nocturnes, donc peu sensibles a la performance.
  • La volumetrie est faible (quelques milliers de lignes) : meme avec tous ces index, le cout reste negligeable.

Bref, le ratio lecture/ecriture favorise clairement l'indexation.

Q10. Pourquoi utiliser DECIMAL plutot que FLOAT pour les mesures ?

FLOAT est une representation binaire approximative : 0.1 + 0.2 != 0.3 en pratique. Pour des mesures medicales (calories, poids, BMI), une erreur d'arrondi pourrait avoir des consequences (pharmacologie, calculs de dose). DECIMAL(p, s) est une representation decimale exacte, adaptee aux calculs financiers et medicaux.

Cout : legerement plus lent et plus lourd en stockage, mais non significatif a notre volumetrie.

Q11. La colonne etl_logs.details est de type TEXT, pas JSONB. Pourquoi ?

C'est un choix d'origine a ameliorer. La colonne stocke effectivement du JSON (serialise par json.dumps cote Python), mais le type de colonne est TEXT dans le schema actuel. Consequence : on ne peut pas faire details->>'error' directement, il faudrait caster details::jsonb->>'error'.

Une future migration V8__etl_logs_details_jsonb.sql convertirait proprement la colonne en JSONB avec ALTER TABLE etl_logs ALTER COLUMN details TYPE JSONB USING details::jsonb. Cela accelererait aussi les requetes analytiques sur les runs ETL.

Q12. Comment sauvegarder/restaurer la BDD ?

  • Sauvegarde : docker exec mspr-healthai-db pg_dump -U healthai_user healthai > backup.sql. Genere un fichier SQL avec tout le schema et les donnees.
  • Restauration : docker exec -i mspr-healthai-db psql -U healthai_user healthai < backup.sql.
  • Pour les exports analytiques (data scientists), on utilise scripts/export_clean_data.sh qui genere des CSV par table via \COPY ... TO STDOUT.

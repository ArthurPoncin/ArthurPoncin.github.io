Fiche de revision : MSPR-FRONT

Support de revision pour la soutenance MSPR1. Objectif : comprendre le role du dashboard, l'organisation Vue 3 et les points techniques importants, sans rentrer dans le detail des templates.

0. Vocabulaire a connaitre avant de lire

Terme Definition en une phrase
SPA (Single Page Application) Application web ou la navigation se fait sans recharger la page. Le routeur change le contenu dynamiquement.
Vue 3 Framework JavaScript front-end, concurrent de React et Angular. Utilise un systeme de composants reactifs.
SFC (Single File Component) Fichier .vue qui regroupe dans un seul fichier le template HTML, la logique TypeScript (<script>) et le style CSS (<style scoped>).

1. TL;DR

MSPR-FRONT est le dashboard d'administration du projet, destine aux admins et data scientists (pas aux utilisateurs finaux). Il permet de :

  • Visualiser les metriques de qualite des donnees (completude, taux de rejet, anomalies)
  • Consulter le rapport ETL et les stats analytiques
  • Nettoyer et editer les anomalies detectees
  • Valider ou rejeter les enregistrements en attente
  • Exporter les donnees en JSON ou CSV

Stack :

  • Vue 3.5 + Composition API + <script setup>
  • TypeScript 6
  • Vite 8 (bundler + dev server)
  • Vue Router 5
  • Pinia 3 (state global)
  • Chart.js 4.5 (visualisations)
  • Vitest 4 (tests)
  • ESLint + oxlint + Prettier

Port dev : 5173. Communique avec : MSPR-AUTH (:3000) pour l'authentification et MSPR-API (:8080/api) pour les donnees metier.

2. Flux d'authentification cote front

sequenceDiagram
    participant U as User
    participant V as AuthView
    participant S as authStore (Pinia)
    participant API as MSPR-AUTH
    participant LS as localStorage

    U->>V: Saisit email + mot de passe
    V->>S: login(email, password)
    S->>API: POST /api/auth/sign-in/email<br/>credentials: 'include'
    API-->>S: Cookie de session + { user }
    S->>API: GET /api/jwt<br/>credentials: 'include'
    API-->>S: { token: "eyJ..." }
    S->>LS: setSession({ user, tokens })
    S-->>V: resolved

    Note over LS: Session persistee<br/>clef : healthai.auth.session

    U->>V: Navigation vers /dashboard
    V->>S: beforeEach guard
    S->>LS: getSession()
    LS-->>S: { user, tokens }
    S-->>V: isAuthenticated = true

A retenir :

  • Le front tient une seule source de verite : le localStorage (via authSessionManager).
  • L'appel GET /api/jwt recupere un JWT signe en HS512 que l'API Spring Boot saura valider.
  • Le cookie better-auth reste dans le navigateur pour pouvoir rebootstraper si le localStorage est vide (ex : apres verification email, Vue vient d'etre rechargee).

5. Points techniques importants

5.1 Composition API avec <script setup>

Exemple minimal d'un composant :

<script setup lang="ts">
import { ref, computed } from 'vue'

interface Props {
  title: string
  value: number
}
const props = defineProps<Props>()

const count = ref(0)
const doubled = computed(() => count.value * 2)

function increment() {
  count.value++
}
</script>

<template>
  <h1>{{ props.title }}</h1>
  <button @click="increment">{{ count }} / {{ doubled }}</button>
</template>

Points cle :

  • Pas de return {} explicite : tout ce qui est declare dans <script setup> est disponible dans le template automatiquement.
  • ref(0) cree une valeur reactive : count.value++ declenche un re-render automatiquement.
  • computed(() => ...) : valeur derivee qui se met a jour quand ses dependances changent.
  • defineProps<Props>() : genere le typage des props a partir de l'interface TypeScript.

5.2 Stores Pinia avec le style composition

export const useAuthStore = defineStore('auth', () => {
  // State = ref()
  const session = ref<AuthSession | null>(null)
  const loading = ref(false)

  // Getters = computed()
  const isAuthenticated = computed(() => session.value !== null)

  // Actions = fonctions async
  async function login(email: string, password: string) {
    loading.value = true
    try {
      session.value = await authApi.login(email, password)
    } finally {
      loading.value = false
    }
  }

  return { session, loading, isAuthenticated, login }
})

Pattern "setup store" (equivalent de <script setup> pour un store) :

  • State, getters, actions definis comme des ref, computed, fonctions.
  • On renvoie ce qui doit etre expose.
  • Dans n'importe quel composant : const auth = useAuthStore(); auth.login(...).

Avantages vs Vuex : pas de mutations, pas de modules imbriques, inference TypeScript parfaite.

5.3 Vue Router avec guards de navigation

const router = createRouter({
  history: createWebHistory(import.meta.env.BASE_URL),
  routes: [
    { path: '/', component: AuthView, meta: { guestOnly: true } },
    { path: '/dashboard', component: DashboardView, meta: { requireAuth: true } },
    { path: '/data-cleaning', component: DataCleaningView, meta: { requireAuth: true } },
    { path: '/validation', component: ValidationView, meta: { requireAuth: true } },
    { path: '/:pathMatch(.*)*', redirect: '/' },  // 404 -> home
  ],
})

router.beforeEach(async (to) => {
  const isAuthenticated = authSessionManager.hasValidSession()

  if (isAuthenticated) {
    if (to.meta.guestOnly) return { name: 'dashboard' }
    return true
  }

  // Tentative de bootstrap depuis le cookie Better Auth
  if (to.meta.requireAuth || to.meta.guestOnly) {
    const bootstrapped = await useAuthStore().bootstrapFromSession()
    if (bootstrapped) {
      if (to.meta.guestOnly) return { name: 'dashboard' }
      return true
    }
  }

  if (to.meta.requireAuth) return { name: 'auth' }
  return true
})

Pattern des meta : chaque route porte des metadonnees (requireAuth, guestOnly) que le guard consulte. Evite de dupliquer la logique d'auth dans chaque composant.

Bootstrap depuis cookie : cas particulier post-verification email. Better Auth a cree un cookie de session cote navigateur, mais le localStorage est vide (car l'email de verification ouvre le lien dans un nouvel onglet). Le guard appelle /api/session avec credentials: include pour recuperer l'utilisateur depuis le cookie et recreer une session locale.

5.4 Client API avec injection automatique du JWT

class ApiClient {
  private async request<T>(endpoint: string, options: RequestInit = {}): Promise<T> {
    const url = `${API_BASE_URL}${endpoint}`
    const accessToken = authSessionManager.getAccessToken()

    const response = await fetch(url, {
      ...options,
      headers: {
        'Content-Type': 'application/json',
        ...(accessToken ? { Authorization: `Bearer ${accessToken}` } : {}),
        ...(options.headers as Record<string, string>),
      },
    })

    if (!response.ok) {
      throw new Error(`API Error: ${response.status} ${response.statusText}`)
    }
    return response.json()
  }

  get<T>(endpoint: string) { return this.request<T>(endpoint, { method: 'GET' }) }
  post<T>(endpoint: string, data: unknown) { return this.request<T>(endpoint, { method: 'POST', body: JSON.stringify(data) }) }
  // ...
}

Point cle : chaque requete vers MSPR-API recoit automatiquement le header Authorization: Bearer <jwt>. Les stores/composants n'ont pas a s'en occuper. Si pas de JWT, on envoie la requete quand meme (l'API renverra 401, gere ailleurs).

5.5 Gestion de la session dans le localStorage

const AUTH_SESSION_STORAGE_KEY = 'healthai.auth.session'
const ACCESS_TOKEN_TTL_MS = 1000 * 60 * 60  // 1h

export const authSessionManager = {
  getSession(): AuthSession | null {
    const stored = localStorage.getItem(AUTH_SESSION_STORAGE_KEY)
    const session = parseStoredSession(stored)
    if (session && isExpired(session.tokens.expiresAt)) {
      localStorage.removeItem(AUTH_SESSION_STORAGE_KEY)
      return null
    }
    return session
  },

  setSession(session: AuthSession): void {
    localStorage.setItem(AUTH_SESSION_STORAGE_KEY, JSON.stringify(session))
  },

  hasValidSession(): boolean {
    return this.getSession() !== null
  },
}

Choix volontaire : localStorage, pas cookie cote front. Raisons :

  • Le cookie est gere cote AUTH (HttpOnly, SameSite) pour la session.
  • Le JWT sert a appeler MSPR-API : il doit etre accessible en JS pour l'ajouter au header Authorization. Un cookie HttpOnly ne serait pas lisible depuis fetch.
  • Risque : localStorage est accessible depuis JavaScript, donc vulnerable a XSS. Mitigation : Vue 3 echappe tout par defaut dans {{ }}, on n'utilise pas v-html avec du contenu externe.

5.6 Mode mock pour developpement sans backend

Dans .env :

VITE_USE_MOCK=true
VITE_API_BASE_URL=http://localhost:8080/api
VITE_AUTH_BASE_URL=http://localhost:3000

Quand VITE_USE_MOCK=true, les services API renvoient des donnees statiques (mockData dans api.ts) au lieu d'appeler le backend. Permet de developper l'UI sans MSPR-API/DB/AUTH qui tournent.

Remarque : dans le Dockerfile (build de prod), on force VITE_USE_MOCK=false. Les variables VITE_* sont injectees dans le bundle au build time, pas au runtime.

5.7 Lint double : oxlint + ESLint

"scripts": {
  "lint": "run-s lint:*",
  "lint:oxlint": "oxlint . --fix",
  "lint:eslint": "eslint . --fix --cache"
}

Pourquoi deux linters :

  • oxlint : linter ecrit en Rust, extremement rapide (~100x ESLint). Implemente les regles ESLint de base et les plus populaires. Parfait pour un premier passage rapide.
  • ESLint : extensible via plugins. On utilise eslint-plugin-vue (regles specifiques aux .vue) et @vue/eslint-config-typescript (regles TS). Incontournable pour Vue mais plus lent.
  • eslint-plugin-oxlint : integre pour qu'ESLint sache quelles regles oxlint a deja verifiees et ne les refasse pas. Evite les doublons.

run-s (de npm-run-all2) execute les scripts en sequence : oxlint d'abord (corrections rapides), ESLint ensuite (regles Vue).

6. Code essentiel a savoir expliquer au jury

6.1 Un composant Vue 3 complet (MetricsCard)

<template>
  <div class="metrics-card" :class="variant">
    <div class="metrics-card__icon"><slot name="icon" /></div>
    <div class="metrics-card__content">
      <h3 class="metrics-card__title">{{ title }}</h3>
      <p class="metrics-card__value">{{ formattedValue }}</p>
      <p v-if="subtitle" class="metrics-card__subtitle">{{ subtitle }}</p>
    </div>
  </div>
</template>

<script setup lang="ts">
import { computed, ref, watch, onBeforeUnmount } from 'vue'
import { formatNumber, formatPercentage } from '@/utils/helpers'

interface Props {
  title: string
  value: number | string
  subtitle?: string
  variant?: 'default' | 'success' | 'warning' | 'danger' | 'info'
  isPercentage?: boolean
}

const props = withDefaults(defineProps<Props>(), {
  variant: 'default',
  isPercentage: false,
})

const animatedValue = ref(0)
let rafId: number | null = null

watch(() => props.value, (newVal) => {
  if (typeof newVal !== 'number') return
  const start = animatedValue.value
  const end = newVal
  const duration = 750
  const startTime = performance.now()

  function tick(now: number) {
    const elapsed = now - startTime
    const p = Math.min(elapsed / duration, 1)
    const eased = 1 - (1 - p) ** 3
    animatedValue.value = start + (end - start) * eased
    if (p < 1) rafId = requestAnimationFrame(tick)
  }
  rafId = requestAnimationFrame(tick)
}, { immediate: true })

onBeforeUnmount(() => {
  if (rafId !== null) cancelAnimationFrame(rafId)
})

const formattedValue = computed(() =>
  props.isPercentage ? formatPercentage(animatedValue.value) : formatNumber(Math.round(animatedValue.value))
)
</script>

Ce qu'il faut savoir dire :

  • Template utilise {{ }} (interpolation) et :class="variant" (binding dynamique). Vue echappe automatiquement le contenu (protection XSS).
  • <slot name="icon" /> : le parent peut injecter n'importe quel contenu dans cette zone (ici, une icone FontAwesome).
  • watch(source, callback) : reagit au changement de la prop value et anime la valeur de animatedValue avec une cubic ease via requestAnimationFrame.
  • onBeforeUnmount : hook Vue qui s'execute juste avant la suppression du composant. On annule le rAF pour eviter une fuite memoire.
  • <style scoped> : les styles sont isoles au composant (classes renommees automatiquement avec un hash). Pas de pollution globale.

6.2 Un store Pinia complet (authStore)

import { defineStore } from 'pinia'
import { ref, computed } from 'vue'
import type { AuthSession } from '@/types'
import { authApi, authSessionManager, tryBootstrapFromCookie } from '@/services/auth'

export const useAuthStore = defineStore('auth', () => {
  const session = ref<AuthSession | null>(authSessionManager.getSession())
  const loading = ref(false)
  const error = ref<string | null>(null)

  const isAuthenticated = computed(() => session.value !== null)
  const currentUser = computed(() => session.value?.user ?? null)

  function setSession(next: AuthSession | null) {
    session.value = next
    if (next) authSessionManager.setSession(next)
    else authSessionManager.clearSession()
  }

  async function login(email: string, password: string) {
    loading.value = true
    error.value = null
    try {
      const next = await authApi.login(email, password)
      setSession(next)
    } catch (e) {
      error.value = e instanceof Error ? e.message : 'Erreur'
      throw e
    } finally {
      loading.value = false
    }
  }

  async function bootstrapFromSession(): Promise<boolean> {
    const next = await tryBootstrapFromCookie()
    if (next) { setSession(next); return true }
    return false
  }

  async function logout() {
    await authApi.logout()
    setSession(null)
  }

  return { session, loading, error, isAuthenticated, currentUser, login, bootstrapFromSession, logout }
})

Ce qu'il faut savoir dire :

  • defineStore('auth', () => { ... }) : setup store (style Composition API). Le store est un fichier a part, mais utilise les memes primitives (ref, computed) qu'un composant.
  • La fonction retourne ce qui est expose. Le reste est prive au store.
  • Usage dans un composant : const auth = useAuthStore(); auth.login(email, pwd). L'appel a useAuthStore() renvoie la meme instance a chaque fois (singleton), donc tous les composants partagent l'etat.
  • bootstrapFromSession gere le cas specifique post-verification email : on restaure la session depuis le cookie better-auth si le localStorage est vide.

6.3 Guard de navigation (router/index.ts)

router.beforeEach(async (to) => {
  const isAuthenticated = authSessionManager.hasValidSession()

  if (isAuthenticated) {
    if (to.meta.guestOnly) return { name: 'dashboard' }  // deja connecte -> dashboard
    return true  // laisse passer
  }

  // Pas de session locale : tente un bootstrap depuis le cookie better-auth
  if (to.meta.requireAuth || to.meta.guestOnly) {
    const bootstrapped = await useAuthStore().bootstrapFromSession()
    if (bootstrapped) {
      if (to.meta.guestOnly) return { name: 'dashboard' }
      return true
    }
  }

  if (to.meta.requireAuth) return { name: 'auth' }  // force le login
  return true
})

Ce qu'il faut savoir dire :

  • beforeEach s'execute avant chaque navigation. On peut renvoyer :
    • true -> autorise
    • { name: 'xxx' } -> redirige
    • false -> bloque
  • Les meta sur les routes (requireAuth: true, guestOnly: true) centralisent la logique : on ne duplique pas if (authenticated) dans chaque composant.
  • Pattern "guest only" : redirige un utilisateur deja connecte depuis / (login) vers /dashboard.
  • Pattern "require auth" : redirige un utilisateur non connecte depuis /dashboard vers / (login).

6.4 Formulaire d'authentification (extrait de AuthView)

<template>
  <form v-if="mode === 'login'" @submit.prevent="submitLogin">
    <label for="email">Email</label>
    <input id="email" v-model.trim="loginForm.email" type="email" required />

    <label for="password">Mot de passe</label>
    <input id="password" v-model="loginForm.password" type="password" required minlength="8" />

    <p v-if="errorMessage" role="alert">{{ errorMessage }}</p>

    <button type="submit" :disabled="authStore.loading">
      {{ authStore.loading ? 'Connexion...' : 'Se connecter' }}
    </button>
  </form>
</template>

<script setup lang="ts">
import { ref } from 'vue'
import { useRouter } from 'vue-router'
import { useAuthStore } from '@/stores/auth'

const router = useRouter()
const authStore = useAuthStore()

const mode = ref<'login' | 'register' | 'forgot'>('login')
const loginForm = ref({ email: '', password: '' })
const localError = ref<string | null>(null)

async function submitLogin() {
  try {
    await authStore.login(loginForm.value.email, loginForm.value.password)
    await router.push({ name: 'dashboard' })
  } catch (e) {
    localError.value = e instanceof Error ? e.message : 'Erreur'
  }
}
</script>

Ce qu'il faut savoir dire :

  • v-model.trim : two-way binding entre l'input et la variable reactive. Le modificateur .trim retire les espaces automatiquement.
  • @submit.prevent : ecoute l'evenement submit ET appelle preventDefault() (evite le reload de la page par le navigateur).
  • :disabled="authStore.loading" : bouton desactive pendant l'appel API. Empeche le double-click.
  • role="alert" : accessibilite, les lecteurs d'ecran annoncent le message d'erreur.
  • Le composant delegue la logique au authStore : il ne sait pas comment on se connecte, il sait juste qu'il faut appeler login().

6.5 Utilitaires de formatage

// utils/helpers.ts
export function formatNumber(num: number): string {
  return new Intl.NumberFormat('fr-FR').format(num)   // 1234567 -> "1 234 567"
}

export function formatPercentage(value: number, decimals = 1): string {
  return `${value.toFixed(decimals)} %`               // 85.237 -> "85.2 %"
}

export function formatDate(isoDate: string): string {
  return new Intl.DateTimeFormat('fr-FR', {
    year: 'numeric', month: 'long', day: 'numeric',
    hour: '2-digit', minute: '2-digit',
  }).format(new Date(isoDate))                        // "2026-04-22T14:30:00Z" -> "22 avril 2026, 14:30"
}

export function downloadFile(blob: Blob, filename: string): void {
  const url = URL.createObjectURL(blob)
  const link = document.createElement('a')
  link.href = url
  link.download = filename
  document.body.appendChild(link)
  link.click()
  document.body.removeChild(link)
  URL.revokeObjectURL(url)                            // libere la memoire
}

Ce qu'il faut savoir dire :

  • Intl.NumberFormat et Intl.DateTimeFormat sont des APIs natives du navigateur pour la localisation. Pas besoin de moment.js ou de librairie tierce.
  • Le parametre 'fr-FR' pilote le formatage selon la locale francaise (separateur d'espace pour les milliers, dates en francais).
  • downloadFile est une astuce classique : cree un Blob URL, declenche un clic sur un <a download> temporaire, puis libere l'URL. Utilise pour les exports CSV/JSON.

6.6 Configuration Vitest (vitest.config.ts)

Les tests unitaires couvrent les stores et utils. Exemple d'un test de store :

import { describe, it, expect, beforeEach, vi } from 'vitest'
import { setActivePinia, createPinia } from 'pinia'
import { useAuthStore } from '@/stores/auth'
import * as authService from '@/services/auth'

describe('useAuthStore', () => {
  beforeEach(() => {
    setActivePinia(createPinia())
  })

  it('login stocke la session en cas de succes', async () => {
    vi.spyOn(authService.authApi, 'login').mockResolvedValue({
      user: { id: '1', username: 'arthur', email: 'a@b.c', role: 'admin' },
      tokens: { accessToken: 'jwt', refreshToken: 'ref', expiresAt: '2099-01-01' },
    })

    const store = useAuthStore()
    await store.login('a@b.c', 'password')

    expect(store.isAuthenticated).toBe(true)
    expect(store.currentUser?.email).toBe('a@b.c')
  })
})

Ce qu'il faut savoir dire :

  • setActivePinia(createPinia()) : isole le store pour chaque test (pas de fuite d'etat entre tests).
  • vi.spyOn(obj, 'method').mockResolvedValue(...) : mocke la methode pour ne pas appeler vraiment l'API AUTH dans le test.
  • On teste le comportement observable (isAuthenticated, currentUser), pas l'implementation interne.

7. Questions probables du jury

Q1. Pourquoi Vue 3 plutot que React ou Angular ?

  • React : librairie UI, il faut assembler un ecosysteme (router, state management, forms). Plus puissant a grande echelle, mais plus de decisions a prendre.
  • Angular : framework complet mais beaucoup de concepts (modules, DI, services, RxJS, templates avec syntax speciale). Courbe d'apprentissage raide.
  • Vue 3 : le "juste milieu". Template HTML classique, reactivite explicite, ecosysteme officiel coherent (Vue Router + Pinia + Vite). Excellent pour un projet de taille MSPR.

Pour un dashboard admin, le choix est peu determinant : les trois feraient tres bien le travail. Vue 3 est cependant plus rapide a prendre en main pour une equipe junior.

Q2. Composition API vs Options API, quelle difference ?

  • Options API (Vue 2, toujours supportee en Vue 3) : le composant est un objet { data() {}, methods: {}, computed: {} }. La logique est dispersee par type.
  • Composition API (Vue 3, recommandee) : la logique est dans une fonction setup() ou un <script setup>. On declare ref, computed, etc. On peut regrouper la logique par fonctionnalite (tout ce qui concerne X est ensemble).

Avantages Composition API :

  • Reutilisation : on extrait de la logique dans un "composable" (fonction qui retourne des ref) partage entre plusieurs composants.
  • TypeScript : inference beaucoup plus precise.
  • Lisibilite : pour un gros composant, tout ce qui traite d'un feature est groupe au lieu d'etre eparpille entre data, methods, computed, watch.

Q3. Pourquoi Pinia et pas Vuex ?

  • Vuex etait le gestionnaire officiel pour Vue 2. Syntaxe verbeuse (mutations separees des actions, modules imbriques, types complexes).
  • Pinia a ete adopte comme successeur officiel pour Vue 3. Plus simple : pas de mutations, juste des fonctions qui modifient l'etat directement.
  • Meilleur support TypeScript (inference automatique).
  • Modulaire : un fichier par store, pas d'arbre de modules.
  • API Composition API-friendly : un store ressemble a un composant.

Q4. Pourquoi stocker le JWT dans le localStorage et pas dans un cookie HttpOnly ?

Compromis classique :

  • Cookie HttpOnly : inaccessible au JavaScript -> protege contre XSS. Mais le navigateur ne l'envoie qu'automatiquement (pas moyen de l'ajouter manuellement a une requete fetch vers une autre origine).
  • localStorage : accessible en JS -> on peut l'ajouter au header Authorization: Bearer ... a chaque requete cross-origin. Mais un XSS peut le voler.

Ici on a fait les deux :

  • Le cookie de session reste cote AUTH (HttpOnly, SameSite, proteger contre CSRF/XSS).
  • Le JWT dans localStorage est utilise uniquement pour appeler MSPR-API cross-origin.

Mitigation XSS : Vue 3 echappe tout par defaut dans {{ }}, pas de v-html sur du contenu utilisateur, et CSP en production.

Q5. Comment le front gere-t-il une session expiree ?

Deux niveaux :

  • Verification locale : authSessionManager.getSession() verifie isExpired(session.tokens.expiresAt) a chaque lecture. Si expire, la session est supprimee du localStorage.
  • Reponse 401 du serveur : l'ApiClient.request leve une erreur. Pour l'instant, on ne l'intercepte pas automatiquement (pas de retry/refresh). Amelioration possible : catcher 401, appeler refreshAccessToken, rejouer la requete.

Le refreshAccessToken actuel appelle simplement GET /api/jwt pour regenerer un JWT, tant que le cookie de session (cote AUTH) est encore valide.

Q6. Que fait Vite et pourquoi c'est different de Webpack ?

  • Webpack bundle tout le code en un seul gros fichier avant de l'envoyer au navigateur. Long au premier demarrage sur un gros projet (~30s).
  • Vite utilise les ES modules natifs du navigateur en developpement : chaque fichier est servi separement a la demande. Demarrage instantane (<1s).
  • Pour la production, Vite utilise Rollup pour faire un bundle optimise.

Resultat : experience de dev bien meilleure (HMR instantane), meme taille de bundle en prod.

Q7. Pourquoi deux linters (oxlint + ESLint) ?

  • oxlint : linter JavaScript/TypeScript ecrit en Rust. ~100x plus rapide qu'ESLint sur les regles de base. Ideal pour un feedback instantane pendant le dev.
  • ESLint : extensible via plugins. On utilise les plugins officiels Vue (eslint-plugin-vue) et TypeScript qui n'existent pas dans oxlint.

Le plugin eslint-plugin-oxlint desactive dans ESLint les regles deja verifiees par oxlint, pour eviter la duplication. Les deux tournent en sequence (run-s).

Q8. Comment tester un composant Vue qui fait des appels API ?

Avec @vue/test-utils + Vitest + mocking :

import { mount } from '@vue/test-utils'
import { setActivePinia, createPinia } from 'pinia'
import AuthView from '@/views/AuthView.vue'

it('affiche le message d\'erreur si le login echoue', async () => {
  setActivePinia(createPinia())
  const wrapper = mount(AuthView)

  // ... simuler la saisie du formulaire
  // ... mocker le store pour renvoyer une erreur
  // ... asserter que l'element d'erreur est visible
})

Dans notre projet, on teste surtout les stores et utils (logique metier), pas les composants eux-memes. Raisons :

  • Les composants sont surtout de la presentation, peu de logique.
  • Les stores concentrent la logique -> beaucoup de valeur a les tester.
  • Les tests de composants sont fragiles (changement de template = test casse).

Q9. L'UI est-elle accessible ?

Le projet vise RGAA niveau AA :

  • Labels explicites, aria-label sur les icones.
  • role="alert" / role="status" pour annoncer les changements.
  • Focus visible, navigation clavier complete.
  • Contrastes conformes (ratio >= 4.5:1).
  • prefers-reduced-motion pour desactiver les animations.
  • Structure HTML semantique (<section>, <nav>, <header>).

Amelioration possible : passer un audit Lighthouse / axe-core en CI pour detecter les regressions d'accessibilite.

Q10. Comment mettre a jour l'URL de l'API en prod sans rebuilder ?

Actuellement, on ne peut pas. Les variables VITE_* sont inlinees dans le bundle au build. Pour changer VITE_API_BASE_URL, il faut reconstruire l'image Docker.

Alternatives possibles :

  • Config a l'execution : le front charge /config.json au demarrage (fichier servi par le reverse proxy). On peut changer le JSON sans rebuild.
  • Variables d'environnement serveur : si on sert via un Node custom au lieu de serve, on peut injecter des valeurs dans index.html au runtime.

Pour la MSPR, un rebuild est acceptable (deploiement via CI/CD de toute facon).

Q11. Pourquoi un mode mock pour le dev ?

Trois raisons :

  • Dev autonome : on peut developper l'UI sans lancer MSPR-DB + MSPR-ETL + MSPR-AUTH + MSPR-API. Utile en avion ou avec un backend en cours de refacto.
  • Demos : on peut montrer le dashboard avec des donnees interessantes meme si le backend renvoie pour l'instant des donnees pauvres.
  • Tests : les mocks servent aussi aux tests unitaires.

Activation via une simple variable d'env (VITE_USE_MOCK=true), commit dans .env.example comme valeur par defaut locale.

Q12. Le front fait du state global avec Pinia, c'est justifie pour 4 vues ?

Oui, pour 2 raisons :

  • Partage de session : le store auth est utilise par AuthView, le router guard, et potentiellement par d'autres vues qui veulent afficher le nom de l'utilisateur. Sans store, il faudrait propager via props ou events, tres verbeux.
  • Partage de donnees metier : le store dataQuality peut etre utilise par DashboardView et par DataCleaningView. Si on clique sur "Resoudre une anomalie" dans DataCleaningView, DashboardView voit automatiquement l'anomalie disparaitre de son compteur (reactivite Pinia).

Pour un projet tres simple (1 seule vue, pas de session), on se passerait de Pinia et on utiliserait juste provide/inject ou des ref locales. Ici c'est justifie.

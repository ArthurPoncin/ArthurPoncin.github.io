Fiche de revision : CI/CD et qualite

Support de revision pour la soutenance MSPR3 (TPRE601). Objectif : savoir derouler la chaine complete commit -> GitHub Actions -> GHCR -> Watchtower, justifier la strategie de tests et de couverture service par service, et commenter les indicateurs qualite (SonarCloud) avec leurs limites.

0. Vocabulaire a connaitre avant de lire

Les 10 termes qui reviennent partout dans cette fiche.

Terme Definition en une phrase
CI (integration continue) A chaque push, une chaine automatisee (lint + tests + build) verifie que le code reste sain avant toute publication.
CD (deploiement continu) Toute image publiee est deployee automatiquement sur l’hote, sans intervention manuelle. Ici : Watchtower.
Registre (de conteneurs) Serveur qui stocke et distribue les images Docker (push depuis la CI, pull depuis l’hote).
GHCR GitHub Container Registry, le registre integre a GitHub : ghcr.io/whitefoxxyt/mspr-<service>.
workflow_call Declencheur GitHub Actions qui rend un workflow appelable par un autre (workflow reutilisable). Ici : docker-publish.yml appele par le workflow de CI.
semver Versionnage semantique MAJEUR.MINEUR.CORRECTIF (ex : v1.2.3), porte par les tags Git vX.Y.Z.
Couverture Pourcentage de lignes (ou de branches) du code executees par les tests. Mesuree par JaCoCo (Java) ou pytest-cov (Python).
Quality gate Critere qui fait passer ou bloquer un build. Ici : la regle JaCoCo 80 % et les dependances needs entre jobs.
Artefact (CI) Fichier produit par un job et conserve apres le run : rapports de couverture (htmlcov/, coverage.xml), screenshots Cypress.
Watchtower Conteneur qui surveille un registre et recree automatiquement les conteneurs listes quand une nouvelle image apparait.

1. TL;DR

Industrialisation de la plateforme HealthAI Coach : chacun des 8 depots (organisation GitHub whitefoxxyt) porte sa propre chaine GitHub Actions qui lint, teste, mesure la couverture, puis build et publie une image Docker sur GHCR. C’est la reponse au sujet : pipelines CI/CD incluant build, tests, analyse de code et deploiement.

  • CI : un workflow par depot, declenche sur push / PR vers la branche par defaut et sur les tags Git vX.Y.Z. Lint selon la techno (ruff, oxlint + eslint + vue-tsc, node --check), tests selon la techno (JUnit, bun test, pytest, Vitest + Cypress, validations SQL / mongosh).
  • Publication conditionnee : docker-publish.yml est appele via workflow_call avec needs sur les jobs de lint / tests, et uniquement sur push (jamais sur PR). Un job rouge bloque la publication : aucune image ne part sur GHCR.
  • Tags d’images (docker/metadata-action) : nom de branche, semver ({{version}} et {{major}}.{{minor}} sur tags Git), SHA court (tracabilite), latest uniquement depuis la branche par defaut.
  • Deploiement : premier demarrage via ./bootstrap.sh (tire les :latest, voir fiche Deploiement), puis CD via Watchtower : poll GHCR toutes les 5 min (WATCHTOWER_POLL_INTERVAL=300), recreation du conteneur sur nouveau :latest, suppression de l’ancienne image (WATCHTOWER_CLEANUP=true).
  • Qualite : seuil de couverture 80 % impose sur l’API (JaCoCo, lignes ET branches, bloquant) et Reco-Fitness (pytest-cov). Mesures reelles : AI-Nutrition 92 % (run du 09/06/2026), Reco-Fitness 85 % (run du 08/06/2026). Analyse statique SonarCloud en mode Automatic Analysis sur l’organisation.
  • Etat au 10/06/2026 : les 8 chaines CI au vert (rapport rapport-tests-qualite.md). Preuve vecue que le pipeline bloque : la suite e2e Cypress du Front en echec du 26/05 au 10/06 a empeche toute publication d’image pendant la periode (section 5.5).

Reference des documents : MSPR-Deploy/CICD.md (chaine), MSPR-Deploy/docs/plan-de-test.md (strategie), MSPR-Deploy/docs/rapport-tests-qualite.md (resultats releves le 10/06/2026).

2. Architecture

flowchart LR
    C[commit / push<br/>branche par defaut ou tag vX.Y.Z] --> A[GitHub Actions<br/>lint + tests + couverture + build]
    A -->|push uniquement, tous jobs verts| G[(GHCR<br/>ghcr.io/whitefoxxyt/mspr-*:latest)]
    G -->|premier deploiement| B[bootstrap.sh<br/>docker compose up -d]
    G -->|poll toutes les 5 min| W[Watchtower]
    W -->|nouveau :latest| R[conteneur recree<br/>sur l'hote]

Le flux complet, tel que documente dans CICD.md :

commit/push (branche par defaut ou tag vX.Y.Z)
   |
   v
GitHub Actions (un workflow par depot)
   |-- lint (selon la techno)
   |-- tests + couverture
   |-- build de l'image Docker
   v
publication sur GHCR (ghcr.io/whitefoxxyt/mspr-<service>:latest)
   |
   +-- premier demarrage : ./bootstrap.sh -> docker compose up -d
   |
   v
Watchtower (sur l'hote) interroge GHCR toutes les 5 min
   |
   v
nouvelle image detectee -> Watchtower recree le conteneur (CD automatique)

Trois points structurants :

  1. Un workflow par depot : chaque service est autonome (sa techno, son lint, ses tests, son image). Pas de pipeline monolithique : un service casse n’empeche pas les autres de publier.
  2. La publication est un workflow reutilisable (docker-publish.yml, declencheur on: workflow_call) appele depuis le workflow de CI avec needs: [...] et if: github.event_name == 'push'. Sur PR, les tests tournent et conditionnent la fusion, mais aucune image n’est publiee.
  3. Deux modes de deploiement : ./bootstrap.sh (prod : tire les images GHCR :latest) et ./bootstrap.sh --dev (clone les 8 depots, build local via docker-compose.dev.yml). bootstrap.sh prepare aussi .env, genere les secrets et dechiffre les cles API : detail dans la fiche Deploiement. Les overlays Compose (monitoring, traefik, watchtower…) sont decrits dans la fiche Configs et resilience.

Detail par service (issu de plan-de-test.md) :

3.1 API (Spring Boot 4, Java 21)

  • Job test : ./mvnw test sous JDK 21 (Temurin), cache Maven.
  • Couverture JaCoCo : rapport genere a la phase test, controle du seuil (regle jacoco-check, element BUNDLE, 80 % lignes ET branches) a la phase verify. Bloquant : un build vert garantit le seuil.
  • En local : ./mvnw test (rapport dans target/site/jacoco/), ./mvnw verify (controle du seuil).

3.2 Auth (Bun, Hono, better-auth)

  • bun install --frozen-lockfile puis bun test (runner integre de Bun).
  • Suites dans src/__tests__/ : routes, entitlements, subscriptions, admin, templates email. Pas de seuil de couverture impose.

3.3 AI-Nutrition (FastAPI, Python 3.12)

  • Job lint : ruff check . (ruff 0.8.4).
  • Job test : double checkout (le depot + MSPR-HealthAI-Coach-BDD pour disposer des migrations, variable MIGRATIONS_DIR), installation des deps via l’index PyTorch CPU, puis pytest -m "not slow" (exclut inference reelle / reseau).
  • Rapports de couverture publies en artefacts : htmlcov/ (HTML) et coverage.xml (XML), meme si le job echoue (if: always()).
  • Couverture pytest-cov (--cov=app), cible 80 %, pas de --cov-fail-under strict a ce stade. Mesure reelle : 92 % (run du 09/06/2026).

3.4 Reco-Fitness (FastAPI, Python 3.12)

  • Job lint : ruff check --config reco-fitness/ruff.toml reco-fitness/app reco-fitness/tests (ruff 0.8.4).
  • Job test : pytest -m "not slow and not integration" -v. Marqueurs unit / integration / slow : les tests integration (containers PostgreSQL + MongoDB ephemeres) et slow se lancent en local uniquement.
  • Couverture pytest-cov (--cov=app), seuil 80 % retenu pour ce service. pytest.ini fixe --cov-fail-under=0 : l’objectif est verifie sur le rapport term-missing. Mesure reelle : 85 % (run du 08/06/2026).

3.5 ETL (Python 3.12)

  • Job lint : ruff check + ruff format --check (ruff 0.15.6, config etl/pyproject.toml).
  • Job test : python -m pytest tests/ -m "not integration" -v (unitaires : cleaners, extractors).
  • Job test-integration : service PostgreSQL 16 dans le runner, puis python -m pytest tests/ -m integration -v avec les variables DB_HOST/PORT/NAME/USER/PASSWORD pointant vers le container. Seul service avec integration reelle en CI.

3.6 Front (Vue 3, Vite, TypeScript)

  • Quatre jobs sous Node 22 : lint (oxlint + eslint), type-check (vue-tsc), test (Vitest --run), e2e (Cypress, needs: [test]).
  • Le job e2e : build en mode test (npm run build:test), cache + installation du binaire Cypress, puis start-server-and-test qui sert l’app (vite preview --port 4173), attend que le port reponde et lance cypress run. Screenshots publies en artefact en cas d’echec.
  • La publication needs: [lint, type-check, test, e2e] : les 4 jobs conditionnent l’image.

3.7 BDD (PostgreSQL 17, migrations SQL)

  • Job validate : service postgres:17-alpine, installation du client psql, application sequentielle des migrations migrations/V*__*.sql triees par sort -V, avec psql -v ON_ERROR_STOP=1. Une erreur SQL stoppe le pipeline.
  • Pas de code applicatif : la validation EST le test (les migrations s’appliquent reellement sur un PostgreSQL vierge).

3.8 MongoDB (init collections / index)

  • Job validate : node --check sur chaque init/*.js (syntaxe), puis demarrage d’un container mongo:7-jammy avec les scripts montes en docker-entrypoint-initdb.d. Un mongosh verifie la presence des collections attendues (user_fitness_profiles, workout_programs, recommendation_history) et de l’index user_id_unique. Collection ou index manquant = job rouge.

4. Strategie d’images et de tags + deploiement continu Watchtower

4.1 Tags produits par docker/metadata-action

Chaque publication produit plusieurs tags pour la meme image :

Regle Tag produit Quand Usage
type=ref,event=branch nom de la branche (main, master) chaque push de branche suivre une branche
type=semver,pattern={{version}} 1.2.3 tag Git v1.2.3 release figee
type=semver,pattern={{major}}.{{minor}} 1.2 tag Git v1.2.3 suivre les correctifs d’une mineure
type=sha,prefix=,format=short SHA court du commit chaque push tracabilite : retrouver le commit exact d’une image
type=raw,value=latest,enable={{is_default_branch}} latest uniquement branche par defaut cible du deploiement prod

Le deploiement en mode prod (bootstrap.sh sans option) tire les images :latest, donc celles publiees depuis la branche par defaut de chaque depot. Les tags sha et semver restent disponibles sur GHCR pour epingler ou revenir a un etat precis.

4.2 CD via Watchtower (docker-compose.watchtower.yml)

Le CD ferme la boucle : git push -> GitHub Actions build et publie -> Watchtower tire la nouvelle image et recree le conteneur, sans intervention manuelle.

  • Fonctionnement : le conteneur mspr-watchtower interroge GHCR toutes les 5 minutes (WATCHTOWER_POLL_INTERVAL=300). Nouveau :latest disponible = arret du conteneur, recreation avec la nouvelle image, suppression de l’ancienne (WATCHTOWER_CLEANUP=true).
  • Services suivis (passes en argument, donc liste blanche explicite) : mspr-api, mspr-auth-service, mspr-etl, mspr-reco-fitness, mspr-ai-nutrition. Ce sont des noms de conteneurs (l’image mspr-auth tourne dans le conteneur mspr-auth-service).
  • Front exclu volontairement : mspr-front tourne sur une image rebuildee localement avec les URLs publiques figees au build (build Vite statique), sans image GHCR a suivre. Son redeploiement reste manuel.
  • Limite (migrations) : le conteneur one-shot mspr-auth-migrate n’est pas rejoue par Watchtower. Si une mise a jour backend embarque une migration, relancer docker compose ... up -d pour declencher le conteneur de migration.
  • Gotcha DOCKER_API_VERSION: "1.44" : l’image containrrr/watchtower embarque un client Docker ancien (API 1.25) que le daemon recent (Docker 29) refuse (“client version 1.25 is too old”). On fige la version d’API client a une valeur supportee par le daemon.

En production, l’overlay se combine aux autres (commande reelle de CICD.md) :

docker compose -f docker-compose.yml -f docker-compose.monitoring.yml \
  -f docker-compose.traefik.yml -f docker-compose.vision.yml \
  -f docker-compose.watchtower.yml up -d

Le detail des overlays est dans la fiche Configs et resilience, la partie monitoring dans la fiche Observabilite.

5. Qualite : plan de test, couvertures, SonarCloud

5.1 Pyramide de tests (plan-de-test.md)

La strategie suit une pyramide classique, adaptee a la techno de chaque service :

  • Unitaires : logique metier isolee (cleaners ETL, scoring fitness, validators, services). Rapides, sans dependance externe.
  • Integration : comportement avec une dependance reelle (PostgreSQL, MongoDB) lancee en service ephemere dans la CI (ETL) ou en local (Reco-Fitness).
  • End-to-end : uniquement sur le Front, via Cypress, sur l’application buildee et servie (pas le dev server).
  • Validation : pour les services sans code applicatif (BDD, MongoDB), on valide l’execution reelle des migrations SQL et de l’init des collections / index.

Le lint et la verification de types completent les tests selon la techno.

5.5 Point technique important : l’incident e2e Front (resolu le 10/06/2026)

C’est la preuve vecue que le pipeline bloque, a raconter au jury.

  • Symptome : suite e2e Cypress du Front en echec du 26/05/2026 au 10/06/2026 (2 specs sur 6). Consequence directe : la publication de l’image mspr-front etait bloquee (le job publish a needs: [lint, type-check, test, e2e]), conformement au comportement attendu du pipeline.
  • Cause 1 (meal-analysis.cy.ts) : mock manquant de GET /api/v1/me/macros, appele au montage de la vue ; sans lui la vue affiche l’ecran “profil incomplet” a la place de la dropzone.
  • Cause 2 (meal-plan.cy.ts) : fixture meal-plan.json restee sur une ancienne structure (breakfast/lunch/dinner par jour) au lieu du contrat actuel days[].meals[] (champ est_budget_eur inclus). Le contrat d’API avait evolue, la fixture non.
  • Resolution : apres correction, la suite complete passe : 6 specs, 10 tests, 0 echec, verifie en local puis en CI (run 27270853990 du 10/06/2026).
  • Lecon : les tests e2e sur l’app buildee detectent les derives de contrat entre front et services ; et un pipeline qui bloque la publication n’est pas une theorie, il a reellement retenu une image non conforme pendant 15 jours.

6. Code essentiel a savoir expliquer au jury

6.1 Le workflow CI de l’API : test puis publication conditionnee

# MSPR-API/.github/workflows/ci.yml (extrait)
on:
  push:
    branches: [main]
    tags: ['v*.*.*']
  pull_request:
    branches: [main]

jobs:
  test:
    name: Tests unitaires (Maven)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - run: ./mvnw test

  publish:
    name: Publication de l'image Docker
    needs: [test]
    if: github.event_name == 'push'
    uses: ./.github/workflows/docker-publish.yml
    secrets: inherit
    permissions:
      contents: read
      packages: write

Ce qu’il faut savoir dire :

  • Les declencheurs couvrent les 3 cas : push sur main (deploiement continu via latest), PR (verification avant fusion, sans publication), tags v*.*.* (release semver).
  • needs: [test] : la publication attend le job de test et ne demarre que s’il est vert. C’est le mecanisme de blocage du pipeline.
  • if: github.event_name == 'push' : sur une PR, publish est saute. Une PR ne peut jamais pousser d’image, meme verte.
  • uses: ./.github/workflows/docker-publish.yml : appel du workflow reutilisable (pattern workflow_call). secrets: inherit transmet les secrets du depot au workflow appele.
  • permissions : le GITHUB_TOKEN du job est restreint a contents: read + packages: write (juste de quoi lire le code et pousser sur GHCR).

6.2 Le workflow de publication : metadata-action et tags

# MSPR-API/.github/workflows/docker-publish.yml (extrait)
on:
  workflow_call:

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: whitefoxxyt/mspr-api
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha,prefix=,format=short
            type=raw,value=latest,enable={{is_default_branch}}

      - uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

Ce qu’il faut savoir dire :

  • on: workflow_call : ce workflow ne se declenche jamais seul, il est appele par le workflow de CI. Garantit qu’aucune image ne part sans etre passee par les tests.
  • docker/metadata-action calcule les tags et labels OCI a partir du contexte Git (branche, tag, SHA). Une seule image, plusieurs tags.
  • enable={{is_default_branch}} : latest n’est produit que depuis la branche par defaut. Une branche de feature publie son tag de branche, jamais latest (donc jamais deployee par Watchtower).
  • type=sha,prefix=,format=short : chaque image porte le SHA court du commit qui l’a produite. Tracabilite : on peut toujours dire de quel commit vient ce qui tourne en prod.
  • cache-from/to: type=gha : cache de layers Docker porte par GitHub Actions, accelere les rebuilds.
  • L’authentification GHCR utilise docker/login-action avec ${{ github.actor }} / ${{ secrets.GITHUB_TOKEN }} : token ephemere fourni par Actions, aucun secret a provisionner.

6.3 La regle JaCoCo : seuil 80 % bloquant (pom.xml de l’API)

<execution>
    <id>jacoco-check</id>
    <goals>
        <goal>check</goal>
    </goals>
    <configuration>
        <rules>
            <rule>
                <element>BUNDLE</element>
                <limits>
                    <!-- Minimum 80% de couverture de lignes -->
                    <limit>
                        <counter>LINE</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>0.80</minimum>
                    </limit>
                    <!-- Minimum 80% de couverture de branches -->
                    <limit>
                        <counter>BRANCH</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>0.80</minimum>
                    </limit>
                </limits>
            </rule>
        </rules>
    </configuration>
</execution>

Ce qu’il faut savoir dire :

  • Trois executions JaCoCo dans le pom.xml (version 0.8.11) : prepare-agent (instrumente la JVM de test), report (genere le rapport a la phase test, dans target/site/jacoco/), jacoco-check (controle du seuil a la phase verify).
  • element BUNDLE : le seuil s’applique au module entier, pas classe par classe.
  • Deux compteurs : LINE et BRANCH a 0.80. La couverture de branches est plus exigeante que les lignes (chaque if doit etre teste dans ses deux issues).
  • COVEREDRATIO < 0.80 = echec du build a mvn verify. C’est un quality gate dans l’outil de build, pas dans un service externe : reproductible en local a l’identique.
  • Le rapport XML (target/site/jacoco/jacoco.xml) est reference par sonar.coverage.jacoco.xmlReportPaths pour l’analyse SonarQube locale.

6.6 L’overlay Watchtower (docker-compose.watchtower.yml)

services:
  watchtower:
    image: containrrr/watchtower:latest
    container_name: mspr-watchtower
    restart: unless-stopped
    security_opt:
      - no-new-privileges:true
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    environment:
      DOCKER_API_VERSION: "1.44"
      WATCHTOWER_CLEANUP: "true"          # supprime l'ancienne image apres maj
      WATCHTOWER_POLL_INTERVAL: "300"     # verifie GHCR toutes les 5 min
      WATCHTOWER_INCLUDE_RESTARTING: "true"
      TZ: Europe/Paris
    command:
      - mspr-api
      - mspr-auth-service
      - mspr-etl
      - mspr-reco-fitness
      - mspr-ai-nutrition

Ce qu’il faut savoir dire :

  • Watchtower a besoin du socket Docker (/var/run/docker.sock) pour inspecter et recreer les conteneurs. C’est un acces puissant, partiellement mitige par no-new-privileges:true.
  • Les arguments de command forment une liste blanche : seuls ces 5 conteneurs sont surveilles. Tout le reste (front, bases, monitoring) est ignore.
  • WATCHTOWER_POLL_INTERVAL: "300" : fenetre de mise a jour de 5 minutes maximum entre la publication GHCR et la recreation du conteneur.
  • WATCHTOWER_CLEANUP: "true" : l’ancienne image est supprimee apres la mise a jour, le disque ne gonfle pas au fil des deploiements.
  • DOCKER_API_VERSION: "1.44" : contournement d’un vrai probleme rencontre, le client Docker embarque dans l’image watchtower (API 1.25) est refuse par le daemon Docker 29 (“client version 1.25 is too old”). On fige une version d’API supportee (>= 1.40).

6.7 Validation BDD et MongoDB : tester sans code applicatif

# Equivalent local de la CI BDD (plan-de-test.md)
for f in $(ls migrations/V*__*.sql | sort -V); do psql -v ON_ERROR_STOP=1 -f "$f"; done
# Equivalent local de la CI MongoDB (plan-de-test.md)
for f in init/*.js; do node --check "$f"; done   # syntaxe
docker compose up -d                              # applique l'init au demarrage

Ce qu’il faut savoir dire :

  • sort -V (tri “version”) garantit l’ordre V1, V2, ... V10 ; un tri lexicographique classerait V10 avant V2. Indispensable pour des migrations sequentielles.
  • psql -v ON_ERROR_STOP=1 : par defaut psql continue apres une erreur SQL ; avec ce flag, la premiere erreur arrete tout et fait echouer le job. Sans lui, la CI pourrait etre verte avec des migrations cassees.
  • La CI BDD execute cela contre un service postgres:17-alpine vierge : on prouve a chaque push que la chaine complete de migrations s’applique depuis zero.
  • Cote MongoDB : node --check valide la syntaxe JS sans executer, puis le container mongo:7-jammy rejoue l’init reel et mongosh verifie les 3 collections et l’index user_id_unique. La validation porte sur le resultat (etat de la base), pas seulement sur l’execution.

8. Questions probables du jury

Q1. Pourquoi GitHub Actions plutot que Jenkins ou GitLab CI ?

Trois arguments :

  1. Le code est deja sur GitHub (organisation whitefoxxyt, 8 depots). Actions est natif : zero infrastructure CI a heberger, securiser et maintenir. Jenkins demande un serveur, des agents, des plugins et leurs mises a jour ; GitLab CI demande une instance GitLab ou une migration des depots.
  2. Integration GHCR sans friction : le GITHUB_TOKEN ephemere du run suffit pour pousser l’image (packages: write). Aucun secret de registre a provisionner ni a faire tourner.
  3. Briques reutilisables : marketplace d’actions maintenues (setup-java, setup-python, metadata-action, build-push-action) et pattern workflow_call pour factoriser la publication.

Tradeoff assume : couplage a GitHub. Acceptable ici, l’exigence du sujet porte sur la chaine (build, tests, analyse, deploiement), pas sur l’outil. Le besoin etant couvert par des runners manages gratuits au scope du projet, un Jenkins auto-heberge aurait ajoute de l’exploitation sans valeur.

Q2. Pourquoi deployer :latest ? Quelles limites, et comment revenir en arriere ?

latest est produit uniquement depuis la branche par defaut (enable={{is_default_branch}}), donc apres lint + tests verts. C’est le contrat le plus simple pour un CD par poll : Watchtower suit un tag fixe, chaque merge sur la branche par defaut part en prod.

Limites :

  • latest est un tag mouvant : “ce qui tourne” depend du moment du pull, pas d’un identifiant fige.
  • Pas de promotion progressive : tout merge part en prod (discipline de branche requise, les PR sont testees avant fusion).

Retour en arriere : chaque image porte aussi un tag SHA court (commit exact) et, sur les releases, des tags semver (1.2.3, 1.2). Pour revenir en arriere : pointer le service du compose sur ghcr.io/whitefoxxyt/mspr-<service>:<sha> (ou une version), relancer up -d, et le sortir de la liste Watchtower le temps du gel. En production plus exigeante, on epinglerait des versions ou des digests et latest ne serait pas la cible de deploiement.

Q3. Que se passe-t-il quand un test echoue ?

Mecaniquement : le job publish a needs sur les jobs de lint / tests ; un job rouge = publish ne tourne pas = aucune image poussee sur GHCR = Watchtower ne voit rien = la prod reste sur la derniere image saine.

Preuve vecue (a raconter) : la suite e2e Cypress du Front a ete en echec du 26/05 au 10/06/2026 (2 specs sur 6). Pendant 15 jours, aucune image front n’a ete publiee, conformement au comportement attendu. Les causes etaient deux derives de contrat dans les tests eux-memes : mock manquant de GET /api/v1/me/macros dans meal-analysis.cy.ts, et fixture meal-plan.json restee sur l’ancienne structure (breakfast/lunch/dinner) au lieu du contrat actuel days[].meals[]. Apres correction : 6 specs, 10 tests, 0 echec (run 27270853990). Sur PR, meme logique sans publication : les tests conditionnent la fusion.

Q4. Pourquoi Watchtower plutot qu’ArgoCD ou Flux ?

ArgoCD et Flux sont des outils GitOps pour Kubernetes : ils reconcilient l’etat d’un cluster avec des manifestes Git, via CRD, controllers et un cluster a operer. Or la plateforme tourne en Docker Compose sur un hote unique : il n’y a pas de cluster, donc pas de place pour ces outils sans introduire Kubernetes uniquement pour le CD.

Watchtower est le CD minimal adapte a Compose : un conteneur, un poll du registre toutes les 5 minutes, recreation du conteneur sur nouvelle image. Cout d’exploitation quasi nul, comprehensible en entier.

Limites assumees en echange : pas de rollback automatique, pas de deploiement progressif (canary / blue-green), pas de reconciliation declarative depuis Git, et les limites de la Q11. A l’echelle d’un hote unique, le ratio simplicite / service rendu est en faveur de Watchtower.

Q5. Comment les images sont-elles tracables ?

Par la regle type=sha,prefix=,format=short de docker/metadata-action : chaque publication produit un tag egal au SHA court du commit. Etant donne une image en prod, on retrouve le commit exact (et inversement : etant donne un commit, son image existe sur GHCR). metadata-action genere aussi les labels OCI standard apposes sur l’image. S’y ajoutent les tags de branche et les tags semver {{version}} / {{major}}.{{minor}} sur les tags Git vX.Y.Z pour identifier les releases. Cette tracabilite est ce qui rend le deploiement :latest acceptable : le tag mouvant est double d’identifiants figes.

Q6. SonarCloud Automatic Analysis vs scanner en CI : avantages et limites ?

Automatic Analysis (retenu) : l’application GitHub SonarCloud installee sur l’organisation analyse chaque push, sans token ni etape CI dans les depots. Avantages : zero configuration par depot, zero secret a gerer, activation centralisee par un admin de l’organisation, et aucune minute de CI consommee.

Limites :

  • L’Automatic Analysis n’execute pas les tests, donc pas de couverture dans SonarCloud. La couverture fait foi en CI (JaCoCo, pytest-cov), c’est documente dans le rapport de tests.
  • Pas de quality gate Sonar bloquant le pipeline dans ce mode : le blocage reste porte par la CI (tests, seuil JaCoCo).

Scanner en CI (alternative) : etape explicite avec SONAR_TOKEN, qui importerait coverage.xml / jacoco.xml et permettrait un gate bloquant. C’est l’evolution naturelle. L’API garde d’ailleurs un SonarQube local (docker-compose.sonar.yml, mvn sonar:sonar vers localhost:9000) ou la couverture JaCoCo est bien importee via sonar.coverage.jacoco.xmlReportPaths.

Q7. Comment fonctionne le job e2e du front ?

Cinq etapes, dans l’ordre :

  1. needs: [test] : ne demarre que si les unitaires Vitest sont verts.
  2. Cache puis installation du binaire Cypress (npx cypress install), cle de cache sur le hash de package-lock.json.
  3. npm run build:test : build de production en mode test (on teste l’artefact builde, pas le dev server).
  4. npx start-server-and-test 'vite preview --port 4173' http://localhost:4173 'cypress run' : sert le build statique, attend que http://localhost:4173 reponde, lance la suite Cypress, puis arrete le serveur. Pas de sleep arbitraire ni de course au demarrage.
  5. En cas d’echec, les screenshots Cypress sont publies en artefact (if: failure()), ce qui a permis de diagnostiquer l’incident du 26/05.

Les appels API sont mockes (fixtures + intercepts Cypress) : l’e2e valide le front de bout en bout sans dependre des backends, c’est precisement ce qui a revele les derives de contrat des fixtures.

Q8. Pourquoi un seuil 80 % seulement sur l’API et Reco-Fitness ?

Le seuil a ete impose la ou il a le plus de valeur : les deux services qui concentrent la logique metier testable unitairement (CRUD / analytics cote API, scoring de recommandation cote Reco-Fitness). Sur l’API il est bloquant (JaCoCo jacoco-check, lignes et branches, phase verify) ; sur Reco-Fitness il est verifie sur le rapport (pytest.ini fixe --cov-fail-under=0, mesure reelle 85 %).

Ailleurs : AI-Nutrition mesure sa couverture en CI avec une cible 80 % sans enforcement strict (mesure reelle 92 %, donc au-dessus de la cible) ; Auth, ETL et Front ont des tests sans seuil a ce stade. Imposer un chiffre uniforme des le depart pousse a ecrire des tests de remplissage pour atteindre le ratio ; on a prefere des seuils bloquants cibles, une mesure partout ou c’est pertinent, et la generalisation des seuils en reste a faire (Q12).

Q9. Que valent les notes SonarCloud (securite E) et que faire du backlog ?

Les notes relevees le 10/06/2026 : maintenabilite A sur les deux projets analyses, fiabilite C, securite E. Point cle a expliquer : la note Sonar reflete la pire issue ouverte, pas une moyenne. La note E en securite est tiree par les vulnerabilites ouvertes (3 sur AI-Nutrition, 1 sur Reco-Fitness) ; il suffit de peu d’issues pour degrader la note, et leur traitement la fait remonter.

Le backlog chiffre : AI-Nutrition 30 bugs, 3 vulnerabilites, 18 hotspots, 102 code smells (duplication 0,7 %) ; Reco-Fitness 35 bugs, 1 vulnerabilite, 8 hotspots, 19 smells (1,5 %). Priorisation : vulnerabilites d’abord (elles font la note E), puis revue des hotspots, puis bugs, puis smells. La maintenabilite A et la duplication faible indiquent une dette structurelle maitrisee. Posture devant le jury : le backlog est mesure, public et assume, c’est exactement le role d’indicateurs qualite en continu.

Q10. Quelle securite sur la chaine de publication ?

  • GITHUB_TOKEN ephemere : genere par Actions pour chaque run, limite au depot, expire a la fin du run. Pas de PAT longue duree ni de mot de passe de registre stocke.
  • Permissions explicites par job : contents: read + packages: write uniquement sur les jobs de publication. Les jobs de test n’ont pas le droit d’ecrire sur GHCR.
  • Publication impossible depuis une PR : if: github.event_name == 'push'. Une PR (y compris externe) fait tourner les tests mais ne peut pas pousser d’image.
  • secrets: inherit ne transmet les secrets qu’au workflow reutilisable du meme depot (uses: ./.github/...), pas a du code tiers.
  • Cote hote : Watchtower tourne avec no-new-privileges:true, mais monte /var/run/docker.sock : c’est un acces fort au daemon Docker, limite connue du CD par poll, compensee par la liste blanche de conteneurs et le fait que seules des images GHCR de l’organisation sont suivies.

Q11. Quelles sont les limites du CD Watchtower ?

A enumerer soi-meme, elles sont documentees dans l’overlay :

  1. Migrations one-shot non rejouees : mspr-auth-migrate est un conteneur one-shot, Watchtower ne le relance pas. Si une mise a jour backend embarque une migration, il faut relancer docker compose ... up -d pour declencher le conteneur de migration.
  2. Front exclu : mspr-front est rebuilde localement avec les URLs publiques figees au build (build statique Vite), il n’a pas d’image GHCR a suivre ; son redeploiement reste manuel.
  3. Fenetre de poll : jusqu’a 5 minutes entre publication et deploiement (WATCHTOWER_POLL_INTERVAL=300).
  4. Pas de rollback automatique ni de sante post-deploiement : si la nouvelle image demarre mal, Watchtower ne revient pas en arriere ; ce sont les healthchecks et la supervision qui alertent (voir fiche Observabilite).
  5. Gotcha de compatibilite : DOCKER_API_VERSION=1.44 impose, car le client Docker embarque de watchtower (API 1.25) est rejete par le daemon Docker 29.

Q12. Que reste-t-il a faire sur la qualite ?

  1. Importer les 5 depots restants dans SonarCloud (API, Auth, ETL, Front, BDD) : import depuis l’interface par un admin de l’organisation, sans configuration cote depot. Et declencher la premiere analyse du projet MongoDB (importe mais jamais analyse).
  2. Traiter le backlog securite : resoudre les 3 + 1 vulnerabilites ouvertes pour faire remonter la note E, puis statuer sur les hotspots.
  3. Durcir les seuils de couverture : activer --cov-fail-under sur AI-Nutrition (deja a 92 %) et Reco-Fitness, definir des seuils pour Auth / ETL / Front.
  4. A terme : passer d’Automatic Analysis a un scanner en CI avec import de couverture et quality gate bloquant, pour unifier “tests verts” et “qualite Sonar” dans le meme verdict de pipeline.

Le reste de la mise en production (bootstrap, overlays, sauvegardes) est couvert par la fiche Deploiement et la fiche Configs et resilience.

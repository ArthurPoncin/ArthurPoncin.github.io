Fiche de revision : Application mobile

Support de revision pour la soutenance MSPR3 (TPRE601). Objectif : comprendre le perimetre de l’application mobile, sa stack Expo / React Native, son integration aux 4 services de la plateforme, son mode d’execution (client, pas service de la stack) et le reste a faire.

0. Vocabulaire a connaitre avant de lire

1. TL;DR

L’application mobile HealthAI Coach est le client Android / iOS de la plateforme, developpe par un autre membre de l’equipe dans le depot whitefoxxyt/MSPR-HealthAI-Coach-Mobile.

Position dans l’architecture : c’est un client de la plateforme, pas un service de la stack. Les 8 services tournent en Docker Compose (fiche Deploiement) ; l’application, elle, s’execute sur le terminal de l’utilisateur (Expo Go en developpement, build natif Android / iOS ensuite) et consomme les APIs depuis l’exterieur.

  • Stack : Expo 54 + React Native 0.81 (nouvelle architecture activee), TypeScript 5.9, Expo Router 6
  • Etat global : React Context (store/AppContext.tsx) + AsyncStorage (session et profil persistes)
  • Reseau : fetch centralise dans un client API unique (services/apiClient.ts), 4 services consommes (auth, api, ai-nutrition, reco-fitness)
  • Parcours couvert : creation de compte / connexion, onboarding en 5 etapes, tableau de bord quotidien (calories, macronutriments, seances), scan de repas par photo, plans nutritionnels et recommandations sportives, profil (poids sur 14 jours, IMC, panneau de parametres)
  • Conteneurisation : un Dockerfile node:20-alpine qui sert le bundler de developpement au reseau local (l’app n’apparait pas dans le compose)
  • Reste a faire (3 points) : alignement des routes d’authentification, correction typecheck / lint + mise en place d’une CI, nom d’affichage et photo de profil modifiables

La reference d’integration cote plateforme est MSPR-Deploy/docs/application-mobile.md (version du depot au 11/06/2026). Cette fiche couvre le comment : comment l’app est structuree, comment elle s’authentifie, comment elle s’execute, et ce qui reste a faire.

4. Integration a la plateforme

L’application consomme les memes services que le front web, avec le meme modele d’authentification (better-auth + JWT). Les URLs des services sont configurables par variables d’environnement ; par defaut, l’application vise une stack locale (le deploiement decrit dans la fiche Deploiement).

4.1 Les 4 services consommes

Service URL par defaut Endpoints consommes
auth (:3000) http://localhost:3000/api authentification, /session, /jwt
api (:8080) http://localhost:8080/api /users/me, /workouts, /nutrition
ai-nutrition (:8001) http://localhost:8001/api/v1 /analyze-meal, /generate-meal-plan, /nutrition-goals/me, /meal-analyses/me, /meal-plans/me
reco-fitness (:8002) http://localhost:8002/api/v1 /recommendations, /fitness-profile, /program-history

4.2 Flux d’authentification

  1. connexion ou inscription aupres du service auth (cookies de session better-auth, requetes en credentials: include) ;
  2. recuperation d’un JWT via GET /api/jwt ;
  3. appels aux services metier avec Authorization: Bearer <jwt> ; le JWT est conserve dans AsyncStorage.
sequenceDiagram
    participant M as App mobile
    participant A as auth (:3000)
    participant S as Services metier

    M->>A: 1. connexion / inscription (credentials: include)
    A-->>M: cookie de session better-auth
    M->>A: 2. GET /api/jwt (cookie de session)
    A-->>M: JWT
    Note over M: JWT conserve dans AsyncStorage
    M->>S: 3. Authorization: Bearer JWT
    S-->>M: donnees metier

C’est exactement le modele du front web : la session par cookie sert uniquement aupres du service auth ; tous les autres services ne voient que le JWT.

4.3 Particularite emulateur Android

L’emulateur Android ne voit pas le localhost de la machine hote : depuis l’emulateur, localhost designe l’emulateur lui-meme. L’alias 10.0.2.2 pointe vers la loopback de l’hote. Le client API gere ce cas automatiquement via Platform.OS (voir section 6.1). Sur iOS (simulateur), localhost fonctionne directement.

4.4 Point de vigilance : les routes d’authentification

Le client appelle des routes d’authentification qui ne correspondent pas a celles exposees par better-auth :

Action Route appelee par le client Route better-auth exposee Etat
Connexion /api/auth/login /api/auth/sign-in/email a aligner
Inscription /api/auth/signup /api/auth/sign-up/email a aligner
Deconnexion /api/auth/logout /api/auth/sign-out a aligner
Session /api/session /api/session aligne
JWT /api/jwt /api/jwt aligne

Tant que les 3 premieres routes divergent, la connexion et l’inscription echouent contre le service auth reel. La correction est localisee : le bloc auth de services/apiClient.ts. Cet alignement fait partie du reste a faire (section 7).

5. Conteneurisation, execution et qualite

5.1 L’application est un client, pas un service

A la difference des 8 services de la plateforme, l’application mobile n’apparait pas dans la stack Docker Compose. Elle s’execute sur le terminal de l’utilisateur :

  • en developpement : via Expo Go, qui charge le bundle JS depuis le bundler Metro ;
  • ensuite : via un build natif Android / iOS.

Le depot fournit tout de meme un Dockerfile, pour un environnement de developpement reproductible : image node:20-alpine, installation des dependances, ports Expo 19000-19006 exposes, demarrage du serveur de developpement (npx expo start --lan --minify). Le conteneur sert le bundler aux appareils du reseau local, pour le developpement et la demonstration. Ce n’est pas une image de production.

5.2 Commandes

npm install
npm start            # serveur de developpement Expo
npm run android      # cible Android
npm run ios          # cible iOS
npm test             # eslint + tsc --noEmit

6. Code essentiel a savoir expliquer au jury

6.1 Les URLs de base et la gestion Platform.OS (services/apiClient.ts)

import { Platform } from 'react-native';

// Base API configuration with environment variables support
const getEnvVar = (name: string, defaultValue: string): string => {
  // In a real app, you would use a proper env library like react-native-config
  // For now, we'll use a simple approach
  return defaultValue;
};

const getBaseUrl = (service: 'api' | 'nutrition' | 'fitness' | 'auth') => {
  const host = Platform.OS === 'android' ? '10.0.2.2' : 'localhost';

  switch (service) {
    case 'api': return getEnvVar('API_SERVICE_URL', `http://${host}:8080/api`);
    case 'nutrition': return getEnvVar('AI_NUTRITION_URL', `http://${host}:8001/api/v1`);
    case 'fitness': return getEnvVar('RECO_FITNESS_URL', `http://${host}:8002/api/v1`);
    case 'auth': return getEnvVar('AUTH_SERVICE_URL', `http://${host}:3000/api`);
    default: return getEnvVar('API_SERVICE_URL', `http://${host}:8080/api`);
  }
};

Ce qu’il faut savoir dire :

  • Un seul point de sortie reseau pour toute l’application : les 4 blocs du client (auth, nutrition, fitness, main) passent tous par getBaseUrl.
  • Platform.OS === 'android' ? '10.0.2.2' : 'localhost' : l’emulateur Android joint l’hote via 10.0.2.2 (alias de la loopback de la machine hote) ; localhost y designerait l’emulateur lui-meme.
  • 4 variables d’environnement sont prevues (AUTH_SERVICE_URL, API_SERVICE_URL, AI_NUTRITION_URL, RECO_FITNESS_URL), avec pour defauts les ports de la stack locale (3000, 8080, 8001, 8002).
  • Dans l’etat actuel, getEnvVar retourne la valeur par defaut (le commentaire du code pointe react-native-config comme brique a brancher) : la configuration est centralisee en un seul endroit, pret a etre raccorde.

6.2 Le bloc auth : session puis JWT (services/apiClient.ts)

login: async (email: string, password: string) => {
  const response = await fetch(`${getBaseUrl('auth')}/auth/login`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({ email, password }),
    credentials: 'include',
  });

  if (!response.ok) {
    const errorData = await response.json().catch(() => ({}));
    throw new Error(errorData.message || 'Login failed');
  }

  return response.json();
},
getJwtToken: async () => {
  const response = await fetch(`${getBaseUrl('auth')}/jwt`, {
    credentials: 'include',
  });

  if (!response.ok) {
    throw new Error('Failed to get JWT token');
  }

  const data = await response.json();
  return data.token;
},

Ce qu’il faut savoir dire :

  • credentials: 'include' : le cookie de session better-auth est envoye et recu par fetch. La session par cookie ne sert que pour le service auth.
  • getJwtToken appelle GET /api/jwt avec le cookie de session et recupere data.token : c’est ce JWT qui sera presente a tous les services metier.
  • La route /auth/login de cet extrait est precisement celle a aligner sur /auth/sign-in/email (point de vigilance 4.4). /jwt et /session, eux, sont deja alignes.
  • La gestion d’erreur lit le corps JSON de l’erreur (errorData.message) avec un fallback (.catch(() => ({}))) si le corps n’est pas du JSON.

6.3 Un appel metier avec le JWT (services/apiClient.ts)

getNutritionGoals: async (token: string) => {
  const response = await fetch(`${getBaseUrl('nutrition')}/nutrition-goals/me`, {
    headers: {
      'Authorization': `Bearer ${token}`,
    },
  });

  if (!response.ok) {
    throw new Error('Failed to get nutrition goals');
  }

  return response.json();
},

Ce qu’il faut savoir dire :

  • Tous les appels aux services metier portent le header Authorization: Bearer <jwt> : meme modele que le front web, le mot de passe ne circule jamais vers ces services.
  • L’endpoint est en /me : le service identifie l’utilisateur a partir du JWT, l’application ne transmet jamais d’identifiant utilisateur dans l’URL.
  • Le token est passe en parametre par l’appelant (AppContext), qui le detient et verifie sa presence avant chaque appel.

6.4 Le Dockerfile complet

# Dockerfile for HealthAi Coach Mobile App (Expo)

# Use Node.js 20 LTS as base image (required for Expo compatibility)
FROM node:20-alpine

# Install dependencies
RUN apk add --no-cache \
    python3 \
    make \
    g++ \
    git \
    openssh-client \
    bash

# Set working directory
WORKDIR /app

# Copy package files first for better caching
COPY package*.json ./

# Install npm dependencies
RUN npm install -g expo-cli @expo/ngrok
RUN npm install

# Copy the rest of the application
COPY . .

# Build the app (if needed)
# RUN npx expo prebuild

# Expo needs to run as non-root for development
RUN addgroup -S expo && adduser -S expo -G expo

# Fix permissions for Expo - create .expo dir and set permissions
RUN mkdir -p /app/.expo

# For development, we'll run as root to avoid permission issues with mounted volumes
# USER expo

# Expose Expo ports
EXPOSE 19000-19006

# Command to start Expo development server with minimal config
CMD ["npx", "expo", "start", "--lan", "--minify"]

Ce qu’il faut savoir dire :

  • node:20-alpine : Node 20 LTS, requis pour la compatibilite Expo ; variante alpine pour la legerete.
  • apk add python3 make g++ git ... : toolchain de compilation pour les dependances npm natives.
  • COPY package*.json ./ puis npm install avant COPY . . : optimisation du cache de layers Docker, les dependances ne sont reinstallees que si le package.json change.
  • EXPOSE 19000-19006 : la plage de ports du bundler et des outils Expo.
  • CMD npx expo start --lan --minify : le conteneur demarre le serveur de developpement en mode LAN ; un telephone avec Expo Go sur le meme reseau charge le bundle.
  • Un utilisateur expo non-root est cree mais la directive USER expo est commentee : en developpement, l’execution en root evite les problemes de permissions sur les volumes montes (le commentaire du fichier l’explique).
  • A bien cadrer pour le jury : ce conteneur ne fait pas tourner l’application, il sert le bundler de developpement. L’app, elle, tourne sur le telephone.

6.6 La persistance AsyncStorage (store/AppContext.tsx)

async function loadData() {
  try {
    const stored = await AsyncStorage.getItem('@vital_profile');
    const token = await AsyncStorage.getItem('@vital_jwt');

    if (stored && token) {
      const parsed = JSON.parse(stored);
      setProfile(parsed);
      setJwtToken(token);

      // Verify session with BetterAuth
      try {
        const sessionData = await apiClient.auth.getSession();
        if (sessionData?.user) {
          setIsAuthenticated(true);
        } else {
          // Session expired, clear data
          await logout();
        }
      } catch (error) {
        console.log('Session verification failed, treating as expired');
        await logout();
      }
    }
  } catch {}
}

Et a la connexion, le chemin inverse (fin de login()) :

setProfile(updatedProfile);
await AsyncStorage.setItem('@vital_profile', JSON.stringify(updatedProfile));
await AsyncStorage.setItem('@vital_jwt', jwtToken);

Ce qu’il faut savoir dire :

  • Deux cles AsyncStorage : @vital_profile (profil utilisateur serialise en JSON) et @vital_jwt (le jeton). Ecrites a la connexion / inscription, lues au demarrage, purgees a la deconnexion.
  • loadData() est appele au montage du provider (useEffect) : c’est ce qui fait que la session survit au redemarrage de l’application.
  • Restaurer ne suffit pas : la session est re-verifiee aupres du service auth (getSession()). Si elle a expire, logout() remet l’etat a zero et supprime les deux cles. Pattern : restauration optimiste locale + verification serveur.
  • login() enchaine exactement le flux de la section 4.2 : authentification, lecture de session, getJwtToken(), puis persistance des deux cles.

6.7 Le hook d’orchestration (hooks/useHealthAI.ts)

const [isLoading, setIsLoading] = useState(false);
const [error, setError] = useState<string | null>(null);

// Auto-fetch data when authenticated
useEffect(() => {
  if (jwtToken) {
    refreshAllData();
  }
}, [jwtToken]);

const refreshAllData = async () => {
  setIsLoading(true);
  setError(null);

  try {
    await fetchUserData();
    await loadWorkouts();
    await loadNutritionPlans();
    await loadFitnessPrograms();
  } catch (err) {
    setError('Failed to load data');
    console.error('Refresh failed:', err);
  } finally {
    setIsLoading(false);
  }
};

Ce qu’il faut savoir dire :

  • useHealthAI est la facade applicative au-dessus du contexte : il centralise les appels aux services IA (analyse de repas, generation de plan, recommandations) et les etats isLoading / error consommes par les ecrans.
  • Le useEffect sur jwtToken declenche le chargement des que l’utilisateur est authentifie : profil, seances, plans nutritionnels, programmes fitness.
  • Les reponses brutes des services sont converties vers le format interne de l’app par utils/dataTransformers.ts (ex : transformMealAnalysis, transformWorkout, transformNutritionPlan).
  • Separation nette : apiClient.ts parle HTTP, AppContext.tsx detient l’etat et le token, useHealthAI.ts orchestre et transforme pour l’UI.

8. Questions probables du jury

Q1. Pourquoi Expo / React Native plutot que deux applications natives ?

Une seule base de code TypeScript produit les cibles Android et iOS. Trois arguments :

  1. Effort : un seul code, deux plateformes ; pas de double developpement Kotlin + Swift.
  2. Coherence d’equipe : TypeScript est deja le langage du front web et du service auth ; la montee en competence est immediate.
  3. Outillage Expo : Expo Go permet de tester sur un vrai telephone sans toolchain native (pas d’Android Studio / Xcode pour developper), Expo Router apporte le routage par fichiers type, le bundler Metro sert le bundle a chaud.

Le projet active la nouvelle architecture React Native (RN 0.81), le mode par defaut moderne du framework.

Q2. Pourquoi l’application n’est-elle pas dans le docker-compose ?

Parce que c’est un client, pas un service. Le compose deploie les 8 services de la plateforme ; l’application mobile s’execute sur le terminal de l’utilisateur (Expo Go en developpement, build natif Android / iOS ensuite) et consomme les APIs depuis l’exterieur du reseau Docker, comme n’importe quel client HTTP. Il n’y a rien a “servir” en continu cote stack pour qu’elle fonctionne : elle embarque son code et appelle les endpoints exposes.

Q3. A quoi sert alors le Dockerfile du depot ?

A fournir un environnement de developpement reproductible : node:20-alpine, toolchain native (python3, make, g++), npm install, ports 19000-19006 exposes, et CMD npx expo start --lan --minify. Le conteneur sert le bundler Metro aux appareils du reseau local : un telephone avec Expo Go scanne et charge le bundle, pour le developpement et la demonstration. Ce n’est pas une image de production : en production, l’app est un build natif distribue sur l’appareil, plus aucun conteneur n’est implique.

Q4. Comment l’application s’authentifie-t-elle aupres de la plateforme ?

Exactement comme le front web (fiche Deploiement) :

  1. connexion / inscription aupres du service auth, en credentials: include (cookie de session better-auth) ;
  2. GET /api/jwt avec ce cookie pour obtenir un JWT ;
  3. appels aux services metier (api, ai-nutrition, reco-fitness) avec Authorization: Bearer <jwt>.

Le JWT est conserve dans AsyncStorage. Au redemarrage, l’app restaure profil + jeton puis re-verifie la session via /api/session ; si la session a expire, tout est purge et l’utilisateur revient a l’ecran de connexion.

Q5. Comment testez-vous sur un emulateur Android en local ?

Depuis l’emulateur Android, localhost designe l’emulateur lui-meme, pas la machine hote. L’alias 10.0.2.2 route vers la loopback de l’hote. Le client API gere ce cas automatiquement :

const host = Platform.OS === 'android' ? '10.0.2.2' : 'localhost';

Sur simulateur iOS, localhost fonctionne directement. Pour un telephone physique, le bundler est servi en --lan et les URLs de services se configurent par variables d’environnement vers l’IP de la machine qui heberge la stack.

Q6. Quelles differences avec le front web Vue 3 ?

Aspect Front web (Vue 3) App mobile (Expo / RN)
Public admins / data scientists utilisateur final (coaching)
Contenu dashboards, qualite de donnees, validation onboarding, scan de repas, plans, recommandations, profil
Execution servi par la stack, dans le navigateur s’execute sur le terminal de l’utilisateur
Place dans le compose service de la stack client externe, absent du compose
Authentification better-auth + JWT identique (meme flux session puis JWT)

Les deux consomment les memes APIs : la plateforme n’a pas eu a etre modifiee pour accueillir un deuxieme client, ce qui valide le decoupage en services.

Q7. Comment l’etat persiste-t-il entre deux lancements de l’application ?

Via AppContext + AsyncStorage. Deux cles : @vital_profile (profil JSON) et @vital_jwt (jeton). Elles sont ecrites a la connexion / inscription, lues par loadData() au montage du provider, et supprimees a la deconnexion. La restauration est suivie d’une verification de session aupres du service auth : on ne fait pas confiance au seul contenu local, une session expiree declenche un logout() complet.

Q8. Comment les URLs des services sont-elles configurees ?

Quatre variables d’environnement sont prevues : AUTH_SERVICE_URL, API_SERVICE_URL, AI_NUTRITION_URL, RECO_FITNESS_URL. Les valeurs par defaut visent la stack locale du compose : ports 3000, 8080, 8001, 8002, avec un hote localhost ou 10.0.2.2 selon la plateforme. Toute la resolution passe par une seule fonction (getBaseUrl dans services/apiClient.ts) : c’est l’unique endroit a brancher pour pointer un autre environnement.

Q9. Quel est l’etat de la qualite du code, et quel est le plan ?

Au 11/06/2026, npm test (eslint + tsc --noEmit) remonte : 9 erreurs de types dans 3 fichiers, et 4 erreurs + 19 avertissements de lint, concentres en particulier sur un composant de demonstration (AIFeaturesDemo.tsx). L’application se lance malgre tout : Metro transpile via Babel sans verifier les types.

Le plan, assume comme reste a faire : corriger ces erreurs, puis mettre en place une chaine CI (lint, verification de types, build) sur le modele des 8 autres depots de la plateforme (fiche CI/CD et qualite). Les commandes a executer en CI existent deja dans le package.json.

Q10. Que faut-il aligner sur les routes d’authentification, et pourquoi ca ne marche pas encore de bout en bout ?

Le client appelle /api/auth/login, /api/auth/signup et /api/auth/logout, alors que better-auth expose /api/auth/sign-in/email, /api/auth/sign-up/email et /api/auth/sign-out. Tant que ces 3 chemins divergent, la connexion et l’inscription echouent contre le service auth reel : pas de session, donc pas de JWT, donc pas d’appels metier.

Le point important a montrer au jury : les routes /session et /jwt sont deja alignees, et tout le reste du flux (Bearer, AsyncStorage, re-verification de session) est correct. La correction se limite aux 3 chemins du bloc auth de services/apiClient.ts. C’est le premier point du plan d’action.

Q11. Ou sont les maquettes et le design system ?

Versionnes dans le depot : assets/design/wireframes.html (24 ecrans de maquettes) et assets/design/design-system.html (design system sombre “Midnight Health”). Avantage : le design suit le meme cycle de vie que le code (commits, revues, historique), sans dependre d’un outil externe ; n’importe quel membre de l’equipe ouvre les fichiers HTML dans un navigateur.

Q12. Comment s’est passee la collaboration sur ce depot ?

L’application a ete developpee par un autre membre de l’equipe, dans son propre depot (whitefoxxyt/MSPR-HealthAI-Coach-Mobile) et a son propre rythme. L’integration est cadree par un contrat simple : l’application consomme les memes APIs publiques que le front web, avec le meme modele d’authentification ; aucun service de la plateforme n’a du etre modifie pour elle.

Cote plateforme, l’integration est documentee (MSPR-Deploy/docs/application-mobile.md) : stack, architecture, services consommes, flux d’authentification, conteneurisation, et surtout les ecarts identifies (routes d’auth, typecheck / lint, CI) consignes comme un reste a faire explicite. C’est cette documentation qui sert de reference commune entre le developpeur mobile et le reste de l’equipe.

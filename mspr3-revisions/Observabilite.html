Fiche de revision : Observabilite et supervision

Support de revision pour la soutenance MSPR3 (TPRE601). Objectif : comprendre l’overlay de supervision (Prometheus + Grafana + Loki), ce qui est surveille et comment, les 3 alertes, l’instrumentation des 4 services applicatifs et la conduite a tenir quand une alerte se declenche.

0. Vocabulaire a connaitre avant de lire

Les 10 termes qui reviennent partout dans cette fiche.

Terme Definition en une phrase
Scraping Collecte en mode pull : Prometheus appelle lui-meme l’endpoint HTTP /metrics de chaque cible a intervalle fixe (ici 15 s).
Exporter Petit service qui traduit l’etat d’un systeme non instrumente (PostgreSQL, MongoDB, hote Linux, conteneurs) en metriques au format Prometheus.
Modele RED Rate, Errors, Duration : les 3 signaux a suivre par service HTTP (debit de requetes, taux d’erreur, latence).
Cardinalite Nombre de series temporelles distinctes generees par une metrique (une serie par combinaison de labels). A garder basse, sinon la base explose.
Label Paire cle/valeur attachee a une metrique ou une ligne de log (job, name, container, stream). C’est la base du filtrage en PromQL/LogQL.
Retention Duree de conservation des donnees avant purge automatique. Ici 7 jours pour les metriques (Prometheus) comme pour les logs (Loki).
Overlay (Compose) Fichier compose additionnel combine au compose de base via un second -f. Il ajoute des services sans modifier les existants.
Provisioning (Grafana) Declaration des datasources et dashboards dans des fichiers YAML/JSON montes au demarrage : zero configuration manuelle a la souris.
Runbook Procedure ecrite de conduite a tenir par alerte. Ici la section 5 de docs/supervision.md.
PromQL / LogQL Langages de requete de Prometheus (metriques) et de Loki (logs). LogQL reprend la syntaxe des labels PromQL.

1. TL;DR

Le livrable 02 (observabilite et supervision) repond a l’exigence du sujet : metriques applicatives consultables via des interfaces web, logs centralises, tableau de bord de la stack complete, alertes basiques.

  • Forme : un overlay docker-compose.monitoring.yml dans MSPR-Deploy, combine au compose applicatif sans le modifier : docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d.
  • 10 composants (9 images distinctes, les 2 postgres-exporter partagent la meme) : Prometheus v2.54.1, Alertmanager v0.27.0, Grafana 11.2.0, Loki 3.1.1, Promtail 3.1.1, cAdvisor v0.49.1, node-exporter v1.8.2, postgres-exporter v0.15.0 x2, mongodb-exporter percona 0.40.
  • Metriques : Prometheus scrape 10 jobs toutes les 15 s, retention 7 jours. 5 jobs infra (cadvisor, node-exporter, 2 postgres, mongo), 4 jobs applicatifs (api, ai-nutrition, reco-fitness, auth), 1 auto-scrape.
  • Logs : Promtail lit la sortie de tous les conteneurs via le socket Docker monte en lecture seule et pousse vers Loki (retention 168 h). Consultation uniquement via Grafana.
  • Dashboards : 4 dashboards provisionnes automatiquement dans le dossier Grafana “MSPR HealthAI” (Vue stack, API Spring Boot, Microservices FastAPI, Observabilite logs + metriques).
  • Alertes : 3 regles Prometheus (CibleInjoignable, ConteneurCpuEleve, ConteneurMemoireElevee), groupees dans Alertmanager. Pas de notification externe (pas d’email/Slack) : consultation dans l’UI, limite assumee en environnement de demonstration.
  • Instrumentation applicative (sprint A2) : vit dans le code source des 4 services. Micrometer + Actuator pour l’API Spring, prometheus-fastapi-instrumentator pour les 2 FastAPI, @hono/prometheus pour AUTH.
  • Verification reelle (smoke test du 10/06/2026) : 10 cibles sur 10 UP, 3 regles chargees a l’etat inactif, logs recus de 23 conteneurs, 4 dashboards provisionnes, stack stable en 84 s.

URLs a citer de tete :

Deux flux independants :

  1. Metriques (pull) : Prometheus interroge chaque cible sur son endpoint HTTP, stocke en TSDB locale, evalue les regles d’alerte toutes les 15 s et pousse les alertes declenchees vers Alertmanager.
  2. Logs (push) : Promtail decouvre les conteneurs via le socket Docker, lit leur stdout/stderr et pousse vers Loki. Grafana est le seul point de consultation des deux flux.

Tout vit sur le meme reseau Docker mspr_data_network que la stack applicative : les cibles sont resolues par nom de conteneur (DNS interne), jamais par IP ou port publie sur l’hote.

Les 10 composants de docker-compose.monitoring.yml, versions epinglees (pas de latest) :

Service Image exacte Port hote Role
prometheus prom/prometheus:v2.54.1 9090 Scrape les 10 jobs, stocke 7 jours (TSDB), evalue les regles d’alerte
alertmanager prom/alertmanager:v0.27.0 9093 Recoit, regroupe et expose les alertes declenchees
grafana grafana/grafana:11.2.0 3001 Tableaux de bord metriques + logs, datasources provisionnees
loki grafana/loki:3.1.1 3100 Stockage des logs (filesystem), retention 168 h
promtail grafana/promtail:3.1.1 (interne) Collecte les logs de tous les conteneurs via le socket Docker (ro)
cadvisor gcr.io/cadvisor/cadvisor:v0.49.1 8085 Metriques par conteneur (CPU, RAM, reseau, IO)
node-exporter prom/node-exporter:v1.8.2 9100 Metriques de l’hote (CPU, RAM, disque, charge)
postgres-exporter prometheuscommunity/postgres-exporter:v0.15.0 9187 Metriques PostgreSQL metier (base healthai)
postgres-exporter-auth prometheuscommunity/postgres-exporter:v0.15.0 9188 Metriques PostgreSQL auth (base auth_db)
mongodb-exporter percona/mongodb_exporter:0.40 9216 Metriques MongoDB (reco_fitness)

Details a connaitre par composant :

  • Prometheus : flags --storage.tsdb.retention.time=7d (purge auto) et --web.enable-lifecycle (rechargement de la config a chaud via POST /-/reload, sans redemarrer le conteneur). Les fichiers prometheus.yml et alerts.yml sont montes en lecture seule.
  • Grafana : GF_SECURITY_ADMIN_USER / GF_SECURITY_ADMIN_PASSWORD surchargeables via .env (GRAFANA_ADMIN_PASSWORD), defaut admin/admin. GF_USERS_ALLOW_SIGN_UP: "false" : pas de creation de compte sauvage. depends_on prometheus + loki. Port hote 3001 (3000 interne deja pris par AUTH).
  • cAdvisor : privileged: true + montages en lecture seule de /:/rootfs, /var/run, /sys, /var/lib/docker, /dev/disk. C’est le prix pour lire les cgroups de tous les conteneurs. Port hote 8085 (8080 interne deja pris par l’API).
  • postgres-exporter x2 : meme image, seule la variable DATA_SOURCE_NAME change (URL de connexion vers mspr-healthai-db:5432/healthai ou mspr-auth-db:5432/auth_db). Le second publie 9188 sur l’hote mais ecoute toujours 9187 en interne (pas de conflit sur le reseau Docker).
  • mongodb-exporter : --mongodb.uri=mongodb://mspr-mongo:27017 + --collect-all (active tous les collecteurs de metriques).
  • node-exporter : monte /proc, /sys et / de l’hote en lecture seule pour exposer les metriques machine.
  • 4 volumes nommes : prometheus_data, grafana_data, loki_data, promtail_positions (la position de lecture des logs survit aux redemarrages, pas de re-ingestion).

4.4 Logs centralises

  • Promtail lit le stdout/stderr de tous les conteneurs (decouverte automatique via le socket Docker, refresh 15 s), pas seulement les conteneurs mspr-*.
  • Chaque ligne est etiquetee par 3 labels : container (nom du conteneur), stream (stdout / stderr), service (nom du service docker-compose).
  • Retention 168 h (7 jours) cote Loki, avec rejet des echantillons plus vieux (reject_old_samples).
  • Consultation uniquement via Grafana (Explore avec la datasource Loki, ou les panneaux logs des dashboards). Loki n’a pas d’interface propre.

5. Points techniques importants

5.1 Un overlay qui ne modifie pas la stack applicative

L’en-tete du fichier docker-compose.monitoring.yml le dit explicitement :

# A combiner avec le compose de base, il ne modifie aucun service applicatif :
#   Mode prod : docker compose -f docker-compose.yml     -f docker-compose.monitoring.yml up -d
#   Mode dev  : docker compose -f docker-compose.dev.yml -f docker-compose.monitoring.yml up -d

Consequences :

  • La supervision est facultative : l’application fonctionne sans. On la lance des qu’on veut observer ou exploiter la plateforme.
  • On peut arreter la supervision seule (docker compose -f docker-compose.monitoring.yml down) sans toucher aux services applicatifs.
  • L’overlay rejoint le meme reseau mspr_data_network, d’ou la resolution DNS des cibles (mspr-api, mspr-ai-nutrition, …).
  • Aucune ligne du compose applicatif n’a ete modifiee pour brancher la supervision : toute l’instrumentation est soit externe (exporters), soit dans le code source des services (sprint A2).

5.2 L’instrumentation vit dans le code source des 4 services

Le sprint A2 a instrumente chaque service dans son propre depot :

Service Fichier(s) Quoi
MSPR-API pom.xml + SecurityConfig.java + application.properties Dependances spring-boot-starter-actuator + micrometer-registry-prometheus, exposition management.endpoints.web.exposure.include=health,info,prometheus, endpoint ouvert sans JWT
MSPR-AI-Nutrition app/main.py Instrumentator().instrument(app).expose(app, ...)
MSPR-Reco-Fitness app/main.py Idem (meme bibliotheque)
MSPR-AUTH src/index.ts Middleware registerMetrics + route GET /metrics

C’est un choix structurant : les exporters couvrent l’infra sans toucher au code, mais les metriques metier HTTP (latence par route, codes de retour) ne peuvent venir que de l’interieur des applications.

5.3 Gotcha : les metriques applicatives exigent un rebuild des images

Point a connaitre absolument (documente dans monitoring/README.md et docs/supervision.md) :

Ces metriques ne sont visibles qu’apres reconstruction des images des services concernes (l’instrumentation vit dans le code source). Tant qu’une image n’est pas a jour, la cible reste vue comme injoignable par Prometheus, sans impact sur les autres.

  • En mode dev : docker compose -f docker-compose.dev.yml -f docker-compose.monitoring.yml up -d --build.
  • En mode prod : apres publication des nouvelles images GHCR par la CI (voir fiche CI/CD et qualite).
  • Cible DOWN != service KO : une image anterieure au sprint A2 fait tomber le job applicatif en DOWN alors que l’application fonctionne normalement. Seule la collecte manque. C’est un cas explicite du runbook (5.6).

5.4 Les 3 alertes : volontairement basiques et larges

Definies dans monitoring/prometheus/alerts.yml, 2 groupes (disponibilite, ressources) :

Alerte Condition Duree Severite
CibleInjoignable up == 0 1 min critical
ConteneurCpuEleve CPU > 0.9 coeur (rate 5 min) 5 min warning
ConteneurMemoireElevee RAM > 2 Go 5 min warning

Choix de conception a defendre :

  • Les deux alertes de ressources ne ciblent que les conteneurs name=~"mspr-.*" : on ne veut pas alerter sur les conteneurs hors plateforme.
  • Les seuils sont volontairement larges (demonstration), a ajuster selon le materiel. Objectif : eviter le bruit, demontrer le mecanisme.
  • La clause for (1 min / 5 min) absorbe les pics transitoires : une alerte passe par l’etat pending avant firing.
  • Pas de notification externe (pas d’email ni de Slack) : le receiver Alertmanager defaut ne route vers rien, on consulte les alertes dans l’UI (:9093). Limite assumee en demo ; en production on brancherait un receiver email/Slack dans alertmanager.yml.
sequenceDiagram
    participant P as Prometheus
    participant A as Alertmanager
    P->>P: evalue alerts.yml toutes les 15 s
    Note over P: condition vraie pendant "for"<br/>pending puis firing
    P->>A: alerte firing

5.5 Grafana provisionne de bout en bout

Rien n’est configure a la main dans Grafana : tout est versionne dans le repo.

  • Datasources (monitoring/grafana/provisioning/datasources/datasources.yml) : Prometheus (uid prometheus, defaut) et Loki (uid loki), toutes deux en mode proxy vers les URLs internes.
  • Dashboards (monitoring/grafana/provisioning/dashboards/dashboards.yml) : provider de type file qui charge les JSON de /var/lib/grafana/dashboards dans le dossier “MSPR HealthAI”, rescan toutes les 30 s, dashboards editables.

Les 4 dashboards provisionnes :

Fichier Titre Contenu
stack-overview.json MSPR HealthAI - Vue stack Cibles UP, disponibilite par job, CPU et memoire par conteneur, flux de logs
api-spring.json MSPR HealthAI - API Spring Boot Requetes/s (+ par statut), latence p95 par route, memoire JVM heap/nonheap, threads JVM, pool Hikari, CPU process
fastapi-services.json MSPR HealthAI - Microservices FastAPI Template par job (ai-nutrition / reco-fitness) : requetes/s, erreurs 5xx/s, latence p95 globale et par route, CPU et memoire process
observabilite.json MSPR HealthAI - Observabilite (logs + metriques) Cibles UP/DOWN, debit et erreurs HTTP par service, latence p95, volume de logs et erreurs de logs par conteneur, panneau de recherche dans les logs

5.6 Le runbook (docs/supervision.md, section 5)

Reflexe general : identifier le service concerne (label name ou job de l’alerte), puis trois etapes.

  1. Etat des conteneurs : docker compose -f docker-compose.yml -f docker-compose.monitoring.yml ps (colonne STATUS, mention healthy/unhealthy).
  2. Logs : docker compose logs --tail=100 <service>, ou Grafana > Explore > datasource Loki avec filtre sur le label container (permet de correler plusieurs services sur la meme periode).
  3. Grafana : dashboard “MSPR HealthAI - Vue stack”, courbes CPU/memoire du conteneur (pic ponctuel ou derive continue).

Par alerte :

  • CibleInjoignable : conteneur arrete ou unhealthy -> lire ses logs puis relancer. Conteneur qui tourne mais cible toujours DOWN -> verifier que l’endpoint de metriques est expose : cas typique de l’image pas encore instrumentee (l’application fonctionne, seule la collecte manque).
  • ConteneurCpuEleve : verifier la charge reelle dans Grafana. Pic transitoire (ETL, inference IA) : non bloquant, l’alerte retombe seule. Derive durable : inspecter les logs, envisager une limite de ressources (configuration performance, voir fiche Configs et resilience).
  • ConteneurMemoireElevee : meme demarche, surveiller une fuite memoire (montee continue sans redescente) ; au besoin redemarrer le conteneur et suivre la tendance.

5.7 Retention et stockage

  • Prometheus : --storage.tsdb.retention.time=7d, donnees dans le volume prometheus_data.
  • Loki : retention_period: 168h + reject_old_samples: true (max_age 168 h), stockage filesystem (pas de S3 : un seul noeud, replication_factor: 1, ring en memoire), volume loki_data.
  • Promtail : fichier de positions dans le volume promtail_positions. Apres un redemarrage, la lecture reprend ou elle s’etait arretee (pas de doublons, pas de trou).
  • 7 jours suffisent pour le besoin : observer la plateforme pendant une semaine d’exploitation et diagnostiquer un incident recent, avec un volume disque borne par la purge automatique.

6. Code essentiel a savoir expliquer au jury

6.1 Le service Prometheus de l’overlay

  prometheus:
    image: prom/prometheus:v2.54.1
    container_name: mspr-prometheus
    restart: unless-stopped
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.path=/prometheus
      - --storage.tsdb.retention.time=7d
      - --web.enable-lifecycle
    volumes:
      - ./monitoring/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - ./monitoring/prometheus/alerts.yml:/etc/prometheus/alerts.yml:ro
      - prometheus_data:/prometheus
    ports:
      - "9090:9090"
    networks:
      - mspr_data_network

Ce qu’il faut savoir dire :

  • --storage.tsdb.retention.time=7d : purge automatique au-dela de 7 jours, volume disque borne.
  • --web.enable-lifecycle : active l’endpoint POST /-/reload pour recharger prometheus.yml et alerts.yml a chaud, sans redemarrer le conteneur. Utilise quand on ajoute une regle d’alerte.
  • Les configs sont montees en lecture seule (:ro) : le conteneur ne peut pas modifier sa propre config, la verite est dans le repo.
  • prometheus_data est un volume nomme : les metriques survivent aux redemarrages.

6.2 Les 4 jobs applicatifs dans prometheus.yml

  # ---------------------------------------------------------------------
  # Cibles applicatives (instrumentees au sprint A2).
  # API Spring Boot : /api/actuator/prometheus (context-path /api).
  # FastAPI (ai-nutrition, reco-fitness) et Auth (Hono) : /metrics.
  # ---------------------------------------------------------------------
  - job_name: api
    metrics_path: /api/actuator/prometheus
    static_configs:
      - targets: ['mspr-api:8080']

  - job_name: ai-nutrition
    metrics_path: /metrics
    static_configs:
      - targets: ['mspr-ai-nutrition:8001']

  - job_name: reco-fitness
    metrics_path: /metrics
    static_configs:
      - targets: ['mspr-reco-fitness:8000']

  - job_name: auth
    metrics_path: /metrics
    static_configs:
      - targets: ['mspr-auth-service:3000']

Ce qu’il faut savoir dire :

  • Les cibles sont les noms de conteneurs resolus par le DNS du reseau mspr_data_network, sur les ports internes. Piege classique : mspr-reco-fitness:8000 (port interne), pas 8002 (port publie sur l’hote).
  • L’API a un metrics_path specifique : /api/actuator/prometheus, a cause du context-path /api de Spring Boot. Les trois autres exposent le /metrics conventionnel.
  • static_configs : la liste des cibles est statique, adaptee a un compose fixe. En Kubernetes on passerait en service discovery.
  • Le scrape_interval global est de 15 s (defini dans le bloc global), tout comme l’evaluation_interval des regles.

6.3 Les 3 regles d’alerte (alerts.yml)

groups:
  - name: disponibilite
    rules:
      - alert: CibleInjoignable
        expr: up == 0
        for: 1m
        labels:
          severity: critical

  - name: ressources
    rules:
      - alert: ConteneurCpuEleve
        expr: sum(rate(container_cpu_usage_seconds_total{name=~"mspr-.*"}[5m])) by (name) > 0.9
        for: 5m
        labels:
          severity: warning

      - alert: ConteneurMemoireElevee
        expr: container_memory_usage_bytes{name=~"mspr-.*"} / 1073741824 > 2
        for: 5m
        labels:
          severity: warning

Ce qu’il faut savoir dire :

  • up == 0 : up est la metrique generee automatiquement par Prometheus pour chaque cible scrappee. C’est le benefice direct du modele pull : la detection de panne est gratuite.
  • rate(container_cpu_usage_seconds_total[5m]) : ce compteur cAdvisor est en secondes CPU cumulees ; le rate sur 5 min donne des coeurs consommes (1.0 = un coeur plein). Le sum ... by (name) agrege les modes CPU par conteneur.
  • 1073741824 = 1024^3 : conversion octets vers Go. Lire : “le conteneur utilise plus de 2 Go”.
  • name=~"mspr-.*" : regex sur le label name de cAdvisor, on ne supervise que les conteneurs de la plateforme.
  • Chaque regle a aussi des annotations (summary, description) avec templating {{ $labels.job }} / {{ $labels.name }} : le message d’alerte nomme directement le coupable.

6.4 La collecte de logs (promtail-config.yml)

scrape_configs:
  # Decouverte automatique des conteneurs via le socket Docker.
  # Les logs de chaque conteneur sont pousses vers Loki, etiquetes par
  # nom de conteneur, flux (stdout/stderr) et service docker-compose.
  - job_name: conteneurs
    docker_sd_configs:
      - host: unix:///var/run/docker.sock
        refresh_interval: 15s
    relabel_configs:
      - source_labels: ['__meta_docker_container_name']
        regex: '/(.*)'
        target_label: 'container'
      - source_labels: ['__meta_docker_container_log_stream']
        target_label: 'stream'
      - source_labels: ['__meta_docker_container_label_com_docker_compose_service']
        target_label: 'service'

Ce qu’il faut savoir dire :

  • docker_sd_configs : decouverte automatique des conteneurs via le socket Docker (monte en lecture seule dans le conteneur Promtail). Un nouveau service apparait dans Loki sans toucher a la config.
  • Les relabel_configs transforment les meta-labels Docker en 3 labels propres : container, stream, service. La regex '/(.*)' retire le / initial du nom de conteneur Docker.
  • On n’etiquette que 3 labels a faible cardinalite : c’est la philosophie Loki (indexer les labels, pas le contenu des lignes).
  • Le client pousse vers http://loki:3100/loki/api/v1/push : les logs sont en mode push, contrairement aux metriques.

6.5 Instrumentation FastAPI (AI-Nutrition et Reco-Fitness)

from prometheus_fastapi_instrumentator import Instrumentator

# ...

# Instrumentation Prometheus : expose /metrics (exclu du schema OpenAPI).
Instrumentator().instrument(app).expose(app, endpoint="/metrics", include_in_schema=False)

Ce qu’il faut savoir dire :

  • Une seule ligne en fin de app/main.py : instrument(app) pose un middleware qui mesure chaque requete, expose(app) ajoute la route GET /metrics.
  • include_in_schema=False : la route n’apparait pas dans le schema OpenAPI (/docs). C’est de l’outillage interne, pas un endpoint metier.
  • Metriques produites : http_requests_total (compteur par handler et code) et http_request_duration_seconds (histogramme de latence). Exactement le modele RED.
  • Le meme pattern est applique dans les deux microservices FastAPI ; le dashboard fastapi-services.json est d’ailleurs un template qui bascule entre les jobs ai-nutrition et reco-fitness.

6.6 Instrumentation AUTH (Hono / Bun)

import { prometheus } from '@hono/prometheus'

// METRICS (Prometheus - RED: Request rate, Errors, Duration)
const { printMetrics, registerMetrics } = prometheus();
app.use("*", registerMetrics);

// ... plus bas dans le fichier
app.get("/metrics", printMetrics)

Ce qu’il faut savoir dire :

  • prometheus() retourne deux fonctions : registerMetrics est un middleware monte sur toutes les routes ("*") qui compte et chronometre chaque requete ; printMetrics est le handler qui serialise le registre au format texte Prometheus sur GET /metrics.
  • Le commentaire du code source annonce explicitement le modele RED.
  • Demontre que l’instrumentation est homogene sur 3 stacks differentes (Java, Python, TypeScript) : meme format d’exposition, meme scrapeur, memes dashboards.

6.7 Instrumentation API Spring Boot (Micrometer + Actuator)

<dependency>

// Note : Spring Security 6+ retire le context-path (server.servlet.context-path=/api)

Ce qu’il faut savoir dire :

Subtilite a connaitre : Spring Security 6+ matche les patterns apres retrait du context-path, donc on ecrit /actuator/prometheus et pas /api/actuator/prometheus (alors que Prometheus, lui, appelle bien /api/actuator/prometheus).

8. Questions probables du jury

Q1. Pourquoi Prometheus + Grafana + Loki plutot que la stack ELK ?

Le sujet recommandait l’une ou l’autre. Quatre arguments pour ce choix :

  1. Couverture du besoin : il faut des metriques ET des logs. ELK (Elasticsearch / Logstash / Kibana) est d’abord une stack de logs ; pour les metriques il faudrait y ajouter Metricbeat. Prometheus est l’outil standard des metriques conteneurisees, avec un ecosysteme d’exporters pret a l’emploi (postgres, mongodb, node, cadvisor).
  2. Modele pull : Prometheus genere la metrique up pour chaque cible, ce qui donne la detection de panne gratuitement (c’est la base de l’alerte CibleInjoignable).
  3. Empreinte memoire : Elasticsearch indexe le contenu complet des logs (JVM gourmande, plusieurs Go de RAM a lui seul). Loki n’indexe que les labels (container, stream, service) ; le contenu est stocke compresse et filtre a la requete. Adapte a un poste de demonstration qui fait deja tourner 20 conteneurs.
  4. Integration unique : Grafana requete les deux datasources. Un seul outil de visualisation pour correler metriques et logs sur la meme periode, un seul login a montrer au jury.

Tradeoff assume : la recherche plein texte de Loki est moins puissante que celle d’Elasticsearch. Acceptable car le besoin est le diagnostic d’incident (filtrer par conteneur, par periode), pas l’analyse forensique de gros volumes.

Q2. Pull vs push : pourquoi le pull pour les metriques ?

  • Pull (Prometheus) : le serveur initie un GET /metrics vers chaque cible toutes les 15 s. Avantages : la liste des cibles est centralisee dans prometheus.yml (on sait exactement ce qui est surveille), une cible morte est detectee immediatement (up == 0), les applications restent passives (pas de logique de retry/buffer cote client), et on peut debugger a la main avec un simple curl http://cible/metrics.
  • Push : le client envoie ses donnees. Necessaire quand la source ne peut pas etre scrapee : jobs batch ephemeres (Pushgateway cote Prometheus) ou… les logs, qui sont des evenements et pas un etat : Promtail pousse vers Loki.

Dans notre stack les deux coexistent donc : metriques en pull, logs en push. C’est le decoupage standard.

Q3. C’est quoi le modele RED ?

Rate, Errors, Duration : pour chaque service HTTP, suivre le debit de requetes (req/s), le taux d’erreurs (5xx/s) et la distribution de latence (p95). Ces 3 signaux suffisent a dire si un service rend correctement son service.

Concretement chez nous :

  • FastAPI : http_requests_total (Rate + Errors via le label de statut) et http_request_duration_seconds (Duration, histogramme).
  • API Spring : http_server_requests_seconds (timer Micrometer qui porte les trois a la fois : count, sum, labels uri/status).
  • AUTH : le commentaire du code source l’annonce explicitement : // METRICS (Prometheus - RED: Request rate, Errors, Duration).

Modele complementaire : USE (Utilization, Saturation, Errors) pour les ressources, couvert chez nous par cAdvisor et node-exporter.

Q4. Pourquoi un overlay separe au lieu d’integrer la supervision au compose principal ?

  • Non-intrusif : la consigne qu’on s’est donnee est de superviser la plateforme sans modifier la stack applicative validee en MSPR2. L’overlay ajoute 10 services, ne touche a aucun existant.
  • Cycle de vie independant : docker compose -f docker-compose.monitoring.yml down arrete la supervision sans toucher l’application, et inversement.
  • Compose-agnostique : le meme overlay se combine au compose prod (images GHCR) comme au compose dev (build local).
  • Facultatif : l’application fonctionne sans la supervision (utile sur un poste contraint) ; on la lance des qu’on exploite.

Le mecanisme -f -f (fusion de fichiers compose) est detaille dans la fiche Deploiement.

Q5. Comment ajoutez-vous une nouvelle alerte ?

  1. Editer monitoring/prometheus/alerts.yml : ajouter une regle dans un groupe existant ou un nouveau groupe (champs alert, expr en PromQL, for, labels.severity, annotations).
  2. Tester l’expression au prealable dans l’onglet Graph de Prometheus (http://localhost:9090) pour verifier qu’elle retourne bien les series attendues.
  3. Recharger a chaud : curl -X POST http://localhost:9090/-/reload (possible grace au flag --web.enable-lifecycle). Pas besoin de redemarrer le conteneur, le fichier est monte en volume.
  4. Verifier dans Status > Rules que la regle est chargee, etat inactive.

Q6. Pourquoi ces seuils (0.9 coeur, 2 Go) ?

Ce sont des seuils de demonstration, volontairement larges, documentes comme tels dans docs/supervision.md (“a ajuster selon le materiel”) :

  • 0.9 coeur pendant 5 min : un conteneur qui sature quasiment un coeur en continu pendant 5 minutes n’est plus dans un pic normal (les pics legitimes, ETL ou inference IA, sont plus courts ou attendus).
  • 2 Go pendant 5 min : au-dela de la consommation nominale attendue des conteneurs de la plateforme, meme les plus lourds (JVM de l’API, services IA).
  • La clause for: 5m filtre les pics transitoires : on alerte sur une derive durable, pas sur un spike.

L’objectif en demo est d’eviter les fausses alertes tout en prouvant que le mecanisme complet (expr -> pending -> firing -> Alertmanager) fonctionne. En production, on calibrerait sur des mesures reelles de charge nominale.

Q7. Une cible est DOWN dans Prometheus : quelle demarche de diagnostic ?

Suivre le runbook (section 5 de docs/supervision.md) :

  1. docker compose ... ps : le conteneur tourne-t-il ? Statut healthy ?
  2. Conteneur arrete ou unhealthy : docker compose logs --tail=100 <service> pour la cause, puis up -d <service> ou restart.
  3. Conteneur qui tourne mais cible toujours DOWN : verifier que l’endpoint de metriques repond (curl depuis le reseau Docker). Cas typique : image pas encore instrumentee (anterieure au sprint A2, voir 5.3). Dans ce cas l’application fonctionne normalement, seule la collecte manque ; la correction est un rebuild/republication de l’image, pas un redemarrage.
  4. Correler dans Grafana (Vue stack + logs Loki du conteneur sur la periode).

Le point a montrer au jury : on distingue panne applicative et panne de collecte, et l’alerte CibleInjoignable couvre les deux avec deux remediations differentes.

Q8. Comment sont geres les logs, et pourquoi Loki ne s’interroge que via Grafana ?

Chaine : conteneurs -> socket Docker (ro) -> Promtail (decouverte auto, refresh 15 s) -> push HTTP vers loki:3100/loki/api/v1/push -> Loki (stockage filesystem, retention 168 h) -> Grafana (datasource provisionnee, Explore + panneaux logs).

Chaque ligne porte 3 labels (container, stream, service), volontairement peu nombreux : Loki n’indexe que les labels, garder la cardinalite basse est la condition de sa legerete.

Pourquoi via Grafana uniquement : Loki n’a pas d’interface graphique propre, c’est une API HTTP de stockage/requete (LogQL). Grafana est son front officiel. Avantage : metriques et logs se consultent au meme endroit, avec la meme selection de periode, ce qui est exactement le besoin en diagnostic d’incident.

Q9. Les endpoints /metrics ne sont pas authentifies : c’est un probleme de securite ?

Reponse en trois temps :

  1. Surface reelle : les metriques sont des compteurs agreges (req/s, latence, heap), pas de donnees personnelles ni de payloads. Le risque est de la fuite d’information technique, pas de donnees metier.
  2. Perimetre reseau : le scraping se fait sur le reseau Docker interne mspr_data_network. Cote API, /actuator/prometheus est en permitAll precisement pour que Prometheus scrape sans JWT (Prometheus ne sait pas s’authentifier en better-auth) ; cote FastAPI, /metrics est exclu du schema OpenAPI. La doc (monitoring/README.md) assume : acceptable en environnement de demonstration.
  3. Exposition publique : en deploiement expose, ces endpoints et les UIs de supervision ne sont pas ouverts au public ; l’acces est restreint au niveau du reverse proxy Traefik (ipallowlist), voir la fiche Configs et resilience.

Amelioration possible en production : TLS + auth basique sur les exporters, ou un reseau de supervision dedie.

Q10. Que voit-on dans le dashboard API Spring ?

Le dashboard “MSPR HealthAI - API Spring Boot” (api-spring.json), alimente par Micrometer :

  • Trafic : requetes/s globales et par statut HTTP (reperer une montee de 4xx/5xx).
  • Latence : p95 par route (reperer LA route lente, pas une moyenne globale qui masque tout).
  • JVM : memoire heap/nonheap (fuite memoire = heap qui monte sans redescendre apres GC), threads.
  • Pool Hikari : connexions actives vers PostgreSQL (pool sature = requetes qui attendent une connexion, symptome typique avant les timeouts).
  • CPU process.

C’est le dashboard de reponse a “l’API est lente” : on localise en quelques clics si c’est une route, la JVM ou la BDD.

Q11. Pourquoi une retention de 7 jours ? Quelle volumetrie ?

  • Valeur identique pour les metriques (--storage.tsdb.retention.time=7d) et les logs (retention_period: 168h) : coherence, une seule regle a retenir.
  • 7 jours couvrent le besoin reel : exploiter la plateforme sur une semaine et diagnostiquer un incident recent. Au-dela, les donnees de demo n’ont pas de valeur.
  • La purge automatique borne le disque : pas de croissance infinie sur le poste de demonstration. Les donnees vivent dans des volumes nommes (prometheus_data, loki_data), donc survivent aux redemarrages mais partent avec un down -v.
  • La volumetrie reste modeste par construction : 10 jobs scrapes toutes les 15 s cote metriques, et cote logs Loki ne stocke que 3 labels d’index + contenu compresse.

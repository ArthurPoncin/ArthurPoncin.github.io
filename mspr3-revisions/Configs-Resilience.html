Fiche de revision : Configurations multi-environnement et resilience

Support de revision pour la soutenance MSPR3 (TPRE601). Objectif : savoir presenter le mecanisme d’overlays Docker Compose, les trois configurations exigees par le sujet (complete, offline, performance), les overlays d’exploitation (Traefik, vision, Watchtower, GPU), la combinaison qui tourne en production et la strategie de sauvegarde / restauration / remise a zero.

0. Vocabulaire a connaitre avant de lire

Les 10 termes qui reviennent partout dans cette fiche.

Terme Definition en une phrase
Overlay (Compose) Fichier compose partiel fusionne par-dessus un fichier de base via -f. Ne contient que les differences (quelques variables, labels ou limites).
Fusion multi -f docker compose -f a.yml -f b.yml up -d : les services de meme nom sont fusionnes, le dernier fichier gagne sur les valeurs simples.

Reverse proxy Point d’entree HTTP(S) unique qui route les requetes vers les conteneurs selon le nom d’hote. Ici Traefik, instance mutualisee du serveur.
certresolver Mecanisme Traefik de fourniture des certificats TLS. Ici le resolver duckdns avec un certificat wildcard *.zespri.duckdns.org deja emis.

1. TL;DR

Le sujet TPRE601 (livrable 01) exige que la demonstration puisse etre executee sous trois configurations distinctes : complete, offline et performance. La reponse du depot MSPR-Deploy : un compose de base unique + des overlays courts, fusionnes a la demande par docker compose -f docker-compose.yml -f <overlay>.yml up -d.

  • 9 fichiers compose : 2 bases (docker-compose.yml prod images GHCR, docker-compose.dev.yml build local) + 7 overlays (monitoring, offline, performance, traefik, vision, watchtower, gpu).
  • Complete : base + monitoring. Tous les services, IA generative active (Ollama local par defaut, Mistral si MISTRAL_API_KEY).
  • Offline : 2 services surcharges seulement. AUTH_OFFLINE=true (inscription/connexion sans verification email, aucun appel Resend) + DEFAULT_LLM=ollama et MISTRAL_API_KEY vide (aucun appel Mistral). Demontrable cable reseau debranche.
  • Performance : limites cpus/memory par service, demarrage allege sans ai-nutrition ni ollama (la generation de plans retombe sur la matrice statique de secours), monitoring reduit a prometheus + grafana + cadvisor.
  • Production (serveur) : base + monitoring + traefik + vision + watchtower (+ gpu une fois le passthrough valide). Exposition HTTPS sur *.zespri.duckdns.org, endpoints de metriques bloques au public.
  • Resilience : 3 scripts bash dans scripts/ : backup.sh (dump horodate des 3 bases dans backups/<timestamp>/), restore.sh (derniere sauvegarde ou dossier precis, remplace l’existant), clean.sh (remise a zero, suppression des volumes).
  • Limites assumees : sauvegardes locales uniquement, pas d’externalisation, pas de test de restauration automatise.

Le compose de base et le bootstrap sont detailles dans la fiche Deploiement. Le contenu de l’overlay monitoring est detaille dans la fiche Observabilite.

4. Les 3 configurations exigees par le sujet

Le sujet demande que la demonstration soit executable sous trois configurations distinctes. Chacune est une combinaison documentee dans CONFIGS.md.

4.1 Configuration COMPLETE

docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d
  • Tous les services : API, Auth, ETL, AI-Nutrition (+ Ollama), Reco-Fitness, Front, PostgreSQL metier + auth, MongoDB. Soit 21 conteneurs avec le monitoring.
  • IA generative operationnelle : Ollama local par defaut (DEFAULT_LLM: ${DEFAULT_LLM:-ollama} dans la base) ; bascule sur Mistral possible si MISTRAL_API_KEY est renseignee dans .env.
  • Observabilite complete : metriques applicatives, conteneurs, hote, BDD + logs centralises (voir fiche Observabilite).

C’est la configuration de reference : tout le reste se definit par rapport a elle (offline retire les dependances internet, performance retire les services lourds).

4.2 Configuration OFFLINE

Mode degrade demontrable sans connexion internet. L’overlay entier tient en quelques lignes :

# docker-compose.offline.yml
services:
  auth:
    environment:
      AUTH_OFFLINE: "true"

  ai-nutrition:
    environment:
      DEFAULT_LLM: ollama
      MISTRAL_API_KEY: ""
docker compose -f docker-compose.yml -f docker-compose.offline.yml up -d

Deux dependances internet sont neutralisees :

  1. Emails (Resend) : AUTH_OFFLINE=true est lu par le code du service AUTH (MSPR-AUTH/src/lib/auth.ts). Consequences : pas d’envoi d’email a l’inscription (sendOnSignUp: !OFFLINE), connexion autorisee sans email verifie (requireEmailVerification: !OFFLINE), et les fonctions d’envoi (verification, reset password) font un retour anticipe avec un simple log. Aucun appel Resend.
  2. LLM (Mistral) : DEFAULT_LLM=ollama force le LLM local et MISTRAL_API_KEY: "" ecrase toute cle presente dans .env (la fusion Compose fait gagner l’overlay). Aucun appel Mistral possible, meme par erreur de config.

Le front reste branche sur le backend local, seede par l’ETL (datasets embarques).

Prerequis, une seule fois avec internet : images construites ou pull, et modele Ollama gemma3:4b (~3 Go) telecharge dans le volume ollama_data. Ensuite, tout tourne hors-ligne : inscription, connexion, generation de plan repas par le LLM local.

4.3 Configuration PERFORMANCE

Optimisee pour materiel modeste : limites de ressources + demarrage allege + monitoring reduit.

# Coeur de stack avec limites de ressources, sans IA generative lourde
docker compose -f docker-compose.yml -f docker-compose.performance.yml up -d \
  db auth-db auth-migrate auth api etl mongo reco-fitness front

# Monitoring simplifie (Prometheus + Grafana + cAdvisor)
docker compose -f docker-compose.monitoring.yml up -d prometheus grafana cadvisor

L’overlay applique des limites cpus / memory par service via deploy.resources.limits (honore par Compose v2 hors Swarm, traduit en limites cgroups) :

Service cpus memory
db 1.0 512M
auth-db 0.5 256M
auth 0.5 256M
api 1.5 768M
etl 0.5 256M
ai-nutrition 1.5 1500M
reco-fitness 1.0 512M
mongo 0.5 512M
front 0.5 256M

Trois mecanismes distincts a savoir expliquer :

  1. Limites de ressources : chaque service est plafonne, aucun ne peut affamer les autres (l’API garde le plus gros budget : 1.5 cpus / 768M, l’IA aurait 1.5 cpus / 1500M si demarree).
  2. Demarrage allege : on liste explicitement les services a demarrer apres up -d. ai-nutrition et ollama (les plus gourmands : modele 4 milliards de parametres, inference CPU tres lente) ne sont pas dans la liste et rien n’en depend, donc ils restent eteints. La generation de plans repas retombe sur la matrice statique de secours : l’utilisateur recoit toujours un plan, sans latence LLM. Pour reintegrer l’IA : ajouter ai-nutrition ollama a la liste.
  3. Monitoring simplifie : seulement prometheus, grafana, cadvisor (metriques essentielles conteneurs), au lieu des 10 services de l’overlay complet. A noter : ollama n’a volontairement pas d’entree dans l’overlay performance, il n’est pas cense tourner dans cette configuration.

5. Overlays additionnels et points techniques

5.1 Le mecanisme de fusion Compose (a maitriser absolument)

docker compose -f base.yml -f overlay.yml fusionne les fichiers par cle de service : api dans la base et api dans l’overlay decrivent le meme service, Compose combine leurs attributs.

Regles de fusion :

  • Mappings (environment, labels en syntaxe map) : fusionnes cle par cle. L’overlay ajoute ses cles et surcharge celles qui existent (ex : MISTRAL_API_KEY: "" de l’offline ecrase ${MISTRAL_API_KEY:-} de la base).
  • Scalaires (image, container_name, restart) : la valeur du dernier -f gagne (ex : image: mspr-front:traefik remplace ghcr.io/whitefoxxyt/mspr-front:latest).
  • Listes (ports, dns, tmpfs) : concatenees. volumes : fusionnes par chemin de montage cible. labels en syntaxe liste "cle=valeur" : fusionnes par cle.
  • networks : union (la base attache mspr_data_network, l’overlay Traefik ajoute proxy_net).
  • L’ordre des -f compte : du plus generique au plus specifique.
  • Verification : docker compose -f ... -f ... config affiche la configuration fusionnee finale (tres utile en demo si le jury doute du resultat).

Exemple concret avec les fichiers reels :

# docker-compose.yml (base, service api, extrait)
  api:
    image: ghcr.io/whitefoxxyt/mspr-api:latest
    environment:
      DB_HOST: mspr-healthai-db
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}

# docker-compose.traefik.yml (overlay, service api, extrait)
  api:
    networks: [mspr_data_network, proxy_net]
    environment:
      CORS_ORIGIN: https://mspr.zespri.duckdns.org

Resultat fusionne : un seul service api, image GHCR de la base, les trois variables d’environnement presentes, les deux reseaux attaches, plus les labels Traefik.

5.2 Overlay TRAEFIK : exposition publique HTTPS

docker-compose.traefik.yml place la plateforme derriere le reverse proxy Traefik (instance mutualisee du serveur, le depot n’ajoute que des labels et le reseau). Routage par nom d’hote sur *.zespri.duckdns.org :

Service Sous-domaine Port interne
front mspr.zespri.duckdns.org 5173
api mspr-api.zespri.duckdns.org 8080
auth mspr-auth.zespri.duckdns.org 3000
ai-nutrition mspr-ai.zespri.duckdns.org 8001
reco-fitness mspr-reco.zespri.duckdns.org 8000
grafana mspr-grafana.zespri.duckdns.org 3000

Points cles :

  • TLS : entrypoint websecure, tls.certresolver=duckdns (certificat wildcard deja emis, un seul certificat couvre tous les sous-domaines).
  • Reseau externe proxy_net : declare external: true, c’est le reseau de l’instance Traefik du serveur. Chaque service expose y est attache en plus de mspr_data_network.
  • CORS alignees sur l’origine du front : CORS_ORIGIN (api, auth) et CORS_ALLOW_ORIGINS (ai-nutrition, reco-fitness) pointent sur https://mspr.zespri.duckdns.org ; BETTER_AUTH_URL et GF_SERVER_ROOT_URL passent en URL publique.
  • Front : image locale mspr-front:traefik : Vite fige les URLs des backends au build. L’image GHCR embarque les URLs localhost ; pour l’exposition publique il faut une image rebuildee localement avec les URLs publiques. Consequence : ce service est exclu de Watchtower (pas de registre source a suivre).
  • Blocage public des metriques : un middleware ipallowlist nomme mspr-metrics-deny (sourcerange 127.0.0.1/32) est applique a des routeurs dedies de priorite 100 qui matchent Path(/metrics) (auth, ai, reco) ou PathPrefix(/api/actuator) (api). Vu de l’exterieur, ces chemins repondent 403 ; Prometheus n’est pas impacte car il scrape en interne via le reseau Docker, sans passer par Traefik. Voir la fiche Securite.

5.3 Overlay VISION : classification photo par Mistral

# docker-compose.vision.yml
services:
  ai-nutrition:
    environment:
      ANALYZE_BACKEND: mistral_vision
  • Bascule la classification d’aliments par photo (route A1) sur le backend Mistral vision, avec repli automatique sur Food-101 (modele local HuggingFace) en cas d’echec.
  • Utilise l’image GHCR officielle (ghcr.io/whitefoxxyt/mspr-ai-nutrition:latest, qui contient le code A1 depuis le commit ab0f5d8). Plus d’image derivee locale : l’image officielle est suivie par Watchtower, donc CD de bout en bout.

5.4 Overlay WATCHTOWER : deploiement continu (renvoi)

docker-compose.watchtower.yml ajoute Watchtower : il interroge GHCR toutes les 5 minutes (WATCHTOWER_POLL_INTERVAL: "300") et recree automatiquement un conteneur des qu’un nouveau :latest est publie. Boucle complete : git push -> GitHub Actions build l’image -> Watchtower la tire et recree le conteneur, sans intervention manuelle. Seuls les conteneurs listes en argument sont surveilles (mspr-api, mspr-auth-service, mspr-etl, mspr-reco-fitness, mspr-ai-nutrition) ; le front est exclu (image locale), et les migrations one-shot (mspr-auth-migrate) ne sont pas rejouees. Detail complet (y compris le fix DOCKER_API_VERSION: "1.44") dans la fiche CI/CD et qualite.

5.5 Overlay GPU : Ollama accelere par le GPU NVIDIA

docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d

Trois reglages, deux services :

  1. Reservation du GPU pour ollama : deploy.resources.reservations.devices avec driver: nvidia, count: all, capabilities: [gpu]. Prerequis hote : driver NVIDIA + NVIDIA Container Toolkit (le runtime nvidia doit apparaitre dans docker info).
  2. OLLAMA_KEEP_ALIVE: "-1" : le modele reste charge en VRAM en permanence, pas de cold start a chaque generation. OLLAMA_NUM_PARALLEL: "1" : une inference a la fois, car la carte du serveur (Quadro P1000) n’a que 4 Go de VRAM.
  3. OLLAMA_NUM_GPU: "99" cote ai-nutrition : force l’offload complet du modele a chaque requete. Sans cela, l’auto-estimation d’Ollama est trop prudente sur la P1000 : ~1 Go offloade seulement, soit un split 81 % CPU, alors que le modele entier tient en 2.8 Go de VRAM mesures (100 % GPU). La variable vit cote client car c’est une option passee a chaque requete a l’API Ollama.

Pourquoi cet overlay est important : en CPU pur, la generation documentee depasse 200 000 ms par plan, au-dela du timeout applicatif. Le GPU rend la generation Gemma3:4b exploitable, et permet d’activer le prompt few-shot complet (FEW_SHOT_FULL_EXAMPLES=true) ainsi que l’eval LLM n=30 (depot AI-Nutrition, docs/GPU_EVAL_PLAYBOOK.md).

Verifications apres demarrage : docker exec mspr-ollama nvidia-smi (la carte est visible dans le conteneur) et docker exec mspr-ollama ollama ps (colonne PROCESSOR = GPU).

5.6 Combinaison de production sur le serveur

docker compose -f docker-compose.yml -f docker-compose.monitoring.yml \
  -f docker-compose.traefik.yml -f docker-compose.vision.yml \
  -f docker-compose.watchtower.yml up -d

Plateforme exposee (Traefik HTTPS), supervisee (monitoring complet), maintenue a jour automatiquement (Watchtower), avec la classification photo Mistral active. Une fois le passthrough GPU valide sur l’hote, on ajoute -f docker-compose.gpu.yml a la commande.

6. Resilience : sauvegarde, restauration, remise a zero

Trois scripts bash dans scripts/, qui operent sur les conteneurs en cours d’execution (via docker exec, pas besoin d’arreter la stack pour sauvegarder).

6.1 backup.sh : sauvegarde horodatee

./scripts/backup.sh                  # dump horodate dans backups/<timestamp>/
flowchart LR
    PG[("mspr-healthai-db<br/>healthai")] -->|pg_dump --clean| F1["healthai.sql.gz"]
    APG[("mspr-auth-db<br/>auth_db")] -->|pg_dump --clean| F2["auth_db.sql.gz"]
    MG[("mspr-mongo<br/>reco_fitness")] -->|mongodump --archive| F3["mongo_reco_fitness.archive.gz"]
    F1 --> DIR["backups/&lt;timestamp&gt;/"]
    F2 --> DIR
    F3 --> DIR
  • Verifie d’abord que les 3 conteneurs de donnees tournent (mspr-healthai-db, mspr-auth-db, mspr-mongo), sinon echec explicite.
  • PostgreSQL metier (healthai) et PostgreSQL auth (auth_db) : pg_dump --clean --if-exists pipe dans gzip. Le dump contient schema + donnees, precede des DROP ... IF EXISTS.
  • MongoDB (reco_fitness) : mongodump --db reco_fitness --archive pipe dans gzip (un seul flux binaire).
  • Sortie horodatee : backups/20260611-..../ (format date +%Y%m%d-%H%M%S, donc tri lexicographique = tri chronologique). Le dossier backups/ n’est pas versionne.

6.2 restore.sh : restauration

./scripts/restore.sh                 # restaure la derniere sauvegarde
./scripts/restore.sh backups/XXXX    # restaure une sauvegarde precise
  • Sans argument : selectionne la derniere sauvegarde (find backups/ ... | sort | tail -n1, correct grace au format horodate).
  • Chaque dump present est restaure individuellement (test if [[ -f ... ]]) : on peut restaurer un dossier partiel.
  • PostgreSQL : gunzip -c | docker exec -i ... psql. Comme le dump a ete fait avec --clean, la restauration remplace les tables existantes.
  • MongoDB : gunzip -c | docker exec -i ... mongorestore --drop --archive. Le --drop supprime chaque collection avant de la recharger.
  • Consequence a assumer devant le jury : la restauration est un remplacement, pas une fusion. Les donnees ecrites apres la sauvegarde sont perdues.

6.3 clean.sh : remise a zero

./scripts/clean.sh                   # stack prod ; --dev pour la base dev ; --force sans confirmation
  • Demande confirmation (sauf --force), puis docker compose ... down -v --remove-orphans sur la base choisie (+ l’overlay monitoring s’il est present).
  • Supprime tous les volumes : BDD metier, BDD auth, Mongo, Ollama, monitoring.
  • Le prochain demarrage repart d’une base vierge : les migrations rejouent, et l’ETL recharge les datasets au prochain run.

6.4 Ce qui est perdu / recuperable apres un clean

Volume Contenu Apres destruction
postgres_data Donnees metier healthai Tables ETL rechargees par l’ETL ; donnees ecrites par les services perdues sans backup
auth_db_data Comptes utilisateurs, sessions Perdu sans backup (irremplacable)
mongo_data Profils fitness, programmes, feedbacks Perdu sans backup (irremplacable)
ollama_data Modele gemma3:4b (~3 Go) Re-telecharge au demarrage (internet requis)
etl_data Exports CSV processed / samples Regenere au prochain run ETL
prometheus_data, grafana_data, loki_data Metriques (retention 7j), dashboards, logs Historique perdu ; dashboards re-provisionnes depuis le depot

Le perimetre de backup.sh (les 3 bases) couvre exactement les donnees non regenerables.

6.5 Limites assumees

  • Sauvegardes locales uniquement : backups/ vit sur le meme disque que les volumes. Une panne disque emporte donnees ET sauvegardes.
  • Pas d’externalisation (stockage objet, seconde machine) ni de planification automatique : execution manuelle.
  • Pas de test de restauration automatise : la restauration est verifiee manuellement.

Ces limites sont documentees et a presenter comme des choix de perimetre (voir Q10 et Q11).

7. Code essentiel a savoir expliquer au jury

7.1 L’overlay offline complet

# docker-compose.offline.yml
services:
  auth:
    environment:
      AUTH_OFFLINE: "true"

  ai-nutrition:
    environment:
      DEFAULT_LLM: ollama
      MISTRAL_API_KEY: ""

Ce qu’il faut savoir dire :

  • Tout l’overlay tient en 2 services et 3 variables : c’est l’argument massue en faveur des overlays (la config offline n’est pas un fork de 250 lignes du compose de base, c’est un delta minimal).
  • MISTRAL_API_KEY: "" n’est pas decoratif : la fusion Compose fait que cette valeur ecrase ${MISTRAL_API_KEY:-} de la base. Meme si une cle est presente dans .env, le service ne la voit pas : aucun appel Mistral possible.
  • AUTH_OFFLINE est un toggle applicatif : l’overlay ne fait que positionner la variable, le comportement vit dans le code du service AUTH (extrait suivant).
  • Prerequis une seule fois avec internet : images + gemma3:4b dans le volume ollama_data.

7.2 Le toggle AUTH_OFFLINE dans MSPR-AUTH

// MSPR-AUTH/src/lib/auth.ts (extrait)
// Mode offline (config performance/offline MSPR3) : desactive la verification email
// et les envois Resend pour une demo sans connexion internet.
const OFFLINE = process.env.AUTH_OFFLINE === "true";

export const auth = betterAuth({
    // ...
    emailVerification: {
        sendOnSignUp: !OFFLINE,
        autoSignInAfterVerification: true,
        async sendVerificationEmail({ user, url, token }, request) {
            if (OFFLINE) {
                console.log("[offline] verification email desactivee pour", user.email);
                return;
            }
            // ... envoi via Resend (necessite internet)
        },
    },

    emailAndPassword: {
        enabled: true,
        requireEmailVerification: !OFFLINE,

        async sendResetPassword({ user, url, token }, request) {
            if (OFFLINE) {
                console.log("[offline] reset password email desactive pour", user.email);
                return;
            }
            // ... envoi via Resend
        }
    }
});

Ce qu’il faut savoir dire :

  • Le toggle agit a trois niveaux : pas d’email a l’inscription (sendOnSignUp), connexion autorisee sans email verifie (requireEmailVerification), et retour anticipe dans les deux fonctions d’envoi (garde-fou si un envoi etait declenche autrement).
  • Le retour anticipe avant l’instanciation de l’appel Resend garantit zero requete sortante ; un log trace le comportement pour la demo.
  • En mode normal (variable absente), OFFLINE vaut false et le comportement nominal (verification email obligatoire via Resend) est inchange : le meme code sert les deux configurations.

7.3 Les limites de ressources (performance)

# docker-compose.performance.yml (extrait)
services:
  db:
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
  api:
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: 768M
  ai-nutrition:
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: 1500M

Ce qu’il faut savoir dire :

  • deploy.resources.limits vient de la spec Compose ; historiquement reserve a Swarm, il est honore par Compose v2 en mode standalone (traduit en limites cgroups sur le conteneur).
  • Les budgets refletent les besoins reels : l’API Spring Boot (JVM) et l’IA ont les plus gros plafonds, les services Bun/FastAPI/front se contentent de 256M.
  • Limite = plafond, pas reservation : un service qui depasse memory est tue (OOM), un service qui sature cpus est throttle. C’est ce qui protege le materiel modeste.
  • ai-nutrition a une limite definie mais n’est pas demarre dans la commande allegee ; la limite ne sert que si on le reintegre explicitement.

7.4 Les labels Traefik de l’API (routeur + blocage metriques)

# docker-compose.traefik.yml (service api, extrait)
  api:
    networks: [mspr_data_network, proxy_net]
    environment:
      CORS_ORIGIN: https://mspr.zespri.duckdns.org
    labels:
      - "traefik.enable=true"
      - "traefik.docker.network=proxy_net"
      - "traefik.http.routers.mspr-api.rule=Host(`mspr-api.zespri.duckdns.org`)"
      - "traefik.http.routers.mspr-api.entrypoints=websecure"
      - "traefik.http.routers.mspr-api.tls.certresolver=duckdns"
      - "traefik.http.services.mspr-api.loadbalancer.server.port=8080"
      # Blocage public des endpoints de metriques (middleware declare une seule fois ici)
      - "traefik.http.middlewares.mspr-metrics-deny.ipallowlist.sourcerange=127.0.0.1/32"
      - "traefik.http.routers.mspr-api-metrics.rule=Host(`mspr-api.zespri.duckdns.org`) && PathPrefix(`/api/actuator`)"
      - "traefik.http.routers.mspr-api-metrics.entrypoints=websecure"
      - "traefik.http.routers.mspr-api-metrics.tls.certresolver=duckdns"
      - "traefik.http.routers.mspr-api-metrics.priority=100"
      - "traefik.http.routers.mspr-api-metrics.middlewares=mspr-metrics-deny"
      - "traefik.http.routers.mspr-api-metrics.service=mspr-api"

Ce qu’il faut savoir dire :

  • Deux routeurs pour un meme service : mspr-api (trafic normal) et mspr-api-metrics (chemins de metriques). Le second a priority=100, donc il gagne sur le routeur general quand l’URL matche PathPrefix(/api/actuator).
  • Le middleware mspr-metrics-deny est un ipallowlist avec sourcerange=127.0.0.1/32 : aucune IP publique ne matche jamais, donc 403 systematique. Il est declare une seule fois (ici) et reference par les routeurs metriques des autres services (auth, ai, reco) : pas de duplication.
  • traefik.docker.network=proxy_net dit a Traefik par quel reseau joindre le conteneur (il est attache a deux reseaux).
  • Prometheus scrape /api/actuator/prometheus et les /metrics en interne via mspr_data_network : le blocage ne concerne que le chemin public via Traefik.

7.5 L’overlay GPU

# docker-compose.gpu.yml (extrait)
services:
  ollama:
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    environment:
      # Modele garde charge en VRAM en permanence : evite le cold start.
      OLLAMA_KEEP_ALIVE: "-1"
      # Une inference a la fois : sur une carte 4 Go (Quadro P1000 du serveur),
      # multiplier les contextes ferait deborder la VRAM.
      OLLAMA_NUM_PARALLEL: "1"

  ai-nutrition:
    environment:
      # Force l'offload complet du modele a chaque requete : l'auto-estimation
      # d'Ollama ne place que ~1 Go sur la P1000 (split 81 % CPU), alors que le
      # modele entier tient en VRAM (2.8 Go mesures, 100 % GPU).
      OLLAMA_NUM_GPU: "99"

Ce qu’il faut savoir dire :

  • reservations.devices est la syntaxe Compose moderne du passthrough GPU (equivalent de docker run --gpus all). Prerequis hote : driver NVIDIA + NVIDIA Container Toolkit.
  • Les trois variables repondent chacune a un probleme mesure : cold start (KEEP_ALIVE=-1), VRAM limitee a 4 Go (NUM_PARALLEL=1), auto-estimation trop prudente (NUM_GPU=99, voir Q7).
  • Chiffre a citer : generation CPU documentee a 200 000+ ms par plan (au-dela du timeout applicatif) ; le GPU la rend exploitable.
  • Overlay optionnel et cumulable : sans GPU exploitable on ne l’inclut pas, Ollama tourne sur CPU. C’est exactement la philosophie des overlays : la capacite materielle est une dimension de configuration comme une autre.

7.6 Le coeur de backup.sh

# scripts/backup.sh (extrait)
TS="$(date +%Y%m%d-%H%M%S)"
OUT_DIR="${1:-$ROOT_DIR/backups/$TS}"

running() { docker ps --format '{{.Names}}' | grep -qx "$1"; }

for c in "$DB_CONTAINER" "$AUTH_DB_CONTAINER" "$MONGO_CONTAINER"; do
  running "$c" || fail "Conteneur $c non demarre. Lance la stack avant de sauvegarder."
done

log "Dump PostgreSQL metier ($DB_NAME)"
docker exec "$DB_CONTAINER" pg_dump -U "$DB_USER" --clean --if-exists "$DB_NAME" | gzip > "$OUT_DIR/healthai.sql.gz"

log "Dump PostgreSQL auth ($AUTH_DB_NAME)"
docker exec "$AUTH_DB_CONTAINER" pg_dump -U "$AUTH_DB_USER" --clean --if-exists "$AUTH_DB_NAME" | gzip > "$OUT_DIR/auth_db.sql.gz"

log "Dump MongoDB ($MONGO_DB)"
docker exec "$MONGO_CONTAINER" mongodump --db "$MONGO_DB" --archive | gzip > "$OUT_DIR/mongo_${MONGO_DB}.archive.gz"

Ce qu’il faut savoir dire :

  • Precondition verifiee : les 3 conteneurs de donnees doivent tourner (grep -qx = match exact du nom). Echec explicite plutot qu’un dump partiel silencieux.
  • pg_dump est un export logique (SQL rejouable), execute dans le conteneur via docker exec, pipe vers gzip sur l’hote : rien n’est ecrit dans le conteneur.
  • --clean --if-exists prepare la restauration : le dump contient les DROP IF EXISTS avant les CREATE, donc restore.sh n’a aucune etape prealable.
  • Sauvegarde a chaud : pg_dump prend un snapshot coherent par transaction ; acceptable pour ce volume de donnees.
  • set -euo pipefail (en tete du script) : toute commande qui echoue arrete le script, y compris dans un pipe.

7.7 La selection de sauvegarde dans restore.sh

# scripts/restore.sh (extrait)
if [[ -z "$BACKUP_DIR" ]]; then
  [[ -d "$ROOT_DIR/backups" ]] || fail "Aucun dossier backups/. Precise un chemin de sauvegarde."
  BACKUP_DIR="$(find "$ROOT_DIR/backups" -mindepth 1 -maxdepth 1 -type d | sort | tail -n1 || true)"
  [[ -n "$BACKUP_DIR" ]] || fail "Aucune sauvegarde trouvee dans backups/."
fi

if [[ -f "$BACKUP_DIR/healthai.sql.gz" ]]; then
  log "Restauration PostgreSQL metier ($DB_NAME)"
  gunzip -c "$BACKUP_DIR/healthai.sql.gz" | docker exec -i "$DB_CONTAINER" psql -U "$DB_USER" -d "$DB_NAME"
fi

if [[ -f "$BACKUP_DIR/mongo_${MONGO_DB}.archive.gz" ]]; then
  log "Restauration MongoDB ($MONGO_DB)"
  gunzip -c "$BACKUP_DIR/mongo_${MONGO_DB}.archive.gz" | docker exec -i "$MONGO_CONTAINER" mongorestore --drop --archive
fi

Ce qu’il faut savoir dire :

  • find ... | sort | tail -n1 selectionne la derniere sauvegarde : le tri lexicographique fonctionne car l’horodatage est au format YYYYmmdd-HHMMSS.
  • Restauration par fichier present : un dossier partiel (par exemple seulement auth_db.sql.gz) est restaure partiellement, sans erreur sur les fichiers absents.
  • docker exec -i (sans -t) : le flux gunzip passe par stdin du process dans le conteneur.
  • mongorestore --drop supprime chaque collection avant de la recharger ; cote PostgreSQL, c’est le --clean du dump qui joue ce role. Dans les deux cas : remplacement, pas fusion.

7.8 La remise a zero dans clean.sh

# scripts/clean.sh (extrait)
BASE="docker-compose.yml"
[[ "$MODE" == "dev" ]] && BASE="docker-compose.dev.yml"

FILES=(-f "$BASE")
[[ -f "$ROOT_DIR/docker-compose.monitoring.yml" ]] && FILES+=(-f docker-compose.monitoring.yml)

if [[ "$FORCE" -ne 1 ]]; then
  printf '\033[1;33m[clean]\033[0m Supprime TOUS les volumes (donnees BDD, Mongo, Ollama, monitoring). Continuer ? [y/N] '
  read -r ans
  [[ "$ans" == "y" || "$ans" == "Y" ]] || { echo "Annule."; exit 0; }
fi

( cd "$ROOT_DIR" && docker compose "${FILES[@]}" down -v --remove-orphans )

Ce qu’il faut savoir dire :

  • down -v : arrete les conteneurs et supprime les volumes nommes ; --remove-orphans nettoie les conteneurs d’overlays qui ne sont plus dans les fichiers passes.
  • Le script inclut l’overlay monitoring dans les -f pour que ses volumes (prometheus_data, grafana_data, loki_data) soient aussi supprimes : sans cela, down -v sur la seule base les ignorerait.
  • Confirmation interactive par defaut (action destructive), --force pour les usages scriptes, --dev pour cibler la base dev.
  • Apres un clean : prochain demarrage vierge, migrations rejouees, datasets recharges par l’ETL au prochain run. C’est la demo “remise a zero” du jury en une commande.

8. Questions probables du jury

Q1. Pourquoi des overlays plutot que trois docker-compose complets dupliques ?

Parce que trois fichiers complets seraient trois copies de ~250 lignes a maintenir en parallele :

  1. Pas de derive de configuration : une correction dans la base (nouvelle variable, healthcheck, image) profite immediatement a toutes les configurations. Avec trois copies, on oublie d’en mettre une a jour et les configs divergent silencieusement.
  2. Lisibilite du delta : l’overlay offline fait 3 variables. On voit en 5 secondes ce qui distingue la config offline de la complete. Dans un fichier duplique, la difference serait noyee.
  3. Combinabilite : les overlays se cumulent (offline + gpu, performance + monitoring simplifie, production = base + 4 overlays). Avec des fichiers monolithiques il faudrait une copie par combinaison.

Tradeoff assume : il faut connaitre les regles de fusion et l’ordre des -f. Mitigation : docker compose ... config affiche le resultat fusionne, et chaque overlay documente sa commande en en-tete.

Q2. Comment Docker Compose fusionne-t-il plusieurs -f ?

Fusion par cle de service : deux blocs api sont combines en un seul. Ensuite, par type d’attribut :

  • Mappings (environment, labels) : fusionnes cle par cle, l’overlay surcharge en cas de conflit.
  • Scalaires (image, restart) : le dernier -f gagne.
  • Listes (ports, tmpfs) : concatenees ; volumes fusionnes par chemin cible ; networks en union.

L’ordre des -f compte donc : base d’abord, overlays ensuite, du plus generique au plus specifique. Exemple concret du projet : MISTRAL_API_KEY: "" (offline) ecrase ${MISTRAL_API_KEY:-} (base) ; image: mspr-front:traefik (traefik) remplace l’image GHCR. Verification : docker compose -f ... -f ... config.

Q3. Comment le mode offline fonctionne-t-il concretement ?

Deux dependances internet sont neutralisees :

  • Verification email : AUTH_OFFLINE=true est lu dans MSPR-AUTH/src/lib/auth.ts. L’inscription n’envoie plus d’email (sendOnSignUp: !OFFLINE), la connexion n’exige plus un email verifie (requireEmailVerification: !OFFLINE), et les fonctions d’envoi font un retour anticipe avec un log [offline]. Aucun appel Resend.
  • Mistral : DEFAULT_LLM=ollama force le LLM local, et MISTRAL_API_KEY: "" ecrase toute cle de .env via la fusion. Aucun appel sortant possible.

Prerequis une seule fois avec internet : images pull/build et gemma3:4b (~3 Go) telecharge dans le volume ollama_data. Demo type : debrancher le reseau, s’inscrire, se connecter, generer un plan repas via le LLM local.

Q4. Pourquoi la config performance omet l’IA generative, et que voit l’utilisateur ?

ai-nutrition + ollama sont les services les plus gourmands : modele 4 milliards de parametres (~3 Go), inference CPU documentee a 200 000+ ms par plan. Sur materiel modeste, ils satureraient la machine et degraderaient toute la stack. La commande allegee liste explicitement les services a demarrer sans eux ; rien n’en depend, donc ils restent eteints.

Pour l’utilisateur : la generation de plans repas retombe sur la matrice statique de secours. Il recoit toujours un plan, immediatement, simplement moins personnalise que la version LLM. C’est un mode degrade voulu : on degrade la qualite de la fonctionnalite, pas sa disponibilite. Pour reintegrer l’IA : ajouter ai-nutrition ollama a la liste (leurs limites de ressources sont deja definies dans l’overlay).

Q5. Comment la plateforme est-elle exposee en HTTPS, et pourquoi Traefik ?

L’overlay traefik attache chaque service a exposer au reseau externe proxy_net (celui de l’instance Traefik du serveur) et declare des labels : regle Host(...) par sous-domaine *.zespri.duckdns.org, entrypoint websecure, tls.certresolver=duckdns (certificat wildcard, un seul certificat pour tous les sous-domaines). Les variables CORS et URLs publiques sont alignees sur l’origine du front.

Pourquoi Traefik plutot qu’un nginx : la configuration vit dans les labels du service concerne (declaratif, versionne avec le compose), Traefik decouvre les conteneurs dynamiquement via le socket Docker, et gere les certificats automatiquement. Pas de fichier nginx central a maintenir ni de reload manuel. Voir la fiche Securite pour le volet exposition.

Q6. Pourquoi bloquer les /metrics au public, et comment ?

Les endpoints /metrics (auth, ai-nutrition, reco-fitness) et /api/actuator (Spring) exposent des informations internes : versions, latences par route, noms de jobs, etat des dependances. C’est de la matiere pour un attaquant (reconnaissance) et cela n’a aucune raison d’etre public.

Mecanisme : pour chaque service expose, un routeur dedie matche le chemin de metriques avec priority=100 (il gagne sur le routeur general) et applique le middleware mspr-metrics-deny, un ipallowlist avec sourcerange=127.0.0.1/32. Aucune IP publique ne matche : 403 systematique. Le middleware est declare une fois (labels du service api) et reference partout.

Pourquoi ne pas supprimer ces endpoints : Prometheus en a besoin. Il les scrape en interne via le reseau Docker mspr_data_network, sans passer par Traefik, donc le blocage public ne l’affecte pas.

Q7. A quoi sert OLLAMA_NUM_GPU=99 ?

C’est le nombre de couches du modele a offloader en VRAM. 99 etant superieur au nombre de couches de Gemma3:4b, cela force l’offload complet.

Pourquoi forcer : l’auto-estimation d’Ollama est trop prudente sur la Quadro P1000 (4 Go) : elle ne place que ~1 Go en VRAM, soit un split 81 % CPU et des performances proches du CPU pur. Or le modele entier tient en 2.8 Go mesures : en forcant, on passe a 100 % GPU.

Pourquoi la variable est cote ai-nutrition et pas cote ollama : c’est une option de requete de l’API Ollama, passee par le client a chaque generation, pas un parametre du serveur. Complement cote serveur : OLLAMA_KEEP_ALIVE=-1 (modele garde en VRAM, pas de cold start) et OLLAMA_NUM_PARALLEL=1 (une inference a la fois pour tenir dans 4 Go).

Q8. Quelle est la strategie de sauvegarde, et comment restaurer ?

  • Quoi : les 3 bases d’etat, c’est-a-dire exactement les donnees non regenerables : PostgreSQL metier (healthai), PostgreSQL auth (auth_db, comptes), MongoDB (reco_fitness, profils/programmes/feedbacks).
  • Comment : ./scripts/backup.sh, a chaud, via docker exec sur les conteneurs en cours : pg_dump --clean --if-exists | gzip pour les deux PostgreSQL, mongodump --archive | gzip pour Mongo. Le script verifie d’abord que les 3 conteneurs tournent.
  • Ou : dossier horodate backups/<timestamp>/ (3 fichiers .gz), local au depot, non versionne.
  • Restauration : ./scripts/restore.sh (derniere sauvegarde) ou ./scripts/restore.sh backups/XXXX (dossier precis). psql rejoue le dump (qui contient les DROP grace a --clean), mongorestore --drop remplace les collections. Restauration = remplacement, pas fusion.

Q9. Que perd-on si on detruit les volumes ?

Reponse en deux categories :

  • Regenerable : les tables chargees par l’ETL (rechargees au prochain run depuis les datasets), le modele Ollama (re-telecharge, ~3 Go, internet requis), les exports ETL, les dashboards Grafana (re-provisionnes depuis le depot).
  • Irremplacable sans sauvegarde : les comptes utilisateurs (auth_db_data), les donnees fitness Mongo (profils, programmes generes, feedbacks), et les donnees metier ecrites par les services apres l’ETL. Plus l’historique de metriques/logs (retention 7 jours, perte acceptee).

C’est precisement ce decoupage qui justifie le perimetre de backup.sh : il couvre les 3 bases, rien d’autre. La sequence clean.sh puis restore.sh permet de demontrer la reprise au jury.

Q10. Pourquoi pas de sauvegarde externalisee ?

Limite documentee et assumee : les sauvegardes restent sur le meme disque que les volumes, donc une panne materielle emporte les deux. Raisons du choix : perimetre MSPR (un seul serveur, pas de budget cloud), et l’objectif du livrable est de demontrer le mecanisme de sauvegarde/restauration, pas d’operer un PRA complet.

Ce qu’on ferait en production reelle : regle 3-2-1 (3 copies, 2 supports, 1 hors site), copie vers un stockage objet ou une seconde machine (rclone/rsync), planification cron avec alerte en cas d’echec, chiffrement des dumps (donnees de sante, sujet RGPD), et politique de retention. Annoncer ces pistes soi-meme avant que le jury ne les pointe.

Q11. Comment teste-t-on qu’une restauration fonctionne ?

Aujourd’hui : manuellement, et c’est demontrable en soutenance en quelques minutes :

  1. ./scripts/backup.sh ; noter un element temoin (un compte utilisateur, un count SQL).
  2. ./scripts/clean.sh --force puis redemarrage de la stack (base vierge, migrations rejouees).
  3. ./scripts/restore.sh ; verifier que le compte temoin se reconnecte et que les counts correspondent.

Limite assumee : pas de test automatise. Piste d’industrialisation : un job planifie qui restaure le dernier dump dans des conteneurs jetables, execute des requetes de sanite (counts non nuls, login d’un compte temoin) et alerte en cas d’echec. Phrase a placer : une sauvegarde non testee n’est pas une sauvegarde, c’est pour cela que la limite est explicitement documentee.

Q12. Quelle combinaison tourne en production sur le serveur ?

docker compose -f docker-compose.yml -f docker-compose.monitoring.yml \
  -f docker-compose.traefik.yml -f docker-compose.vision.yml \
  -f docker-compose.watchtower.yml up -d

Soit : base prod (images GHCR) + observabilite complete + exposition HTTPS sur *.zespri.duckdns.org + classification photo Mistral vision + deploiement continu Watchtower. L’overlay gpu s’ajoute a cette commande une fois le passthrough NVIDIA valide sur l’hote (driver + Container Toolkit).

C’est l’illustration finale du mecanisme : la production n’est pas un fichier a part, c’est la meme base que la demo du jury, plus quatre overlays. Toute correction sur la base profite a la fois aux configurations de demonstration et a la production.

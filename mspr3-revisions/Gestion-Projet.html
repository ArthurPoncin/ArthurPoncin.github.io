Fiche de revision : Gestion de projet agile

Support de revision pour la soutenance MSPR3 (TPRE601). Objectif : savoir presenter la demarche agile adaptee a l’equipe, le decoupage en 4 sprints thematiques, les ceremonies allegees, le tableau Kanban GitHub et la gestion des risques (livrable 05).

0. Vocabulaire a connaitre avant de lire

Les 8 termes qui reviennent partout dans cette fiche.

Terme Definition en une phrase
Sprint Periode de travail bornee qui produit un increment demontrable. Ici : 4 sprints thematiques (A a D), tous termines.
Increment Resultat concret livre a la fin d’un sprint, verifiable de bout en bout : la stack demarre, la nouveaute est demontrable.
Backlog Liste ordonnee des taches restantes, materialisee ici par les issues GitHub (colonnes Backlog / Ready du tableau).
Kanban Tableau visuel de suivi par colonnes. Ici : GitHub Project “MSPR” de l’organisation whitefoxxyt, commun a tous les depots.

Definition du fini Critere objectif qui declare un sprint termine. Ici : la stack demarre et le nouvel increment est demontrable.
Pull request (PR) Proposition de fusion de code sur GitHub. Une PR par lot de travail, mergee apres tests verts ; sert de point de revue.

1. TL;DR

La MSPR3 (TPRE601) porte sur la mise en production de la plateforme HealthAI Coach construite lors des MSPR1 (backend metier) et MSPR2 (IA et frontend) : conteneurisation, orchestration locale Docker Compose, observabilite, CI/CD, securite, configurations multi-environnement et resilience.

L’organisation du travail (livrable 05-gestion-de-projet/) repose sur :

  • Une approche agile et iterative, adaptee a la taille reelle de l’equipe et au perimetre. Principe : livrer par increments fonctionnels verifiables de bout en bout plutot que tout produire en une seule passe.
  • Pas de processus lourd : le pilotage se fait directement dans GitHub (issues, pull requests, Actions). Pas de daily formel, points d’avancement asynchrones.
  • 4 sprints thematiques, tous termines : A Observabilite, B Configurations + resilience, C CI/CD et qualite, D Documentation, securite et gestion de projet.
  • Un Kanban GitHub Project commun a tous les depots (projet “MSPR”, organisation whitefoxxyt), taches MSPR3 prefixees [MSPR3][Sprint A..D]. Capture fournie dans les livrables (kanban-github-project.png).
  • Une gestion des risques pragmatique : tableau risque / impact / parade, base sur les risques concrets rencontres.
  • La cible de mise en production est un deploiement local orchestre par Docker Compose (bootstrap.sh) : c’est le point d’evaluation et de demonstration, et le decoupage en sprints est pense autour de cette cible.

Preuve de pilotage par la qualite : au releve du 10/06/2026, les 8 chaines CI GitHub Actions sont au vert et la publication d’image sur GHCR est conditionnee aux tests (source : rapport-tests-qualite.md).

L’application mobile est prise en charge par un autre membre de l’equipe avec son propre rythme : les sprints decrits ici ne la concernent pas (voir fiche Application mobile).

3. Methodologie

3.1 Agile et iterative, adaptee

L’approche retenue est agile et iterative, adaptee a la taille reelle de l’equipe et au perimetre de la MSPR3. Le principe directeur :

Livrer par increments fonctionnels, chacun verifiable de bout en bout (la stack demarre, les nouveaux elements sont demontrables), plutot que de tout produire en une seule passe.

Trois elements de contexte expliquent les choix :

  1. Petite equipe : pas de processus lourd. Les ceremonies sont allegees et le pilotage se fait directement dans GitHub (issues, pull requests, Actions).
  2. Application mobile a part : portee par un autre membre avec son propre rythme, hors des sprints decrits ici.
  3. Cible claire : la mise en production est un deploiement local orchestre par Docker Compose (bootstrap.sh), qui sert de point d’evaluation et de demonstration. Le decoupage en sprints est pense autour de cette cible : chaque sprint enrichit la stack deployable.

3.2 Pourquoi pas de Scrum complet

Les ceremonies Scrum classiques sont conservees dans leur intention mais allegees :

  • Un Scrum complet (daily quotidien formel, roles dedies, estimation en points, suivi de velocite) aurait un cout disproportionne pour une equipe de cette taille travaillant sur un perimetre d’industrialisation.
  • L’outillage GitHub porte deja le suivi : l’etat des issues, des PR et des runs Actions rend visible l’avancement sans reunion supplementaire.
  • Ce qui est conserve : la logique d’iteration (sprints), un objectif clair par sprint (le theme), une definition du fini verifiable, une revue par demonstration et une retrospective courte.

3.3 Sprints thematiques plutot que calendaires

Les 4 sprints sont definis par leur theme (observabilite, configurations, CI/CD, documentation et securite), pas par des dates fixes. Chaque sprint se termine quand sa definition du fini est atteinte : la stack demarre et le nouvel increment est demontrable. Les quatre sprints ont ete reellement suivis, dans l’ordre A puis B puis C puis D, et sont tous termines.

3.4 Le flux d’une tache

Cycle de vie type d’un lot de travail, entierement porte par GitHub :

  1. Issue creee et prefixee [MSPR3][Sprint X], placee dans Backlog / Ready du Kanban en planification.
  2. In progress : developpement, la carte suit l’issue.
  3. Pull request ouverte (une PR par lot) : la carte passe en In review, la chaine Actions tourne (lint, tests, couverture).
  4. Merge apres tests verts : sur push, le workflow docker-publish (appele via workflow_call) publie l’image sur GHCR.
  5. Done : la PR est mergee et l’increment est verifie sur la stack locale.

4. Les 4 sprints en detail

4.1 Sprint A : Observabilite

Objectif. Doter la plateforme d’un systeme de supervision : savoir si les services sont vivants, suivre leurs ressources, centraliser les logs, etre alerte en cas de probleme.

Principales taches.

  • Overlay docker-compose.monitoring.yml ajoutant la stack d’observabilite sans modifier la stack applicative : Prometheus, Grafana, Loki, Promtail, Alertmanager.
  • Exporters d’infrastructure : cAdvisor (conteneurs), node-exporter (hote), postgres-exporter x2 (bases metier et auth), mongodb-exporter.
  • Instrumentation applicative des 4 services dans leur code source : API via Actuator / Micrometer (/api/actuator/prometheus), AI-Nutrition et Reco-Fitness via prometheus-fastapi-instrumentator (/metrics), Auth via @hono/prometheus (/metrics).
  • Trois regles d’alerte Prometheus (prometheus/alerts.yml) : CibleInjoignable (up == 0 pendant 1 min, critical), ConteneurCpuEleve (> 0.9 coeur CPU pendant 5 min, warning), ConteneurMemoireElevee (> 2 Go de RAM pendant 5 min, warning).
  • Dashboard Grafana “MSPR HealthAI - Vue stack” provisionne automatiquement (cibles UP, disponibilite par job, CPU / memoire par conteneur, flux de logs).

Livrables. Overlay monitoring fonctionnel, instrumentation des 4 services, alertes, dashboard provisionne, documentation monitoring/README.md. Detail technique : fiche Observabilite.

4.2 Sprint B : Configurations multi-environnement et resilience

Objectif. Rendre la stack adaptable a plusieurs contextes de demonstration et capable de sauvegarder / restaurer ses donnees.

Principales taches.

  • Trois configurations via overlays Compose, documentees dans CONFIGS.md :
    • complete : tous les services + monitoring, IA generative active (docker-compose.yml + docker-compose.monitoring.yml) ;
    • offline : sans internet (docker-compose.offline.yml), LLM force sur Ollama local, Auth sans verification email (AUTH_OFFLINE=true, aucun appel Resend) ;
    • performance : limites CPU / RAM par service (docker-compose.performance.yml), IA generative lourde omise du demarrage par defaut (repli sur la matrice statique), monitoring reduit a l’essentiel.
  • Scripts de resilience dans scripts/, operant sur les conteneurs en cours : backup.sh (dump horodate : pg_dump x2 + mongodump), restore.sh (pg_dump --clean, mongorestore --drop), clean.sh (remise a zero des volumes).

Livrables. Trois overlays operationnels, CONFIGS.md, trois scripts de sauvegarde / restauration / nettoyage, section dediee du README.md. Detail technique : fiche Configs et resilience.

4.3 Sprint C : CI/CD et qualite

Objectif. Industrialiser : chaque depot construit, teste et publie automatiquement son image, avec des garde-fous de qualite.

Principales taches.

  • 8 chaines GitHub Actions (une par depot) : lint selon la techno, tests + couverture, build de l’image Docker, publication sur GHCR (ghcr.io/whitefoxxyt/mspr-<service>).
  • Publication conditionnee : uniquement sur push (pas sur les pull requests) et seulement si lint et tests passent. Les workflows docker-publish sont appeles via workflow_call.
  • Couverture imposee a 80 % cote API (JaCoCo) et Reco-Fitness (pytest-cov).
  • Strategie de tags via docker/metadata-action : branche, semver sur tags vX.Y.Z, SHA court, latest depuis la branche par defaut.
  • Analyse de code SonarCloud via l’application GitHub installee sur l’organisation whitefoxxyt (Automatic Analysis a chaque push, sans token dans les depots). L’API embarque aussi un environnement Sonar local (docker-compose.sonar.yml) pour une analyse manuelle.
  • Durcissement des conteneurs (volet securite operationnelle) : les 6 services applicatifs tournent en utilisateur non-root, HEALTHCHECK presents, no-new-privileges, rotation des logs json-file (max-size: 10m, max-file: 3), ports des bases (5433 / 5434 / 27018) bindes sur 127.0.0.1.

Livrables. 8 pipelines CI/CD publiant sur GHCR, seuils de couverture configures, analyse SonarCloud, docker-compose.yml durci, CICD.md. Detail technique : fiche CI/CD et qualite.

4.4 Sprint D : Documentation, securite et gestion de projet

Objectif. Finaliser les livrables redactionnels, consolider la gestion des secrets et formaliser le suivi projet.

Principales taches.

  • Documentation de deploiement : README.md (prerequis, demarrage en une commande, acces aux services, depannage), CONFIGS.md, CICD.md, monitoring/README.md.
  • Gestion des secrets : bootstrap.sh genere BETTER_AUTH_SECRET (openssl rand) et les mots de passe des bases (plus de defaut “password” en exploitation) ; les cles API (Resend, Mistral) sont chiffrees dans secrets/*.enc (openssl aes-256-cbc, pbkdf2), dechiffrees a la volee ; .env hors versionnement.
  • Rappel du socle RGPD herite des MSPR precedentes : datasets sources anonymises, table users supprimee (migration V7), pas d’identifiant commun ni de PII dans les donnees chargees.
  • Redaction du document de gestion de projet.

Livrables. Jeu de documents MSPR-Deploy/ a jour, mecanisme de secrets en place, document de gestion de projet. Detail technique : fiche Securite et fiche Deploiement.

6. Gestion des risques

Approche simple : identifier les risques concrets rencontres et la parade mise en place.

Risque Impact Parade
Ollama (gemma3:4b) lourd en CPU / RAM Stack lente ou instable sur materiel modeste Configuration performance qui omet ai-nutrition + ollama par defaut (repli sur la matrice statique) et applique des limites CPU / RAM ; alerte ConteneurCpuEleve.
Dependance a internet (pull d’images, modele Ollama, emails Resend, API Mistral) Demo impossible hors-ligne Configuration offline : Ollama local, AUTH_OFFLINE=true (sans Resend), prerequis telecharges une fois avec internet.
Premier pull tres long (Ollama ~3 Go) Demarrage initial lent Documente dans le README.md (depannage), suivi via docker compose logs -f ollama.
Gestion des secrets Fuite de cle / mot de passe par defaut Secrets generes par bootstrap.sh (openssl rand), cles API chiffrees dans secrets/*.enc (aes-256-cbc), .env hors versionnement, bases bindees sur 127.0.0.1.
Metriques applicatives invisibles Supervision incomplete Documente : l’instrumentation vit dans le code source, donc visible seulement apres rebuild (mode dev) ou republication des images GHCR (mode prod).
Conflit de ports sur la machine hote Echec du up Liste des ports requis dans le README.md, remappage de la partie hote possible dans le compose.

7. Elements concrets a citer au jury

7.1 La definition du fini

Un sprint est termine quand la stack demarre et le nouvel increment est demontrable. C’est un critere binaire et verifiable, pas une estimation. Exemples : fin du sprint A, le dashboard Grafana provisionne s’affiche avec les cibles UP ; fin du sprint B, on demarre la stack en configuration offline sans internet ; fin du sprint C, les 8 chaines CI publient sur GHCR.

7.2 Une revue de sprint type

Deroulement concret de la demonstration de l’increment :

# 1. Lancer la stack avec l'overlay du sprint (ou bootstrap.sh)
docker compose up -d

# 2. Verifier que tout est vivant
docker compose ps          # conteneurs Up, healthchecks au vert

# 3. Verifier les endpoints de sante des services

# 4. Ouvrir le dashboard Grafana "MSPR HealthAI - Vue stack"
#    (cibles UP, CPU / memoire par conteneur)

# 5. Montrer le dernier run GitHub Actions au vert sur le depot concerne

Chiffres du smoke test final (10/06/2026, rapport-tests-qualite.md) qui prouvent que la definition du fini tient : stack stable en 84 secondes (exigence du cahier des charges : moins de 10 minutes), 20 conteneurs actifs, 10 cibles Prometheus sur 10 UP, 3 regles d’alerte chargees, logs de 23 conteneurs dans Loki, 4 dashboards Grafana provisionnes.

7.3 Frictions reelles rencontrees

Deux exemples sortis des retrospectives, a citer tels quels :

  • Premier pull d’Ollama tres long (~3 Go) : demarrage initial lent. Ajustement : documentation dans le README.md (section depannage), suivi via docker compose logs -f ollama, et configuration offline qui suppose les prerequis telecharges une fois avec internet.
  • Metriques applicatives visibles seulement apres rebuild : l’instrumentation (Actuator, instrumentator FastAPI, @hono/prometheus) vit dans le code source des services, donc elle n’apparait qu’apres rebuild des images en dev ou republication sur GHCR en prod. Ajustement : limite documentee dans le tableau des risques.

8. Questions probables du jury

Q1. Pourquoi pas de daily formel, et comment vous synchronisiez-vous ?

Vu la taille de l’equipe, un daily quotidien formel aurait coute plus qu’il n’apporte. La synchronisation est informelle et asynchrone : commentaires d’issues, etat des pull requests et des runs Actions. Chacun voit en permanence ou en sont les autres sans reunion : une PR ouverte = travail en cours, un run vert = lot pret a merger, une carte en Done = increment verifie. L’intention du daily (visibilite sur l’avancement et les blocages) est conservee, le rituel quotidien ne l’est pas.

Q2. Pourquoi des sprints thematiques (A/B/C/D) plutot que des iterations calendaires strictes ?

Le perimetre MSPR3 se decoupe naturellement en blocs de capacites (observabilite, configurations, CI/CD, documentation et securite) qui correspondent d’ailleurs aux livrables attendus. Un sprint = un theme = un increment demontrable sur la cible de deploiement. Des iterations calendaires strictes auraient force a couper artificiellement ces blocs. La fin d’un sprint est definie par sa definition du fini (la stack demarre, l’increment est demontrable), pas par une date.

Q3. Comment etait definie la fin d’un sprint (definition du fini) ?

Deux criteres, fixes en planification de sprint : la stack demarre et le nouvel increment est demontrable. C’est verifiable objectivement (commande docker compose ps, demonstration en revue), donc pas de debat sur “fini ou pas fini”. Cette definition est orientee vers la cible du projet : un deploiement local orchestre par Docker Compose qui sert de point d’evaluation.

Q4. Comment se passait une revue de sprint concretement ?

Demonstration de l’increment sur la stack locale : lancement de l’overlay concerne, docker compose ps (conteneurs Up et healthy), verification des endpoints de sante, dashboard Grafana, et run CI vert sur les depots touches. Exemple sprint A : on lance docker-compose.monitoring.yml, on montre Prometheus avec ses cibles UP et le dashboard “MSPR HealthAI - Vue stack” provisionne. Exemple sprint B : on demarre la configuration offline et on montre que l’authentification fonctionne sans Resend.

Q5. Quels ont ete les principaux points de friction et qu’avez-vous ajuste ?

Deux frictions documentees dans les retrospectives :

  1. Duree du premier pull d’Ollama (~3 Go) : demarrage initial lent. Ajustements : section depannage du README.md, suivi par docker compose logs -f ollama, configuration offline qui prepare les prerequis une fois pour toutes.
  2. Instrumentation visible seulement apres rebuild des images : les metriques applicatives vivent dans le code source des services. Ajustement : limite documentee (rebuild en mode dev, republication GHCR en mode prod).

S’y ajoute l’incident e2e du Front (specs Cypress en echec), qui a valide le garde-fou CI : image non publiee tant que les tests ne passaient pas.

Q6. Comment mesuriez-vous l’avancement sans outil de velocite ?

Trois indicateurs concrets remplacent les points de velocite :

  1. Le Kanban : la position des cartes [MSPR3][Sprint X] (Backlog a Done) donne l’avancement du sprint d’un coup d’oeil.
  2. Les runs GitHub Actions : l’etat des 8 chaines fait office d’indicateur de qualite continu ; un run rouge = un lot non livrable.
  3. Les increments demontrables : a tout moment, on peut demarrer la stack et constater ce qui fonctionne. L’avancement se mesure en capacites demontrables, pas en estimation.

Q7. Comment s’articulait le travail de l’application mobile portee par un autre membre ?

L’application mobile est prise en charge par un autre membre de l’equipe, avec son propre rythme de travail : les sprints A a D ne la concernent pas. Elle est documentee a part (livrable 06-application-mobile/, voir fiche Application mobile) et consomme les services de la plateforme tels qu’exposes. Ce decoupage evite de coupler le rythme d’industrialisation de la plateforme au rythme de developpement mobile.

Q8. Ou est le tableau Kanban et comment est-il organise ?

C’est un GitHub Project commun a tous les depots de la plateforme : projet “MSPR” de l’organisation whitefoxxyt. Colonnes Backlog / Ready / In progress / In review / Done. Les taches de la MSPR3 y sont regroupees par sprint avec le prefixe [MSPR3][Sprint A..D]. Une capture du tableau est fournie dans les livrables (kanban-github-project.png). Le projet est commun aux depots parce que la plateforme est multi-repos : un tableau par depot aurait disperse le suivi.

Q9. Quels risques aviez-vous identifies et lesquels se sont materialises ?

Six risques au tableau (voir section 6) : Ollama lourd en CPU / RAM, dependance a internet, premier pull tres long, gestion des secrets, metriques applicatives invisibles, conflits de ports. L’approche est volontairement concrete : ce sont des risques rencontres, chacun avec sa parade en place. Le pull Ollama et les metriques visibles seulement apres rebuild se sont materialises en cours de projet et ont ete traites par configuration (offline, performance) et documentation. Cote qualite, l’echec e2e du Front a montre que le garde-fou de publication conditionnee fonctionnait reellement.

Q10. Qu’auriez-vous fait differemment ?

Trois pistes honnetes, tirees des limites constatees :

  1. Instrumenter les services plus tot : la friction “metriques visibles apres rebuild” vient du fait que l’instrumentation vit dans le code source ; la poser des le debut aurait lisse le sprint A.
  2. Importer tous les depots dans SonarCloud des le sprint C : au releve du 10/06/2026, seuls AI-Nutrition, Reco-Fitness et MongoDB sont importes ; API, Auth, ETL, Front et BDD restent a importer (operation cote interface SonarCloud, sans configuration dans les depots).
  3. Documenter les prerequis lourds en amont : le pull Ollama de ~3 Go a ete documente apres coup dans le depannage ; l’annoncer des le depart aurait evite des demarrages initiaux percus comme bloques.

Q11. Si le projet continuait, quel serait le sprint E ?

Des pistes realistes dans la continuite des sprints existants :

  • Import SonarCloud des depots restants (API, Auth, ETL, Front, BDD) pour une couverture d’analyse statique complete de l’organisation.
  • Scan d’images de conteneurs dans les chaines CI, en complement du durcissement deja en place (non-root, no-new-privileges, healthchecks).
  • Notifications Alertmanager : les 3 regles d’alerte existent et sont chargees ; il reste a router les alertes vers un canal de notification.
  • Externalisation des sauvegardes : backup.sh produit des dumps horodates locaux ; les pousser vers un stockage externe completerait la resilience.

Q12. En quoi GitHub seul suffit-il comme outillage projet a cette echelle ?

Tout le cycle tient dans un seul outil, sans double saisie ni synchronisation entre un outil de ticketing et le code :

  • Issues = backlog, decoupage par sprint ;
  • Projects = Kanban commun multi-depots ;
  • Pull requests = revue de code et point de validation (merge apres tests verts) ;
  • Actions = CI/CD et indicateur de qualite continu ;
  • GHCR = registre d’images, source du mode prod.

A l’echelle d’une equipe de 4 sur une plateforme multi-depots, un outil de gestion de projet separe ajouterait de la friction sans gain : les artefacts de pilotage (cartes, PR, runs) sont deja la ou le travail se fait. Limite assumee : pas de gestion de capacite ni de velocite, acceptable car les increments sont courts et demontrables (voir Q6).

Fiche de revision : Deploiement et orchestration

Support de revision pour la soutenance MSPR3 (TPRE601). Objectif : savoir defendre la conteneurisation et l’orchestration de la plateforme HealthAI Coach : le depot MSPR-Deploy comme point d’entree unique, le script bootstrap.sh, les deux modes prod/dev, le compose de base (11 services), les reseaux, les dependances de demarrage et la gestion des secrets.

0. Vocabulaire a connaitre avant de lire

Les 10 termes qui reviennent partout dans cette fiche.

Terme Definition en une phrase
Orchestration Coordination automatisee du cycle de vie d’un ensemble de conteneurs : ordre de demarrage, reseaux, volumes, politique de redemarrage.
Docker Compose Outil d’orchestration declaratif mono-machine : toute la stack est decrite dans un fichier YAML versionne, lancee avec docker compose up.
GHCR GitHub Container Registry. Les 8 images applicatives y sont publiees : ghcr.io/whitefoxxyt/mspr-<service>:latest.
Ancre YAML Mecanisme natif YAML (&nom definit, *nom reference, <<: fusionne) qui factorise un bloc de configuration commun a plusieurs services.
Healthcheck Commande executee periodiquement par Docker dans le conteneur ; son code retour determine l’etat healthy / unhealthy.
depends_on (condition) Declaration d’ordre de demarrage entre services, avec 3 conditions possibles : service_started, service_healthy, service_completed_successfully.
Conteneur one-shot Conteneur qui execute une tache puis se termine (restart: "no"). Ici : auth-migrate, qui applique les migrations Drizzle.
Reseau bridge Reseau virtuel Docker avec DNS integre : les conteneurs se joignent par nom de service ou par container_name, jamais par IP.
Volume nomme Espace de stockage persistant gere par Docker ; survit a la destruction des conteneurs (mais pas a docker compose down -v).
JWT HS512 Jeton signe en HMAC-SHA512 avec un secret symetrique partage (BETTER_AUTH_SECRET), validable localement par chaque service.

1. TL;DR

MSPR-Deploy est le depot d’orchestration de la plateforme : le point d’entree unique exige par le sujet MSPR3 (mise en production entierement scriptee). Une seule commande, ./bootstrap.sh, verifie les prerequis, prepare le .env, genere les secrets, dechiffre les cles API, puis lance les 11 conteneurs via Docker Compose.

  • Point d’entree : ./bootstrap.sh. Mode prod par defaut (pull des images GHCR), mode dev avec --dev (clone des 8 depots sources + build local), option --no-up (preparation sans lancement).
  • 11 services : db, auth-db, auth-migrate, auth, api, etl, ai-nutrition, ollama, mongo, reco-fitness, front.
  • 2 reseaux bridge : mspr_data_network (principal, nomme) + ai_internal (isole, reserve a Ollama).
  • 5 volumes nommes : postgres_data, auth_db_data, etl_data (partage etl/api), ollama_data, mongo_data.
  • Exigence du sujet : stack operationnelle en moins de 10 minutes. Mesure reelle : stack stable en 84 secondes (10/06/2026, images et modele deja telecharges). Premier run : 5 a 10 min (pull des images + telechargement du modele Ollama gemma3:4b, ~3 Go).
  • Secrets : BETTER_AUTH_SECRET genere (openssl rand -base64 64), mots de passe BDD generes (24 caracteres alphanumeriques, plus de defaut “password” en exploitation), cles API Resend/Mistral chiffrees en AES-256-CBC (PBKDF2, 100000 iterations) et dechiffrees a la volee.
  • Durcissement : no-new-privileges + rotation des logs sur tous les services via ancres YAML, ports des bases bindes sur 127.0.0.1, Ollama sans aucun port expose. Detail dans la fiche Securite.
  • Bonus Kubernetes mono-noeud du sujet : non realise, choix assume (Docker Compose suffit pour la cible “poste local de demonstration”, orchestration locale autorisee par le sujet).

Les overlays (monitoring, offline, performance, traefik, vision, watchtower, gpu) sont traites dans la fiche Configs et resilience et la fiche Observabilite. La construction des images GHCR par les CI des depots sources est traitee dans la fiche CI/CD et qualite.

4. bootstrap.sh : le deploiement en une commande

Exigence du sujet MSPR3 : un deploiement entierement scripte, stack operationnelle en moins de 10 minutes. Reponse : un script Bash unique de ~220 lignes, idempotent, qui enchaine 5 etapes.

4.1 Une commande, deux modes

./bootstrap.sh           # mode prod (defaut) : pull GHCR + up
./bootstrap.sh --dev     # mode dev : clone des 8 depots + build local
./bootstrap.sh --no-up   # prepare l'environnement sans lancer la stack
  • Mode prod : aucune source clonee, les images viennent de GHCR (ghcr.io/whitefoxxyt/mspr-<service>:latest). C’est le mode evaluation/demo : reproductible, l’image executee est exactement celle produite par la CI.
  • Mode dev : clone les 8 depots whitefoxxyt dans sources/ sur leurs branches actives (main, master ou dev selon le depot), puis build local via docker-compose.dev.yml (up -d --build).
  • --no-up sert a inspecter ou modifier le .env avant le premier lancement.

4.2 Verification des prerequis

for cmd in docker openssl; do
  command -v "$cmd" >/dev/null || fail "Commande requise absente : $cmd"
done
if ! docker compose version >/dev/null 2>&1; then
  fail "Docker Compose v2 introuvable. Mettre a jour Docker."
fi
if ! docker info >/dev/null 2>&1; then
  fail "Docker daemon non accessible. Verifier que Docker tourne."
fi

Quatre checks : binaire docker, binaire openssl, plugin Compose v2 (la syntaxe depends_on avec conditions et les ancres utilisees l’exigent), et daemon Docker accessible (docker info echoue si le service est arrete ou si l’utilisateur n’a pas les droits). Echec = message explicite + exit 1, pas d’erreur cryptique a mi-parcours.

4.3 Preparation idempotente du .env

if [[ ! -f "$ENV_FILE" ]]; then
  cp "$ROOT_DIR/.env.example" "$ENV_FILE"
  log ".env cree depuis .env.example"
fi

Le .env n’est cree que s’il n’existe pas. Ensuite, chaque variable sensible n’est renseignee que si elle est absente ou vide (fonction ensure_env_value, voir section 6.2). Consequence : relancer ./bootstrap.sh sur un environnement existant ne modifie rien, le script converge au lieu d’ecraser.

4.4 Generation des secrets

Trois valeurs sont generees au premier lancement si absentes :

Variable Generation Format
BETTER_AUTH_SECRET openssl rand -base64 64 \| tr -d '\n' 64 octets aleatoires en base64 (minimum requis pour HS512)
DB_PASSWORD gen_password 24 caracteres alphanumeriques
AUTH_DB_PASSWORD gen_password 24 caracteres alphanumeriques

Le format alphanumerique des mots de passe est volontaire : ils sont interpoles dans des chaines postgres://user:pass@host, un caractere special casserait l’URL (voir section 6.2). Il n’y a plus de defaut “password” en exploitation : la voie officielle de deploiement passe par bootstrap, qui garantit des valeurs fortes.

4.5 Dechiffrement des cles API chiffrees

Les cles tierces (Resend pour les emails, Mistral pour le LLM primaire) ne sont jamais versionnees en clair. Elles sont chiffrees dans secrets/resend.enc et secrets/mistral.enc (AES-256-CBC, sel, PBKDF2 100000 iterations). Le script demande la passphrase en interactif (read -rs, rien ne s’affiche) ou la lit dans la variable MSPR_PASS :

MSPR_PASS="<passphrase fournie par l'equipe>" ./bootstrap.sh

Le resultat du dechiffrement est valide par format (une cle Resend commence par re_) : une passphrase fausse produit du bruit, detecte immediatement au lieu d’echouer plus tard dans le service auth. Detail du chiffrement dans la fiche Securite. Si les .enc sont absents, le script logue comment renseigner les cles a la main (et ai-nutrition retombe sur Ollama si MISTRAL_API_KEY reste vide).

4.6 Lancement et temps de demarrage

if [[ "$MODE" == "dev" ]]; then
  COMPOSE_FILE="$ROOT_DIR/docker-compose.dev.yml"
  UP_FLAGS=(-d --build)
else
  COMPOSE_FILE="$ROOT_DIR/docker-compose.yml"
  UP_FLAGS=(-d)
fi
# ...
docker compose -f "$COMPOSE_FILE" --env-file "$ENV_FILE" up "${UP_FLAGS[@]}"

Chiffres a connaitre :

  • Premier run : 5 a 10 minutes (pull des 8 images + telechargement du modele Ollama gemma3:4b, ~3 Go). Le script previent : “Au premier run, comptez 5 a 10 min (pull/build + telechargement Ollama).”
  • Runs suivants : stack stable en 84 secondes (mesure du 10/06/2026, images et modele deja en cache local). Tres en dessous de l’exigence “moins de 10 minutes” du sujet.
  • Le modele Ollama est persiste dans le volume ollama_data : il n’est telecharge qu’une fois, les down/up suivants le retrouvent.

En sortie, le script affiche les commandes de suivi (ps, logs -f) et les URLs d’acces (front http://localhost:5173, Swagger http://localhost:8080/api/swagger-ui.html).

5. Points techniques importants

5.1 Ancres YAML : durcissement et rotation des logs sur tous les services

Le compose de base ouvre sur deux ancres (x-logging, x-hardening) fusionnees dans chacun des 11 services via <<: *hardening (code en section 6.1). Effet :

  • no-new-privileges:true : un processus dans le conteneur ne peut pas elever ses privileges (setuid, sudo).
  • Rotation des logs json-file : 10 Mo max par fichier, 3 fichiers max, soit 30 Mo de logs par conteneur au maximum. Sans cela, un service verbeux peut saturer le disque en exploitation continue.

Un seul endroit a modifier pour durcir toute la stack : c’est l’argument cle face au jury (factorisation = pas d’oubli possible sur un nouveau service). Complement dans la fiche Securite.

5.2 Les trois conditions depends_on

Condition Garantie Utilisee pour
service_started Le conteneur est lance (aucune garantie de readiness) ollama (pour ai-nutrition), auth (pour reco-fitness), front (syntaxe courte)
service_healthy Le healthcheck passe db, auth-db, mongo (pour tous leurs consommateurs)
service_completed_successfully Le conteneur s’est termine avec exit 0 auth-migrate (pour auth)

Pourquoi ollama n’est qu’en service_started : au premier run, son entrypoint telecharge un modele de ~3 Go ; un healthcheck “modele pret” bloquerait ai-nutrition (et la perception de la stack entiere) pendant plusieurs minutes. ai-nutrition tolere l’indisponibilite temporaire d’Ollama : Mistral est le LLM primaire, Ollama le fallback.

Limite honnete : depends_on n’agit qu’au demarrage. Si une base tombe en cours de vie, c’est restart: unless-stopped et la logique de reconnexion applicative qui prennent le relais (cf. fiche Configs et resilience).

5.3 auth-migrate : les migrations en conteneur one-shot

auth-migrate reutilise l’image de auth mais avec command: sh -c "bun run db:migrate" et restart: "no". Il attend auth-db healthy, applique les migrations Drizzle, puis se termine. auth ne demarre que sur service_completed_successfully.

Benefices : les migrations sont jouees exactement une fois par deploiement (pas de course si on scale auth), et un echec de migration est un echec visible du deploiement (auth ne demarre pas) plutot qu’un service qui boote sur un schema bancal.

5.4 Isolation reseau d’Ollama

ollama est le seul service du reseau ai_internal (avec ai-nutrition, qui est rattache aux deux reseaux). Il n’a aucune section ports : impossible de le joindre depuis l’hote ou depuis les autres conteneurs. L’API Ollama n’a pas d’authentification par defaut ; l’isolation reseau est la contre-mesure. ai-nutrition le joint via OLLAMA_HOST: http://ollama:11434 (DNS Docker du reseau ai_internal).

5.5 Ports des bases bindes sur 127.0.0.1

    ports:
      - "127.0.0.1:5434:5432"   # db metier
      - "127.0.0.1:5433:5432"   # auth-db
      - "127.0.0.1:27018:27017" # mongo

Les bases restent inspectables depuis l’hote (psql, mongosh) mais sont invisibles depuis le reseau. Important car Docker, par defaut, publie sur 0.0.0.0 et ses regles iptables court-circuitent les firewalls applicatifs type ufw. Les ports decales (5434, 5433, 27018) evitent les conflits avec des instances locales deja installees. Developpe en Q12.

5.6 Le volume etl_data partage (producteur / consommateur en lecture seule)

L’etl ecrit ses sorties (rejets, samples, exports CSV) dans etl_data:/app/data. L’api monte le meme volume en lecture seule : etl_data:/app/etl-data:ro. Les endpoints de qualite de donnees et d’export de l’API lisent ces fichiers sans pouvoir les corrompre. Le :ro est une garantie d’architecture : le producteur est unique, le consommateur ne peut pas ecrire.

5.7 SCORING_AUTOTRAIN : le modele de scoring entraine au demarrage

      # L'image n'embarque pas scoring_model.pkl (gitignore) : entrainement au
      # demarrage depuis le catalogue PG, requis pour le scoring hybride premium.
      SCORING_AUTOTRAIN: "1"

L’image mspr-reco-fitness n’embarque pas le pickle du modele de scoring (gitignore : on ne versionne pas de binaire entraine). Au demarrage, le service reentraine le modele depuis le catalogue PostgreSQL. Tradeoff assume : quelques secondes de demarrage en plus contre une image reproductible sans artefact binaire.

5.8 Flux d’authentification JWT

sequenceDiagram
    participant C as Client (front)
    participant A as auth (:3000)
    participant S as Service metier (api / ai-nutrition / reco-fitness)

    C->>A: POST /api/auth/sign-in (email + mot de passe)
    A-->>C: JWT signe HS512 (BETTER_AUTH_SECRET)
    C->>S: requete + Authorization: Bearer <jwt>
    S->>S: validation locale de la signature (meme secret)
    S-->>C: 200 ou 401
  • auth (better-auth) est le seul a gerer des comptes. Les services metier valident le JWT localement avec le BETTER_AUTH_SECRET partage (injecte par variable d’environnement dans auth, api, ai-nutrition, reco-fitness) : pas d’aller-retour reseau vers auth a chaque requete, pas de point de defaillance au moment de la validation.
  • HS512 = HMAC symetrique : tout detenteur du secret peut emettre des jetons, d’ou un secret de 64 octets genere et jamais versionne. L’alternative asymetrique (RS256 + JWKS) est l’evolution naturelle si un service tiers devait valider sans pouvoir signer. Voir fiche Securite.
  • ai-nutrition et reco-fitness connaissent aussi AUTH_API_URL: http://mspr-auth-service:3000 pour les appels internes qui necessitent le service auth.

5.9 Le bonus Kubernetes : non realise, choix assume

Le sujet proposait en bonus un deploiement Kubernetes mono-noeud. Non realise, et c’est un choix : la cible du livrable est un poste local de demonstration, l’orchestration locale est explicitement autorisee par le sujet, et Docker Compose couvre tout le besoin (dependances, healthchecks, reseaux, volumes, redemarrage). Le temps a ete investi sur le monitoring, la securite et la resilience (fiches dediees). La reponse complete pour le jury est en Q1.

6. Code essentiel a savoir expliquer au jury

6.1 Les ancres de durcissement (docker-compose.yml)

# Reglages communs de durcissement (mise en production MSPR3) :
# - no-new-privileges : empeche l'elevation de privileges dans le conteneur
# - rotation des logs json-file : evite la saturation disque en exploitation
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

x-hardening: &hardening
  security_opt:
    - no-new-privileges:true
  logging: *default-logging

services:
  db:
    <<: *hardening
    image: ghcr.io/whitefoxxyt/mspr-db:latest

Ce qu’il faut savoir dire :

  • x- est le prefixe d’extension Compose : ces blocs ne sont pas des services, juste des fragments reutilisables.
  • &hardening definit l’ancre, <<: *hardening la fusionne dans chaque service : une seule definition, 11 applications, aucun service oublie.
  • no-new-privileges:true bloque l’elevation de privileges (binaire setuid, escalade apres compromission d’un process).
  • La rotation 10m x 3 borne les logs a 30 Mo par conteneur : exigence d’exploitation (la stack tourne en continu), pas de saturation disque silencieuse.
  • L’ancre *default-logging est elle-meme referencee dans x-hardening : composition d’ancres.

6.2 Generation des mots de passe (bootstrap.sh)

# Set-or-append d'une variable dans .env, uniquement si elle est absente ou vide.
ensure_env_value() {
  local var="$1" value="$2" current
  current=$(grep -E "^${var}=" "$ENV_FILE" | head -1 | cut -d= -f2- || true)
  if [[ -z "$current" ]]; then
    # ... reecriture du .env via awk (remplace la ligne ou l'ajoute en fin) ...
    log "$var genere"
  fi
}

# Mot de passe alphanumerique (URL-safe pour les chaines postgres://...).
gen_password() { openssl rand -base64 32 | tr -dc 'A-Za-z0-9' | head -c 24; }

ensure_env_value DB_PASSWORD "$(gen_password)"
ensure_env_value AUTH_DB_PASSWORD "$(gen_password)"

Ce qu’il faut savoir dire :

  • gen_password : 32 octets aleatoires (openssl), filtres en alphanumerique pur, tronques a 24 caracteres. Alphanumerique car le mot de passe est interpole dans DATABASE_URL: postgres://user:pass@host : un / ou un @ casserait le parsing de l’URL.
  • ensure_env_value lit la valeur courante avant d’ecrire : si la variable est deja renseignee, no-op. C’est ce qui rend bootstrap relancable sans risque.
  • Plus de defaut “password” en exploitation : avant MSPR3, les composes utilisaient le defaut ${DB_PASSWORD:-password} tel quel. La voie officielle passe desormais par bootstrap, qui force une valeur generee.
  • Limite a connaitre (commentee dans le script) : PostgreSQL n’applique le mot de passe qu’a l’initialisation du volume. Changer DB_PASSWORD sur un volume deja initialise impose un reset (down -v).

6.3 Generation du BETTER_AUTH_SECRET (bootstrap.sh)

current_secret=$(grep -E '^BETTER_AUTH_SECRET=' "$ENV_FILE" | head -1 | cut -d= -f2- || true)
if [[ -z "$current_secret" ]]; then
  new_secret=$(openssl rand -base64 64 | tr -d '\n')
  tmp=$(mktemp)
  awk -v secret="$new_secret" '
    BEGIN { set = 0 }
    /^BETTER_AUTH_SECRET=/ { print "BETTER_AUTH_SECRET=" secret; set = 1; next }
    { print }
    END { if (!set) print "BETTER_AUTH_SECRET=" secret }
  ' "$ENV_FILE" > "$tmp"
  mv "$tmp" "$ENV_FILE"
  log "BETTER_AUTH_SECRET genere"
fi

Ce qu’il faut savoir dire :

  • 64 octets aleatoires : le minimum documente dans .env.example pour HS512 (taille de sortie de SHA-512).
  • tr -d '\n' : openssl plie le base64 sur plusieurs lignes au-dela d’une certaine longueur ; le secret doit tenir sur une ligne du .env.
  • Le pattern awk “set-or-append” : remplace la ligne si elle existe, l’ajoute en fin sinon. Ecrit dans un fichier temporaire puis mv : pas de .env a moitie ecrit en cas d’interruption.
  • Genere uniquement si vide : un environnement existant garde son secret (sinon tous les JWT emis seraient invalides au redemarrage).
  • Ce secret est ensuite injecte dans 4 services : auth (signature) et api / ai-nutrition / reco-fitness (validation).

6.4 Dechiffrement des cles API avec validation de format (bootstrap.sh)

if [[ -n "${MSPR_PASS:-}" ]]; then
  pass="$MSPR_PASS"
else
  printf '\033[1;34m[bootstrap]\033[0m Passphrase pour dechiffrer les cles API (Resend + Mistral) : '
  read -rs pass
  echo
fi

if decrypted=$(openssl enc -aes-256-cbc -d -pbkdf2 -iter 100000 -salt -pass pass:"$pass" -in "$RESEND_ENC" 2>/dev/null) \
    && [[ "$decrypted" =~ ^re_ ]]; then
  # ... injection de RESEND_API_KEY dans .env via awk ...
  log "RESEND_API_KEY dechiffree depuis secrets/resend.enc"
else
  fail "Dechiffrement Resend echoue (passphrase incorrecte ?). Relancez ou renseignez RESEND_API_KEY a la main."
fi
unset decrypted

Ce qu’il faut savoir dire :

  • Les cles tierces sont chiffrees dans le depot (secrets/*.enc), jamais en clair : le depot peut etre public sans fuiter de secret.
  • aes-256-cbc + -salt + -pbkdf2 -iter 100000 : la cle de chiffrement est derivee de la passphrase avec 100000 iterations PBKDF2, ce qui ralentit massivement le brute-force.
  • La validation de format (^re_ pour Resend, ^[A-Za-z0-9]{20,}$ pour Mistral) est cruciale : avec CBC, une mauvaise passphrase peut produire une sortie “valide” mais aleatoire. Sans ce check, l’erreur n’apparaitrait que bien plus tard dans le service auth.
  • read -rs ne fait pas echo de la passphrase ; MSPR_PASS permet le mode non-interactif (CI, demo) ; unset pass / unset decrypted limitent la duree de vie en memoire shell.
  • Echec = fail avec consigne de repli (renseigner la cle a la main dans .env).

6.5 auth-migrate et auth : le one-shot et ses conditions (docker-compose.yml)

  auth-migrate:
    <<: *hardening
    image: ghcr.io/whitefoxxyt/mspr-auth:latest
    container_name: mspr-auth-migrate
    command: sh -c "bun run db:migrate"
    depends_on:
      auth-db:
        condition: service_healthy
    restart: "no"

  auth:
    <<: *hardening
    image: ghcr.io/whitefoxxyt/mspr-auth:latest
    depends_on:
      auth-db:
        condition: service_healthy
      auth-migrate:
        condition: service_completed_successfully

Ce qu’il faut savoir dire :

  • Meme image que auth, seule la command change : aucune image supplementaire a construire ou maintenir, l’outillage Drizzle est deja dans l’image.
  • restart: "no" : le conteneur execute bun run db:migrate puis se termine. C’est la definition d’un one-shot ; les autres services sont en unless-stopped.
  • La chaine de demarrage est : auth-db healthy, puis auth-migrate jusqu’a exit 0, puis auth. Le schema est garanti a jour avant que le service auth n’accepte une requete.
  • Si la migration echoue (exit != 0), auth ne demarre pas : echec franc et visible dans docker compose ps, pas de service qui tourne sur un schema invalide.

6.6 Ollama isole et ai-nutrition double reseau (docker-compose.yml)

  ollama:
    <<: *hardening
    image: ollama/ollama:latest
    container_name: mspr-ollama
    volumes:
      - ollama_data:/root/.ollama
    entrypoint: ["/bin/sh", "-c", "ollama serve & sleep 5 && ollama pull gemma3:4b && wait"]
    networks:
      - ai_internal

  ai-nutrition:
    environment:
      OLLAMA_HOST: http://ollama:11434
      # ...
    networks:
      - mspr_data_network
      - ai_internal

Ce qu’il faut savoir dire :

  • L’entrypoint enchaine : ollama serve & (serveur en arriere-plan), sleep 5 (laisser l’API ecouter), ollama pull gemma3:4b (telechargement du modele, ~3 Go au premier run, no-op ensuite grace au volume ollama_data), wait (raccroche le processus serveur en avant-plan pour que le conteneur vive).
  • Aucune section ports : Ollama n’est joignable ni depuis l’hote ni depuis le reseau local. Son API n’a pas d’authentification, l’isolation reseau est la protection.
  • ai_internal est un second reseau bridge : seul ai-nutrition, rattache aux deux reseaux, peut atteindre http://ollama:11434 (resolution DNS du nom de service).
  • Le volume ollama_data est la cle du demarrage rapide des runs suivants : le modele n’est telecharge qu’une fois.

6.7 Healthcheck et bind localhost de la base metier (docker-compose.yml)

  db:
    <<: *hardening
    image: ghcr.io/whitefoxxyt/mspr-db:latest
    container_name: mspr-healthai-db
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U healthai_user -d healthai"]
      interval: 10s
      timeout: 5s
      retries: 5
    ports:
      - "127.0.0.1:5434:5432"

Ce qu’il faut savoir dire :

  • pg_isready teste la readiness reelle (PostgreSQL accepte les connexions), pas juste “le process tourne”. Mongo a l’equivalent : mongosh --eval "db.adminCommand('ping').ok".
  • Cadence : test toutes les 10 s, timeout 5 s, 5 echecs avant unhealthy. C’est ce healthcheck que consomment les depends_on: condition: service_healthy de api, etl, ai-nutrition et reco-fitness.
  • 127.0.0.1:5434:5432 : publication sur la boucle locale uniquement. Depuis l’hote : psql -h 127.0.0.1 -p 5434. Depuis le reseau : rien.
  • Le conteneur garde son container_name: mspr-healthai-db, utilise comme DB_HOST par tous les services consommateurs (DNS Docker).

6.8 Clone des sources en mode dev (bootstrap.sh)

# Mapping : nom_local | repo_distant_whitefoxxyt | branche_active
REPOS=(
  "MSPR-DB|MSPR-HealthAI-Coach-BDD|main"
  "MSPR-AUTH|MSPR-HealthAI-Coach-Auth|main"
  # ... 6 autres depots (API, ETL, FRONT, AI-Nutrition, Reco-Fitness, MongoDB) ...

if [[ -d "$target/.git" ]]; then
  log "$local_name : fetch + checkout $branch"
  git -C "$target" fetch --quiet origin
  git -C "$target" checkout --quiet "$branch"
  git -C "$target" pull --quiet --ff-only origin "$branch"
else

  git clone --quiet --branch "$branch" "$url" "$target"

Ce qu’il faut savoir dire :

  • Le mapping nom_local|repo_distant|branche encode le fait que les depots n’ont pas tous la meme branche active (main, master, dev pour le front) : le script clone la bonne branche sans intervention.
  • Logique clone-or-update : premier run = clone, runs suivants = fetch + checkout + pull --ff-only (le fast-forward only refuse d’ecraser un travail local divergent).
  • Les sources atterrissent dans sources/, repertoire non versionne, consomme par les build: context: ./sources/<repo> de docker-compose.dev.yml.
  • Ce sont les memes depots qui alimentent les images GHCR via leur CI : parite prod/dev par construction (fiche CI/CD et qualite).

8. Questions probables du jury

Q1. Pourquoi Docker Compose plutot que Kubernetes ? Le sujet proposait un bonus K8s mono-noeud.

Le bonus n’a pas ete realise, et c’est un choix assume. La cible du livrable est un poste local de demonstration ; le sujet autorise explicitement l’orchestration locale. Docker Compose couvre tout le besoin reel : ordre de demarrage (conditions depends_on), sante (healthcheck), isolation (2 reseaux), persistence (5 volumes), redemarrage (unless-stopped), durcissement (ancres). Kubernetes apporterait l’auto-healing multi-noeud, le scaling horizontal et les rolling updates natifs : surdimensionne pour un hote unique et un evaluateur. Un minikube ajouterait une VM, une registry locale et des manifests pour 11 services, sans gain fonctionnel pour la demo. Le temps a ete investi ailleurs : monitoring, securite, resilience. On sait neanmoins decrire la migration : chaque service devient un Deployment + Service, les volumes des PVC, le .env des Secrets/ConfigMaps, les healthchecks des liveness/readiness probes, et depends_on disparait (remplace par les probes et les retries applicatifs).

Q2. Comment garantissez-vous le demarrage en moins de 10 minutes ?

Par la mesure et par la conception. Mesure : le 10/06/2026, la stack complete est stable en 84 secondes (images et modele deja telecharges), tres en dessous de l’exigence. Le premier run, lui, prend 5 a 10 minutes : pull des 8 images GHCR + telechargement du modele gemma3:4b (~3 Go), et le script l’annonce. Conception : images prebuildees sur GHCR (aucun build local en mode prod), modele Ollama persiste dans ollama_data (telecharge une seule fois), healthchecks courts (interval 10 s) qui debloquent les dependances des que les bases sont pretes, et demarrage en parallele de tout ce qui ne depend pas des bases.

Q3. Pourquoi deux modes prod et dev ?

Deux usages distincts. Prod : evaluation et demo. Zero clone, pull GHCR : l’image executee est exactement celle produite par la CI du depot source, reproductible sur n’importe quel poste. Dev : developpement. Les 8 depots sont clones dans sources/ sur leurs branches actives et buildes localement ; on peut modifier un service et tester immediatement (docker compose -f docker-compose.dev.yml up -d --build api). Un seul script gere les deux (selection du compose file et des flags), donc une seule procedure a documenter et a maintenir.

Q4. A quoi sert auth-migrate, et pourquoi un conteneur one-shot ?

Il applique les migrations Drizzle sur auth-db (bun run db:migrate) avant le demarrage du service auth. One-shot (restart: "no") pour trois raisons : les migrations doivent etre jouees une fois par deploiement, pas a chaque redemarrage du service ; si on scalait auth a plusieurs replicas, on eviterait que chaque replica rejoue les migrations en concurrence ; et un echec de migration devient un echec de deploiement visible (auth exige service_completed_successfully, donc ne demarre pas) au lieu d’un service qui tourne sur un schema invalide. Il reutilise l’image de auth, seule la commande change : rien de plus a maintenir.

Q5. Quelles sont les trois conditions depends_on utilisees, et leurs differences ?

  • service_started : le conteneur est lance, aucune garantie qu’il soit pret. Utilise pour ollama et auth (cotes consommateurs), et implicitement par front (syntaxe courte en liste).
  • service_healthy : le healthcheck du service passe. Utilise pour les trois bases (pg_isready, mongosh ping) : api, etl, ai-nutrition, reco-fitness ne demarrent que sur des bases reellement pretes.
  • service_completed_successfully : le conteneur s’est termine avec exit 0. Utilise uniquement pour auth-migrate : c’est la condition adaptee a un one-shot.

Nuance a donner spontanement : ollama n’est qu’en service_started car un healthcheck “modele charge” bloquerait la stack plusieurs minutes au premier run ; ai-nutrition tolere son indisponibilite (Mistral primaire, Ollama fallback). Et depends_on n’agit qu’au demarrage : en cours de vie, ce sont restart: unless-stopped et les reconnexions applicatives qui jouent.

Q6. Pourquoi Ollama est-il isole sans port expose ?

Parce que son API n’a aucune authentification par defaut : quiconque la joint peut consommer du compute LLM, voire charger des modeles. Trois barrieres : aucune section ports (rien sur l’hote), un reseau dedie ai_internal (les autres conteneurs de mspr_data_network ne le voient pas), et un seul client legitime, ai-nutrition, qui est le seul service rattache aux deux reseaux. C’est du moindre privilege applique au reseau : le perimetre d’exposition d’un service correspond exactement a ses consommateurs. Detail dans la fiche Securite.

Q7. Comment les services se resolvent-ils entre eux ?

Par le DNS interne de Docker sur les reseaux bridge : chaque conteneur est resolvable par son nom de service compose et par son container_name. Exemples reels du compose : DB_HOST: mspr-healthai-db (container_name), MONGO_URI: mongodb://mongo:27017 (nom de service), AUTH_API_URL: http://mspr-auth-service:3000, OLLAMA_HOST: http://ollama:11434. Toujours le port interne (5432, 27017, 11434), jamais le port publie sur l’hote. Et jamais localhost : dans un conteneur, localhost designe le conteneur lui-meme. Honnetement, les deux conventions (nom de service / container_name) coexistent dans le compose, heritage des composes MSPR1 et MSPR2 ; les deux fonctionnent, une harmonisation serait cosmetique.

Q8. Que fait bootstrap.sh si .env existe deja ?

Il converge sans rien casser. Le cp .env.example .env n’a lieu que si le fichier est absent. Chaque secret n’est genere que si la variable est vide : BETTER_AUTH_SECRET (sinon tous les JWT emis seraient invalides), DB_PASSWORD, AUTH_DB_PASSWORD (via ensure_env_value, qui lit la valeur courante avant d’ecrire). Les cles API ne sont dechiffrees que si la variable est vide et le .enc present ; sinon, simple message d’information. On peut donc relancer bootstrap a volonte : c’est de l’idempotence, indispensable pour un script de mise en production. Seule subtilite documentee dans le script : changer un mot de passe de base apres initialisation du volume PostgreSQL impose un down -v (PostgreSQL n’applique le mot de passe qu’a l’init du volume).

Q9. Pourquoi generer les mots de passe plutot que garder un defaut ?

Parce que MSPR3 est une mise en production et que le depot est public : un defaut “password” versionne est un mot de passe connu de tous. gen_password produit 24 caracteres alphanumeriques tires de 32 octets d’aleatoire openssl. Le format alphanumerique est un choix d’ingenierie : le mot de passe est interpole dans DATABASE_URL: postgres://user:pass@host, un caractere special casserait le parsing de l’URL. Nuance honnete : le fallback ${DB_PASSWORD:-password} existe encore dans le YAML (filet si quelqu’un lance compose sans bootstrap), mais la procedure officielle, documentee et scriptee, passe par bootstrap qui garantit une valeur forte avant le premier up.

Q10. Image GHCR vs build local : quelle difference, quand utiliser quoi ?

L’image GHCR est produite par la CI du depot source (build + push sur ghcr.io/whitefoxxyt/, voir fiche CI/CD et qualite) : immuable, identique pour tous les postes, pull rapide. C’est le mode evaluation, demo et serveur ; l’overlay Watchtower s’appuie dessus pour le redeploiement automatique. Le build local reflete l’etat des sources clonees : indispensable pour tester une modification non publiee, au prix d’un build plus long et d’un resultat dependant du poste. Regle simple : on demontre en prod, on developpe en dev. Limite assumee : le tag latest (un versionnage semantique v1.2.3 faciliterait les rollbacks ; acceptable au scope MSPR).

Q11. Comment ajouter un nouveau service a la stack ?

  1. Creer le depot avec son Dockerfile et une CI qui publie l’image sur GHCR.
  2. docker-compose.yml : ajouter le bloc service avec <<: *hardening (durcissement et rotation des logs garantis d’office), container_name, l’image GHCR, les variables d’environnement, le ou les reseaux, les depends_on avec la bonne condition, un healthcheck si d’autres services en dependent, un volume nomme s’il a de l’etat.
  3. docker-compose.dev.yml : meme bloc en build: context: ./sources/<repo>.
  4. bootstrap.sh : une ligne dans REPOS ("nom_local|repo_distant|branche").
  5. .env.example : documenter les nouvelles variables ; si secret, l’ajouter aux ensure_env_value ou aux .enc.
  6. Monitoring : declarer la cible Prometheus (fiche Observabilite).

L’essentiel du travail est deja factorise par les ancres et par bootstrap : le cout marginal d’un service est faible.

Q12. Pourquoi les ports des bases sont-ils bindes sur 127.0.0.1 ?

"127.0.0.1:5434:5432" publie le port uniquement sur la boucle locale de l’hote. Sans ce prefixe, Docker publie sur 0.0.0.0 et, piege classique, ses regles iptables court-circuitent les firewalls hote type ufw : une base PostgreSQL ou MongoDB exposee sur une machine reliee a un reseau serait joignable de l’exterieur. Les conteneurs, eux, n’utilisent pas ces ports publies : ils passent par le reseau Docker interne (5432, 27017). Le bind localhost ne sert qu’au confort d’administration (psql, mongosh, client graphique depuis l’hote pendant la demo). Les numeros decales (5434 metier, 5433 auth, 27018 mongo) evitent les conflits avec des instances locales existantes. En production stricte, on pourrait ne publier aucun port de base et passer par docker exec ; le compromis retenu privilegie l’inspectabilite pour la soutenance.

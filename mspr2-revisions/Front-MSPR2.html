Fiche de revision : MSPR-FRONT (MSPR2)

Support de revision pour la soutenance MSPR2. Objectif : comprendre l’evolution du dashboard MSPR1 vers une application utilisateur complete, les 11 nouvelles vues, le design system editorial, l’accessibilite WCAG AA et l’integration des APIs IA.

1. TL;DR

MSPR-FRONT est la SPA Vue 3 destinee aux utilisateurs finaux pour exploiter les capacites IA livrees par la MSPR 2 :

  • analyse nutritionnelle d’une photo de repas,
  • generation de plans repas personnalises,
  • recommandation de programmes fitness.

C’est l’evolution du dashboard admin MSPR1 (4 vues /admin/* conservees) vers une application multi-design-system : interface utilisateur grand public en theme clair editorial (creme + lime) et module admin en theme sombre iOS (heritage MSPR1, vue Lighthouse 100/100).

  • Stack : Vue 3.5, Vite 8, TypeScript 6, Vue Router 5, Pinia 3, Chart.js 4.5
  • Vues : 11 vues utilisateur MSPR2 + 4 vues admin MSPR1 conservees
  • Stores Pinia : 8 stores metier
  • Composants : 21 composants reutilisables (ui/, common/, racine)
  • Tests : 683 tests unit + 6 specs Cypress, couverture 92.45 %
  • Lighthouse : 100/100 sur les 4 axes (a11y, perf, best practices, SEO)
  • Image Docker : ghcr.io/whitefoxxyt/mspr-front:latest

L’authentification est deleguee a MSPR-AUTH (better-auth) : cookie de session HttpOnly + JWT recupere via GET /api/auth/token pour les requetes vers AI-Nutrition (8001) et Reco-Fitness (8002).

Le store auth est hydrate au demarrage via App.vue::onMounted -> hydrateFromStorage(). Les stores metier exposent des actions load(), submit(), reset() et signalent leurs erreurs via un champ error type {status, message, retryAfter?}.

8.2 Authentification : cookie de session + JWT recovery

Flow d’auth :

sequenceDiagram
    participant User
    participant Front
    participant AUTH as MSPR-AUTH :3000
    participant AI as MSPR-AI-Nutrition :8001

    User->>Front: Saisie email + password
    Front->>AUTH: POST /api/auth/sign-in
    AUTH-->>Front: Set-Cookie: session=... (HttpOnly)
    Front->>AUTH: GET /api/auth/token
    AUTH-->>Front: { token: "<JWT>" }
    Front->>Front: Stocker JWT en memoire (Pinia)
    Front->>AI: POST /analyze-meal (Authorization: Bearer JWT)
    AI->>AI: Decode JWT HS256 local
    AI-->>Front: 200 OK (analyse + macros)

Le cookie de session (HttpOnly, SameSite=Lax) est gere par better-auth. Pas accessible en JavaScript -> protection XSS.

Le JWT est recupere via GET /api/auth/token (avec cookie) et stocke en memoire dans le store Pinia (pas en localStorage). Si le user rafraichit la page, le store est rehydrate via la session cookie -> nouveau JWT.

8.3 Clients HTTP dedies

Trois clients dans src/services/ :

// aiNutritionApi.ts
export const aiNutritionApi = {
  async analyzeMeal(file: File, mealType: string): Promise<MealAnalysis> {
    const formData = new FormData()
    formData.append('image', file)
    formData.append('meal_type', mealType)
    return apiRequest('/api/v1/analyze-meal', {
      method: 'POST',
      body: formData,
      service: 'ai-nutrition',
    })
  },

  async generateMealPlan(inputs: MealPlanInputs): Promise<MealPlan> {
    return apiRequest('/api/v1/generate-meal-plan', {
      method: 'POST',
      body: JSON.stringify(inputs),
      headers: { 'Content-Type': 'application/json' },
      service: 'ai-nutrition',
    })
  },
}

// api.ts (wrapper commun)
async function apiRequest(path: string, options: ApiRequestOptions) {
  const authStore = useAuthStore()
  const baseUrl = options.service === 'ai-nutrition'
    ? import.meta.env.VITE_AI_NUTRITION_BASE_URL
    : import.meta.env.VITE_RECO_FITNESS_BASE_URL
  const response = await fetch(`${baseUrl}${path}`, {
    ...options,
    headers: {
      ...options.headers,
      Authorization: `Bearer ${authStore.jwt}`,
    },
  })
  return handleApiResponse(response)
}

handleApiResponse gere :

  • 401 -> authStore.logout() + redirect /login
  • 403 -> emit error sur le store (denied page)
  • 429 -> banniere RateLimitBanner avec compteur Retry-After
  • 5xx -> message d’erreur explicite + retry button

8.4 Gestion robuste des APIs externes

Le sujet exige une gestion robuste :

“Mise en place d’une gestion robuste des appels aux APIs externes pour assurer la performance et la fiabilite de l’application, incluant des mecanismes de mise en cache, de gestion des limites de taux (rate limiting), et de gestion des pannes.”

Cache cote client (stores Pinia) :

  • profil utilisateur (/nutrition-goals/me, /fitness-profile/me) : conserve en memoire tant que la session est active,
  • entitlements (tier free / premium) : caches a duree egale,
  • listes d’historique (analyses, plans, programmes) : invalidees apres mutation (cf. methodes refresh()).

Rate limiting :

  • desactivation du bouton “Generer” pendant 60 s apres un essai (anti-double-clic),
  • composant RateLimitBanner quand 429 recu, avec compteur de temps restant base sur Retry-After,
  • conservation de l’etat du formulaire pour re-tentative.

Fallback en cas de panne :

Service Panne Strategie frontend
MSPR-AUTH Indisponible AuthView affiche message d’erreur, retry manuel
MSPR-AI-Nutrition Indisponible Boutons “Analyser” / “Generer” grises, message explicite
MSPR-Reco-Fitness Indisponible FitnessProgramView grisee, dernier programme reste accessible
Mistral down (backend) Bascule auto vers Ollama (cote backend) Aucun impact UX, latence plus longue

8.5 Selecteur LLM Mistral / Ollama

La vue /parametres expose un selecteur Mistral / Ollama avec auto-save :

<template>
  <div class="llm-selector">
    <h3>Backend IA pour la generation de plans</h3>
    <p class="hint">
      Mistral est plus rapide. Ollama tourne en local, vos donnees ne sortent pas du serveur.
    </p>
    <div role="radiogroup" aria-labelledby="llm-label">
      <label v-for="option in options" :key="option.value">

          type="radio"
          :value="option.value"
          v-model="selected"

          :aria-describedby="`llm-${option.value}-desc`"

        <span :id="`llm-${option.value}-desc`" class="desc">{{ option.description }}</span>
      </label>
    </div>
    <span v-if="saving" aria-live="polite">Sauvegarde en cours...</span>
    <span v-if="saved" aria-live="polite">Preference enregistree</span>

<script setup lang="ts">
import { ref } from 'vue'
import { useLlmPreferencesStore } from '@/stores/llmPreferences'

const store = useLlmPreferencesStore()
const selected = ref(store.preferred_llm)
const saving = ref(false)
const saved = ref(false)

async function save() {
  saving.value = true
  try {
    await store.setPreference(selected.value)
    saved.value = true
    setTimeout(() => (saved.value = false), 3000)

    saving.value = false

Mecanique :

  • composant LLMSelector.vue consomme le store llmPreferences,
  • charge la preference courante au montage (GET /api/v1/me/preferences),
  • envoie un PATCH a chaque changement,
  • affiche un toast de confirmation,
  • gere les codes 401 / 403 / 429.

Le selecteur sert deux usages :

  1. comparer la qualite des plans entre les deux providers (data scientists),
  2. forcer Ollama pour les cas B2B refusant l’envoi de donnees vers une API externe.

9. Code essentiel a savoir expliquer au jury

9.1 Store Pinia : mealPlan

import { defineStore } from 'pinia'
import { ref } from 'vue'
import { aiNutritionApi } from '@/services/aiNutritionApi'
import type { MealPlan, MealPlanInputs, ApiError } from '@/types'

export const useMealPlanStore = defineStore('mealPlan', () => {
  const plan = ref<MealPlan | null>(null)
  const loading = ref(false)
  const error = ref<ApiError | null>(null)
  const generationStart = ref<Date | null>(null)

  async function generate(inputs: MealPlanInputs) {
    loading.value = true
    error.value = null
    generationStart.value = new Date()
    try {
      const result = await aiNutritionApi.generateMealPlan(inputs)
      plan.value = result
    } catch (err) {
      error.value = err as ApiError
      // Le service AI-Nutrition peut retourner :
      // - 429 + Retry-After : rate limit (la banniere s'affiche)
      // - 503 InfeasibleConstraintsError : contraintes infaisables (message dedie)
      // - 5xx : panne backend (message generique)
    } finally {
      loading.value = false
    }
  }

  function reset() {
    plan.value = null
    error.value = null
    generationStart.value = null
  }

  return { plan, loading, error, generationStart, generate, reset }
})

Ce qu’il faut savoir dire :

  • Style Composition API (defineStore avec setup function). Plus modulaire que l’Options API.
  • ref<T>() cree un proxy reactif. Vue re-render quand plan.value = ....
  • L’erreur est typee : ApiError = { status, message, retryAfter? }. Le composant peut conditionnellement afficher selon le code.
  • generationStart est trace pour afficher un compteur dans l’UI (Generation en cours depuis 12 s...). Utile car Ollama peut prendre 4 min sur CPU.

  // Tente d'hydrater la session depuis le cookie (premier passage)
  if (!auth.isHydrated) {
    await auth.hydrateFromStorage()
  }

  if (to.meta.requiresAuth && !auth.isAuthenticated) {
    return next({ path: '/login', query: { redirect: to.fullPath } })
  }
  if (to.meta.guestOnly && auth.isAuthenticated) {
    return next({ path: '/' })
  }
  if (to.meta.requiresAdmin && !auth.isAdmin) {
    return next({ path: '/' })
  }
  next()
})

export default router

Ce qu’il faut savoir dire :

  • beforeEach est un guard global qui s’execute avant chaque navigation. Trois cas :
    • requiresAuth non authentifie -> redirect /login avec ?redirect= pour revenir apres login,
    • guestOnly deja authentifie -> redirect / (eviter d’aller sur /login quand on est connecte),
    • requiresAdmin pas admin -> redirect / (les utilisateurs normaux ne voient pas l’admin).
  • hydrateFromStorage : au tout premier passage, le store n’a pas encore essaye de lire le cookie. On force l’hydratation avant de decider de la redirection.
  • Lazy loading des views (() => import(...)) : Vite genere un chunk JS par vue. Le bundle initial est plus petit, on charge la vue a la demande.

9.3 Composant FileDropzone (upload accessible)

<template>
  <div
    ref="dropzone"
    class="dropzone"
    :class="{ active: isDragOver }"
    @drop.prevent="onDrop"
    @dragover.prevent="isDragOver = true"
    @dragleave="isDragOver = false"
    @click="trigger"
    @keydown.enter="trigger"
    @keydown.space.prevent="trigger"
    role="button"
    tabindex="0"
    :aria-label="`Telecharger une photo de repas. Formats acceptes : JPEG, PNG, WebP. Taille max ${MAX_SIZE_MB} Mo.`"
  >
    <input
      ref="input"
      type="file"
      accept="image/jpeg,image/png,image/webp"
      :aria-describedby="error ? 'dropzone-error' : undefined"
      @change="onChange"
    />
    <p v-if="!file">Glissez-deposez une photo ici ou cliquez pour parcourir</p>
    <p v-else>{{ file.name }} ({{ formatSize(file.size) }})</p>
    <p v-if="error" id="dropzone-error" role="alert" class="error">{{ error }}</p>
  </div>
</template>

<script setup lang="ts">
import { ref } from 'vue'
const MAX_SIZE_MB = 10
const ACCEPTED_TYPES = ['image/jpeg', 'image/png', 'image/webp']

const props = defineProps<{ modelValue: File | null }>()
const emit = defineEmits<{ 'update:modelValue': [File | null] }>()

const dropzone = ref<HTMLElement>()
const input = ref<HTMLInputElement>()
const file = ref<File | null>(props.modelValue)
const isDragOver = ref(false)
const error = ref<string | null>(null)

function validate(f: File): string | null {
  if (!ACCEPTED_TYPES.includes(f.type)) return 'Format non supporte. Utilisez JPEG, PNG ou WebP.'
  if (f.size > MAX_SIZE_MB * 1024 * 1024) return `Taille superieure a ${MAX_SIZE_MB} Mo.`
  return null
}

function setFile(f: File | null) {
  error.value = f ? validate(f) : null
  file.value = error.value ? null : f
  emit('update:modelValue', file.value)
}

function trigger() { input.value?.click() }
function onDrop(e: DragEvent) {
  isDragOver.value = false
  setFile(e.dataTransfer?.files?.[0] ?? null)
}
function onChange(e: Event) {
  setFile((e.target as HTMLInputElement).files?.[0] ?? null)
}

function formatSize(bytes: number) {
  return bytes < 1024 * 1024
    ? `${(bytes / 1024).toFixed(0)} Ko`
    : `${(bytes / 1024 / 1024).toFixed(1)} Mo`
}
</script>

Ce qu’il faut savoir dire :

  • Accessibilite : role="button", tabindex="0" (focus clavier), @keydown.enter / @keydown.space (activation clavier), aria-label descriptif.
  • Drag & drop : @drop.prevent + @dragover.prevent pour empecher le comportement par defaut du browser (ouvrir l’image dans un nouvel onglet).
  • Validation cote client : type MIME + taille. Premiere ligne de defense, le backend revalide.
  • Pattern v-model : defineProps + defineEmits('update:modelValue') rend le composant utilisable comme <FileDropzone v-model="myFile" />.
  • Message d’erreur lu par lecteur d’ecran : role="alert" + lien aria-describedby.

  • Couleurs du design system : #C8FF47 est le --c-acid (CTA). Les pastels sont des accents calmes.
  • watch reactif : si macros change (nouveau plan genere), le chart se met a jour sans recreer le canvas.

9.5 RateLimitBanner avec compteur

<template>
  <div role="alert" aria-live="assertive" class="rate-limit-banner">
    <h3>Vous avez depasse le quota de generation</h3>
    <p>Prochain essai possible dans : <strong>{{ formatRemaining }}</strong></p>
    <p class="hint">
      Cette limite (30 plans / heure) protege le service. Elle se reinitialise automatiquement.
    </p>
  </div>
</template>

<script setup lang="ts">
import { ref, computed, onMounted, onBeforeUnmount } from 'vue'

const props = defineProps<{ retryAfter: number }>()  // secondes
const remaining = ref(props.retryAfter)

let interval: ReturnType<typeof setInterval>

onMounted(() => {
  interval = setInterval(() => {
    remaining.value = Math.max(0, remaining.value - 1)
  }, 1000)
})

onBeforeUnmount(() => clearInterval(interval))

const formatRemaining = computed(() => {
  const m = Math.floor(remaining.value / 60)
  const s = remaining.value % 60
  return m > 0 ? `${m} min ${s} s` : `${s} s`
})
</script>

Ce qu’il faut savoir dire :

  • role="alert" aria-live="assertive" : les lecteurs d’ecran annoncent immediatement la banniere, sans attendre la prochaine pause naturelle. Adequat pour une erreur.
  • setInterval(..., 1000) : countdown a la seconde. onBeforeUnmount(() => clearInterval(interval)) est crucial : sans ca, l’interval continuerait apres demontage du composant -> fuite memoire.
  • Math.max(0, remaining - 1) : floor a 0 pour eviter d’afficher du temps negatif.
  • Retry-After est lu de l’entete HTTP du 429 backend, transmis a la banniere par le store.

9.6 Hydratation au demarrage

// stores/auth.ts
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'
import { authService } from '@/services/auth'

export const useAuthStore = defineStore('auth', () => {
  const jwt = ref<string | null>(null)
  const user = ref<User | null>(null)
  const isHydrated = ref(false)

  const isAuthenticated = computed(() => jwt.value !== null && user.value !== null)
  const isAdmin = computed(() => user.value?.role === 'admin')

  async function hydrateFromStorage() {
    try {
      // Le cookie de session est envoye automatiquement par fetch
      const session = await authService.getSession()
      if (session) {
        const tokenResponse = await authService.getToken()
        jwt.value = tokenResponse.token
        user.value = session.user
      }
    } catch (err) {
      // Pas de session valide, c'est OK
    } finally {
      isHydrated.value = true
    }
  }

  async function login(email: string, password: string) {
    await authService.signIn(email, password)
    await hydrateFromStorage()
  }

  async function logout() {
    await authService.signOut()
    jwt.value = null
    user.value = null
  }

  return { jwt, user, isHydrated, isAuthenticated, isAdmin, hydrateFromStorage, login, logout }
})

Ce qu’il faut savoir dire :

  • isHydrated est un flag separe de isAuthenticated : permet au router de savoir si on a deja tente l’hydratation (sinon, au premier refresh, le guard requireAuth redirigerait /login avant qu’on ait lu le cookie).
  • hydrateFromStorage ne lit pas un localStorage. Le terme est legacy. En realite, on appelle authService.getSession() qui envoie le cookie de session HttpOnly.
  • logout vide le store puis appelle signOut() cote AUTH (qui invalide le cookie cote serveur). Ordre important : si on appelle d’abord signOut, on perd le moyen d’appeler signOut proprement (defensive : on appelle quand meme).

11. Questions probables du jury

Q1. Pourquoi Vue 3 et pas React ?

Le critere decisif est la continuite avec le dashboard MSPR1 (poids 30 % dans le score pondere). Le dashboard etait deja en Vue 3, Lighthouse 100/100, audit RGAA passe. Reprendre React aurait force une refonte complete pour zero benefice (les utilisateurs ne voient pas le framework, et l’equipe de 4 apprenants ne maitrisait pas plus React que Vue).

Autres points :

  • Vue 3 a la courbe d’apprentissage la plus douce des 3 (SFC .vue tres proches du HTML/CSS).
  • Bundle minimal : ~32 KB gzipped (vs 42 KB React, 150 KB Angular).
  • Composition API native pour la modularite du code.

React reprend l’avantage sur un projet greenfield avec un ecosysteme RSC + Next.js. Pas notre cas.

Q2. Pourquoi Pinia et pas Vuex ?

Pinia est le successeur officiel de Vuex (Vuex est en mode maintenance, plus de nouvelles features). Avantages :

  • TypeScript natif : pas besoin de surcharger les types comme dans Vuex.
  • API plus simple : defineStore avec setup function, comme un composant Vue.
  • Devtools integres : meme outils que Vue Devtools (time-travel debugging).
  • Pas de mutations : on appelle directement les actions, pas de boilerplate mutations + actions.

Pinia est recommande par Evan You (createur de Vue) depuis Vue 3.

Q3. Comment gerez-vous l’expiration du JWT ?

Trois niveaux :

  1. Cote client : jwt-decode lit exp du JWT. Un setInterval qui verifie exp toutes les minutes. Si expire dans < 5 min, on tente GET /api/auth/token pour en avoir un nouveau (le cookie de session a une duree de vie plus longue que le JWT).
  2. Cote backend : si un service AI-Nutrition / Reco-Fitness recoit un JWT expire (ExpiredSignatureError), il renvoie 401.
  3. Cote frontend (response handler) : sur 401, on tente getToken() une fois (peut-etre que le cookie est valide). Si echec, redirect /login.

Avantage : pas besoin de refresh token explicite. Le cookie de session HttpOnly + le JWT court vivant suffisent.

Q4. Comment l’application est-elle accessible (WCAG AA) ?

Une dizaine de mecanismes concrets :

  1. Skip link “Aller au contenu principal” en tete de UserLayout.
  2. aria-label explicites sur boutons icones.
  3. aria-live="polite" ou assertive sur les notifications / banners.
  4. Focus visible (outline 2 px contraste).
  5. Navigation clavier complete (Tab, Shift+Tab, Enter, Escape).
  6. Contrastes >= 4.5:1 (texte normal) et >= 3:1 (texte large).
  7. <label for> lies aux champs de formulaire.
  8. Messages d’erreur de formulaire lus par aria-live.
  9. alt sur images, description longue sur graphiques Chart.js.
  10. Pas de piege au clavier.

Verifie par Lighthouse (score a11y 100/100) et axe-core en CI (chaque PR).

Q5. Comment gerez-vous une API qui repond lentement (LLM Mistral 4 s, Ollama 4 min) ?

Trois mecanismes :

  1. Estimation visuelle : un compteur “Generation en cours depuis 12 s…” dans le store mealPlan. Permet a l’utilisateur de savoir que ca avance (pas un freeze).
  2. Pas de timeout cote client : le fetch natif n’a pas de timeout par defaut. On laisse le backend gerer (60 s Mistral, 180 s Ollama).
  3. Annulation : un bouton “Annuler” qui envoie un AbortController.abort() au fetch. Permet a l’utilisateur de couper si trop long.

Pour Ollama qui peut prendre 4 min, on affiche un message explicite “Mode local choisi, comptez ~3-4 min de generation”. Pas de surprise.

Q6. Pourquoi des stores Pinia separes plutot qu’un seul “appState” ?

Deux raisons :

  1. Isolation : si le store mealPlan est en erreur, le store fitnessProgram continue de marcher. Un seul store global serait fragile.
  2. Code splitting : les stores sont charges quand on visite leur vue. mealPlanStore n’est pas charge sur /fitness-program. Reduit le bundle initial.

8 stores correspondent aux 8 domaines metier (analyse, plan, profil nutrition, profil fitness, programme, feedback, prefs LLM, auth). Granularite adequate.

Q7. Comment fonctionne le selecteur LLM ?

Trois etapes :

  1. Au montage de SettingsView : GET /api/v1/me/preferences -> recupere preferred_llm et effective_llm. Affiche le radio button correspondant.
  2. A chaque changement : PATCH /api/v1/me/preferences -> envoie la nouvelle preference. Auto-save.
  3. Au prochain POST /generate-meal-plan : le backend lit nutrition_goals.preferred_llm (cache 60 s) -> effective_llm -> route vers le bon provider. Trace dans meal_plans.llm_backend_used.

Si la preference est NULL (defaut), on utilise settings.default_llm (variable d’env du backend, actuellement mistral).

L’UX a un toast “Preference enregistree” affiche pendant 3 s. Le compteur aria-live="polite" annonce le changement aux lecteurs d’ecran.

Q8. Comment testez-vous la couche frontend ?

Trois niveaux :

  • Tests unitaires Vitest : 683 tests, 63 fichiers. Couvrent les stores Pinia, les services HTTP, les utils, et les composants UI. Couverture 92.45 % lignes.
  • Tests d’integration Vitest : montent les vues avec @vue/test-utils, mockent les API avec vi.mock, assertent le DOM apres interactions.
  • Tests E2E Cypress : 6 specs (auth, admin-guard, meal-analysis, meal-plan, fitness-program, llm-selector). Lances en CI sur vite preview build.

Lighthouse + axe-core en complement pour l’accessibilite.

Pas de tests visuels (regression visuelle type Percy / Chromatic) : trop couteux a maintenir au scope MSPR2. Acceptable.

Q9. Comment se passe l’authentification ?

Flow complet :

  1. User entre email + password sur /login (AuthView).
  2. Frontend appelle POST /api/auth/sign-in sur MSPR-AUTH avec credentials.
  3. MSPR-AUTH valide, cree une session, renvoie Set-Cookie: session=... (HttpOnly, SameSite=Lax).
  4. Frontend appelle GET /api/auth/token (avec cookie). MSPR-AUTH renvoie { token: "<JWT HS256>" }.
  5. Le JWT est stocke en memoire dans le store auth. Le user est redirige vers / (ou ?redirect= si pre-existant).
  6. Pour chaque requete vers AI-Nutrition / Reco-Fitness, le frontend ajoute Authorization: Bearer <JWT>.
  7. Les services backend decodent le JWT localement avec BETTER_AUTH_SECRET partage.
  8. Au refresh de page, le store est rehydrate via le cookie de session -> nouveau JWT.

Avantage : protection XSS (JWT en memoire, pas localStorage), protection CSRF (SameSite=Lax sur le cookie), pas de stockage permanent.

Q10. Comment l’application est-elle responsive ?

Trois niveaux :

  • Breakpoints CSS : variables --bp-sm: 480px, --bp-md: 768px, --bp-lg: 1024px, --bp-xl: 1280px. Utilises avec @media (min-width: ...).
  • Sidebar drawer mobile : la sidebar persistante du UserLayout se transforme en drawer (overlay) sur < 768px. Hamburger menu pour ouvrir.
  • Fonts fluides : font-size: clamp(0.875rem, 0.7rem + 0.5vw, 1rem). Le texte grandit avec la largeur de l’ecran, dans une plage definie.

Pas de framework CSS lourd type Tailwind ou Bootstrap. Tout custom dans tokens.css + composants .vue.

Q11. Comment se passe l’upload de photo (cote performance / UX) ?

Trois etapes :

  1. Cote client : FileDropzone valide le type MIME et la taille (max 10 Mo). Si valide, on cree un FormData avec le fichier brut (sans compression cote client : Pillow le fait cote backend).
  2. Upload HTTP : fetch avec body: formData. Pas de progress bar visible (mais facilement ajoutable avec XMLHttpRequest.upload.onprogress si besoin).
  3. Cote backend : AI-Nutrition recoit l’image, la passe au classifier HuggingFace, genere une thumbnail base64 (Pillow 512x512 q75), la stocke en BDD, retourne l’analyse.

Latence typique : ~3-5 s (1-2 s upload + 1-2 s classification + 1-2 s LLM recommandation). Acceptable en UX interactive.

Pas de cache cote client de la reponse : chaque upload est unique. Mais la recommandation (insight IA) est cachee 30 jours cote backend par (top_food_label, health_goal, imbalances) -> si on scan deux pizzas, la recommandation est servie depuis le cache.

Q12. Comment se deroule la CI/CD ?

Workflow GitHub Actions en 6 etapes :

  1. Lint : oxlint --fix --cache (rapide, Rust) puis eslint --cache (complementaire).
  2. Type check : vue-tsc --build (compile TypeScript).
  3. Tests unit : vitest run (683 tests).

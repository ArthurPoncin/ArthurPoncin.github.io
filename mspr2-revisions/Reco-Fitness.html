Fiche de revision : MSPR-Reco-Fitness

Support de revision pour la soutenance MSPR2. Objectif : comprendre le role du moteur de recommandation fitness, l’algorithme de scoring hybride (rule-based + RandomForest), et le freemium graduel.

0. Vocabulaire a connaitre avant de lire

Les 9 termes qui reviennent partout dans cette fiche.

Terme Definition en une phrase
NoSQL “Not only SQL”. Famille de bases de donnees non-relationnelles. MongoDB stocke des documents JSON plutot que des lignes / colonnes.
MongoDB BDD NoSQL orientee document. Choix impose par le sujet MSPR2 pour le moteur de reco.

1. TL;DR

MSPR-Reco-Fitness est le microservice de recommandation d’activites physiques, expose sur le port 8002. Il genere des programmes d’entrainement personnalises selon 5 criteres : objectif, niveau d’experience, equipement, historique, limitations physiques.

C’est le moteur de reco impose par le sujet MSPR2 (livrable n 7) : “Moteur de recommandation, sous forme de micro-service separe de l’application principale, connecte a une base de donnees NoSQL.”

  • Stack : Python 3.12, FastAPI, motor (Mongo async), SQLAlchemy 2.0 (PG read-only), scikit-learn 1.5, Pydantic v2
  • BDD principale : MongoDB 7 (reco_fitness), 3 collections (user_fitness_profiles, workout_programs, recommendation_history)
  • BDD secondaire : PostgreSQL 17 healthai (lecture seule du catalogue exercises et des biometric_entries)
  • Auth : JWT HS256 partage avec MSPR-AUTH (decode local)
  • Tests : 260 tests, couverture lignes 92.23 %

Trois strategies de scoring selon le tier :

Tier Strategie Duree programme Donnees biometriques
free rule-based seul 2 semaines fixes non
premium hybrid_rank_fusion (50/50 rule-based + ML) 4 a 6 semaines non
premium_plus hybrid + biometric_reader 4 a 6 semaines oui (FC, poids -> charge ajustee)

4. Pourquoi MongoDB

Le sujet impose une BDD NoSQL. Parmi les options (MongoDB, Redis, Cassandra, Elasticsearch), MongoDB a ete retenu pour 4 raisons :

  1. Adapte aux documents semi-structures : un programme fitness contient une liste d’exercices, eux-memes composes de series, repetitions, durees, poids. Un document JSON imbrique est plus naturel qu’un schema relationnel.
  2. Flexibilite du schema : les criteres pris en compte par le scoring evolueront (ajout d’indicateurs biometriques, nouveaux feedbacks). Un schema fixe ralentirait les iterations.
  3. Index secondaires natifs : les requetes “programmes de l’utilisateur X tries par date” et “historique des feedbacks” beneficient d’index composes simples a poser.
  4. Documentation officielle citee dans le sujet (section V.4 Webographie : https://www.mongodb.com/).

Inconvenient connu : pas de jointures cross-collection comme en SQL. Mais le pattern d’acces est volontairement document-oriente : on lit un programme entier, pas des morceaux disperses.

Tous les endpoints metier sont versionnes sous /api/v1/. Pattern /me pour les endpoints utilisateur (user_id du JWT, jamais de l’URL ou du body).

6. Points techniques importants

6.1 L’algorithme de scoring rule-based

Chaque exercice candidat recoit un score pondere sur 5 dimensions :

score = w_goal      * goal_match(exercise, user.goal)
      + w_level     * level_match(exercise, user.experience)
      + w_equipment * equipment_match(exercise, user.gear)
      + w_novelty   * novelty_and_feedback_score(exercise, user.history)
      + w_limit     * limitation_filter(exercise, user.injuries)

Les poids varient par objectif (matrice versionnee dans app/data/scoring_weights.py) :

Objectif w_goal w_level w_equipment w_novelty w_limit
fat_loss 0.35 0.20 0.15 0.20 0.10
muscle_strength 0.40 0.25 0.10 0.15 0.10
endurance 0.30 0.15 0.10 0.30 0.15
general_health 0.25 0.20 0.15 0.25 0.15

Somme par objectif = 1.0. Pas d’override par variable d’env (traçabilite des deploiements).

Les exercices avec limitation_filter=0 (incompatibles avec une blessure) sont elimines avant le scoring. Les autres sont tries par score decroissant.

6.2 Le scoring ML (RandomForestRegressor)

Hyperparametres :

  • 200 arbres (n_estimators=200)
  • profondeur 15 (max_depth=15)
  • seed 42 (random_state=42 pour reproductibilite)

Dataset d’entrainement : 5000+ paires (exercice, profil) etiquetees par le rule-based comme oracle. Split 60/20/20 train/val/test.

Persistance : bundle app/data/scoring_model.pkl (joblib pickle) qui contient {model, vocab, feature_columns}. Charge en lazy singleton.

Cible PRD : F1 > 0.7 sur le seuil score > 0.5. Resultat actuel : F1 = 0.978.

Detail technique important : le rule-based sert d’oracle au ML. Si on modifie les poids du rule-based, le dataset d’entrainement devient incoherent et le ML perd en F1. Procedure obligatoire dans le meme commit :

python scripts/generate_training_data.py --n-profiles 25 --seed 42
python scripts/train_scoring_model.py

6.3 Fusion par tier (freemium graduel)

Trois strategies selon le tier de l’utilisateur :

def recommendations(profile, history, catalog, tier, biometrics=None):
    if tier == "free":
        return recommend_free(profile, history, catalog)
    if tier == "premium":
        return recommend_premium(profile, history, catalog)
    if tier == "premium_plus":
        return recommend_premium_plus(profile, history, catalog, biometrics)
  • Free : recommend_free -> rule-based seul, 2 semaines fixes. Catalogue filtre par passes_hard_filters (limitations + equipement), trie par score decroissant, decoupe en sessions.
  • Premium : recommend_premium -> hybrid_rank_fusion(top_rule_based[:20], top_ml[:20]) puis decoupe pleine duree (4-6 semaines selon le goal).
  • Premium+ : recommend_premium_plus -> idem premium + ajustement charge si la FC moyenne 7 derniers jours > 80 bpm (-1 seance/semaine).

6.4 Hybrid rank fusion

def _rank_fusion(rule_based_ranking, ml_ranking):
    rb_rank = {ex.id: i for i, ex in enumerate(rule_based_ranking)}
    ml_rank = {ex.id: i for i, ex in enumerate(ml_ranking)}

    seen = {}
    for ex in rule_based_ranking + ml_ranking:
        seen.setdefault(ex.id, ex)

    def fused_rank(ex):
        r1 = rb_rank.get(ex.id, len(rule_based_ranking))  # rang manquant = max+1
        r2 = ml_rank.get(ex.id, len(ml_ranking))
        return 0.5 * r1 + 0.5 * r2

    return sorted(seen.values(), key=fused_rank)

Tradeoff entre robustesse (rule-based) et signal donnees (ML). Un exercice absent d’une des deux listes herite du rang max+1 de cette liste (penalise sans etre exclu).

Poids 50/50 hardcode : pas exposes en variable d’env pour figer la traçabilite. Test sur d’autres ratios = commit + redeploiement.

6.5 Progression adaptative et anti-monotonie

A chaque feedback utilisateur (PUT /api/v1/programs/{program_id}/feedback) :

  • la note (1-5) et le commentaire sont enregistres dans recommendation_history,
  • le profil user_fitness_profiles est mis a jour (charge totale par seance, progression),
  • level_match est ajuste pour la prochaine generation : passage beginner -> intermediate automatique si 3 programmes consecutifs notes >= 4 et completes.

Anti-monotonie : le score novelty_and_feedback_score est defini avec une decroissance exponentielle :

_NOVELTY_TAU_DAYS = 7.0

def novelty_and_feedback_score(exercise, history):
    last = _last_occurrence(exercise, history)
    if last is None:
        return 1.0  # jamais propose -> score max
    days = _days_since(last.created_at)
    novelty = 1.0 - math.exp(-days / _NOVELTY_TAU_DAYS)  # 0 a J+0, ~1 a J+30
    return novelty * _feedback_multiplier(last.feedback_score)

Plus le tau est petit (7 jours), plus la rotation est rapide. Au-dela de 2 semaines sans repetition, l’exercice retrouve un score proche de 1 (donc peut etre re-propose).

_feedback_multiplier penalise les exercices mal notes (score 1 -> facteur 0.2, score 2 -> 0.5, score >= 3 -> 1.0). Un exercice mal note ne sera pas re-propose meme si la novelty est haute.

6.6 Integration biometrique (Premium+)

Le service biometric_reader.py lit les biometric_entries PostgreSQL en lecture seule :

def get_recent_biometrics(user_id, db, days=7):
    rows = db.execute(
        text("""
            SELECT AVG(heart_rate) AS avg_hr, MAX(weight_kg) AS recent_weight, MAX(age) AS age
            FROM biometric_entries
            WHERE user_id = :user_id
              AND created_at > NOW() - INTERVAL ':days days'
        """),
        {"user_id": user_id, "days": days},
    ).fetchone()
    return Biometric(
        avg_heart_rate_bpm=rows.avg_hr,
        weight_kg=rows.recent_weight,
        age=rows.age,
    )

Si la FC moyenne 7 derniers jours > 80 bpm, le moteur reduit la charge hebdomadaire (-1 seance/semaine). Acceptation criteria du ticket RF-11.

Pour les tiers free et premium, biometric_reader n’est pas appele (filtre au niveau de l’orchestrateur).

6.7 Feedback idempotent

def record_feedback(user_id, program_id, exercise_id, feedback_score, comment, mongo_client):
    filter_ = {
        "user_id": user_id,
        "program_id": program_id,
        "exercise_id": exercise_id,  # None = feedback program-level
    }
    update = {
        "$set": {
            "feedback_score": feedback_score,
            "feedback_comment": comment,
            "updated_at": datetime.now(timezone.utc),
        },
        "$setOnInsert": {"created_at": datetime.now(timezone.utc)},
    }
    mongo_client.recommendation_history.update_one(filter_, update, upsert=True)

L’idempotence sur (user_id, program_id, exercise_id) est garantie par un update_one(filter, upsert=True) au niveau applicatif, pas par un index unique MongoDB.

Pourquoi pas un index unique : exercise_id=None represente un feedback program-level. MongoDB traite null differemment selon la version pour les index uniques. Plus simple de gerer l’idempotence cote app.

exercise_id=null -> note globale du programme. exercise_id=<int> -> feedback granulaire par exercice. Plusieurs PUT successifs ne creent pas de doublons.

6.9 Cache du catalogue PG (TTL 1h, process-local)

@dataclass
class CachedCatalog:
    exercises: list[Exercise]
    cached_at: datetime

_cache: CachedCatalog | None = None
_TTL_SECONDS = 3600

def get_all() -> list[Exercise]:
    global _cache
    now = datetime.now(timezone.utc)
    if _cache and (now - _cache.cached_at).total_seconds() < _TTL_SECONDS:
        return _cache.exercises
    rows = _fetch_from_pg()
    _cache = CachedCatalog(exercises=rows, cached_at=now)
    return _cache.exercises

Une migration MSPR-DB qui modifie la table exercises n’est prise en compte qu’apres redemarrage ou expiration du TTL. En multi-instance, chaque process a son cache propre (pas partage Redis).

Acceptable au scope MSPR2 : le catalogue evolue rarement.

7. Code essentiel a savoir expliquer au jury

7.1 Score d’un exercice (rule-based)

def goal_match(exercise: Exercise, health_goal: HealthGoalFitness) -> float:
    affinity = GOAL_CATEGORY_AFFINITY.get(health_goal.value, {})
    if exercise.category is None:
        return _DEFAULT_AFFINITY  # 0.5
    return affinity.get(exercise.category, _DEFAULT_AFFINITY)

def level_match(exercise, experience_level) -> float:
    ex_idx = _LEVEL_ORDER.get(exercise.difficulty, 0)
    user_idx = _LEVEL_ORDER[experience_level.value]
    gap = abs(ex_idx - user_idx)
    if gap == 0:
        return 1.0  # parfait
    if gap == 1:
        return 0.5  # acceptable
    return 0.0     # trop ecarte

def score_exercise(exercise, profile, history) -> float:
    weights = SCORING_WEIGHTS[profile.health_goal_fitness.value]
    return (
        weights["goal"] * goal_match(exercise, profile.health_goal_fitness)
        + weights["level"] * level_match(exercise, profile.experience_level)
        + weights["equipment"] * equipment_match(exercise, profile.equipment)
        + weights["novelty"] * novelty_and_feedback_score(exercise, history)
        + weights["limit"] * limitation_filter(exercise, profile.limitations)
    )

Ce qu’il faut savoir dire :

  • goal_match utilise une matrice GOAL_CATEGORY_AFFINITY : pour fat_loss, cardio = 1.0, strength = 0.5, flexibility = 0.3. Les valeurs viennent de la litterature sport-sante.
  • level_match est une distance discrete : un beginner qui recoit un exercice advanced (gap=2) a score 0. Un beginner -> intermediate (gap=1) a score 0.5. Strict mais lisible.
  • Les poids sont charges depuis SCORING_WEIGHTS[goal] (matrice par objectif). Pas de tuning runtime.
  • limitation_filter peut annuler le score (retourne 0) si l’exercice cible un muscle ou une categorie blesse. Pre-filtre AVANT le scoring dans recommend_*.

7.2 Singleton du modele ML

MODEL_PATH = Path(__file__).resolve().parent.parent / "data" / "scoring_model.pkl"
_model_bundle: dict | None = None

def get_model() -> dict:
    global _model_bundle
    if _model_bundle is not None:
        return _model_bundle
    if not MODEL_PATH.exists():
        raise FileNotFoundError(
            f"scoring_model.pkl introuvable a {MODEL_PATH}. "
            "Lance `python scripts/train_scoring_model.py` pour le generer."
        )
    import joblib
    _model_bundle = joblib.load(MODEL_PATH)
    return _model_bundle

def score_exercise(exercise, profile) -> float:
    bundle = get_model()
    row = encode_pair(exercise, profile, score=0.0, vocab=bundle["vocab"])
    features = [row[col] for col in bundle["feature_columns"]]
    prediction = float(bundle["model"].predict([features])[0])
    return max(0.0, min(1.0, prediction))  # clamp dans [0, 1]

Ce qu’il faut savoir dire :

  • Le bundle {model, vocab, feature_columns} est sauve avec joblib (plus rapide que pickle pour les arrays NumPy).
  • encode_pair(exercise, profile, vocab) transforme la paire en features numeriques (one-hot encoding du goal, du niveau, etc.).
  • feature_columns est la liste ordonnee des features attendues par le modele. Critique : si on change l’ordre ou on ajoute une colonne, le modele predit n’importe quoi sans erreur.
  • clamp(0, 1) est defensif : RandomForestRegressor peut sortir hors bornes (extrapolation), on contraint.

7.3 Decoupage en semaines / seances / exercices

_GOAL_SHAPE: dict[str, tuple[int, int, int]] = {
    "fat_loss": (4, 8, 4),         # 4 sessions/sem, 8 ex/session, 4 sem premium
    "muscle_strength": (4, 6, 6),
    "endurance": (5, 6, 6),
    "general_health": (3, 6, 4),
}
_FREE_DURATION_WEEKS = 2
_TOP_N_CANDIDATES = 20

def _structure_program(ranked, duration_weeks, sessions_per_week, exercises_per_session, strategy):
    if not ranked:
        raise EmptyCatalogError(...)
    needed_per_week = sessions_per_week * exercises_per_session
    weeks = []
    for w in range(duration_weeks):
        week_sessions = []
        for s in range(sessions_per_week):
            session = []
            for e in range(exercises_per_session):
                # Cycle sur la liste rangee si plus petite que weeks * sessions * exercises
                idx = (w * needed_per_week + s * exercises_per_session + e) % len(ranked)
                session.append(ranked[idx])
            week_sessions.append(session)
        weeks.append(week_sessions)
    return WorkoutProgram(weeks=weeks, duration_weeks=duration_weeks, scoring_strategy=strategy)

Ce qu’il faut savoir dire :

  • La shape par goal est un tuple (sessions_per_week, exercises_per_session, duration_weeks_premium). Ex : fat_loss = (4, 8, 4) = 4 sessions de 8 exercices sur 4 semaines = 128 exercices au total.
  • L’index (w * needed + s * exercises + e) % len(ranked) permet de cycler sur la liste rangee si le catalogue filtre est plus petit. Sans ca, un user avec peu d’equipement aurait un programme tronque.
  • L’EmptyCatalogError est levee si tous les exercices ont ete filtres par limitations + equipment. Le caller retourne HTTP 422 avec un message explicite.
  • strategy est un litteral "rule_based" ou "hybrid_rank_fusion", persiste dans le document pour audit.

Ce qu’il faut savoir dire :

);

Ce qu’il faut savoir dire :

  • Le script est dans le repo MSPR-MongoDB (separe). Execute par Mongo Docker au premier demarrage uniquement (volume vide).
  • Idempotent : createCollection echoue silencieusement si la collection existe deja, et createIndex est idempotent par defaut (cle identique = pas d’erreur).
  • Les index nommes (name: "user_id_unique") sont plus faciles a debugger : db.collection.dropIndex("user_id_unique") plutot que recopier la cle.
  • L’ordre { user_id: 1, created_at: -1 } est important : on filtre par user_id puis on trie par created_at desc. MongoDB utilise l’index pour les deux operations en un passage.

9. Questions probables du jury

Q1. Pourquoi MongoDB et pas Redis ou Cassandra ?

Le sujet impose une BDD NoSQL. Parmi les options :

  • MongoDB : document-oriente, adapte aux programmes (liste d’exercices imbriques), index secondaires natifs, documentation officielle citee dans le sujet.
  • Redis : key-value, excellent pour le cache mais pas pour stocker des documents persistants riches. Pas de queries sur le contenu.
  • Cassandra : column-family, optimise pour les ecritures massives (logs, telemetry). Surdimensionne pour notre cas.
  • Elasticsearch : moteur de recherche, optimise pour la full-text. Pas notre besoin principal.

MongoDB gagne sur la maniere naturelle de modeliser un programme fitness : un document = un programme.

Q2. Comment ce moteur reagirait a une augmentation de la volumetrie (1M users) ?

Trois axes :

  1. Cache catalogue PG : TTL 1h, process-local. A 1M users, on passerait a Redis partage entre instances. Acceptable.
  2. MongoDB : sharding par user_id. Les requetes naturelles {user_id: ...} ciblent un seul shard, scaling lineaire.
  3. Scoring : le rule-based est O(n) sur le catalogue (~1500 exercices). A 1M users, on bench le P95 pour confirmer < 500 ms. Le ML est lui-aussi O(n) (prediction de chaque paire).

Limites identifiees :

  • SlowAPI in-memory : a remplacer par slowapi[redis] pour le multi-instance.
  • exercise_catalog cache process-local : a invalider centralement quand le catalogue change.
  • Re-entrainement du modele ML : actuellement manuel (python scripts/train_scoring_model.py). En prod, on bascule sur un schedule (Airflow / Argo Workflows) ou un trigger sur evenement.

Q3. Pourquoi un scoring hybride et pas du ML pur ?

Trois raisons :

  1. Cold start : un nouveau user n’a pas d’historique, le ML predit mal. Le rule-based marche immediatement.
  2. Explicabilite : on peut expliquer un score rule-based (“0.35 sur l’objectif, 0.20 sur le niveau…”). Un score ML brut est opaque.
  3. Compliance : pour la sante, on veut pouvoir justifier chaque recommandation. Le rule-based fournit la justification.

Le ML apporte du signal donnees sur les patterns que les regles ne capturent pas (preferences implicites). Sa contribution est limitee a 50 % du score final (rank_fusion 50/50).

Q4. Comment garantissez-vous qu’un user blesse au genou ne recoit pas de squat ?

limitation_filter(exercise, limitations) :

def limitation_filter(exercise, limitations):
    blocked = set(limitations)
    if blocked & set(exercise.target_muscles):
        return 0.0
    if exercise.category and exercise.category in blocked:
        return 0.0
    return 1.0

Si "knee_right" figure dans les limitations et que target_muscles de l’exercice contient "knee", la fonction retourne 0, ce qui multiplie le score final par 0 -> exercice exclu.

ET en complement, passes_hard_filters (au-dessus du scoring) elimine ces exercices avant le scoring pour ne pas pollluer le top-N.

Verrouille par le test test_violation_contraintes_is_zero : 0 % de violations sur 5000 paires synthetiques.

Q5. Pourquoi le rule-based sert d’oracle au ML, n’est-ce pas circulaire ?

C’est volontaire et documente. Sans dataset reel labelise (notes utilisateurs reels en masse), on bootstrap le ML sur la connaissance metier expert (le rule-based).

Le ML apporte deux choses :

  • une representation continue des features (vs le rule-based qui est discret),
  • une capacite a apprendre des patterns non-lineaires entre les criteres (le rule-based est lineaire par construction).

Avec du dataset reel, on remplacerait le rule-based comme oracle par des notes utilisateurs aggregees (proxies du score reel). Le rule-based deviendrait alors un guardrail (pas de violation des limitations) et le ML porterait le signal.

Q6. Que se passe-t-il si l’utilisateur n’a aucun equipement ?

Le filtre passes_hard_filters exige que tous les equipements requis soient possedes. Sans equipement, seuls les exercices equipment=["none"] ou equipment=[] passent (categorie poids du corps : pompes, squats sans charge, planche, burpees…).

A volume ~1500 exercices dans le catalogue, on estime que ~200 exercices sont sans equipement. Largement suffisant pour 4 semaines de programme.

Si le catalogue filtre est vide -> EmptyCatalogError -> HTTP 422 avec un message demandant a l’utilisateur de relacher une contrainte.

Q7. Comment fonctionne le feedback adaptatif ?

A chaque feedback (PUT /programs/{program_id}/feedback), trois choses se passent :

  1. La note (1-5) et le commentaire sont persistes dans recommendation_history.
  2. Le profil user_fitness_profiles est mis a jour si necessaire (passage beginner -> intermediate apres 3 programmes consecutifs notes >= 4 et completes).
  3. Le scoring de la prochaine generation utilise l’historique :
    • novelty_and_feedback_score : un exercice recemment fait a un score novelty bas (decroissance exponentielle, tau = 7 jours).
    • _feedback_multiplier : un exercice mal note (score 1) recoit un multiplicateur 0.2. Un exercice bien note (score >= 3) garde son multiplicateur a 1.0.

Resultat : un exercice “deteste” est rapidement evince ; un exercice “adore” reste dans le pool.

Q8. Comment ce moteur respecte-t-il le RGPD ?

Le service ne collecte pas de PII (Personally Identifiable Information) :

  • user_id est un nanoID opaque (~32 chars) genere par better-auth. Pas d’email, pas de nom.
  • Le profil contient des donnees fitness (objectif, equipement, limitations) qui ne sont pas des donnees de sante au sens strict (article 9 RGPD). Limitation = ergonomie sportive, pas un diagnostic medical.
  • Les programmes sont stockes sans donnees identifiantes (juste user_id).
  • Les biometriques (Premium+) sont en lecture seule depuis PostgreSQL, deja anonymisees par l’ETL MSPR1 (suppression des FK users).

Pour la suppression d’un compte : un DELETE /api/v1/me/data (non implemente, hors scope MSPR2) supprimerait user_fitness_profiles, workout_programs, recommendation_history filtres par user_id.

Q9. Quel est l’impact d’un changement des poids de scoring ?

Quatre consequences en cascade :

  1. Tous les scores changent : les programmes generes apres le commit sont differents des anciens.
  2. Le dataset d’entrainement du ML est invalide : il etait etiquete par l’ancien rule-based. Le ML doit etre re-entraine dans le meme commit.
  3. Les metriques (F1, latence, etc.) changent : il faut recalculer docs/metrics.{json,md} pour le jury.
  4. L’historique des programmes n’est pas reconstruit : les anciens programmes restent visibles, mais ne refletent plus la logique de scoring courante. Acceptable (le tier_at_generation est aussi fige).

Procedure documentee dans CLAUDE.md :

# 1. Modifier app/data/scoring_weights.py (le commit)
# 2. Regenerer le dataset
python scripts/generate_training_data.py --n-profiles 25 --seed 42
# 3. Re-entrainer
python scripts/train_scoring_model.py
# 4. Recalculer les metriques
python scripts/eval_metrics.py --synthetic 70 --n-profiles 120 --seed 42 --out docs
# 5. Verifier les cibles PRD (F1 > 0.8, p95 < 500ms, violations = 0)
# 6. Commit le tout dans un seul PR

92.23 % de couverture lignes, 260 tests passes :

Q11. Comment se passe le re-entrainement du modele ML en production ?

Actuellement manuel (script train_scoring_model.py). Procedure :

  1. Verifier que scoring_weights.py n’a pas change recemment (sinon, regenerer le dataset d’abord).
  2. python scripts/train_scoring_model.py :
    • charge les paires synthetiques de data/training_data.csv,
    • split 60/20/20 train/val/test,
    • entraine un RandomForestRegressor(n_estimators=200, max_depth=15, random_state=42),
    • evalue sur le val set : F1, MAE, R2,
    • persiste le bundle {model, vocab, feature_columns} dans data/scoring_model.pkl,
    • ecrit data/training_report.json (audit).
  3. Verifier le F1 du report (cible > 0.7, idealement > 0.95).
  4. Commit le pickle + le report.
  5. Au prochain demarrage du service, get_model() charge le nouveau pickle.

Pour la prod a plus grande echelle : passer a un schedule (Airflow / Argo Workflows) ou trigger sur evenement (nouveau seuil de feedbacks accumules).

Q12. Que verrait un utilisateur tier “premium_plus” vs “premium” ?

Memes endpoints, meme UI, mais :

  • Duree : premium_plus peut avoir un programme 4-6 semaines selon le goal (idem premium).
  • Adaptation biometrique : si la FC moyenne 7 derniers jours > 80 bpm, le moteur reduit la charge (-1 seance/semaine, plancher 1). Permet d’eviter le surentrainement.
  • Trace dans le doc : scoring_strategy="hybrid_rank_fusion", tier_at_generation="premium_plus". Apres downgrade, les anciens programmes restent visibles tels qu’ils ont ete generes.

Au-dela de ces deux differences techniques, c’est la promesse commerciale qui change : suivi medicalise, recommandations basees sur les donnees reelles plutot que sur les declarations user (qui peuvent etre approximatives).

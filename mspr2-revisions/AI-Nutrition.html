Fiche de revision : MSPR-AI-Nutrition

Support de revision pour la soutenance MSPR2. Objectif : comprendre le role du service, le pipeline IA Vision + LLM, et les points techniques importants (multi-provider, DeCRIM-light, few-shot).

0. Vocabulaire a connaitre avant de lire

Les 10 termes qui reviennent partout dans cette fiche.

Terme Definition en une phrase

1. TL;DR

MSPR-AI-Nutrition est le microservice IA d’analyse nutritionnelle, expose sur le port 8001. Il fait deux choses :

  1. Analyse de repas (POST /api/v1/analyze-meal) : photo en entree, classification HuggingFace (modele nateraw/food fine-tune sur Food-101), lookup dans la table nutrition_entries (peuplee par l’ETL MSPR1), detection de desequilibres macros vs profil utilisateur, recommandations IA.
  2. Generation de plans repas (POST /api/v1/generate-meal-plan) : objectif + regime + allergies + budget en entree, LLM multi-provider (Mistral Small primaire, Ollama Gemma3:4b en fallback), validation par DeCRIM-light (retry partiel ou complet selon le type de violation), persistance en BDD.
  • Stack : Python 3.12, FastAPI 0.115, PyTorch 2.7 (CPU), HF Transformers, Mistral SDK, Ollama, SQLAlchemy 2.0, Pydantic v2, SlowAPI
  • Entree : photo (JPEG / PNG / WebP, max 10 Mo) OU JSON de contraintes
  • Sortie : analyse JSON (top-3 aliments, macros, desequilibres) ou plan repas JSON (1 a 30 jours)
  • BDD : partage healthai (PostgreSQL 17) avec le reste de la plateforme, 3 nouvelles tables (meal_analyses, meal_plans, nutrition_goals)
  • Tests : 428 tests, couverture lignes 96.28 %, branches 85.66 %

Le service ne gere pas d’utilisateurs en propre. L’identite vient du JWT HS256 emis par MSPR-AUTH (secret partage BETTER_AUTH_SECRET). Les tiers (free / premium / premium_plus) sont resolus via GET /api/entitlements/me sur MSPR-AUTH avec cache TTL 60 s.

Trois mecanismes de resilience :

  • FallbackChain (Mistral -> Ollama) : couvre les pannes reseau, timeouts, 429, 5xx du primaire.
  • DeCRIM-light retry : valide le JSON et les contraintes metier (allergies, regime, budget), retry partiel sur le repas fautif (allergie / regime) ou complet du jour (budget).
  • Fallback statique : matrice de plans pre-valides par (objectif, regime). Charge si LLM + retries echouent.

5. Points techniques importants

5.1 Lazy singleton du classifier HuggingFace

Le modele ViT (nateraw/food) pese 328 Mo et met ~3-5 s a se charger. Au lieu de le recharger a chaque requete, on utilise un lazy singleton : la variable globale _classifier est initialisee a None puis instanciee lors du premier appel. Toutes les requetes suivantes reutilisent l’instance en memoire. Pattern standard pour les modeles deep learning.

5.2 Decoupage des deux flux LLM

MSPR-AI-Nutrition heberge deux pipelines LLM bien distincts qu’il ne faut pas confondre :

  • analyze-meal : utilise un LLM (Ollama-only, pas de Mistral ici) pour generer les recommandations textuelles a partir du label de classification et du profil. Cache 30 jours par hash (top_food_label, health_goal, imbalances).
  • generate-meal-plan : utilise le multi-provider LLM (Mistral primaire + Ollama fallback) pour generer un plan repas JSON structure. Cache 7 jours par hash (inputs, llm_backend_used).

Le llm_backend_used est inclus dans le hash pour eviter qu’un switch utilisateur Mistral -> Ollama ne retourne un plan cross-backend du cache.

5.3 Architecture multi-provider Mistral + Ollama

Le sujet du PDF MSPR2 impose des mecanismes de fallback pour assurer la continuite de service (section III.3). L’approche retenue est une FallbackChain :

PATCH /api/v1/me/preferences -> nutrition_goals.preferred_llm

                                effective_llm
                              (user pref > env default)

              | Mistral    | <-- primaire fallback->| Ollama     |

Pivot Mistral : le service a demarre en Ollama-only. Le prompt few-shot (~2245 tokens) timeout systematiquement Gemma3:4b sur CPU (Ollama renvoie 500 / aborted avant le 1er token). Le pivot vers Mistral en primaire a divise la latence p50 par ~50 et fait passer le constraint_satisfaction=full de 0.20 a 0.71.

Ollama reste branche pour trois cas :

  • mode offline / on-premise : deploiement hospitalier qui refuse l’exfiltration de donnees sante (RGPD article 9).
  • eval differee sur GPU : reproductibilite des chiffres comparatifs.
  • fallback : si Mistral renvoie 5xx / 429 / timeout, la FallbackChain route sur Ollama et taggue le plan avec compliance_warning.

5.4 Orchestrateur DeCRIM-light

Un LLM “nu” interroge avec un prompt direct produit souvent des plans repas qui violent une ou plusieurs contraintes utilisateur (allergie ignoree, budget depasse). DeCRIM-light ajoute une boucle de validation + retry :

1. Generation initiale (prompt structure + few-shot)
2. Validation Pydantic (JSON valide ? types corrects ?)
3. Validation metier (allergies absentes ? budget respecte ? regime conforme ?)
4. Si violation :
   - allergie / regime  -> retry partiel sur le SEUL repas fautif
   - budget             -> retry complet du jour fautif
   - persistance apres 2 retries -> bascule fallback statique
5. Si fallback statique aussi viole (allergies / regime) -> 503

Mesure d’impact (Mistral N=100) :

Indicateur Naive (1 call) Pipeline DeCRIM Delta
constraint_satisfaction global 0.33 0.71 +0.38
Allergies respectees 0.67 1.00 +0.33
Diete respectee 0.63 1.00 +0.37
Budget respecte 0.76 0.96 +0.20
Latence p50 4 022 ms 4 163 ms +3.5 %
Latence p95 5 614 ms 9 760 ms +73 %

Tradeoff : DeCRIM-light gagne +38 points de conformite globale, au prix de +4 s sur le p95 (retries declenches par les violations).

5.5 Few-shot prompting

Trois exemples sont prefixes au prompt principal :

  • un plan omnivore objectif weight_loss,
  • un plan vegan + sans gluten,
  • un plan rejete annote pour montrer un cas a eviter.

Le bloc d’exemples est tronque a un jour (days[:1]) au formatage du prompt pour rester sous le seuil de timeout Gemma3:4b sur CPU. Le prefill passe de ~2245 a ~590 tokens supplementaires tout en conservant la structure syntaxique et semantique attendue. Sur Mistral, qui n’a pas cette contrainte CPU, les exemples peuvent etre complets.

Variable FEW_SHOT_ENABLED=false permet de desactiver pour les comparaisons (cf. metrics.md).

5.6 Cache applicatif en BDD (pas de Redis)

Deux caches sont implementes directement en BDD :

  • meal_plans.inputs_hash : SHA256 hex du JSON canonicalise des inputs (objectif, regime, allergies triees, budget, calories cible, user_id, llm_backend_used). TTL 7 jours.
  • meal_analyses.recommendations_hash : SHA256 hex du tuple (top_food_label, health_goal, imbalances triees). Cache global (sans user_id), TTL 30 jours.

Avantage : pas de dependance Redis, persiste aux redemarrages. Inconvenient : un cache hit coute une requete SQL (acceptable au volume MSPR2).

5.7 Rate limiting via SlowAPI

Limite par user_id (extrait du JWT), pas par IP. Sinon un utilisateur derrieres un NAT partagerait son quota avec tout le sous-reseau.

@limiter.limit("30/hour;10/minute")
async def generate_meal_plan(...): ...

Au depassement, le serveur repond 429 Too Many Requests avec un entete Retry-After indiquant le delai avant nouvelle tentative. Le frontend affiche un composant RateLimitBanner avec compteur.

Limite connue : SlowAPI in-memory, process-local. Acceptable au scope MSPR2 ; multi-instance requerrait slowapi[redis].

5.8 Stockage des photos de repas (thumbnail base64)

Pour eviter de provisionner un bucket S3 / MinIO juste pour les thumbnails :

  • Pillow genere une thumbnail 512x512 JPEG qualite 75 (~30-80 Ko par image).
  • Le bloc binaire est encode base64 dans une data URL (data:image/jpeg;base64,...).
  • Stocke dans meal_analyses.photo_url (TEXT, migration V15).

Trois benefices :

  • pas de service externe a deployer / monitorer,
  • l’historique reste transactionnel sur la meme couche que les macros,
  • la photo est supprimee en meme temps que l’analyse (RGPD : pas de fuite).

6.1 Le classifier HuggingFace (lazy singleton)

from io import BytesIO
from PIL import Image
from transformers import pipeline

_classifier = None
_MODEL_ID = "nateraw/food"
DEFAULT_CONFIDENCE_THRESHOLD = 0.10

def _get_classifier():
    global _classifier
    if _classifier is None:
        _classifier = pipeline("image-classification", model=_MODEL_ID)
    return _classifier

def classify_image(
    image_bytes: bytes,
    top_k: int = 5,
    confidence_threshold: float = DEFAULT_CONFIDENCE_THRESHOLD,
) -> list[tuple[str, float]]:
    image = Image.open(BytesIO(image_bytes)).convert("RGB")
    results = _get_classifier()(image, top_k=top_k)
    return [
        (r["label"], round(r["score"], 4))
        for r in results
        if r["score"] >= confidence_threshold
    ]

Ce qu’il faut savoir dire :

  • pipeline("image-classification", model=...) est l’API haut niveau de HuggingFace Transformers. Elle telecharge le modele depuis le Hub (premiere fois uniquement), instancie le pre-processor (resize 224x224, normalisation), le modele ViT, et le tokenizer.
  • Le lazy singleton evite de recharger 328 Mo a chaque requete : la premiere requete paie le cout, les suivantes sont gratuites.
  • confidence_threshold=0.10 filtre les predictions a faible confiance. Le seuil 10 % vient de l’eval : en dessous, les fausses correlations dominent.
  • convert("RGB") est defensif : les images en mode RGBA (PNG transparents) ou LA (greyscale + alpha) cassent le pre-processor ViT qui attend 3 canaux.

6.2 Le LLMProvider et la factory

from abc import ABC, abstractmethod
import httpx
from app.config import settings
from app.services.schema_sanitizer import sanitize_for_mistral_strict

class LLMProvider(ABC):
    @abstractmethod
    async def generate(self, prompt: str, schema: dict | None) -> str:
        raise NotImplementedError

class MistralProvider(LLMProvider):
    def __init__(self, api_key, model="mistral-small-latest", base_url=..., timeout=60.0):
        self._api_key = api_key
        ...
    async def generate(self, prompt, schema):
        payload = {
            "model": self._model,
            "messages": [{"role": "user", "content": prompt}],
        }
        if schema is not None:
            payload["response_format"] = {
                "type": "json_schema",
                "json_schema": {
                    "name": "response",
                    "schema": sanitize_for_mistral_strict(schema),
                    "strict": True,  # rejette tout JSON malforme
                },
            }
        headers = {"Authorization": f"Bearer {self._api_key}"}
        async with httpx.AsyncClient(timeout=self._timeout) as client:
            resp = await client.post(
                f"{self._base_url}/chat/completions",
                json=payload, headers=headers,
            )
            resp.raise_for_status()
        return resp.json()["choices"][0]["message"]["content"]

def get_provider(name: str | None = None) -> LLMProvider:
    backend = (name or settings.default_llm).lower()
    if backend == "ollama":
        return OllamaProvider(base_url=settings.ollama_host)
    if backend == "mistral":
        if not settings.mistral_api_key:
            raise ValueError("MISTRAL_API_KEY manquante.")
        return MistralProvider(api_key=settings.mistral_api_key, ...)
    raise ValueError(f"Backend LLM inconnu : {backend!r}")

Ce qu’il faut savoir dire :

  • LLMProvider est une interface abstraite (ABC). Permet d’ajouter un 3e provider (Claude, GPT-4) sans toucher au reste du code, juste en implementant generate(prompt, schema).
  • response_format.json_schema.strict=true (Mistral) : le serveur valide la sortie contre le schema Pydantic avant de la renvoyer. JSON malforme = erreur immediate, pas de retry inutile cote client.
  • sanitize_for_mistral_strict() retire les proprietes que Mistral strict mode refuse (examples, default, etc.) pour eviter une 400 sur des schemas Pydantic verboses.
  • httpx.AsyncClient plutot que requests : on est en environnement async (FastAPI), un appel bloquant ferait s’effondrer la concurrence.

6.3 FallbackChain entre providers

class FallbackChain:
    def __init__(self, providers: dict[str, LLMProvider]) -> None:
        self._providers = providers

    async def generate(self, prompt, schema, primary_backend) -> tuple[str, str]:
        if primary_backend not in self._providers:
            # Misconfiguration : DEFAULT_LLM=mistral mais MISTRAL_API_KEY vide.
            # build_default_chain n'a ajoute qu'Ollama. On respecte le contrat
            # "fallback automatique" plutot que de remonter une erreur opaque.
            fallback = next(iter(self._providers))
            content = await self._providers[fallback].generate(prompt, schema)
            return content, fallback
        try:
            content = await self._providers[primary_backend].generate(prompt, schema)
            return content, primary_backend
        except httpx.HTTPError:
            secondary = self._pick_secondary(primary_backend)
            if secondary is None:
                raise
            content = await self._providers[secondary].generate(prompt, schema)
            return content, secondary

Ce qu’il faut savoir dire :

  • La methode retourne un tuple (content, used_backend) plutot que juste le contenu. Le backend reellement utilise est trace dans meal_plans.llm_backend_used pour l’audit.
  • Le except httpx.HTTPError capture tous les echecs HTTP : connection error, timeout, 5xx, 429. C’est volontairement large pour maximiser la chance d’avoir une reponse.
  • Si les deux providers echouent, la derniere exception remonte au caller (decrim_retry_orchestrator), qui declenchera le static_fallback applicatif.
  • La construction du chain (build_default_chain) ajoute Mistral seulement si MISTRAL_API_KEY est defini. Permet le deploiement “Mistral non configure” sans casse.

6.4 DeCRIM-light retry orchestrator

async def generate_with_retry(
    inputs: PlanInputs,
    max_retries: int = 3,
    chain: FallbackChain | None = None,
    primary_backend: str | None = None,
) -> tuple[FallbackMealPlan, ComplianceStatus, str | None]:
    primary = primary_backend or settings.default_llm
    active_chain = chain or build_default_chain()
    used_backends: list[str] = []

    async def llm_gen(prompt, schema):
        content, used = await active_chain.generate(prompt, schema, primary)
        used_backends.append(used)
        return content

    spec = _build_constraint_spec(inputs)
    plan = await _call_for_plan(_build_plan_prompt(inputs), llm_gen)

    meal_retry_counts: dict[tuple[int, int], int] = {}
    for _ in range(max_retries):
        violations = validate_constraints(plan, spec)
        if not violations:
            return plan, ComplianceStatus.full, ...

        first = violations[0]
        if first.type in (ViolationType.allergy, ViolationType.diet):
            # Retry partiel sur le repas fautif uniquement
            key = (first.day, first.meal_index or 0)
            if meal_retry_counts.get(key, 0) >= 2:
                # Anti-cycle : passe en retry complet apres 2 retries cibles
                plan = await _call_for_plan(_build_plan_prompt(inputs), llm_gen)
                meal_retry_counts.clear()
                continue
            meal_retry_counts[key] += 1
            new_meal = await _call_for_meal(_build_meal_regen_prompt(first, inputs), llm_gen)
            plan = _replace_meal(plan, first.day, first.meal_index, new_meal)
            continue

        if first.type is ViolationType.budget:
            # Retry complet du jour fautif
            new_day = await _call_for_day(_build_day_regen_prompt(plan, first, spec), llm_gen)
            plan = _replace_day(plan, first.day, new_day)
            continue

    # Apres epuisement des retries : decide entre full / partial_budget / fallback statique
    plan, status = _resolve_after_retries(plan, inputs, spec)
    return plan, status, _pick_secondary_used(used_backends, primary)

Ce qu’il faut savoir dire :

  • La closure llm_gen enrobe active_chain.generate et trace tous les backends utilises. Permet de detecter “Mistral a echoue 1 fois sur 3 retries, Ollama a pris le relais sur 1 retry”.
  • Retry partiel vs complet : une allergie peut etre corrigee sur le seul repas fautif (gain de tokens et de latence). Un depassement budget necessite de regenerer le jour entier (sinon les ratios cassent).
  • Garde-fou anti-cycle : si la meme position viole encore apres 2 retries cibles, on bascule en retry complet du plan. Sinon, un LLM “tetu” peut boucler indefiniment sur un cas pathologique.
  • Le fallback statique est charge dans _resolve_after_retries quand le LLM a epuise ses 3 retries. Plan pre-valide par (objectif, regime). Si ce fallback viole aussi les contraintes -> InfeasibleConstraintsError -> HTTP 503.

6.5 Detection des desequilibres macros

def detect_imbalances(macros: Macros, goal: NutritionGoal) -> list[str]:
    imbalances = []

    # Ratio proteines : cible varie selon l'objectif
    protein_ratio = (macros.protein_g * 4) / macros.calories  # 4 kcal/g
    if goal == "muscle_gain" and protein_ratio < 0.25:
        imbalances.append("low_protein_for_muscle_gain")
    elif goal == "weight_loss" and protein_ratio < 0.30:
        imbalances.append("low_protein_for_weight_loss")

    # Ratio lipides
    fat_ratio = (macros.fat_g * 9) / macros.calories  # 9 kcal/g
    if fat_ratio > 0.40:
        imbalances.append("high_fat")
    elif fat_ratio < 0.20:
        imbalances.append("low_fat_essential_fa_risk")

    # Sodium
    if macros.sodium_mg > 2300:
        imbalances.append("high_sodium")
    # ... etc.
    return imbalances

Ce qu’il faut savoir dire :

  • Les seuils viennent des recommandations PNNS (Programme National Nutrition Sante) francais et de l’AFSSA.
  • Les facteurs 4 kcal/g (proteines, glucides) et 9 kcal/g (lipides) sont les coefficients d’Atwater, base de tout calcul nutritionnel.
  • Les tags d’imbalance servent a deux choses : (1) prompt le LLM pour generer une recommandation contextuelle, (2) faire un cache de recommandations stable (meme tuple de tags = meme recommandation).
  • Les seuils ne sont pas configurables par variable d’env par choix de simplicite. Une evolution serait de les versionner dans une table SQL et faire un audit log des changements.

6.6 Calcul TDEE (Mifflin-St Jeor)

def compute_tdee(gender, age, weight_kg, height_cm, activity_level) -> int:
    # BMR : Basal Metabolic Rate (calories au repos)
    if gender == "male":
        bmr = 10 * weight_kg + 6.25 * height_cm - 5 * age + 5
    else:  # female
        bmr = 10 * weight_kg + 6.25 * height_cm - 5 * age - 161

    # TDEE = BMR * facteur d'activite
    activity_factors = {
        "sedentary": 1.2,
        "light": 1.375,
        "moderate": 1.55,
        "active": 1.725,
        "very_active": 1.9,
    }
    return int(bmr * activity_factors[activity_level])

Ce qu’il faut savoir dire :

  • La formule Mifflin-St Jeor (1990) est la formule recommandee par l’Academy of Nutrition and Dietetics pour estimer le BMR. Plus precise que Harris-Benedict pour les populations modernes.
  • Les facteurs d’activite (1.2 a 1.9) sont des standards de la litterature : sedentary = bureau, peu de marche ; very_active = athlete pro.
  • Le TDEE est la cible calorique de maintien. Pour perte de poids -> -300 a -500 kcal/j. Pour prise de masse -> +250 a +500 kcal/j.
  • Champs optionnels en BDD : si gender / age / weight / height / activity_level sont NULL, l’endpoint GET /me/macros retourne profile_completion_required=true au lieu de planter.

6.7 Decode JWT local (pas d’aller-retour reseau)

import jwt
from app.config import settings

def decode_jwt(token: str) -> dict:
    try:
        payload = jwt.decode(
            token,
            settings.better_auth_secret,
            algorithms=["HS256"],
        )
    except jwt.ExpiredSignatureError:
        raise HTTPException(status_code=401, detail="JWT expired")
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401, detail="JWT invalid")
    return payload

Ce qu’il faut savoir dire :

  • Le JWT est decode localement avec le secret HS256 partage. Pas de POST /api/auth/verify-token sur MSPR-AUTH a chaque requete -> 0 latence d’auth.
  • Le secret BETTER_AUTH_SECRET est partage entre MSPR-AUTH (emetteur) et MSPR-AI-Nutrition (verificateur) via le fichier .env racine. C’est le point d’attention securite : si ce secret fuit, n’importe qui peut signer un JWT valide.
  • algorithms=["HS256"] force l’algorithme cote verificateur. Sans ca, un attaquant pourrait signer un JWT avec alg: none et passer.
  • Seul le tier (free / premium) demande un aller-retour reseau (cache TTL 60 s pour amortir).

6.8 Healthcheck multi-dependances

@router.get("/health")
async def health(db: Session = Depends(get_db)):
    checks = {"postgres": "ok", "ollama": "unknown", "mistral": "unknown"}
    status_code = 200

    # PG : ping rapide
    try:
        db.execute(text("SELECT 1"))
    except Exception:
        checks["postgres"] = "ko"
        status_code = 503

    # Ollama : timeout court pour ne pas bloquer la sonde
    async with httpx.AsyncClient(timeout=2.0) as client:
        try:
            await client.get(f"{settings.ollama_host}/api/tags")
            checks["ollama"] = "ok"
        except httpx.HTTPError:
            checks["ollama"] = "ko"
            # Ollama down n'est pas bloquant si Mistral est configure
            if not settings.mistral_api_key:
                status_code = 503

    # Mistral : ping minimal si configure
    if settings.mistral_api_key:
        ...

    return JSONResponse(checks, status_code=status_code)

Ce qu’il faut savoir dire :

  • Trois sondes en parallele : PG, Ollama, Mistral. Chacune avec son propre timeout court pour ne pas bloquer la sonde liveness.
  • PG est bloquant : si la BDD tombe, tout le service est down (503).
  • Ollama est conditionnel : si Mistral est configure, Ollama peut etre down sans impact (le fallback est l’inverse). Si Mistral non configure, Ollama devient bloquant.
  • Docker / Kubernetes utilise ce healthcheck pour decider de redemarrer le conteneur ou de le sortir du load balancer.

8. Questions probables du jury

Q1. Pourquoi un microservice IA separe au lieu d’integrer dans le Spring Boot existant ?

Trois raisons :

  1. Maturite des libs : l’ecosysteme IA Python (PyTorch, Transformers) est ~10x plus mature que les equivalents Java (DL4J, ONNX-Java).
  2. Isolation des crashes : si le pipeline IA crashe (OOM sur une image trop grosse, deadlock Ollama), l’API metier reste fonctionnelle. Un service unique aurait expose le metier au moindre bug IA.
  3. Deploiement independant : on peut redeployer le service IA pour mettre a jour le modele sans toucher au Spring Boot. On peut aussi le placer sur une machine GPU plus tard sans toucher au reste.

Le tradeoff est une latence reseau inter-services (~1 ms en interne Docker), tres acceptable.

Q2. Pourquoi HuggingFace nateraw/food plutot que Google Vision API ?

Trois criteres :

  1. Cout : pas de cle d’API, pas de quota, pas de risque de depassement. Google Vision est gratuit jusqu’a 1000 images/mois, puis $1.50 / 1000. A volume MSPR2 (~50k users), c’est non negligeable.
  2. Reproductibilite : le modele est telecharge une fois et embarque. Les metriques mesurees aujourd’hui restent valides demain, contrairement a une API tierce dont le modele peut changer sans preavis.
  3. Confidentialite : les photos ne quittent jamais le reseau Docker. Argument decisif pour le RGPD et les contraintes B2B (mutuelles, entreprises).

Q3. Pourquoi Mistral en primaire et Ollama en fallback, pas l’inverse ?

L’objectif premier d’une UX interactive est la latence. Mistral repond en ~4 s p50, Ollama Gemma3:4b sur CPU en ~250 s p50 (deux ordres de grandeur). Ollama en primaire serait inutilisable en interactif.

Mais Ollama reste pertinent pour 3 cas hors UX :

  • mode offline / on-premise (hopital qui refuse l’exfiltration de donnees sante),
  • eval differee sur GPU,
  • fallback : si Mistral renvoie 5xx / 429 / timeout, on bascule sur Ollama et on taggue le plan d’un compliance_warning.

Le sujet impose une “continuite de service” (PDF section III.3) : un seul provider satellite ne couvre pas. Le multi-provider la garantit.

Q4. Comment fonctionne le scoring DeCRIM-light ?

DeCRIM (Decomposed Constraint Refinement and Iterative Generation) est une famille d’orchestrateurs IA qui valident la sortie d’un LLM contre des contraintes formelles puis retry en cas de violation. Notre version “light” :

  1. Genere le plan initial avec un prompt few-shot.
  2. Valide Pydantic (JSON bien forme, types corrects).
  3. Valide les contraintes metier (allergies absentes, regime conforme, budget respecte).
  4. Si violation : retry partiel (repas fautif) pour allergie/regime, complet (jour fautif) pour budget.
  5. Garde-fou anti-cycle : apres 2 retries sur la meme position, bascule en retry complet du plan.
  6. Apres 3 retries sans succes : partial_budget (LLM conserve, budget viole loggue) ou fallback statique selon le type de violation persistante.

Le gain : +38 points de constraint_satisfaction global par rapport au LLM nu (0.33 -> 0.71 sur Mistral N=100).

Q5. Pourquoi un cache 30 jours sur les recommandations d’analyse ?

Deux raisons :

  • Cout LLM : une recommandation = un appel Ollama / Mistral. Sur 100 utilisateurs qui scannent une pizza, on regenererait 100x le meme texte.
  • Stabilite de la reponse : un meme tuple (top_food_label, health_goal, imbalances) doit produire la meme recommandation. Sinon, deux utilisateurs avec exactement les memes inputs auraient des reponses differentes (incoherence).

La cle de cache exclut volontairement user_id (le cache est global), mais inclut le tier (free / premium) pour ne pas donner la meme reponse complete aux deux.

TTL 30 jours : si on change le prompt, on attend que le cache se vide naturellement (vs. invalider de force). Acceptable car les recommandations sont generiques (pas de PII).

Q6. Comment se passe l’authentification entre le frontend et le service IA ?

  1. Le client (frontend Vue) s’authentifie sur MSPR-AUTH (better-auth) via POST /api/auth/sign-in.
  2. MSPR-AUTH renvoie un JWT HS256 signe avec BETTER_AUTH_SECRET.
  3. Le frontend ajoute Authorization: Bearer <jwt> a chaque requete vers AI-Nutrition.
  4. AI-Nutrition decode localement le JWT avec la meme cle HS256. Pas de round-trip reseau.
  5. Le user_id extrait du JWT est utilise pour les queries (WHERE user_id = ?).
  6. Si l’endpoint demande un tier specifique (premium pour /generate-meal-plan), un GET /api/entitlements/me sur AUTH renvoie le tier (cache TTL 60 s).

Avantage : tous les services peuvent verifier l’auth sans dependre de MSPR-AUTH a chaque requete. Inconvenient : la revocation d’un JWT n’est pas immediate (il faut attendre l’expiration). Acceptable au scope MSPR.

Q7. Que se passe-t-il si Ollama et Mistral sont tous les deux down ?

FallbackChain.generate essaie le primaire (Mistral), recoit httpx.HTTPError, bascule sur Ollama, recoit aussi une erreur, et remonte la derniere exception au caller.

Le caller (generate_with_retry) capture l’erreur et bascule sur le fallback_loader : une matrice statique de plans pre-valides indexee par (objectif, regime). Le plan retourne est marque static_fallback.

Si meme ce fallback viole les contraintes (ex : allergie au lactose alors que tous les plans muscle_gain / omnivore du fallback contiennent du lait), on renvoie une InfeasibleConstraintsError traduite en HTTP 503 avec un message explicite.

C’est la chaine de continuite exigee par le PDF MSPR2 section III.3.

Q8. Le service est-il rate-limite ? Comment ?

Oui, via SlowAPI sur l’endpoint POST /api/v1/generate-meal-plan :

@limiter.limit("30/hour;10/minute")

La cle de limit est le user_id extrait du JWT, pas l’IP (sinon un sous-reseau partage ferait du faux positif). Au depassement : HTTP 429 + entete Retry-After.

Limite connue : SlowAPI in-memory, process-local. Sur une plateforme multi-instance, chaque instance aurait son propre compteur. Pour la prod a plus grande echelle, on passerait a slowapi[redis] pour un compteur partage.

analyze-meal n’a pas de rate-limit explicite : le filtre tier (free n’a pas acces, premium oui) suffit a borner l’usage.

Q9. Comment garantissez-vous que le LLM retourne du JSON bien forme ?

Deux mecanismes :

  • Cote Mistral : response_format.json_schema.strict=true. Le serveur valide la sortie contre le schema Pydantic avant de l’envoyer. JSON malforme = erreur immediate.
  • Cote Ollama : parametre format au niveau du payload /api/generate. Best-effort (le modele essaie de respecter mais ne le garantit pas).

Mesure : json_validity_rate = 1.0 sur 100 generations Mistral. Sur Gemma3:4b CPU, ~0.95 (mais difficile a evaluer car les timeouts cachent les vrais ratios).

Apres reception : Pydantic v2 valide le JSON avec FallbackMealPlan.model_validate(parsed). Si la validation echoue (JSON structurellement correct mais types incorrects), le retry est declenche.

Q10. Que stockez-vous comme photo de repas ? Comment gerez-vous la confidentialite ?

Stockage : une thumbnail 512x512 JPEG qualite 75 (~30-80 Ko) encodee en base64 dans une data URL, persistee dans meal_analyses.photo_url (colonne TEXT depuis V15).

Trois choix concrets :

  • pas de bucket S3 / MinIO (simplicite de la stack MSPR2),
  • thumbnail seulement (pas l’original) pour reduire l’empreinte BDD,
  • photo supprimee en meme temps que l’analyse (RGPD : pas de fuite d’images orphelines).

Confidentialite : la photo ne quitte jamais le reseau Docker. Le classifier tourne en local (PyTorch CPU). Les inputs vers Mistral / Ollama sont uniquement textuels (label de classification + profil), jamais l’image.

Q11. Comment evolueriez-vous le pipeline pour des plats hors-distribution (cassoulet, couscous) ?

Trois pistes :

  1. Fine-tuning : entrainer un modele complementaire sur un dataset elargi (FoodX-251, Recipe1M+, ou un dataset custom de plats traditionnels francais). Output : un classifier specialise qui prend le relais quand Food-101 retourne une confidence basse.
  2. Cascade de modeles : un premier classifier “broad” (cuisine francaise / asiatique / mexicaine) puis un classifier specialise par cuisine. Reduit le bruit.
  3. Segmentation prealable : utiliser un modele de segmentation (DETR, Mask R-CNN) pour isoler les composants de l’assiette, puis classifier chacun separement. Permet de gerer les plats mixtes.

A volume MSPR2, pas justifie. A volume reel B2B, le 1) serait le plus pertinent.

Q12. Quelle strategie de tests sur l’IA ?

96 % de couverture lignes, 86 % branches, 428 tests passes :

  • Tests unitaires : imbalance_detector, constraint_validator, decrim_retry_orchestrator (avec mocks LLM), food_classifier (avec image fixture). Aucun I/O reseau.
  • Tests d’integration : endpoints FastAPI avec PostgreSQL ephemere via testcontainers. Chaque test demarre un container Postgres, applique les migrations V1-V14, execute le test, detruit le container. Les appels HTTP vers Mistral / Ollama / MSPR-AUTH sont mockes avec respx.
  • Tests d’eval : couvrent la chaine d’evaluation des metriques (scripts/eval_metrics.py) pour que les chiffres du livrable n 1 soient reproductibles (--seed 42).
  • Tests slow : @pytest.mark.slow, lances en CI sur main seulement. Touchent vraiment Ollama et HuggingFace, pas mockes.

Les chiffres ne sont pas verrouilles dans les tests (eviter le test flaky : un modele peut changer son score top-1 de 0.5 % entre deux runs). Mais la structure des sorties l’est (champs presents, types corrects).

Fiche de revision : Modele de donnees MSPR2

Support de revision pour la soutenance MSPR2. Objectif : comprendre les adaptations du schema MSPR1 pour stocker les artefacts IA, et comment les 3 bases (PostgreSQL healthai, PostgreSQL auth, MongoDB fitness) coexistent autour d’un meme user_id.

0. Vocabulaire a connaitre avant de lire

Les 10 termes qui reviennent partout dans cette fiche.

Terme Definition en une phrase
Migration Script SQL versionne qui modifie le schema (CREATE, ALTER, DROP). Numerote V01, V02, …
JSONB Type PostgreSQL stockant du JSON avec indexation possible. Plus rapide a lire / interroger que TEXT. Format binaire.
BIGSERIAL Type PostgreSQL = BIGINT auto-incremente. Equivalent de AUTO_INCREMENT MySQL.
VARCHAR(64) Chaine de caracteres de longueur max 64. Choisi pour les nanoID better-auth (~32 chars).
nanoID ID alphanumerique compact emis par better-auth. Format rzbzCOvEkAGxy3ADYY7OxFEnR5EqSm3c (32 chars).
CHECK constraint Contrainte SQL qui rejette une ligne si l’expression est fausse. Ex : preferred_llm IN ('mistral', 'ollama').
TOAST The Oversized-Attribute Storage Technique. Mecanisme PostgreSQL qui stocke les valeurs > 2 Ko separement de la table principale.
UML Unified Modeling Language. Norme de diagramme orient objet / relationnel.
Pivot ID Identifiant partage entre plusieurs bases. Ici : user_id (du JWT) lie healthai, auth et fitness.
TEXT[] Type PostgreSQL : tableau de chaines. Stocke une liste dans une seule colonne (ex : allergies = ['gluten', 'lactose']).

1. TL;DR

Le modele de donnees MSPR2 etend la base MSPR1 (healthai PostgreSQL 17) pour stocker les artefacts produits par les microservices IA, et introduit une base NoSQL MongoDB pour le moteur de reco.

Trois bases coexistent dans la plateforme HealthAI Coach :

Base Type Port Repo Role
healthai PostgreSQL 17 5434 MSPR-DB Donnees metier (catalogue exercices, nutrition, biometrie, analyses IA, plans repas)
auth PostgreSQL 17 5433 MSPR-AUTH Identites, sessions, JWT (better-auth)
fitness MongoDB 7 27018 MSPR-MongoDB Programmes fitness, profils, historique recommandations

Heritage MSPR1 : 6 tables (exercises, nutrition_entries, exercise_entries, biometric_entries, diet_recommendations, etl_logs) + 7 migrations (V1-V7).

Ajouts MSPR2 :

  • 8 nouvelles migrations (V8 a V15) sur healthai
  • 3 nouvelles tables PostgreSQL : meal_analyses, meal_plans, nutrition_goals
  • 3 nouvelles collections MongoDB : user_fitness_profiles, workout_programs, recommendation_history
  • Pivot user_id unique cross-bases (alignement nanoID via V14)

3. Les 8 nouvelles migrations (V8 a V15)

Version Fichier Apport
V8 V08__ai_nutrition_tables.sql Creation des 3 tables AI-Nutrition (meal_analyses, meal_plans, nutrition_goals)
V9 V09__ai_nutrition_enrichment.sql Ajout nutrition_goals.health_goal (CHECK), meal_plans.inputs_hash, meal_analyses.recommendations
V10 V10__meal_analyses_recommendations_hash.sql Ajout meal_analyses.recommendations_hash + index dedie (cache LLM par tuple)
V11 V11__ai_nutrition_v11.sql Ajout meal_analyses.imbalances, serving_sizes, meal_type, meal_plans.compliance_status, compliance_warnings
V12 V12__nutrition_goals_biometrics.sql Ajout gender, age, weight_kg, height_cm, activity_level (calcul TDEE Mifflin-St Jeor)
V13 V13__llm_backend_selection.sql Ajout nutrition_goals.preferred_llm + meal_plans.llm_backend_used + CHECK
V14 V14__user_id_to_varchar.sql Conversion user_id BIGINT -> VARCHAR(64) (alignement nanoID better-auth)
V15 V15__meal_analyses_image_data.sql Conversion photo_url VARCHAR(500) -> TEXT (data URL JPEG base64)

Pattern d’idempotence : toutes les migrations utilisent IF NOT EXISTS (CREATE TABLE, ADD COLUMN, CREATE INDEX) et ADD CONSTRAINT ... IF NOT EXISTS (ou equivalent). Permet de relancer les migrations sans erreur.

4. Les 3 tables PostgreSQL ajoutees (V8)

4.1 meal_analyses

Une ligne par analyse photo. Audit trail complet.

CREATE TABLE meal_analyses (
    id                BIGSERIAL PRIMARY KEY,
    user_id           VARCHAR(64) NOT NULL,        -- V14: nanoID better-auth
    photo_url         TEXT,                          -- V15: data URL base64
    detected_foods    JSONB NOT NULL DEFAULT '[]',
    macros            JSONB NOT NULL DEFAULT '{}',
    confidence_scores JSONB NOT NULL DEFAULT '{}',
    recommendations   TEXT,                          -- V9: insight IA
    recommendations_hash CHAR(64),                   -- V10: SHA256 cache 30j
    imbalances        TEXT[],                        -- V11: tags
    serving_sizes     JSONB,                         -- V11: portions PNNS
    meal_type         VARCHAR(20),                   -- V11: breakfast / lunch / dinner / snack
    created_at        TIMESTAMP NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_meal_analyses_user_id     ON meal_analyses (user_id);
CREATE INDEX idx_meal_analyses_created_at  ON meal_analyses (created_at DESC);
CREATE INDEX idx_meal_analyses_reco_hash   ON meal_analyses (recommendations_hash) WHERE recommendations_hash IS NOT NULL;

Decisions de modelisation :

  • Pas de FK vers users : la table a ete droppee en V7 (MSPR1). user_id est un identifiant opaque issu du JWT, decode localement.
  • JSONB pour les structures variables : detected_foods (liste de {label, score}), macros (dict calories/protein/carbs/fat), serving_sizes (PNNS guidelines). Permet d’evoluer le schema sans migration.
  • recommendations_hash partiel index (WHERE NOT NULL) : la grande majorite des lignes ont un hash, mais l’option NULL existe pour les vieilles lignes pre-V10. L’index partiel reduit la taille de l’index.

4.2 meal_plans

Une ligne par plan repas genere. Contient le plan complet en JSONB.

CREATE TABLE meal_plans (
    id                  BIGSERIAL PRIMARY KEY,
    user_id             VARCHAR(64) NOT NULL,
    plan                JSONB NOT NULL DEFAULT '{}',
    objective           VARCHAR(100),
    constraints         JSONB NOT NULL DEFAULT '{}',
    inputs_hash         CHAR(64),                       -- V9: SHA256 cache 7j
    compliance_status   VARCHAR(20) NOT NULL DEFAULT 'full', -- V11: full / partial_budget / static_fallback
    compliance_warnings TEXT[],                          -- V11: messages d'audit
    llm_backend_used    VARCHAR(20) NOT NULL DEFAULT 'ollama' -- V13: trace audit + cache filter
        CHECK (llm_backend_used IN ('ollama', 'mistral')),
    generated_at        TIMESTAMP NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_meal_plans_user_id      ON meal_plans (user_id);
CREATE INDEX idx_meal_plans_generated_at ON meal_plans (generated_at DESC);
CREATE INDEX idx_meal_plans_inputs_hash  ON meal_plans (inputs_hash, llm_backend_used) WHERE inputs_hash IS NOT NULL;

Decisions de modelisation :

  • plan en JSONB : structure imbriquee {days: [{day: 1, meals: [...]}]}. Pourrait etre normalise en tables meal_plan_days / meal_plan_meals / meal_plan_ingredients mais la lecture est toujours WHERE id = X (recuperer tout le plan d’un coup). Pas de gain a normaliser.
  • compliance_status en VARCHAR + CHECK plutot que ENUM : les ENUM PostgreSQL sont compliques a modifier (ALTER TYPE ... ADD VALUE est non transactional). VARCHAR + CHECK permet d’evoluer librement.
  • Index compose (inputs_hash, llm_backend_used) : critique pour le cache. Un switch utilisateur Mistral -> Ollama doit produire un nouveau plan plutot qu’un cache hit cross-backend.

4.3 nutrition_goals

Une ligne par utilisateur (pas par requete). Pattern upsert via INSERT ... ON CONFLICT (user_id) DO UPDATE.

CREATE TABLE nutrition_goals (
    user_id         VARCHAR(64) PRIMARY KEY,          -- V14: PK directement, 1 ligne par user
    calories_target INTEGER,
    protein_g       DECIMAL(8, 2),
    carbs_g         DECIMAL(8, 2),
    fat_g           DECIMAL(8, 2),
    allergies       TEXT[],
    diet_type       VARCHAR(50),
    health_goal     VARCHAR(50)                       -- V9: CHECK liste fermee
        CHECK (health_goal IS NULL OR health_goal IN (
            'weight_loss', 'maintain', 'muscle_gain', 'general_health'
        )),
    -- V12: biometrie pour calcul TDEE
    gender          VARCHAR(10) CHECK (gender IS NULL OR gender IN ('male', 'female')),
    age             INTEGER     CHECK (age IS NULL OR (age > 0 AND age < 130)),
    weight_kg       DECIMAL(5, 2) CHECK (weight_kg IS NULL OR (weight_kg > 0 AND weight_kg < 500)),
    height_cm       DECIMAL(5, 2) CHECK (height_cm IS NULL OR (height_cm > 0 AND height_cm < 300)),
    activity_level  VARCHAR(20)   CHECK (activity_level IS NULL OR activity_level IN (
        'sedentary', 'light', 'moderate', 'active', 'very_active'
    )),
    -- V13: selecteur LLM utilisateur
    preferred_llm   VARCHAR(20) CHECK (preferred_llm IS NULL OR preferred_llm IN ('ollama', 'mistral'))
);

Decisions de modelisation :

  • user_id PRIMARY KEY : une seule ligne par utilisateur. Pas besoin d’un id BIGSERIAL separe. Upsert direct via ON CONFLICT (user_id) DO UPDATE.
  • Biometrie nullable : un profil sans donnees biometriques reste valide. L’endpoint GET /me/macros retourne profile_completion_required=true au lieu de planter.
  • allergies TEXT[] : tableau natif PostgreSQL. Stocke ['gluten', 'lactose'] dans une seule colonne. Indexable via GIN si besoin.
  • CHECK constraints exhaustives : toutes les colonnes “enum-like” ont une CHECK. Garde-fou contre les bugs applicatifs (un mauvais activity_level ne peut pas s’inserer).

5. Les 3 collections MongoDB

Detail complet dans la fiche MongoDB. Resume :

Collection Document type Cle pivot Indexes
user_fitness_profiles Profil fitness (objectif, materiel, limitations, niveau) user_id user_id (unique)
workout_programs Programmes generes (liste d’exercices, duree, semaines) program_id UUID (user_id, created_at desc)
recommendation_history Feedback + completion des programmes (user_id, program_id, exercise_id) (user_id, created_at desc)

Pivot user_id : meme valeur dans les 3 bases.

Base Type SQL / Mongo Format
MSPR-AUTH (auth) TEXT (cle primaire) nanoID better-auth (~32 chars)
PostgreSQL healthai (V14) VARCHAR(64) meme nanoID, lu depuis le JWT
MongoDB fitness String (libre) meme nanoID, lu depuis le JWT

La coherence est garantie par le JWT signe : tous les services decodent le meme token avec BETTER_AUTH_SECRET partage et extraient le meme user_id.

6. Points techniques importants

6.1 V14 : pourquoi changer user_id de BIGINT vers VARCHAR(64) ?

Avant V14, les colonnes user_id etaient declarees en BIGINT (heritage V8 quand le user_id etait suppose numerique).

MSPR-AUTH (better-auth) emet en realite des nanoID : chaines alphanumeriques de ~32 caracteres, ex. rzbzCOvEkAGxy3ADYY7OxFEnR5EqSm3c. Le code AI-Nutrition tentait int(user_id) -> ValueError -> 500.

V14 corrige :

ALTER TABLE meal_analyses
    ALTER COLUMN user_id TYPE VARCHAR(64) USING user_id::VARCHAR(64);

ALTER TABLE meal_plans
    ALTER COLUMN user_id TYPE VARCHAR(64) USING user_id::VARCHAR(64);

ALTER TABLE nutrition_goals
    ALTER COLUMN user_id TYPE VARCHAR(64) USING user_id::VARCHAR(64);
  • VARCHAR(64) couvre largement les nanoID (32 chars) et laisse de la marge pour un UUID (36 chars) ou un identifiant federe externe plus long.
  • USING user_id::VARCHAR(64) est un cast explicite : preserve les fixtures numeriques de dev (ex : user_id=42 devient "42").
  • Aucune donnee n’a ete migree en pratique : les inserts pre-V14 ne pouvaient pas venir d’un client reel avec un JWT better-auth valide.

6.2 V13 : selecteur utilisateur du backend LLM

Apporte par le pivot Mistral (cf. fiche AI-Nutrition). Deux colonnes liees :

ALTER TABLE nutrition_goals
    ADD COLUMN IF NOT EXISTS preferred_llm VARCHAR(20)
    CHECK (preferred_llm IS NULL OR preferred_llm IN ('ollama', 'mistral'));

ALTER TABLE meal_plans
    ADD COLUMN IF NOT EXISTS llm_backend_used VARCHAR(20) NOT NULL DEFAULT 'ollama'
    CHECK (llm_backend_used IN ('ollama', 'mistral'));
  • preferred_llm : prefere de l’utilisateur. Modifiable via PATCH /me/preferences. NULL = utilise le defaut env (settings.default_llm).
  • llm_backend_used : trace du backend qui a effectivement genere le plan (apres FallbackChain). NOT NULL DEFAULT 'ollama' pour la retro-compatibilite (les plans persistes avant V13 ont ete generes par Ollama).

Deux usages :

  1. Audit a posteriori : SELECT llm_backend_used, COUNT(*) FROM meal_plans GROUP BY llm_backend_used pour segmenter les analyses qualite par backend.
  2. Filtre du cache : un switch utilisateur Mistral -> Ollama doit produire un nouveau plan plutot qu’un cache hit cross-backend.

6.3 V15 : stockage des photos en base64

Avant V15, meal_analyses.photo_url etait VARCHAR(500) prevu pour une URL externe (jamais utilisee). V15 convertit en TEXT pour stocker une data URL JPEG base64 :

ALTER TABLE meal_analyses
    ALTER COLUMN photo_url TYPE TEXT;

Trois choix :

  • Stockage en BDD plutot que bucket S3 / MinIO : la stack MSPR n’inclut ni MinIO ni volume partage. La BDD est l’option la plus simple.
  • Thumbnail 512x512 qualite JPEG 75 : ~30-80 Ko par image (genere par app/services/image_thumbnail.py avec Pillow). En dessous du seuil TOAST de PostgreSQL (~2 Ko effectif, mais dans la pratique TOAST est efficace jusqu’a quelques Mo).
  • NULL pour les lignes pre-V15 : la migration ne retro-remplit pas, les analyses anterieures affichent un placeholder cote UI.

6.4 Hashes de cache (SHA256 hex)

Deux caches applicatifs sont implementes en BDD (pas de Redis) :

  • meal_plans.inputs_hash (V9) : SHA256 hex du JSON canonicalise des inputs (objectif, regime, allergies triees, budget, calories cible, user_id). TTL 7 jours. Inclut llm_backend_used pour eviter cache hit cross-backend.
  • meal_analyses.recommendations_hash (V10) : SHA256 hex du tuple (top_food_label, health_goal, imbalances triees). Cache global (sans user_id), TTL 30 jours.
def compute_hash(payload: dict) -> str:
    canonical = json.dumps(payload, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canonical.encode()).hexdigest()

Important : la canonicalisation (sort_keys=True, separators sans espaces) garantit que deux payloads logiquement equivalents produisent le meme hash. Sans ca, {"a":1, "b":2} et {"b":2,"a":1} auraient des hashes differents.

6.5 Pourquoi pas de FK vers les autres bases ?

Trois raisons :

  1. Bases physiquement separees : auth (port 5433) et healthai (port 5434) sont deux instances PostgreSQL distinctes. PostgreSQL ne supporte pas les FK cross-database (FDW = solution lourde et inutile ici).
  2. fitness (MongoDB) ne supporte pas les FK par definition (NoSQL document-oriente).
  3. Couplage faible : permettre a un service de supprimer un user (ex : RGPD) sans casser toute la plateforme. Les bases sont eventuellement coherentes : si un user est supprime cote AUTH, les lignes orphelines dans healthai et fitness ne posent pas probleme car aucune requete ne peut etre faite sans JWT valide.

Le pivot logique est le JWT signe. Tant qu’un service peut le decoder avec BETTER_AUTH_SECRET, il peut faire confiance au user_id qu’il contient.

6.6 Architecture des migrations

Les migrations PostgreSQL healthai sont centralisees dans le repo MSPR-DB (volume monte dans /docker-entrypoint-initdb.d/). Elles s’executent par ordre alphabetique au premier demarrage du container.

# docker-compose.yml (MSPR-Deploy)
services:
  healthai-db:
    image: postgres:17
    volumes:
      - healthai_data:/var/lib/postgresql/data
      - ./MSPR-DB/migrations:/docker-entrypoint-initdb.d
    environment:
      POSTGRES_DB: healthai
      POSTGRES_USER: healthai_user
      POSTGRES_PASSWORD: ...

L’idempotence est garantie par :

  • CREATE TABLE IF NOT EXISTS sur les tables,
  • ALTER TABLE ADD COLUMN IF NOT EXISTS sur les colonnes,
  • CREATE INDEX IF NOT EXISTS sur les indexes,
  • ALTER TABLE ... TYPE ... USING ... sur les conversions (V14).

Pour appliquer une nouvelle migration en local : docker compose down -v && docker compose up -d (destruction du volume, re-execution de toutes les migrations).

Pour la prod, on basculerait sur un outil de migration type Flyway ou Liquibase qui versionne l’historique des migrations dans une table flyway_schema_history. Hors scope MSPR2.

6.7 Migrations MongoDB

Le repo MSPR-MongoDB ne gere qu’un seul script d’init (01-init-reco-fitness.js). Pas de versioning multi-fichiers.

Si on devait ajouter une collection, on editerait le script et on rebuilderait l’image. Acceptable au scope MSPR2.

Pour la prod : passer a Mongock ou un outil equivalent qui versionne les migrations Mongo. Pattern de versioning identique a Flyway/Liquibase.

6.8 Migrations AUTH (Drizzle Kit)

Le repo MSPR-AUTH (Bun + Hono + Drizzle) gere ses propres migrations via Drizzle Kit dans src/db/migrations/. Le container auth-migrate (one-shot) execute les migrations au demarrage de la stack avant que le container auth ne demarre.

Schema better-auth standard :

Table Role
user Identites utilisateurs (id nanoID, email, name, email_verified, image)
session Sessions actives (token, expires_at, ip_address, user_agent)
account Comptes liees (provider_id, access_token, refresh_token, password)
verification Tokens de verification (email, reset password)
jwks Cles publiques / privees pour signer les JWT (rotation possible)

7. Code essentiel a savoir expliquer au jury

7.1 V8 : creation des 3 tables AI-Nutrition

CREATE TABLE meal_analyses (
    id                BIGSERIAL PRIMARY KEY,
    user_id           BIGINT NOT NULL,                 -- V14 corrige en VARCHAR(64)
    photo_url         VARCHAR(500),                    -- V15 corrige en TEXT
    detected_foods    JSONB NOT NULL DEFAULT '[]',
    macros            JSONB NOT NULL DEFAULT '{}',
    confidence_scores JSONB NOT NULL DEFAULT '{}',
    created_at        TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE TABLE meal_plans (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT NOT NULL,
    plan         JSONB NOT NULL DEFAULT '{}',
    objective    VARCHAR(100),
    constraints  JSONB NOT NULL DEFAULT '{}',
    generated_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE TABLE nutrition_goals (
    user_id         BIGINT PRIMARY KEY,                -- V14: VARCHAR(64)
    calories_target INTEGER,
    protein_g       DECIMAL(8, 2),
    carbs_g         DECIMAL(8, 2),
    fat_g           DECIMAL(8, 2),
    allergies       TEXT[],
    diet_type       VARCHAR(50)
);

Ce qu’il faut savoir dire :

  • BIGSERIAL PRIMARY KEY : auto-incremente, 64-bit. Sequence implicite (meal_analyses_id_seq).
  • JSONB avec DEFAULT : '[]' (tableau vide) ou '{}' (objet vide). Evite NULL.
  • Pas de FK : user_id est juste un BIGINT sans contrainte, car la table users a ete droppee en V7.
  • Pas d’index sur user_id en V8 : ajoutes immediatement apres dans la meme migration (CREATE INDEX idx_meal_analyses_user_id ON meal_analyses (user_id)).

7.2 V13 : CHECK constraint pour le selecteur LLM

ALTER TABLE nutrition_goals
    ADD COLUMN IF NOT EXISTS preferred_llm VARCHAR(20);

ALTER TABLE nutrition_goals
    ADD CONSTRAINT nutrition_goals_preferred_llm_check
    CHECK (preferred_llm IS NULL OR preferred_llm IN ('ollama', 'mistral'));

ALTER TABLE meal_plans
    ADD COLUMN IF NOT EXISTS llm_backend_used VARCHAR(20) NOT NULL DEFAULT 'ollama';

ALTER TABLE meal_plans
    ADD CONSTRAINT meal_plans_llm_backend_used_check
    CHECK (llm_backend_used IN ('ollama', 'mistral'));

Ce qu’il faut savoir dire :

  • CHECK plutot qu’ENUM : ENUM PostgreSQL est complique a etendre (ALTER TYPE ... ADD VALUE non transactional, pas de retrait sans drop). CHECK + VARCHAR est plus flexible.
  • IS NULL OR preferred_llm IN (...) : preferred_llm est nullable (NULL = utiliser le defaut env). llm_backend_used est NOT NULL avec DEFAULT ‘ollama’.
  • IF NOT EXISTS sur l’ADD COLUMN, mais pas sur l’ADD CONSTRAINT (PostgreSQL n’a pas IF NOT EXISTS sur les contraintes < 17). Si la contrainte existe deja, la migration plante a la 2e execution. Acceptable car le docker-entrypoint-initdb.d/ execute le script une seule fois.

7.3 V14 : conversion de type sans perte

ALTER TABLE meal_analyses
    ALTER COLUMN user_id TYPE VARCHAR(64) USING user_id::VARCHAR(64);

ALTER TABLE meal_plans
    ALTER COLUMN user_id TYPE VARCHAR(64) USING user_id::VARCHAR(64);

ALTER TABLE nutrition_goals
    ALTER COLUMN user_id TYPE VARCHAR(64) USING user_id::VARCHAR(64);

Ce qu’il faut savoir dire :

  • USING user_id::VARCHAR(64) est le cast explicite. PostgreSQL ne sait pas automatiquement convertir BIGINT en VARCHAR : il faut lui dire “appelle ::VARCHAR(64) sur chaque ligne”.
  • L’operation est lourde sur une grosse table (re-ecrit chaque ligne). Sur healthai, les tables sont vides ou quasi-vides en V14, donc instantane.
  • En production, on aurait fait :
    1. Ajouter une colonne user_id_new VARCHAR(64) nullable,
    2. Backfill user_id_new = user_id::VARCHAR(64),
    3. Swap (rename user_id -> user_id_old, user_id_new -> user_id),
    4. Drop user_id_old.
    Permet de ne pas lock la table pendant des minutes. Hors scope MSPR2.

7.4 Insert + upsert pattern (Python + SQLAlchemy)

from sqlalchemy.dialects.postgresql import insert

def upsert_nutrition_goal(user_id: str, payload: dict, db: Session):
    stmt = insert(NutritionGoal).values(
        user_id=user_id,
        **payload,
    )
    stmt = stmt.on_conflict_do_update(
        index_elements=["user_id"],
        set_=payload,  # met a jour toutes les colonnes du payload
    )
    db.execute(stmt)
    db.commit()

Ce qu’il faut savoir dire :

  • insert().on_conflict_do_update() est le dialecte PostgreSQL specifique (clause ON CONFLICT). Pas dans SQL standard, pas dans MySQL (qui utilise ON DUPLICATE KEY UPDATE).
  • index_elements=["user_id"] cible la PK. Si la PK existe, on UPDATE ; sinon, on INSERT.
  • set_=payload ecrase toutes les colonnes fournies. Pour un upsert partiel (NULL = “ne change pas”), il faudrait set_={col: stmt.excluded[col] for col in payload if payload[col] is not None}.
  • Le pattern garantit qu’on ne cree jamais deux lignes pour le meme user_id.

7.5 Query avec JSONB

# Compter les analyses par type de meal
results = db.execute(text("""
    SELECT meal_type, COUNT(*) AS count
    FROM meal_analyses
    WHERE user_id = :user_id
      AND created_at > NOW() - INTERVAL '30 days'
    GROUP BY meal_type
    ORDER BY count DESC
"""), {"user_id": user_id}).fetchall()

# Lire un champ JSONB precis (top food label)
top_food = db.execute(text("""
    SELECT detected_foods->0->>'label' AS top_label
    FROM meal_analyses
    WHERE id = :id
"""), {"id": analysis_id}).scalar()

# Filtrer sur un champ JSONB
high_protein = db.execute(text("""
    SELECT id, macros
    FROM meal_analyses
    WHERE user_id = :user_id
      AND (macros->>'protein_g')::numeric > 30
"""), {"user_id": user_id}).fetchall()

Ce qu’il faut savoir dire :

  • -> retourne du JSONB (objet ou tableau), ->> retourne du TEXT (chaine extraite). Ex : detected_foods->0->>'label' = premier element du tableau, champ label, comme TEXT.
  • (macros->>'protein_g')::numeric : extrait du TEXT puis cast en numeric pour la comparaison. Sans le cast, on comparerait des strings (donc “9” > “30” alphabetiquement, faux).
  • Pour des queries frequentes sur un champ JSONB, on peut creer un index GIN ou un index B-tree sur une expression (CREATE INDEX ON meal_analyses ((macros->>'protein_g'))). Hors scope MSPR2.

7.6 Calcul hash de cache (Python)

import json
import hashlib

def compute_inputs_hash(inputs: dict, llm_backend: str, user_id: str) -> str:
    """SHA256 hex du tuple canonicalise (inputs, backend, user)."""
    payload = {
        "user_id": user_id,
        "objective": inputs["objective"],
        "diet_type": inputs.get("diet_type"),
        "allergies": sorted(inputs.get("allergies", [])),  # tri pour stabilite
        "budget_per_day": inputs.get("budget_per_day"),
        "calories_target": inputs.get("calories_target"),
        "duration_days": inputs["duration_days"],
        "llm_backend": llm_backend,
    }
    canonical = json.dumps(payload, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canonical.encode()).hexdigest()

def lookup_cached_plan(user_id, inputs, llm_backend, db):
    h = compute_inputs_hash(inputs, llm_backend, user_id)
    return db.execute(text("""
        SELECT id, plan, generated_at FROM meal_plans
        WHERE user_id = :user_id
          AND inputs_hash = :hash
          AND llm_backend_used = :backend
          AND generated_at > NOW() - INTERVAL '7 days'
        ORDER BY generated_at DESC
        LIMIT 1
    """), {"user_id": user_id, "hash": h, "backend": llm_backend}).fetchone()

Ce qu’il faut savoir dire :

  • sorted(allergies) : tri obligatoire pour la stabilite du hash. ['gluten', 'lactose'] et ['lactose', 'gluten'] doivent produire le meme hash.
  • json.dumps(..., sort_keys=True, separators=(",", ":")) : canonicalisation. Sans sort_keys, l’ordre d’iteration du dict Python (insertion order) produirait des hashes differents pour des dicts logiquement equivalents.
  • TTL 7 jours via la clause WHERE generated_at > NOW() - INTERVAL '7 days' : pas de purge proactive, juste un filtre a la lecture. Les lignes expirees restent en BDD mais ne sont jamais lues. A nettoyer par un cron mensuel en prod.
  • LIMIT 1 : si plusieurs plans matchent (cas rare), on prend le plus recent.

8. Questions probables du jury

Q1. Pourquoi 3 bases plutot qu’une seule ?

Trois raisons :

  1. Specialisation : PostgreSQL est excellent pour le relationnel (catalogue, analyses, audit trail). MongoDB est excellent pour le document-oriente (programmes fitness, profils variables). Mettre tout dans une seule BDD aurait force des compromis.
  2. Isolation des pannes : si auth tombe, on peut continuer a lire / ecrire healthai (degrade silencieux). Un seul SGBD aurait expose tout le service au moindre incident.
  3. Contrainte du sujet : la MSPR2 impose une BDD NoSQL pour le moteur de reco (livrable n 7). Cela force d’avoir au moins 2 bases.

Pourquoi alors deux PostgreSQL (healthai + auth) ? Parce que better-auth gere son propre schema (geneere par Drizzle) qu’on ne veut pas voir polluer le schema metier. Et la BDD auth a un cycle de vie different (ports, migrations, backups). Acceptable au scope MSPR2.

Q2. Comment se passe une migration en production ?

En production, on n’utilise pas docker compose down -v (destruction du volume = perte de donnees). On utilise un outil de migration type Flyway ou Liquibase qui :

  1. Verifie une table flyway_schema_history pour savoir quelles migrations ont deja ete appliquees.
  2. Applique les nouvelles migrations dans l’ordre.
  3. Marque chaque migration comme appliquee.
  4. Cree un lock pour eviter les applications concurrentes (multi-instance).

Au scope MSPR2, on utilise le /docker-entrypoint-initdb.d/ de l’image Postgres : execute les scripts au premier demarrage uniquement (volume vide). Pour reset : docker compose down -v && up -d. Acceptable pour une demo / dev.

Q3. Comment se gere la suppression d’un utilisateur (RGPD article 17) ?

L’utilisateur supprime son compte cote MSPR-AUTH (DELETE /api/auth/delete-user). MSPR-AUTH retire la ligne user (cascade sur session, account).

A ce stade, les lignes orphelines dans healthai et fitness ne posent pas de probleme legal car aucune requete ne peut etre faite sans JWT valide (et le JWT a ete invalide avec le compte).

Pour une vraie suppression RGPD, il faudrait un cron qui :

-- PostgreSQL healthai
DELETE FROM meal_analyses WHERE user_id NOT IN (SELECT id FROM auth.user);
DELETE FROM meal_plans WHERE user_id NOT IN (SELECT id FROM auth.user);
DELETE FROM nutrition_goals WHERE user_id NOT IN (SELECT id FROM auth.user);

Cross-database depuis PostgreSQL healthai necessiterait un FDW (Foreign Data Wrapper) vers auth. Hors scope MSPR2 mais documente dans la conduite du changement (livrable n 10).

Pour MongoDB, idem cote applicatif :

const orphans = await mongo.user_fitness_profiles.distinct("user_id");
const valid_ids = await pgClient.query("SELECT id FROM auth.user");
const to_delete = orphans.filter(id => !valid_ids.includes(id));
await mongo.user_fitness_profiles.deleteMany({user_id: {$in: to_delete}});

Q4. Pourquoi JSONB et pas une table separee meal_plan_days / meal_plan_meals ?

Trois raisons :

  1. Pattern d’acces : on lit toujours un plan complet (SELECT * FROM meal_plans WHERE id = X). Pas de query type SELECT meal_name FROM ... WHERE day = 3. Normaliser n’apporterait rien en performance lecture.
  2. Variabilite : un plan peut avoir 1 a 30 jours, chaque jour 3 a 6 repas, chaque repas N ingredients. Modeliser ca en 3-4 tables relationnelles serait verbeux.
  3. Evolution : le LLM peut decider d’ajouter un champ cooking_time_min ou prep_difficulty. Avec JSONB, pas de migration. Avec un schema relationnel, il faut ajouter une colonne (ou une table).

Inconvenient : impossible d’indexer un meal precis (“plans contenant du poulet”). Mais ce n’est pas un besoin actuel.

Q5. Comment garantissez-vous la coherence du user_id entre les 3 bases ?

Trois mecanismes :

  1. JWT signe HS256 : le token contient user_id et est signe avec BETTER_AUTH_SECRET. Si quelqu’un tente d’injecter un faux user_id, la signature ne valide pas.
  2. Decode local : chaque service decode le JWT avec la meme cle. Le user_id extrait est forcement celui qui a ete signe par MSPR-AUTH.
  3. Pas de FK cross-database : les bases sont eventuellement coherentes, pas immediatement coherentes. Un user supprime cote AUTH laisse des lignes orphelines cote healthai et fitness. Mais ces lignes deviennent inaccessibles (pas de JWT valide).

Le seul risque est un bug applicatif qui ecrirait dans healthai ou fitness avec un user_id non issu du JWT (ex : user_id dans le body). Tests verrouillent ce cas.

Q6. Comment evolueriez-vous le schema pour une scalabilite x1000 ?

Plusieurs axes :

  1. Partitioning : meal_analyses et meal_plans partitionnees par created_at (par mois). Permet d’archiver les vieilles donnees facilement.
  2. Index B-tree partiel : recommendations_hash est deja indexe en partiel (WHERE NOT NULL). Etendre a inputs_hash aussi.
  3. TimescaleDB : si on faisait du time-series sur les analyses, TimescaleDB (extension PostgreSQL) automatiserait le partitioning + compression. Hors scope MSPR2.
  4. Read replicas : reads de l’historique /me/meal-analyses peuvent etre routes vers un replica. Streaming replication PostgreSQL.
  5. Sharding MongoDB : sur user_id. Les requetes naturelles {user_id: ...} ciblent un seul shard, scaling lineaire.

Au scope MSPR2 (cibles ~50k users), aucune de ces optimisations n’est necessaire.

Q7. Pourquoi auth et healthai sur deux PostgreSQL distincts plutot que deux schemas dans une seule instance ?

Trois raisons :

  1. Cycle de vie independant : MSPR-AUTH evolue avec better-auth (migrations Drizzle). MSPR-DB evolue avec les besoins metier (migrations SQL). Deux instances permettent de redeployer l’une sans toucher l’autre.
  2. Ports / connexions : auth ecoute sur 5433, healthai sur 5434. Permet de configurer des pool de connexions independants, des timeouts differents, des credentials differents.
  3. Securite : un compromis sur le service AUTH (vol des hashes de password) ne donne pas acces aux donnees metier. Defense en profondeur.

Inconvenient : 2x la consommation memoire (2 instances Postgres au lieu d’une). ~150 Mo de RAM en plus. Acceptable.

Q8. Comment testez-vous les migrations ?

Trois niveaux :

  • Tests d’integration AI-Nutrition / Reco-Fitness : utilisent testcontainers pour demarrer un PostgreSQL ephemere, appliquent toutes les migrations V1 a V14 dans l’ordre, executent les tests, detruisent le container. Si une migration casse, les tests echouent.
  • Tests E2E plateforme : bootstrap.sh lance tout le stack, les tests Cypress verifient que les flux end-to-end marchent. Implicite validation des migrations.
  • Snapshot OpenAPI : docs/openapi.json est commit. Si une migration casse un modele SQLAlchemy, l’OpenAPI change et le test snapshot echoue.

Pas de tests isoles des migrations (ex : “V14 reussit a convertir un BIGINT en VARCHAR sans perdre les fixtures”). Acceptable au scope MSPR2, le coverage indirect est suffisant.

Q9. Pourquoi un index partiel sur recommendations_hash ?

CREATE INDEX idx_meal_analyses_reco_hash
ON meal_analyses (recommendations_hash)
WHERE recommendations_hash IS NOT NULL;

Deux raisons :

  1. Taille de l’index : ne stocke pas les lignes ou recommendations_hash IS NULL (lignes pre-V10). Reduit la taille de l’index de ~20 % au moment de V10.
  2. Performance lookup : le query WHERE recommendations_hash = ? benefice quand meme de l’index (les NULL ne sont jamais matches par =).

Pour inputs_hash, idem : on indexe (inputs_hash, llm_backend_used) partiel sur WHERE inputs_hash IS NOT NULL.

Q10. Quelle est la difference entre created_at et generated_at ?

meal_analyses.created_at : timestamp de la creation de l’enregistrement (insert SQL).

meal_plans.generated_at : timestamp de la generation du plan par le LLM. En theorie egal a created_at car on insert juste apres la generation, mais le nom est plus parlant pour ce qui est genere par IA.

Choix de naming pour le metier. created_at standard ailleurs (audit trail), generated_at specifique aux artefacts IA pour bien signaler “c’est sorti d’un LLM, pas d’une saisie utilisateur”.

Q11. Comment se passe le rollback d’une migration ?

PostgreSQL ne supporte pas le rollback automatique d’une migration. Le /docker-entrypoint-initdb.d/ n’a pas de mecanisme down.

En cas de bug grave dans une migration en prod :

  1. Roll forward : ecrire une nouvelle migration qui corrige (V16 qui annule V15).
  2. Restauration backup : pg_restore depuis un snapshot pre-V15.

Au scope MSPR2, on a docker compose down -v pour reset complet. En prod, on utilisera Flyway qui supporte les migrations _R__ repeatable et les _U__ undo.

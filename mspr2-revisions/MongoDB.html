1. TL;DR

MSPR-MongoDB est un repo court dedie a l’initialisation des collections et des index MongoDB du moteur de recommandation fitness (MSPR-Reco-Fitness).

C’est un repo separe pour garder la coherence avec MSPR-DB (qui porte les migrations PostgreSQL). Les services applicatifs (MSPR-Reco-Fitness) connaissent le schema de leurs documents mais ne gerent pas l’infrastructure des collections / index. Cette responsabilite est centralisee ici.

  • Stack : Mongo Shell (mongosh), MongoDB 7-jammy
  • Contenu : 1 Dockerfile + 1 script JS d’init + 1 README
  • Image publiee : ghcr.io/whitefoxxyt/mspr-mongodb:latest
  • Collections initialisees : user_fitness_profiles, workout_programs, recommendation_history
  • Index : 1 unique + 2 composes
  • Usage : lance comme service au demarrage du compose racine (MSPR-Deploy)

Le sujet impose une BDD NoSQL pour le moteur de reco (livrable n 7). MongoDB est retenu pour les raisons developpees dans la fiche Reco-Fitness. Cette fiche couvre le comment : comment les collections sont creees, indexees, et integrees dans la stack.

4. Les 3 collections

4.1 user_fitness_profiles

Un seul document par utilisateur. Pattern upsert au niveau applicatif (update_one avec upsert=True).

Schema :

{
  "_id": "ObjectId()",
  "user_id": "rzbzCOvEkAGxy3ADYY7OxFEnR5EqSm3c",
  "goal": "muscle_gain",
  "equipment": ["dumbbells", "pull_up_bar"],
  "limitations": ["knee_right"],
  "experience_level": "intermediate",
  "preferences": {
    "duration_min_per_session": 45,
    "sessions_per_week": 4
  },
  "updated_at": "ISODate('2026-05-18T10:30:00Z')"
}

Index : { user_id: 1 } unique. L’unicite est garantie cote Mongo (et redondee cote app par l’upsert).

4.2 workout_programs

Tous les programmes generes pour tous les utilisateurs. Un document par programme.

Schema :

{
  "_id": "ObjectId()",
  "program_id": "uuid-v4",
  "user_id": "rzbzCOvEkAGxy3ADYY7OxFEnR5EqSm3c",
  "duration_weeks": 4,
  "scoring_strategy": "hybrid_rank_fusion",
  "tier_at_generation": "premium",
  "weeks": [
    {
      "sessions": [
        {
          "exercises": [
            {
              "exercise_id": 1234,
              "name": "Developpe couche",
              "sets": 4,
              "reps": 8,
              "weight_kg": 60
            }
          ]
        }
      ]
    }
  ],
  "level": "intermediate",
  "goal": "muscle_gain",
  "created_at": "ISODate('2026-05-18T10:30:00Z')"
}

Index : { user_id: 1, created_at: -1 }. Optimise la requete “historique des programmes du user X tries du plus recent au plus ancien”.

program_id est un UUID v4 plutot que _id Mongo. Permet de l’utiliser dans les URLs (/programs/{program_id}/feedback) sans exposer la structure interne.

4.3 recommendation_history

Feedbacks utilisateur sur les programmes / exercices.

Schema :

{
  "_id": "ObjectId()",
  "user_id": "rzbzCOvEkAGxy3ADYY7OxFEnR5EqSm3c",
  "program_id": "ObjectId('...')",
  "exercise_id": null,
  "feedback_score": 4,
  "completed": true,
  "feedback_comment": "Bon programme, manque de variete sur les jambes",
  "created_at": "ISODate('2026-05-25T18:00:00Z')"
}

Index : { user_id: 1, created_at: -1 }. Idem workout_programs.

Cle d’idempotence applicative : (user_id, program_id, exercise_id). Plusieurs PUT successifs ne creent pas de doublons (geree par update_one(filter, upsert=True)).

exercise_id=null -> feedback program-level (note globale). exercise_id=<int> -> feedback granulaire par exercice. Pas d’index unique Mongo car null est ambigu (selon la version Mongo, null peut etre considere absent ou egal a lui-meme).

5. Points techniques importants

5.1 Pourquoi un repo separe ?

Trois raisons :

  1. Coherence MSPR-DB : MSPR-DB porte les migrations PostgreSQL. MSPR-MongoDB porte les migrations MongoDB. Meme logique pour les deux couches de persistence.
  2. Reutilisation : si on ajoute demain un microservice qui veut Mongo, on n’a pas a dupliquer les scripts d’init.
  3. Cycle de vie : les changements de collections / index sont versionnes independamment du code applicatif (qui consomme la structure).

Tradeoff : un repo de plus a maintenir. Acceptable au scope MSPR2.

5.2 Le script d’init est idempotent

const target = db.getSiblingDB("reco_fitness");

const collections = ["user_fitness_profiles", "workout_programs", "recommendation_history"];
const existing = target.getCollectionNames();
collections.forEach((name) => {
    if (!existing.includes(name)) {
        target.createCollection(name);
    }
});

target.user_fitness_profiles.createIndex(
    { user_id: 1 },
    { unique: true, name: "user_id_unique" }
);
target.workout_programs.createIndex(
    { user_id: 1, created_at: -1 },
    { name: "user_recent" }
);
target.recommendation_history.createIndex(
    { user_id: 1, created_at: -1 },
    { name: "user_recent" }
);

Deux mecanismes d’idempotence :

  • createCollection est appele dans une boucle qui filtre sur l’existant (getCollectionNames()). Pas d’erreur si la collection existe deja.
  • createIndex est idempotent par defaut : appeler avec une cle deja indexee = no-op. Appeler avec une cle differente sous le meme nom = erreur (utile pour detecter les conflits).

Resultat : on peut relancer le script N fois, l’etat final est le meme.

5.3 /docker-entrypoint-initdb.d/ n’execute qu’au premier demarrage

FROM mongo:7-jammy
COPY init/ /docker-entrypoint-initdb.d/

L’image officielle mongo:7-jammy execute les scripts deposes dans /docker-entrypoint-initdb.d/ uniquement si le volume de donnees est vide au demarrage. Mecanisme standard MongoDB / PostgreSQL.

Consequence : pour appliquer un nouveau script d’init, il faut soit :

  • detruire le volume (docker compose down -v && docker compose up -d) -> reset complet, perte de donnees,
  • executer manuellement le script via mongosh dans le container existant (docker exec).

Acceptable au scope MSPR2 : les changements de structure (ajout d’une collection, d’un index) sont rares et planifies.

5.4 Index nommes pour faciliter le debug

target.user_fitness_profiles.createIndex(
    { user_id: 1 },
    { unique: true, name: "user_id_unique" }
);

Le name: "user_id_unique" explicite est plus lisible que le nom auto-genere (user_id_1). Permet :

  • de retrouver rapidement l’index dans db.collection.getIndexes(),
  • de le supprimer ciblement avec db.collection.dropIndex("user_id_unique"),
  • de detecter les collisions (si on ajoute un autre index sous le meme nom).

5.5 L’ordre des champs dans l’index compose

{ user_id: 1, created_at: -1 } : MongoDB peut utiliser cet index pour deux types de queries :

  • find({ user_id: "..." }).sort({ created_at: -1 }) : pleinement servi par l’index, scan zero docs hors filtre.
  • find({ user_id: "..." }) : utilise l’index pour le filtre, sort ignore mais OK.

L’ordre inverse ({ created_at: -1, user_id: 1 }) ne servirait pas le filtre find({ user_id: "..." }) efficacement (Mongo scannerait toutes les entrees triees par created_at avant de filtrer par user_id).

Regle generale : champ d’egalite en premier, champ de tri en dernier.

5.6 Verification post-deploiement

docker exec mspr-mongodb mongosh --quiet --eval '

6. Code essentiel a savoir expliquer au jury

6.1 Le Dockerfile

FROM mongo:7-jammy
COPY init/ /docker-entrypoint-initdb.d/

Ce qu’il faut savoir dire :

  • L’image de base est mongo:7-jammy (Mongo 7 sur Ubuntu 22.04). Version LTS, support jusqu’en 2026.
  • COPY init/ /docker-entrypoint-initdb.d/ copie le script d’init dans le dossier convention MongoDB. Le script sera execute au premier demarrage du container.
  • Pas d’ENTRYPOINT ou de CMD : on herite ceux de l’image officielle (mongod qui lit /docker-entrypoint-initdb.d/ puis demarre le serveur).
  • Image finale legere (~700 Mo, dont 695 Mo de MongoDB et 5 Mo d’init).

6.2 Le script d’init complet

const target = db.getSiblingDB("reco_fitness");

const collections = [
    "user_fitness_profiles",
    "workout_programs",
    "recommendation_history",
];

const existing = target.getCollectionNames();
collections.forEach((name) => {
    if (!existing.includes(name)) {
        target.createCollection(name);
    }
});

target.user_fitness_profiles.createIndex(
    { user_id: 1 },
    { unique: true, name: "user_id_unique" }
);

target.workout_programs.createIndex(
    { user_id: 1, created_at: -1 },
    { name: "user_recent" }
);
target.recommendation_history.createIndex(
    { user_id: 1, created_at: -1 },
    { name: "user_recent" }
);

Ce qu’il faut savoir dire :

  • db.getSiblingDB("reco_fitness") cible la base reco_fitness (creee implicitement si absente).
  • Le filtre if (!existing.includes(name)) est defensif : sans ce check, createCollection leverait une erreur en cas d’execution multiple. Le test n’est pas strictement necessaire (mongo 6+ tolere createCollection sur existant) mais le rend lisible.
  • L’index user_id_unique sur user_fitness_profiles garantit qu’un user n’a qu’un seul profil. L’upsert applicatif s’appuie dessus.
  • Les deux index user_recent (composes) sont identiques en structure ({user_id: 1, created_at: -1}) mais sur deux collections distinctes.

6.3 Integration dans le compose racine MSPR-Deploy

# docker-compose.yml (MSPR-Deploy)
services:
  mongo:
    image: ghcr.io/whitefoxxyt/mspr-mongodb:latest
    container_name: mspr-mongodb
    ports:
      - "27018:27017"  # 27018 sur host pour eviter conflit avec un Mongo local
    volumes:
      - mongo_data:/data/db
    networks:
      - mspr_data_network
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "mongosh", "--quiet", "--eval", "db.adminCommand('ping')"]
      interval: 10s
      timeout: 5s
      retries: 3

  reco-fitness:
    image: ghcr.io/whitefoxxyt/mspr-reco-fitness:latest
    environment:
      - MONGO_URI=mongodb://mongo:27017
      - MONGO_DATABASE=reco_fitness
    depends_on:
      mongo:
        condition: service_healthy

Ce qu’il faut savoir dire :

  • Le port host est 27018 (pas 27017) pour eviter le conflit avec un Mongo deja installe sur la machine du jury.
  • Le volume nomme mongo_data persiste les donnees entre redemarrages. Detruire ce volume = reset complet, mais aussi = re-execution du script d’init.
  • Le healthcheck mongosh ping permet a Docker de monitorer le container. reco-fitness attend service_healthy avant de demarrer (pas juste service_started).
  • MONGO_URI=mongodb://mongo:27017 : le client utilise le nom du service Docker (mongo), resolu par le DNS interne du reseau mspr_data_network. Pas l’IP host, pas le port externe.

6.4 Lecture cote MSPR-Reco-Fitness (driver motor)

# app/db/mongo.py
import motor.motor_asyncio
from app.config import settings

_client = None

def get_client():
    global _client
    if _client is None:
        _client = motor.motor_asyncio.AsyncIOMotorClient(
            settings.mongo_uri,
            tz_aware=True,  # IMPORTANT : datetimes UTC en sortie
        )
    return _client

def get_db():
    return get_client()[settings.mongo_database]

# Usage
async def get_profile(user_id: str):
    db = get_db()
    doc = await db.user_fitness_profiles.find_one({"user_id": user_id})
    if doc is None:
        return None
    return FitnessProfile.model_validate(doc)

Ce qu’il faut savoir dire :

  • motor est le driver async officiel MongoDB pour Python. Equivalent async de pymongo. Integration native avec FastAPI (async def).
  • tz_aware=True est obligatoire : les services stockent datetime.now(timezone.utc). Sans tz_aware, le client renvoie des datetimes naive (sans tz), ce qui casse la validation Pydantic v2.
  • find_one retourne None si pas de match (pas une exception). On le check explicitement.
  • model_validate(doc) convertit le dict Mongo en FitnessProfile Pydantic, valide les types au passage.

6.5 Ecriture cote MSPR-Reco-Fitness

async def upsert_profile(user_id: str, profile: FitnessProfileRequest):
    db = get_db()
    doc = {
        "user_id": user_id,
        "goal": profile.health_goal_fitness.value,
        "equipment": profile.equipment,
        "limitations": profile.limitations,
        "experience_level": profile.experience_level.value,
        "preferences": profile.preferences.model_dump() if profile.preferences else {},
        "updated_at": datetime.now(timezone.utc),
    }
    await db.user_fitness_profiles.update_one(
        {"user_id": user_id},
        {"$set": doc, "$setOnInsert": {"created_at": datetime.now(timezone.utc)}},
        upsert=True,
    )

Ce qu’il faut savoir dire :

  • update_one + upsert=True est le pattern upsert : si le filter matche, on met a jour ; sinon, on insere.
  • $set ecrase les champs existants ; $setOnInsert ne s’applique qu’a l’insert (pas a l’update). Permet de distinguer created_at (date de creation, fixe) de updated_at (date de derniere modif, change a chaque update).
  • L’index unique sur user_id garantit qu’on n’aura jamais deux profils pour le meme user, meme en cas de race condition.

7. Comparaison rapide PostgreSQL / MongoDB

Aspect PostgreSQL (MSPR-DB) MongoDB (MSPR-MongoDB)
Modele Relationnel (tables) Document (JSON)
Migrations SQL versionne (V1-V15) Script JS d’init unique
Schema Strict (CREATE TABLE) Implicite (defini par l’app)
Transactions ACID, multi-table natif Single-doc atomique, multi-doc complexe
Jointures JOIN, FK Pas de JOIN, denormalisation
Index B-tree, GIN, BRIN B-tree, compose, unique, geospatial
Cas d’usage MSPR Tables nutrition / exercises / biometric / meal_* Profils, programmes, feedback fitness

Les deux bases coexistent par choix architectural : PostgreSQL pour le catalogue partage (exercises, biometric_entries, meal_plans), MongoDB pour le domaine fitness specifique (profils, programmes, feedback). Cf. fiche Data-Model pour la vue globale.

8. Questions probables du jury

Q1. Pourquoi un repo separe pour 3 fichiers ?

Trois raisons :

  1. Coherence avec MSPR-DB. Memes patterns : un repo dedie aux migrations / init de chaque couche de persistence.
  2. Reutilisation : un futur microservice qui voudra son propre Mongo n’aura qu’a ajouter un script dans init/. Pas de duplication.
  3. Versioning independant du code applicatif. Les changements de collections / index ne doivent pas etre couples au cycle de release des services.

C’est un choix de structure, pas de complexite : le repo reste trivial.

Q2. Comment ajoute-t-on une nouvelle collection ?

  1. Editer init/01-init-reco-fitness.js : ajouter le nom dans la liste, ajouter les createIndex necessaires.
  2. Commit + push sur master. GitHub Actions rebuild et publie ghcr.io/whitefoxxyt/mspr-mongodb:latest.
  3. Pour appliquer en local / en jury : docker compose down -v (destruction du volume), puis docker compose up -d (re-execution de l’init).

Alternative sans destruction : docker exec mspr-mongodb mongosh --eval "<script>".

Notes :

  • Le script est idempotent, donc lancer 2 fois n’est pas dangereux.
  • Pour la prod (volume permanent), on bascule sur un outil de migration type Mongock ou un script de migration manuel.

Q3. Pourquoi indexer {user_id: 1, created_at: -1} plutot que {created_at: -1, user_id: 1} ?

Regle generale : champ d’egalite (filtre exact) en premier, champ de plage ou tri en dernier.

La query type est find({user_id: "..."}).sort({created_at: -1}) :

  • {user_id: 1, created_at: -1} : Mongo localise le sous-arbre du user_id, puis lit les entrees triees par created_at desc. Scan zero docs hors filtre.
  • {created_at: -1, user_id: 1} : Mongo scannerait toutes les entrees triees par created_at, en filtrant par user_id au passage. Scan O(N) ou N est le nombre total de docs.

Sur un user avec 100 programmes parmi 1M de programmes au total, c’est ~10 000x plus rapide d’avoir {user_id: 1, ...} en premier.

Q4. Que se passe-t-il si le script d’init plante en cours d’execution ?

MongoDB ne fait pas de rollback du script d’init (pas de transaction multi-statement par defaut). Si le script crashe a mi-parcours, certaines collections / index existeront, d’autres non.

Mitigation :

  • L’idempotence du script permet de le rejouer sans creer de doublons. On peut donc relancer apres correction.
  • Pas de dependance d’ordre forte entre les operations : creer recommendation_history avant workout_programs ou inverse ne change rien.
  • Pour debug : docker exec mspr-mongodb mongosh --quiet --eval "db.getSiblingDB('reco_fitness').getCollectionNames()" pour voir l’etat reel.

Q5. Pourquoi MongoDB 7 et pas 8 ?

MongoDB 7 est la version LTS (Long Term Support) la plus recente au moment du dev (avril 2026). Support actif jusqu’en 2026, security patches jusqu’en 2027.

MongoDB 8 est sorti debut 2025 mais reste “rapid release” (cycle court de support). Pour un livrable academique, on prefere la version stable.

Le code applicatif n’utilise aucune feature recente : update_one, find_one, create_index. Compatible Mongo 5+ techniquement, mais on aligne sur 7 pour la securite.

Q6. Comment ce repo s’integre-t-il dans la CI/CD ?

Workflow GitHub Actions minimal :

Q7. Comment se passe la suppression d’un utilisateur (RGPD) ?

Le repo MSPR-MongoDB ne gere pas la suppression (c’est applicatif). Cote MSPR-Reco-Fitness, il faudrait un endpoint DELETE /api/v1/me/data qui :

async def delete_user_data(user_id: str):
    db = get_db()
    await db.user_fitness_profiles.delete_one({"user_id": user_id})
    await db.workout_programs.delete_many({"user_id": user_id})
    await db.recommendation_history.delete_many({"user_id": user_id})

Pas implemente dans le scope MSPR2 mais documente dans la conduite du changement (livrable n 10). En production, on ajouterait un cron qui purge les workout_programs et recommendation_history de plus de 5 ans (retention RGPD raisonnable).

Q8. Comment monitorer MongoDB en production ?

Trois niveaux :

  1. Healthcheck Docker : mongosh ping. Si ko, le container est marque unhealthy et le load balancer (ou orchestrateur) sort le service du pool.
  2. Logs MongoDB : niveau verbosity par defaut (-v). Recuperes par Docker logs ou drivers (Loki, Elasticsearch).
  3. Metriques internes : db.serverStatus() expose les counters (ops/sec, connections, memoire). A scraper avec un exporter Prometheus (percona-mongodb-exporter).

Au scope MSPR2, on s’arrete au healthcheck Docker. Suffisant pour une demo.
